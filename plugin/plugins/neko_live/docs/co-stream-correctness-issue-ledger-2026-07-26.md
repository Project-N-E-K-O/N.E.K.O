## 1. 当前希望得到的产品行为

人猫同播不是“猫猫完全静默”，也不是“所有直播事件都立即抢话”。目标分层如下：

| 输入 | 目标行为 |
| --- | --- |
| 主播正在说话 | 主播拥有话权；猫猫不得抢话或触发语音热切换 |
| 普通房间事实、轻量/中量礼物 | 作为短期被动语境，不独立触发语音 |
| 被选中的高价值弹幕 | 可以排队一次主动回应 |
| 高价值礼物、SC、舰长等里程碑 | 可以排队一次简短主动感谢 |
| 已经开始的猫猫语音被主播打断 | 立即停止；普通事件不重播，重要支持事件是否补说必须受限且可去重 |
| 多个事件同时到达 | 有界排队、按优先级处理、过期丢弃，不得形成连续语音堵塞 |

当前本地改动已经恢复：

- 人猫同播中被选中的弹幕走主动 `respond`；
- 高价值 / 里程碑支持事件走主动 `respond`；
- 轻量 / 中量支持事件保留为被动语境。

这只是恢复了入口选择，并没有解决下面的端到端正确性问题。

## 2. 结论摘要

目前最大的结构性问题是：系统能够知道“主动请求已被核心接受”，却不能可靠知道“这条回应实际播放完成”。

主动回应在请求发出约 50 ms 后就会确认成功并从队列移除。随后即使主播插话，实时语音会正确取消当前响应和剩余音频，但原事件不会恢复。因此：

- 好处：不会因为一次打断就无限重试或立即造成重复感谢；
- 问题：高价值礼物感谢可能只说半句、几乎没出声，甚至完全没被观众听到，却已经被记为成功。

这里缺少的是端到端投送生命周期，而不是更多提示词。

## 4. 详细问题

### CSL-001：主动回应过早确认成功

当前实时语音主动投送在以下时点处理回执：

1. 核心把回调渲染成一次主动通知；
2. 向实时 Provider 发送文本注入和 `response.create`；
3. 等待约 50 ms 的异步拒绝窗口；
4. 如果没有收到 `response_already_active` 等拒绝，就把回调确认为成功并从队列删除。

这个确认只证明“请求没有立即被拒绝”，不证明：

- Provider 已经生成语音；
- 已经收到首个音频块；
- 前端已经开始播放；
- 前端播放队列已经排空；
- 观众实际听到了完整回应。

主要代码：

- `main_logic/core/proactive.py`
- `main_logic/core/_shared.py`
- `main_logic/omni_realtime_client/_responses.py`

需要把状态至少拆成：

```text
queued -> accepted -> first_audio -> playback_started
       -> completed
       -> interrupted / expired / failed
```

在此之前，所有 `delivered=True` 都只能解释为“核心接受”，不能解释为“播放完成”。

### CSL-002：重要支持事件被打断后不会补说

当实时 Provider 已开始响应，主播麦克风触发 VAD：

1. `input_audio_buffer.speech_started` 被接收；
2. 当前 `response` 被取消；
3. 后续模型输出被抑制；
4. 转录缓冲被清空；
5. 未播放的音频被丢弃。

这是正确的抢话优先级，但主动回调在更早之前已经被确认并移出队列，因此不会恢复。

影响最大的场景：

- SC / 舰长 / 高价值礼物感谢刚起头就被主播插话；
- 猫猫还没出首音，主播开始说话；
- 前端仍有缓冲音频，但模型侧已经 `response.done`；
- 麦克风回声或误判 VAD 触发取消。

建议策略：

- 普通弹幕：被打断后直接消费，不重试；
- 轻量 / 中量支持：本来就是被动语境，不产生补说；
- 高价值 / 里程碑支持：允许一次短句补偿；
- 补偿必须等待主播说完且前端播放空闲；
- 补偿有效期建议 8–12 秒，超过即丢弃；
- 相同 `provider_event_id` 最多补偿一次；
- 不从断点续说，不原样重播长句，而是生成新的短感谢；
- 新一轮用户话语、直播会话切换或更新的同类事件可以使旧补偿失效。

该前向兼容声明已经退役。插件现在明确使用 `interrupt_policy="drop"`，不透传
幂等键、补偿文本或补偿 TTL。

### CSL-003：被动上下文可能错误触发语音热切换

人猫同播需要大量“只读、不抢话”的直播上下文。历史问题是：插件使用 `ai_behavior="read"` 后，宿主仍可能把内容放入实时语音的待注入路径，并准备或提升新会话。结果是被动层间接造成语音切换、额外响应或堵塞。

当前实现已收敛为宿主 `main_logic/core/lifecycle.py` 的自然消费点：
被动 callback 留在有界队列中，只有自然用户轮次或本来就会发生的安全
会话切换才会消费。曾经的 `passive_plugin_context.py` /
`instruction_overlay.py` 中途覆盖路径已删除，插件侧 45 秒刷新任务也已删除。

验收标准：

- 纯被动 `read` 不独立创建响应；
- 纯被动 `read` 不独立触发实时会话热切换；
- 如果本来就发生自然会话切换，被动上下文可以随新会话进入；
- 被动上下文过期或下播后不得残留；
- 不同 Provider 行为一致。

### CSL-004：缺少统一的话权信号

当前主动投送会检查：

- 核心主动状态机是否空闲；
- Provider 是否已有活动响应；
- 前端是否仍在播放猫猫语音。

但这些信号主要描述“猫猫是否忙”，并不能完整描述“主播是否正在说、马上要说或刚说完”。VAD 与主动注入之间仍存在检查后竞态：

```text
检查时主播未说话
    -> 主动请求开始发送
    -> 主播在数十毫秒窗口内开口
    -> 请求已接受或被 Provider 拒绝
```

如果 Provider 返回 `response_already_active`，当前代码可以重新排队；如果请求已经接受再被主播打断，则落入 CSL-001/002。

需要一个核心级“话权闸门”，至少包含：

- `host_speaking`；
- `host_recently_spoke` 宽限期；
- `cat_generating`；
- `cat_playing`；
- `session_switching`；
- 单调递增的 epoch/generation，用于使过时请求失效。

插件不应自行猜测话权。

### CSL-005：拒绝重试与播放打断是两套不同问题

当前代码对异步 `response_already_active` 做了较严谨的处理：

- 给注入事件分配可关联的 `event_id`；
- 收到冲突拒绝时把回调重新放回队列；
- 避免立即重试形成拒绝死循环；
- 等现有响应结束后再触发。

这只能解决“请求没有被 Provider 接受”。它不能解决：

- 请求被接受但未出首音；
- 已出首音后被打断；
- 前端播放失败；
- 前端音频队列被清空；
- 会话在播放中切换。

后续实现不得把这两类失败混成一个无条件重试开关，否则会重新引入重复感谢和语音堵塞。

### CSL-006：礼物调度完全不重试

`live_support_events/scheduler.py` 当前明确规定：一次 dispatch 抛错后记录 `support.dispatch_failed`，不重试，以避免重复输出。

问题在于 dispatch 返回只代表插件请求已交给下游，不代表完成播放；而异常也可能发生在实际输出之前。当前无法区分：

- 根本没交给宿主；
- 宿主已接受但 Provider 拒绝；
- 已开始播放；
- 播放被打断；
- 已经完整播放，只是回执链路失败。

在没有幂等投送 ID 和明确生命周期前，保持“不盲目重试”是安全选择，但会牺牲重要事件可靠性。

### CSL-007：运行状态把“排队”描述得像“已完成”

插件 Pipeline 常返回：

```text
queued_to_neko(..., ai_behavior=respond, ...)
```

运行结果中也可能记录 `status="pushed"`。这些状态只表示插件调用了宿主入口，不能作为语音完成证据。

建议统一术语：

- `queued`：进入插件或宿主队列；
- `accepted`：宿主接受投送；
- `speaking`：已产生首音或开始播放；
- `completed`：前端确认播放结束；
- `interrupted`：开始后被打断；
- `expired/dropped`：未播放即失效。

在生命周期完善前，UI 和日志不得把 `queued/pushed` 翻译成“猫猫已经回应”。

### CSL-008：积压事件可能过时

主动投送管理器已有优先级、合并、TTL 和播放闸门，但人猫同播可能长时间由主播占据话权。此时：

- 被选中的弹幕可能在数秒后才播，语境已经变化；
- 连续高价值事件可能形成主动队列；
- 高优先级事件可能把旧事件留到更晚；
- 主播暂停后猫猫可能连续播出多条，重新形成堵塞感。

需要针对同播场景单独验证：

- 普通弹幕 TTL；
- 支持事件 TTL；
- 每个空闲窗口最多播几条；
- 同一观众/同一事件的合并规则；
- 主播恢复说话时未开始项目如何失效；
- 下播、切房、切模式时是否彻底清队列。

### CSL-009：缺少明确的打断策略矩阵

目前底层对所有已接受的主动回调基本采用同一套“发送成功即消费”语义，但产品价值不同：

| 事件 | 被打断后的建议 |
| --- | --- |
| 普通被选弹幕 | 丢弃 |
| 轻量 / 中量礼物 | 不应主动说；保留被动事实 |
| 高价值礼物 | 最多补一次短感谢 |
| SC / 舰长里程碑 | 最多补一次短感谢 |
| 系统安全告警 | 由各自模块定义，不能套用礼物规则 |

该矩阵应由事件元数据表达，核心只执行通用策略；不能在核心硬编码 NEKO Live 的礼物类型。

### CSL-010：Provider 行为不完全对称

实时语音 Provider 对以下能力的实现并不完全相同：

- 是否提供服务端 VAD；
- 是否回传请求 `event_id`；
- `response_already_active` 的错误格式；
- 是否使用 OpenAI 风格 `response.create`；
- 是否能区分生成完成与播放完成；
- 打断时是否仍可能漏出旧音频。

当前代码包含无 ID 错误的启发式关联和 Gemini 特殊路径。这些兼容逻辑降低了丢消息概率，但也意味着不能只靠单元测试证明所有 Provider 行为一致。

最低实机矩阵应包含：

- OpenAI 风格服务端 VAD Provider；
- 无服务端 VAD / 客户端 VAD Provider；
- Gemini Live 路径；
- 至少一个独立 TTS 路径；
- 网页单窗口与 Electron 多窗口播放。

### CSL-011：在途路径过多，容易重新形成双投送或错误屏蔽

这项已收敛为两个生产语义：

- 正常主动 `respond`：统一进入主动管理器，受话权、TTL、合并和打断策略约束；
- 被动 `read/passive_context`：只排队，等待自然消费点，不主动开口。

`deferred_candidate` 的插件桥、存储和测试已删除。被动上下文只依赖
`ai_behavior="read"`，插件不依赖宿主识别或降级任何遗留
`delivery_intent`。后续不得用“短形式尚未贯通”为理由恢复第三条投送路径；
若实现 `pause`，必须归属于独立的通用宿主核心。

### CSL-012：文档与当前实现冲突

现有 `docs/modules/live_support_events.md` 一方面写明人猫同播的 high/milestone 会产生主动感谢，另一方面仍写着：

> a high/milestone request ... cannot enter callback or voice hot-swap queues

这与当前恢复的主动 `respond` 路径不一致，也混淆了“不得进入被动热切换”和“不得进入主动回调”。

在行为稳定前先保留本台账作为问题证据；最终修复后必须同步清理模块文档、开发文档和测试名称。

### CSL-013：测试通过不等于直播体验通过

2026-07-27 当前整理任务的最新插件全量基线为：

```text
1668 passed, 1 skipped, 2 warnings
```

这些测试可以证明路由、队列、去重、文档契约和部分核心竞态，但无法证明：

- 真实麦克风 VAD 打断时机；
- 首音延迟；
- 浏览器/Electron 音频缓冲；
- 观众是否听到完整句子；
- 长时间同播后是否积压；
- Provider 的真实错误格式。

因此必须增加现场测试记录，不能把该测试数量写成“问题已修复”。

### CSL-014：缺少端到端可观测性

当前要回答“这份礼物感谢到底有没有播完”，需要同时推测插件结果、核心队列、Provider 事件和前端播放状态，缺少同一个事件 ID 的闭环。

建议仅记录脱敏、结构化生命周期，不记录原始弹幕或对话：

```text
trace_id
provider_event_id_hash
event_class
priority
queued_at
accepted_at
first_audio_at
playback_started_at
completed_at
terminal_state
interrupt_source
attempt
```

必须遵守隐私规则：不持久化原始弹幕、礼物留言、语音转录、密钥或用户敏感字段。

## 5. 当前不可混淆的两个生产语义

### 被动上下文

- 可以影响以后自然发生的回复；
- 不独立请求模型回应；
- 不独立准备或提升实时语音会话；
- 有明确 TTL 和下播清理。

### 主动回应

- 等待话权和播放空闲；
- 主动请求一次模型回应；
- 可以被主播立即打断；
- 必须有明确的终止状态。

`deferred_candidate` 已退役，不是第三种生产语义。插件不得再生产或依赖该
intent；真正的被动语义由 `ai_behavior="read"` 保证。

## 6. 推荐修复顺序

1. **先固定生命周期语义**：把 accepted 与 completed 分开。
2. **建立核心话权闸门**：统一主播说话、猫猫生成、猫猫播放和会话切换状态。
3. **接入打断终态**：让核心知道哪一批主动回调被哪个 response 打断。
4. **只给重要支持事件增加一次有界补偿**：普通弹幕保持丢弃。
5. **保持 deferred candidate 退役状态**：禁止重新形成双路投送。
6. **修正文档和 UI 状态词**：不再把 queued/pushed 当成已播。
7. **做多 Provider + 网页/Electron 实机测试**。
8. **最后再调节优先级、TTL 和补偿时间**，不要先用提示词掩盖链路问题。

## 7. 修复验收场景

### 场景 A：普通弹幕被打断

1. 猫猫开始回应一条普通弹幕；
2. 主播立即开口；
3. 猫猫在可接受延迟内停止；
4. 剩余句子不重播；
5. 队列不会因此堵塞；
6. 该弹幕终态为 `interrupted_consumed` 或等价状态。

### 场景 B：高价值礼物尚未出声就被抢占

1. 礼物进入主动队列；
2. 请求被接受；
3. 首音前主播开口；
4. 原请求终止；
5. 主播结束后，在 TTL 内最多补一次短感谢；
6. 不能出现两条完整感谢。

### 场景 C：高价值礼物说到一半被打断

1. 已确认前端开始播放；
2. 主播插话，猫猫停止；
3. 不续播残句；
4. 若补偿仍有效，只说新的短感谢；
5. 同一事件总补偿次数不超过一次。

### 场景 D：主播持续讲话

1. 持续产生普通弹幕和礼物事件；
2. 被动事实保持有界；
3. 猫猫不抢话；
4. 过期普通弹幕被丢弃；
5. 主播停下后不会连续倾倒大量旧事件。

### 场景 E：误触 VAD / 回声

1. 猫猫播放时出现短噪声或自身回声；
2. 不应频繁取消并补偿；
3. 若仍被判定为真实打断，补偿次数也必须有界；
4. 不得产生“取消 -> 重试 -> 再取消”的循环。

### 场景 F：下播或切换模式

1. 队列中存在主动、被动和可能的补偿事件；
2. 下播、切房或从同播切换模式；
3. 所有旧会话事件失效；
4. 新会话不得播出旧礼物感谢或旧弹幕。

## 9. 完成定义

只有同时满足以下条件，才能宣布“人猫同播主动回应打断问题已修复”：

- 被动上下文不会独立触发语音或热切换；（离线已实现，真机未验）
- ⛔ 主播话权优先且无明显竞态抢话；（当前远端无通用话权闸门，转独立宿主能力）
- ⛔ 主动回应没有插件可见 accepted、generation_done、completed、interrupted 终态；（明确移出 #2491，不再作为本轮验收）
- ✅ 普通弹幕被打断后不会重播；
- ⛔ 高价值支持事件补偿；（明确移出 #2491；插件也已删除惰性补偿 metadata）
- ✅ deferred candidate 与 overlay 插件路径已退役；被动语义只依赖 `ai_behavior="read"`；
- ⛔ per-cue TTL 尚待 #2491 宿主改动；priority / FIFO / 显式 coalesce 已是既有能力，不建设第二套队列或 lifecycle；
- ⛔ `pause` 短形式与 `brief_text` 选择；（独立后续宿主能力 / 产品实验，不在 RFC #2491 当前范围）
- ✅ RoomVerdict 不再以插件 `pushed` 结果开票；缺少宿主播放完成回流时保持关闭并记录 `delivery_unconfirmed`；
- ⛔ 至少完成一次真实麦克风、真实 Provider、网页和 Electron 场景验证；
- 文档、测试、运行状态和实际行为一致。（每轮整理与真机后均须复核）

## 10. 2026-07-27 被否决的本地宿主原型记录（远端已移除）

本节是本地原型的历史证据，不是当前远端 `neko-live` 的运行契约。原型涉及的
`main_logic/core/delivery_lifecycle.py`、宿主接线、设计文档与宿主专项测试均已
从远端分支移除，后续由
[RFC #2491](https://github.com/Project-N-E-K-O/N.E.K.O/issues/2491)
独立研究；#2491 已在 2026-07-28 收束并明确拒绝把其中的生命周期、补偿、
brief cue 或插件 ID 升格为当前核心协议。NEKO Live 的礼物 / 弹幕分级和开放
字典 metadata 声明仍留在插件侧。以下各小节描述的“实现”仅指历史原型，不是
待恢复能力、验收矩阵或未来兼容承诺。

### 10.1 投送生命周期终态（CSL-001 / CSL-005）

历史原型曾由 `main_logic/core/delivery_lifecycle.py` 提供单在飞批次槽位：

```text
queued → accepted → generation_done → completed
                 → rejected / interrupted_generation / interrupted_playback / expired
```

关键补齐：`OmniRealtimeClient` 的 `on_interrupt` 回调（类文档一直声明、但从未接线）现在在 OpenAI 路径 `handle_interruption()` 与 Gemini 路径 `server_content.interrupted` 两处触发，并在两个会话构造点接到 `handle_voice_interruption`。此外 `handle_new_message` 兜底覆盖"无显式打断事件但真实用户话轮开始且前端仍在播"的场景。单调 floor epoch 使跨会话的迟到信号失效。

### 10.2 话权闸门（CSL-004）

历史原型曾把 `host_floor_state()` 归一为 `held / pause / open`，后层
`select_floor_appropriate_batch()` 能在 `pause` 选择 `brief_text`。但
`ProactiveDeliveryManager` 的 `_can_release_proactive` 当前仍通过
`_host_floor_blocked()` 同时拦住 `held` 和 `pause`，所以正常管理器路径
到不了短形式选择器。该方向已经明确移出 #2491。当前收束方案只在真实发声 /
播放期间关闭窄闸门，开门后释放未过期完整 cue，不识别换气口或选择 brief cue。

### 10.3 一次有界补偿（CSL-002 / CSL-009）

历史原型中的 producer metadata（全部 opt-in，不设置即维持旧行为）：

| 键 | 含义 | 边界 |
| --- | --- | --- |
| `delivery_ttl_seconds` | 单条 cue 排队 TTL | 钳制 [3, 90] |
| `interrupt_policy` | `drop`（默认）/ `compensate_once` | — |
| `delivery_key` | 幂等键，补偿必需 | 缺失即不补偿 |
| `compensation_text` | 补偿用的新短句指令 | 可选 |
| `compensation_ttl_seconds` | 补偿条目 TTL | 钳制 [3, 30]，默认 10 |

补偿只在打断终态触发，同 key 至多一次（LRU 256），复用原 coalesce key（更新的同类事件可覆盖过期补偿），不带图、不续播残句、超时静默丢弃。会话边界一律不补偿。

### 10.4 生命周期观测（CSL-014 部分）

`manager.proactive_delivery_trace()` 提供 100 条脱敏环形记录（事件名、条数、
coalesce key 哈希、delivery key 哈希、epoch），不含原始 key 或任何消息文本。
**仍缺**：首音时刻、`voice_play_end` 的 turn_id 校验、Dashboard 接线。

### 10.5 插件侧策略声明

插件当前只在 request metadata 中声明 TTL 与显式 drop 策略；补偿、幂等键和
短形式字段已经从 producer 与 `adapters/output_contract_bridge.py` 透传白名单中
移除：

| 路径 | 声明内容 |
| --- | --- |
| co_stream 全部支持事件 | `delivery_ttl_seconds=45`、`interrupt_policy=drop` |
| co_stream 普通弹幕 | `delivery_ttl_seconds=20`、`interrupt_policy=drop` |
| solo_stream 全部路径 | 不声明，沿用宿主默认（打断即丢弃） |

契约见 `docs/modules/live_support_events.md`「Delivery Policy」。

### 10.6 历史原型测试

- 已移除的 `tests/unit/test_delivery_lifecycle.py`（宿主）曾有 27 条测试，覆盖终态归属、一次性补偿、TTL 钳制、话权闸门、会话边界失效、per-cue TTL 与 trace 脱敏。

### 10.7 本轮工作区整理边界

为避免把大改重新拆散或误当作混入，本轮未提交差异按责任归为三组：

1. **宿主通用交付安全**：本地原型已从远端 `neko-live` 移除并转交 RFC #2491；本地备份保留供独立研究，不在 Live 分支继续演进。
2. **插件直播正确性**：支持事件的 provider ID 先经过公开 ID 校验；短形式和补偿控制提示只使用固定事件类别，不拼入昵称、SC 文本或 provider label；Ritual 只有完整提示块真正进入预算后才计为使用；RoomVerdict 正确处理平票，并在没有播放确认时安全保持关闭。
3. **维护性清理**：删除未消费的被动状态字段、环境 revision、死 helper 和被同名定义静默覆盖的重复测试；兼容 facade 改为显式重导出，不改变既有运行入口。

不在本轮内擅自完成的项目仍是：`pause` 选择性释放、RoomVerdict 的播放完成回流、Provider 真机矩阵和前端播放完成关联。它们需要跨宿主接口或现场环境，不能混进插件本地整理。
