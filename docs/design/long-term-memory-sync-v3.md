# 长期记忆同步 schema 3：各端要遵守的规则

本文写给实现同步客户端的人。线上格式和服务端行为见同步服务仓库的 `docs/long-term-memory-v3.md`；这里写客户端一侧：怎么保存基线、怎么合并、提取进度和整理权怎么用。

电脑端的实现在 `memory/long_term_merge.py`（合并，纯函数）、`memory/long_term_sync.py`（导出、导入、本机状态）、`app/memory_server/long_term_sync.py`（发布、应用、整理权）、`services/chat_sync/long_term.py`（上传和拉取）。

合并规则有一份各端共用的样例：`tests/fixtures/long_term_merge_cases.json`。每条样例给出基线、本机、远端三份文档和期望的合并结果，期望结果是手写的。另一端的实现跑同一份样例，结果必须逐字段相同。样例由 `scripts/make_long_term_merge_cases.py` 生成，改规则时先改这个脚本里的期望值。

## 1. 基线和待上传

每个角色在本机存两样东西：

| 名称 | 内容 | 什么时候更新 |
| --- | --- | --- |
| 基线 | 服务器确认过的版本号、那一版的文档原样、以及「把那份文档导入本机再导出」得到的条目 | 自己的上传被接受；完整应用了一个远端版本 |
| 待上传 | 一个操作号、它基于的版本号、要上传的文档 | 本机内容和基线不一样时生成；被接受后清掉；应用远端版本时清掉 |

没被服务器接受的上传不能当基线。它只说明本机有什么，不说明别的设备有什么。

基线要存两种形式，是因为导入再导出不是原样往返：默认值、本机不认识的字段、来源 ID 的写法都会变。判断「本机改没改」拿本机导出和基线的本机形式比；判断「远端改没改」拿远端文档和基线的文档原样比。只存一种，没改过的条目会被当成改过。

## 2. 上传和拉取

```
上传：
  有待上传 → PUT {operationId, baseRevision, document}
    accepted           → 待上传变成基线
    conflict           → 什么都不记，接着拉取
    两者都不是         → 换新的操作号和完成时间，退避后重试
    服务器返回 400     → 服务器还不认识这种写法；照常拉取，然后退避重试
拉取：
  远端已过期             → 基线版本号跟到远端的版本号，内容不动；
                           之前没读到过那一版的话，下次上传把 lineage 加 1
  远端版本号 < 基线版本号 → 服务器丢了历史，丢掉基线
  远端版本号 = 基线版本号 → 不动，记下「此刻手里是最新的」
  否则取回整份，交给合并
合并（在本机记忆锁里）：
  local  = 导出本机现状
  merged = merge(基线, local, remote)
  把 merged 写进本机
  基线 = (remote 的版本号, remote 文档原样, remote 单独导入再导出的条目)
  merged 和 remote 内容不同 → 排一次发布
```

连续 5 次冲突后退避，不无限重试。

上传还在路上时，本机可能又生成了一份新的待上传快照。被换下来的那份要留着（电脑端留最近 3 份）：

- 服务器接受的是被换下来的那份：它成为基线，新的待上传改为基于这个新版本号。
- 回执丢了、之后拉到的远端版本内容和自己发过的某一份相同：直接把它记为基线，不做合并。它本来就在本机里，再合并一次会把它的增量算两遍。

写入本机时，merged 里和本机当前导出完全相同的条目，本机那一行不动。整行重建会丢掉协议里没有的本机字段。

## 3. 合并规则

条目的键是 `(kind, subject, id)`。下面「本机改了」指本机导出和基线的本机形式不同，「远端改了」指远端文档和基线的文档原样不同。

| 基线 | 本机 | 远端 | 结果 |
| --- | --- | --- | --- |
| 有 | 没改 | 改了或删了 | 取远端 |
| 有 | 改了 | 没改 | 取本机 |
| 有 | 删了 | 没改 | 删 |
| 有 | 删了 | 改了 | 取远端 |
| 有 | 改了 | 删了 | 删；本机的修改是用户确认（`userConfirmCount` 增加）或纠正（`versionHistory` 里出现了基线没有的 `correction`，按 `text` 和 `replacedAt` 比，不按条数比，因为历史只留最后几条）时保留本机 |
| 有 | 改了 | 改了 | 按字段合并 |
| 无 | 有 | 无 | 取本机，不产生退役记录；但事实的 ID 在远端的退役记录里时丢弃 |
| 无 | 无 | 有 | 取远端 |
| 无 | 有 | 有 | 按字段合并 |

没有基线（第一次同步、升级后分不清上次上传有没有被接受、基线和远端的 `lineage` 不同）时，整份按「无」的三行处理。

按字段合并时，每个字段先看哪一边相对基线变了：只有一边变就取那一边；两边都变才用下表。

| 字段 | 两边都变时 |
| --- | --- |
| `absorbed`、`archived`、`signalJudged` | 任一为真则为真 |
| `status` | 取更靠后的：`pending` < `active` < `confirmed` < `promote_blocked` < `promoted` < `archived` < `denied`／`merged`／`superseded`／`retracted` |
| `reinforcement`、`disputation`、`userConfirmCount`、`userFactReinforceCount`、`importance` | 远端的值 + (本机的值 − 基线里本机形式的值)；两边值相同也照此相加，因为是两次独立的增加。`importance` 截到 1–10。没有基线时取较大值 |
| `subZeroDays`、`subZeroLastIncrementDate` 和各个「最近一次」时间（`updatedAt`、`reinLastSignalAt`、`dispLastSignalAt`、`promotedAt`、`confirmedAt`、`archivedAt`、`voidedAt`、`suppressedAt`、`evidenceReviewedAt`、`evidenceReviewAttemptAt`、`sourceUpgradedAt`） | 取较大值。两台设备在同一天各记一次负分天数，是同一天，不能相加 |
| `sourceMessageIds`、`sourceFactIds`、`sourceReflectionIds`、`mergedFromIds`、`countedFactIds`、`signalFactIds` | 远端的顺序在前，接上本机多出来的，去掉任何一边相对基线删掉的，超出上限保留靠后的 |
| 正文和其余字段 | 先定出合并后的 `status` 和 `archived`；本机达到了这个状态而远端没有时取本机，否则取远端 |
| 一边有、另一边没有的字段 | 没有的那一边基线里也没有：取有的一边。基线里有（是删掉的）：按上一行处理 |

文档顶层：

- `evidence.retirements` 按 `id` 三方合并，保持远端的顺序，本机新增的接在后面。同一条两边都改时合并来源；合并后如果有纠正消息的时间还没解析出来，就去掉截止时间，等下次解析。
- `evidence.confirmations` 按 `fingerprint` 三方合并。
- 两个列表合并后各自最多留 20000 条，超出时从最前面丢。两份各自合法的列表合起来可能超限，不截断的话合并结果既写不进本机也传不上去。
- `progress` 见第 4 节，`organizer` 见第 5 节。
- `maintenance` 每个键取较大值；`lineage` 取较大值。

远端是 schema 1 或 2 时先当成 schema 3 读：事实一律算已判分，`evidence`、`progress` 按空处理。schema 1 文档里缺少的未确认反思不算删除（schema 1 从不带它们）。

## 4. 提取进度

`progress.a` 和 `progress.b` 记「哪些消息已经送去提取过事实」，内容是消息的 32 位 ID。`a` 是只看用户发言的那一遍，`b` 是看双方发言的那一遍。有没有提取出事实都要记。

- 记进度和保存事实在同一把锁里做，先存事实再存进度。导出快照也在这把锁里读，所以快照里出现某条进度时，它对应的事实一定也在。
- 合并：远端的列表在前，接上本机相对基线新增的，超过 2000 条从最前面丢。服务器的版本是一条线，所以丢哪些各端一致，不需要看时间。
- 组提取窗口时去掉 ID 已在对应进度里的消息；窗口空了就不调模型。没有共用 ID 的消息总是照常提取。
- 别的设备说的话，收到后至少等 15 分钟，并且**在等待结束之后**确认过一次自己手里是最新的快照（远端版本号等于基线、没有待应用的远端版本），才由本机提取。等待期间做过的检查不算：对方可能在那之后才发布进度。等待用本机时钟计。
- 积压的消息分轮提取，每轮有条数上限，只删掉这一轮处理完的；某一轮反复失败只放弃那一轮。
- 被丢出进度的旧消息可能被再提取一次。新事实和更早提取出的事实引用了同一条消息时，把这一对送去现有的去重仲裁，由模型判断是不是同一件事。**不能只因为来源相同就合并。**

电脑端目前只对收到的消息跑 `a` 这一遍。

## 5. 整理权

`organizer: {deviceId, renewedAt, rank}` 记哪台设备在整理这个角色。只有持有者做反思合成、晋升并合入画像、反思和画像精炼、每周自省、判分、旧条目复查。提取事实、用户的确认／否认／删除／纠正、展示后的反馈、群组分区，各端照常做。

`rank`：电脑且开了证据链（强力记忆）4，手机且开了 3，电脑 2，手机 1。模型配置不全的设备记 0：不认领，正持有就放弃。

「持有」的判断只看基线：基线文档里的 `organizer.deviceId` 等于本机设备 ID。本机改了待上传文档里的 `organizer` 不算，要等服务器接受。没开同步的角色不受这套规则限制。

本机另存一条不上传的记录：最近一次看到 `organizer` 的 `(deviceId, renewedAt)` 发生变化的本机时间。本机时钟被往回调就把它重置为现在。

```
h = 基线里的 organizer，r = 本机的 rank
r == 0            → h 是自己就放弃，否则不动
h 不存在          → 认领
h 是自己          → rank 变了，或距上次看到变化满 1 小时 → 续期（写新的 renewedAt）
r > h.rank        → 认领
距上次看到变化满 2 小时 → 认领
其余              → 不动
```

`renewedAt` 取自持有者自己的时钟，任何设备都只拿它判断「变没变」，不拿它和自己的时钟比大小。

合并 `organizer`：本机没改取远端；远端没改取本机；两边都改时，本机的 `rank` 严格更高才保留本机，否则取远端。所以两台设备同时认领只有一台成功。

服务端只接受声明里写的那台设备发布、更新或撤掉这份声明；其他设备上传时要把已发布的 `organizer` 原样带上。

## 6. 已判分

事实的 `signalJudged` 表示它已经判过分。不是持有者的设备提取出的事实带着 `signalJudged: false` 发布；持有者拉到后补判，判完置真，分数和标记在同一份快照里发出。合并时任一边为真即为真。

持有者没开证据链时不判分，这些事实保持未判，等开了的设备成为持有者后补判。

## 7. 其他约定

- 事实的 `eventWhen`、反思的 `temporalScope` 允许显式写 `null`，表示这条已经检查过事件时间、没有可填的。接收方见到这个键就不再让模型检查一遍。
- 反思和画像带 `userConfirmCount`、`countedFactIds`、`factSourceCounts`。接收方手里有全部 `countedFactIds` 对应的事实时自己按事实当前状态算来源计数（已撤回的不算），缺了就用带来的 `factSourceCounts`。条目本身没变、只有它依据的事实变了的时候也要重算。
- 退役和确认记录超过 16000 条时，由持有者从最早的开始清到 12000 条；单条退役记录的来源只留最新 2000 个。只清服务器已经有的内容。
