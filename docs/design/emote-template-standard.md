# 表情模板标准与通用动画导入方案

文档性质：**Implemented design record / Historical proposal**。初稿日期：2026-11-01。当前实施范围见下一节；其余内容是保留的原生模板标准草案，不代表已经支持的文件格式。

## 2026-11-03 实施范围调整

当前决定先采用 **Spine ZIP 导入**：用户自行把完整骨架、图集和全部引用贴图打包，制作器只识别 ZIP 内资源。不扫描本机目录、不补选外部模型贴图，也不解释第三方软件的角色、场景、CSV、皮肤分组或命名标签。当前运行时版本范围为 Spine 4.3；JSON 骨架和二进制骨架均由真实运行时验证后提交编辑器状态，普通动作使用原名，皮肤按完整原名选择。

包内文件保持相对路径，允许外层包装目录；存在多个骨架或图集时明确选择。ZIP 上限 64 MiB、最多 5000 个条目、路径最多 16 层、资源解压合计最多 512 MiB、单资源最多 64 MiB、单图集文本最多 8 MiB、累计扫描读取最多 128 MiB。缺文件、同名引用冲突、路径越界和不支持的版本必须明确拒绝，失败不替换当前模板。

本地库使用所选骨架、图集及贴图内容生成的 `spine-<sha256>` 标识，保存为用户表情模板目录下的 `spine-<sha256>/template.zip` 与 `meta.json`。内部副本文件名固定，下载或重开时使用 `spine-<sha256>.zip`；原上传名称只记录为显示信息。相同资源仅改变 ZIP 文件名不会生成重复条目，所选资源发生变化则生成新标识。额外的第三方配置不参与身份计算和资源副本。用户在编辑器中添加的图片仍属于独立的会话素材。

## 内置 YUI 0.5

YUI 0.5 的素材和换装清单随桌面版分发，挂件的骨骼标签、优先绑定和动作切换规则随换装清单提供。后端从 `NEKO_EMOTE_TEMPLATE_DIR` 指定的目录读取 `yui-0.5/yui-0.5.zip` 和 `yui-0.5/neko-template.json`。本地联调时可使用主仓下的 `N.E.K.O.-PC/assets/emote-templates`。缺少资源时，模板库仍支持用户导入普通 Spine ZIP。

模板库沿用 `builtin:yui-0.2` 存储键，旧会话的 `d_angry` 和 `d_surprise` 分别映射到 `d_angry2` 和 `d_surprise1`。默认眼睛拆成 A、B、C 三层，分别支持调色。B、C 层尺寸随 0.5 更新，尺寸不匹配的旧替换贴图保留在用户目录，渲染时使用新版贴图。内置素材只读，换装和组设置随模板会话保存。

外部 Spine ZIP 提供普通动画与原生皮肤播放。外部包里的清单不会启用换装项。已保存的旧包仍沿用其原内容标识。内置清单的 `format` 为 `neko.emote-template`，`formatVersion` 为 `1`。

每个部件用 `slot` 引用原始插槽，`labels` 提供界面名称，`attachments` 列出可选附件。`kind` 为 `toggle` 时声明一个开启用附件，支持跟随动作、开启和关闭。开启且当前插槽没有附件时才使用声明的附件。开启或动画显示时可以用 `hideSlots` 隐藏被覆盖的插槽。`kind` 为 `choice` 时只在动画显示该插槽的帧替换附件，`attachmentLabels` 可为附件提供界面名称。模板声明的部件也可在着色面板单独调色。

播放器解码后验证插槽和附件引用，部件选择与着色随模板会话及分组保存。所有部件默认跟随原动作。YUI 的说话手势遵循动画的显隐，洛丽塔衣服显示时会遮住原上衣。

**以下各节保留为后续原生模板标准的历史草案。** 普通 Spine ZIP 的导入仍只要求骨架、图集和贴图。完整原生清单、换装预设、目录导入和第三方场景迁移属于草案范围。

制作器采用一个导入入口，接收原生标准模板和已支持引擎的普通动画资源。两种输入转换为统一的内部描述，复用播放、画布编辑、模板库和导出流程。原生模板通过明确的资源映射提供部件替换、分区着色和组合预设；普通动画资源提供能够验证的基础播放能力，不推断部件语义。

## 已确定的方向

- 移除 EmoteLab 专属包适配，以及依赖其目录、CSV、命名标签和特殊模型标识的解释逻辑。
- 建立 N.E.K.O 原生表情模板标准，第一版标识为 `neko.emote-template`，格式版本为 `1`。
- 普通动画资源无需改成原生标准，也无需提供换装部件。第一版通用导入只覆盖受支持版本的 Spine 资源。
- 目录名不承担模板身份或功能语义。标准模板通过清单引用资源，普通资源根据文件内容和引用关系识别。
- 模板格式与动画引擎分开。Spine 是第一种引擎适配，不是标准协议本身。
- 本次只编写方案；实现、示例资源、JSON Schema 和校验工具分阶段交付，不在本次修改中加入。

删除专属适配不等于按来源拉黑文件。一个旧包如果包含能够独立读取的 Spine 资源，可以按普通资源规则重新识别，但不再恢复 EmoteLab 专属的换装、滑条和场景语义。原生格式不能自动扩大任何素材或运行时的使用授权。

以下是 2026-11-01 的代码基线，用于定位改造范围，后续实现以代码和测试为准。

## 功能分级

原生标准是否合规，与模板是否提供高级编辑功能，是两个维度。原生基础模板可以只包含动画，社区作者不必先制作全套换装系统。

| 能力 | 原生基础模板 | 原生可编辑模板 | 普通 Spine 资源 |
| --- | --- | --- | --- |
| 列出动作、播放、暂停、进度、循环和速度 | 支持 | 支持 | 从解码成功的模型读取 |
| 整体位置、缩放、旋转、镜像和画布构图 | 支持 | 支持 | 支持 |
| 背景、文字、叠加素材及现有画布效果 | 支持 | 支持 | 支持 |
| PNG 和 GIF 导出 | 按导出预算支持 | 按导出预算支持 | 在可正常渲染时支持 |
| 原生整套皮肤切换 | 模板声明时提供 | 模板声明时提供 | 有可用皮肤时提供原始列表 |
| 刘海、马尾、衣服等独立替换 | 不要求 | 按部件声明开放 | 不自动推断 |
| 分区着色与组合预设 | 不要求 | 按绑定声明开放 | 不自动推断 |
| 体型参数、物理参数编辑 | 不纳入首轮标准承诺 | 后续通过明确的扩展加入 | 不自动生成控制项 |

支持普通资源的已有骨骼、网格、权重、动画和原生物理，不意味着能够从 PNG、GIF 或 PSD 自动推断骨骼、拆件和绑定。GIF、APNG、帧序列、Live2D 等输入需要各自的适配器，不混入第一版普通 Spine 导入范围。

## 统一导入流程

导入入口接受目录或 ZIP，按以下顺序处理：

1. 建立保留相对路径的资源索引，检查路径和资源预算。
2. 查找唯一的 `neko-template.json`。允许 ZIP 外层有一个包装目录；清单的资源引用始终相对清单所在目录解析。
3. 找到原生清单时，检查格式标识、格式版本、引用和引擎要求，再交给对应引擎解码。
4. 没有原生清单时，根据文件内容与资源引用，查找普通动画模型和完整的资源组合。
5. 有多个清单、模型或可能的图集组合时，返回候选，让用户明确选择。不能按文件排序选第一个，也不能把几个模型的贴图混在一起。
6. 解码并检查实际动作、皮肤和编辑绑定，生成统一内部描述，计算当前可用能力。
7. 成功后提交编辑器状态和模板库副本；失败时保留原先正在使用的模板。

标准清单损坏、版本未知或引用无效时，应报告具体错误，不能静默退回普通资源模式而丢掉作者声明的功能。如果提供“作为普通动画导入”，必须是用户明确选择的独立操作。

目录与 ZIP 使用相同的识别和校验逻辑。不能出现同一组文件在目录模式被拒绝、打成 ZIP 后却通过的两套规则。

导入诊断区应列出错误资源、原因和修复方向；普通使用界面只显示当前可用功能，不要求用户理解适配器名称、内部版本或模型命名约定。

## 原生标准清单

推荐的包结构如下，只有清单名称固定，其他路径可以由作者组织：

```text
example-template/
├─ neko-template.json
├─ LICENSE.txt
├─ preview.png
└─ assets/
   ├─ character.skel
   ├─ character.atlas
   └─ texture.png
```

| 字段 | 要求与含义 |
| --- | --- |
| `format` | 必填，固定为 `neko.emote-template` |
| `formatVersion` | 必填，第一版为整数 `1`，表示清单结构和字段语义 |
| `id` | 必填，作者命名空间下的稳定模板标识；修改显示名称不应改变 ID |
| `version` | 必填，模板内容版本，如 `1.0.0`，与格式版本分开 |
| `name` | 必填，语言到显示名称的映射，至少有一种非空名称 |
| `author` | 必填，作者署名信息 |
| `license`、`licenseFile` | 必填，资源许可标识及包内授权说明；自定义许可可以使用 `LicenseRef-...` |
| `preview` | 可选，包内缩略图路径；缺少时可由预览生成 |
| `engine` | 必填，引擎类型、实际导出版本及模型和图集引用 |
| `stage` | 必填，逻辑画布与默认取景范围 |
| `actions`、`defaultAction` | 必填，至少一条有效动作及其默认选择 |
| `customization` | 可选，部件、颜色区域与组合预设；缺少时为原生基础模板 |
| `extensions` | 可选，带命名空间的数据扩展；不能携带可执行代码 |

名称的语言键可使用 `zh-CN`、`en` 等标记。展示时依次使用当前语言、英文、清单中第一种有效名称，最后回退到稳定 ID。社区作者无需为每个模板提供八种翻译；应用新增的 UI 字符串仍遵守项目的八语言规则。

`engine.exportVersion` 记录资产真实导出版本，不能填运行时版本冒充。检查器应比对模型数据中的版本。第一版只开放经过实际验证的 Spine 4.3 版本范围；不同主次版本不能仅以警告放行，同一主次版本也需要解码成功才能获得播放能力。

下例是目标格式示例，不是可直接导入的示例包。对应的骨架、皮肤、槽位和动画必须由后续官方示例真实提供。

```json
{
  "format": "neko.emote-template",
  "formatVersion": 1,
  "id": "example.character",

  "licenseFile": "LICENSE.txt",

  "engine": {

    "exportVersion": "4.3.13",
    "skeleton": "assets/character.skel",
    "atlas": "assets/character.atlas",
    "baseSkin": "base"
  },
  "stage": {
    "width": 1024,
    "height": 1024,
    "viewBox": { "x": -512, "y": 0, "width": 1024, "height": 1024 }
  },
  "defaultAction": "idle",
  "actions": [
    {
      "id": "idle",
      "label": { "zh-CN": "待机", "en": "Idle" },
      "animation": "Idle",
      "loop": true
    }
  ],
  "customization": {
    "rigVersion": "1",

      {
```

## 动作与构图约定

动作 ID、显示名称和引擎内动画名称分开。上例中的 `idle` 是稳定接口，`待机` 是显示名称，`Idle` 是模型中的实际动画名。动作时长从解码结果读取，不相信作者填写的另一个时长副本。第一版只支持逐条播放已有动作，不加入脚本执行或自定义动作编程。

`stage.width`、`stage.height` 表示逻辑画布，不是每张贴图的尺寸。`viewBox` 表示模型在引擎原生坐标下的取景矩形；对 Spine，`x`、`y` 是矩形左下角，宽高使用模型单位。渲染器负责转换到画布坐标，不改写骨骼、网格或权重。

取景矩形等比映射到逻辑画布，不拉伸模型。宽高比不一致时保留空白。默认取景保持稳定，不能每帧根据当前包围盒重新缩放；切换部件或播放跳跃时也不应造成角色忽大忽小。用户主动调整取景属于编辑器会话，不写回原始素材。

动作可选提供完整的 `viewBox` 覆盖，用于作者有意安排的特写或不同构图；同一动作播放过程中仍保持该取景范围固定。未声明覆盖时使用模板默认取景。

## 部件与预设约定

### 部件替换

第一版用显式部件 ID、受管槽位和选项皮肤表达替换关系。`hair.fringe`、`hair.ponytail.left`、`outfit` 等可作为推荐语义 ID，但不要求模型的骨骼、槽位或皮肤采用这些名称。

- 每个部件声明它管理的槽位，以及可选皮肤的精确名称。选项皮肤只负责该部件，不能悄悄替换整个角色。
- 不同部件不能同时声明拥有同一槽位。颜色区域可以作用于某个部件的填充槽位，不表示接管其附件选择。
- 必选部件必须有有效默认选项。可选部件允许选项为 `null`，渲染器需要保持对应槽位隐藏，不能被下一帧动画或基础皮肤重新带出来。
- 切换时先解除上一个选项，再应用新选项，不能把多个互斥选项累加。动画播放、跳转、循环和更换动作都要保留用户选择。
- 第一版部件选项适用于模板声明的全部动作。只适用于部分动作的选项需要额外兼容协议，不在缺少声明时自动放行。

第一版支持简单的选项约束：`options[].requires` 和 `options[].excludes` 都是“其他部件 ID 到选项 ID 数组”的映射；`null` 仅能用于可选部件。前者表示必须满足的选择集合，后者表示不能同时出现的选择集合。同一条件不能同时要求和排除同一选项。依赖不得形成环，复杂联动应合并为一个部件或通过完整预设表达。

用户选择与当前组合冲突时，应禁用该选项并解释冲突，或拒绝提交该次变更；不能猜测其他部件该换成什么。成套预设先对最终组合整体校验，再一次提交，避免逐项应用时短暂出现缺失部件。

### 分区着色

颜色区域必须绑定到精确槽位集合。第一版使用 `multiply`，即在模型原始和动画产生的颜色基础上施加 RGB 乘色；它不是能够把任意深色纹理准确变成任意目标颜色的通用重着色算法。

声明完整发色、服装色选择的作者应使用适合乘色的中性填充和明暗纹理，并将固定色描边、肤色和饰品放在不受该颜色区域影响的槽位中。上面的示例假设 `fringe_fill` 使用中性纹理，`#585868` 是默认乘色，`fringe_ink` 保留描边。已有深色彩色贴图也可以乘色，但 UI 应按实际效果称为色调调整，不能承诺任意颜色替换。

默认值只施加一次。重置、撤销、重新加载和切换动作都从同一原始模型基线计算，不能在上一帧或上一次编辑结果上重复累乘。RGB 调整不能修改透明通道，也不能把半透明边缘硬阈值化。

同一槽位在第一版只允许被一个可编辑颜色区域控制，避免不同颜色控件互相覆盖。整张角色的全局滤镜可以继续作为画布效果，但不能据此声明独立部件着色能力。

### 预设与兼容范围

预设是部件选择和颜色值的命名快照。预设遗漏的字段回到模板默认值，不继承用户上一次编辑后留下的随机状态。检查器验证引用、必选部件和选项约束，应用过程必须可撤销。

`id`、`version`、`formatVersion`、`customization.rigVersion` 分别表示模板身份、内容版本、协议版本和骨架编辑接口版本。骨骼关系、受管槽位或绑定方式发生不兼容变化时升级 `rigVersion`，不能只改显示名称来掩盖接口变化。

第一版部件选择限定在同一模板包内。符合相同格式不代表不同角色的衣服、刘海或骨骼可以互换。独立部件包、跨模板换装、自动权重迁移和任意 PNG 替换不属于第一版承诺；这些能力需要另外定义尺寸、锚点、网格与动作兼容规则。

## 尺寸与资源建议

| 项目 | 推荐值 | 规则 |
| --- | --- | --- |
| 逻辑画布 | 1024×1024 | 推荐值，不要求所有模板为正方形；宽高必须为正整数 |
| 原画制作 | 1024×1024，精细版本可用 2048×2048 | 原画尺寸与骨骼坐标、导出尺寸分别声明或保留 |
| 部件 PNG | 按实际可见内容裁切 | 保留引擎所需的锚点、裁切偏移和原始布局，不能要求所有部件铺满 1024 画布 |
| 图集页 | 默认以 2048×2048 为单页打包上限，支持多页 | 大型模板可用 4096；实际加载还要检查设备纹理上限与总资源预算 |
| 缩略图 | 256×256 或 512×512 | 可选 PNG，不参与骨架贴图匹配 |
| 图集区域间隔 | 至少 2px 作为默认建议 | 配合适当的边缘复制和正确的 alpha 渲染方式减少串色 |

默认静止姿态可占画布长边约 80%，给头发、装饰和动作留空间；最终以动作完整播放的效果验收。有意裁切的特写需要明确设置动作取景。

已有低分辨率素材保留原始像素，不要求先插值放大。提高画布或图集尺寸不能补回原画细节。部件裁切、图集预乘 alpha 和渲染器混合方式必须一致；尺寸合规不等于边缘质量合格。

图集裁切、区域间隔和 alpha 行为参考 [Spine 官方纹理打包说明](https://esotericsoftware.com/spine-texture-packer)。

## 普通 Spine 资源导入

普通导入查找受支持版本的 Spine JSON 或二进制骨架、文本图集和图集引用的图片。标准导出常见的 `.json`、`.skel`、`.atlas`、`.png` 应可识别；`.skel.bytes`、`.atlas.txt` 等扩展名变体可以作为候选，但必须检查实际内容，不能因扩展名匹配就假定可用。

骨架 JSON 根据结构和版本识别，不能把所有 JSON 都当作模型。骨架和图集的匹配需要检查附件和图集区域引用；有多个可能的有效组合时让用户选择。贴图按图集相对路径解析；只有匹配唯一时才允许文件名回退，不能在冲突时取第一张同名图片。

普通资源不要求 `Characters`、场景 JSON、专属 CSV 或自定义清单。动作列表从实际解码数据生成，显示名称默认使用原始动画名称；首次导入选定一个动作后固定默认取景，后续不逐帧自动适配。骨架本身没有有效动画时，可以提供明确标识的静态姿态预览和 PNG 导出，播放与 GIF 功能保持不可用，不能合成一个虚假的动作条目冒充源模型动画。

模型有皮肤时可以提供整套皮肤列表，按模型的默认状态初始化；需要选择时由用户明确选择。不得把全部皮肤自动叠加，也不能根据皮肤名字生成刘海、马尾等独立编辑面板。

缺少图集或贴图时说明具体缺失引用，允许用户重新选择完整目录或明确补充文件。不再要求通过放进某个约定目录来“补全”模型。

## 统一内部描述与功能开放

包解析层回答“有哪些资源和声明”，引擎解码层回答“哪些数据实际可用”，编辑器回答“当前环境能提供哪些功能”。三者不能共用一个未经验证的能力开关。

统一内部描述至少包含：

- 输入来源类型、稳定模板身份、源文件指纹和资源索引。
- 引擎类型、导出版本、运行时匹配结果和解码状态。
- 解码后的动作、皮肤、默认姿态和默认取景。
- 原生部件、颜色和预设的声明，以及逐项绑定检查结果。
- 声明能力、已验证能力、当前可用能力，以及结构化错误与警告。

原生能力由有效声明与真实资源共同确定，普通资源只开放能够从模型验证的基础能力。最终 UI 使用“已验证能力与当前渲染器能力的交集”，不能因为清单自称可换装就打开换装控件，也不能仅因服务端读到了文件就标记预览和导出可用。

基础模型、默认动作、默认皮肤、必选部件和引用资源无效时拒绝原生导入。可选预览图缺失或无法识别的可选扩展可以降级并给出诊断；损坏的部件声明和预设引用不能被静默丢弃后仍宣称原生模板校验通过。

内部描述版本、公开 `formatVersion`、本地模板库版本独立维护。原包身份与内容指纹也应分开：ID 用于识别模板，指纹用于判断资源是否变化；新版本不能悄悄套用不兼容的旧编辑会话。

## 文件路径与资源预算

清单只能引用包内相对资源，不允许通过绝对路径、`..`、符号链接、远程 URL 或包内脚本获取依赖。索引保留完整路径，统一分隔符和 Unicode 归一化；拒绝会在目标平台产生歧义的重复路径和大小写冲突。原始模型导出信息中的作者本机路径不能成为读取本机其他文件的授权。

第一轮实现以当前导入预算为基线，作为应用默认限制，不作为格式永久上限。传输预算与资源内容预算分开：

| 项目 | 初始应用限制 |
| --- | --- |
| 上传 ZIP 的传输大小 | 64 MiB |
| 包内文件数量 | 5000 |
| 所引用资源的总解压大小 | 512 MiB |
| 单个描述元数据 JSON、CSV 或图集文本 | 8 MiB |

目录与 ZIP 使用相同的内容预算，包括文件数、资源总大小与解析限制。上传 ZIP 额外受 64 MiB 传输上限约束，诊断中需要明确区分“传输包过大”和“模板内容无效”。目录模式应在批量读取前按文件大小预检；是否保留中间内存 ZIP 由传输实现决定，不能把它的偶然压缩率当作目录完整性的判据。

骨架 JSON 是模型数据，不能直接套用小型描述元数据的 8 MiB 上限。实施时需要为 JSON 与二进制骨架定义一致的模型解析预算，并用代表性资产验证；该预算与贴图解码预算一并固化后，才作为 v1 发布配置对外公布。

贴图还需检查解码后的宽高、总像素量及设备限制，压缩后的 PNG 文件大小不能替代内存预算。具体像素预算应由代表性示例在网页和 Electron 中测定后固化，不把未经验证的数值写成通用保证。

## 旧模板库迁移

旧库可能保存原始 ZIP、附带贴图、EmoteLab 归一化清单和编辑会话。迁移必须保留原包与用户文件，不按旧格式类型直接删除条目。

1. 标记旧清单版本，不将旧 `source.kind` 或目录名字视为原生标准标识。
2. 从已保存的资源副本按普通资源规则重新检查。必须合并用户明确附带的贴图索引，同时处理同名冲突，不猜测外部缓存目录。
3. 可以播放的条目恢复为普通动画资源，只迁移仍能明确对应的动作选择和整体取景；旧的专属换装、滑条与角色配置不强行映射。
4. 缺资源或版本不支持的条目保留并显示修复原因。重命名、重新导入和删除仍由用户决定。
5. 原生模板更新时，只有模板身份、动作或控件 ID、`rigVersion` 和资源校验兼容，才恢复对应编辑会话；不兼容项应回到新模板默认值并说明原因。

迁移应可重试，失败不能覆盖原包或破坏旧会话。旧文件修复后应能重新检查，而不需要用户清空整个模板库。

## 实施顺序

### 第一阶段 定义合同与样例

固化 v1 字段、JSON Schema、内部描述和引擎接口。准备一个原创基础动画包和一个原创可编辑包；可编辑包至少有一个部件的两个真实选项、一个独立颜色区域和两个完整预设。示例不能依赖 EmoteLab 模型、贴图、骨架或动画。

### 第二阶段 替换导入流程

增加统一导入接口，例如 `POST /api/emote-maker/import`，共用归档检查与资源索引，分派原生和普通资源。目录输入只负责索引和传输。接入多模型选择、缺失文件诊断、未知格式和不支持版本错误，再替换编辑器入口。

### 第三阶段 接入编辑映射与模板库迁移

将部件、颜色和预设绑定转为引擎可执行的操作，移除名称猜测、第三方角色默认项和专属场景换算。基础播放、画布效果、导出和 PNGTuber 导出继续复用同一套流程。加入旧库重新检查和会话兼容判断。

### 第四阶段 清理旧适配并回归

删除 EmoteLab provider、专用导入路由、专属目录识别和遗留 UI 标识，更新相关测试与文案。新解析路径和引擎适配保持相同接口结构，不能为某个示例角色另加特判。

后端检查与归一化逻辑应可被导入接口和离线校验工具复用，路由只处理传输。仅供某个页面使用的辅助逻辑不放入通用 `main_logic`。修改 `main_logic`、`main_routers` 或 `app` 时，按项目要求检查相关模块回归；UI 字符串同步更新全部八个 locale。

网页和 Electron 必须读取同一套模板数据与资源索引。资源 URL、运行时加载和 API 使用当前窗口实际后端，不假设所有窗口都从 `/` 初始化，也不依赖作者本机的绝对文件路径。

## 验收规则

### 数据与导入

- 同一资源集合使用目录和 ZIP 导入，得到相同的模型、动作、贴图引用和功能判断。
- 任意命名和嵌套目录的普通 Spine 包，不提供角色配置、场景目录或 CSV 也能播放已有动作。
- 多模型、同名贴图和多个图集不会被静默合并；缺文件、坏清单和不支持版本均有具体原因。
- 明确声明原生格式的坏包不会自动伪装为普通包成功导入。
- 声明的动作、皮肤、槽位、部件选项、颜色和预设引用均经过实际数据校验。

### 功能与画面

- 普通资源和原生基础模板能够播放、暂停、拖动进度、循环、调整速度、整体构图并导出。
- 部件切换、无部件选项、换动作、跳转、循环、撤销、重置与重新打开保持一致，不累积旧皮肤或意外恢复隐藏部件。
- 发色或衣服颜色只影响声明的区域；默认预设重置后还原原始设计，不逐次变暗，不改变边缘透明度。
- 每个官方预设检查全部示例动作，验证资源完整、组合合法、构图稳定且没有意外空白。自动采样检查不代替人工观察整个动作。
- 可替换部件单独置于白、深色和高对比背景检查边缘，回拼后再检查遮挡与接缝。只通过图层数量、alpha 或 JSON 检查不能证明美术质量合格。
- 原始帧图挂在空骨架上，不能以此声明独立部件骨骼动画或换装能力。

### 存储与运行环境

- 旧库迁移、缺资源修复、模板版本更新和失败导入不丢失用户原包。
- 渲染资源切换与销毁不残留旧纹理、动画循环或旧模板状态。
- 开发网页和 Electron 均验证导入、库恢复、预览与 PNG/GIF 导出；PNGTuber 导出覆盖现有状态、帧数和图集布局规则。
- Windows 人工验证使用可见浏览器与可见命令行；Python 脚本和测试统一通过 `uv run` 执行。

1. 维护者可审阅的字段规范和 JSON Schema。
2. 可直接导入的原创基础示例与可编辑示例，以及其作者资源许可。
3. 一个统一导入入口、普通 Spine 适配与原生标准适配。
