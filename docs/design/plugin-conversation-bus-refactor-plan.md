# 插件对话 Bus 重构与兼容计划

状态：已在当前工作区实现并完成针对性验证，尚未发布。按项目约定保持 SDK 0.1.0，不因新增 API 调整版本号；沿用既有版本声明与兼容入口；未设旧入口删除期限。本文保留目标契约和基线核对，实际覆盖、初始资源参数及验证边界见下方实现记录，不将测试替身解释成完整生产环境验收。

讨论日期：2026-10-29 至 2026-10-31。已收敛公开契约、兼容和第 0 步核对；本轮进一步限定非 plugin 改动，按既有归属／发布出口分批接入回复和播放，并同步实施依赖与文件归属。继续按“如无需求勿增实体”执行。现状分析基线：`560f5e25d11f82f67feab03748b072ceb5cbb549`。后续实现以届时的代码、测试和正式接口文档为准。

本次重构面向插件获取前台角色对话信息的能力。主要目标是支持 `watch()`，补齐记录身份、结构化查询和刷新的一致性，减少插件作者自行轮询、过滤、去重的重复代码。`self.bus.conversations_v2` 纳入后续重构计划：新旧 SDK 入口共用重构后的对话底层，旧入口保持兼容，新入口提供明确的新契约。

v2 同时承担对话文本的查询与观察，覆盖已接受的用户文字和语音转写。一个 watcher 应能同时提供新记录通知与最近 N 条视图变化通知；两者共用筛选条件、记录身份和生命周期，但使用不同回调语义。当前 `voice_transcript` 的语音输入观察职责融入 v2，旧 custom event 入口在兼容期保留。

文字输入支持早期提交观察：首个覆盖范围为普通文字对话，在路由归属明确且必要检查通过后、昂贵准备之前观察提交正文。Main/Agent 仅补最小发布与标识透传，插件侧承担读取与监听；具体代码位置在接入该路径时核对。

回复来源是重点新增功能。SDK 提供消息读取、按输入关联的交互详情，以及回复文字和前台播放边界观察。文字收口与播放停止分别表达，不设置一个总完成状态。实现可按纵向能力分批交付，不为方法齐全先建空系统；早期输入、来源和播放等已确认目标仍保留。

当前保守资源初值为：新订阅每插件 128／总 4096；SDK watcher 待处理 512 条／2 MiB、运行中最多 8，窗口受宿主实际 effective_limit 限制；新 Message Plane 读取结果 2 MiB、Core 默认执行器中新读取最多在途 4 项，按线程使用唯一 DEALER 身份；详情共用 512 项／8 MiB、单项 64 KiB、TTL 600 秒；下行 bounded 单帧 2 MiB、每宿主待发 128 条／8 MiB、进程待发 1024 条／32 MiB，发送端 SNDHWM=8。新读取超限明确失败，不静默缩小窗口或全面收紧旧读取／旧 Bus 载荷类型。这些是实现初值，不是新增可配置策略体系；已进入 libzmq／接收端的帧不计入应用待发额度，也不能被 STOP 抢占。

真实临时 socket 混合负载覆盖约 120 KB 观察与约 900 KB 响应、连接后暂停读取、多宿主独立停止和关闭；验证有界积压及端口释放。测得的短延迟仅代表该负载，扩大真实插件／长时间运行后仍需校准；不据此承诺固定毫秒 SLA、端到端总内存等于待发额度或无遗漏。

本轮实现复审进一步固定边界：Main 观察调度在无事件循环或任务拒收时安全释放协程；Realtime 终止事实服从原 arbiter 的响应归属；头像拖放等合成输入不冒充普通文字早期提交；前台随机 ID 生成失败不阻断播放器。SDK watcher 启动中不可修改回调或重复登记，stop 后的迟到登记会注销；初始化合并缓冲同时限条数和字节。缓冲溢出后最多立即补一次快照，持续溢出则保留刷新标记等待后续信号，不无限追赶。消息平面成功替换快照（含空替换）触发既有视图失效；新 conversations 取消订阅在状态锁内核验所属插件，旧 Bus 的接口语义保持。Memory 的读取安全修正只在其领域计划记录。上述修正均复用既有对象和生命周期，SDK 保持 0.1.0。

完整测试中的受控负载确认：新 MP 读取若接纳 32 项，会在慢服务时占满默认执行器，连带阻塞旧控制 RPC 的 queue.put。现将新读取在途上限收紧为 4，超额使用现有 TransportError(code="BUSY")；为 Python 3.11 标准最小 5 线程默认池留一个线程，不新建执行器、等待队列或 QoS 服务。这不保证插件自行配置更小线程池、或其他任务已经占用线程时仍有余量。SDK 只将 BUSY 快照失败标为等待额度；成功 MP 读取释放额度后，复用 rev 登记向常驻接收循环合并一次本地提示，唤醒这类待刷新视图，使多 watcher 启动不因一次接纳失败永久缺 initial。协议错误、超时或普通 dirty 不因此自动重试，也不新增轮询或连接。SDK 版本仍为 0.1.0。

## Best effort 与系统稳定性

插件对话观察首先是 best-effort 通道。设计目标是在不影响本体稳定性的前提下低延迟交付信息，并通过合理缓冲、批量派发、连接复用和故障隔离尽量减少常态与短时突发中的丢失。允许信息缺失、延迟、重复或未知，不以恢复完整状态、逐消费者确认或端到端无遗漏作为成立条件。

| 优先事项 | 设计方向 |
| --- | --- |
| 本体不被拖慢 | 观察发布轻量、非阻塞，不等待插件和详情构造 |
| 交付及时 | 宿主已有事件内容时直接派发，不要求每次先远端查询和重建视图 |
| 正常运行少丢失 | 减少无意义中转、重复序列化、逐事件任务创建和调度阻塞 |
| 过载有界 | 有界队列与缓存，必要时丢弃，恢复后继续工作 |
| 故障隔离 | 慢插件、慢回调和 Memory 查询不阻塞其他订阅或本体 |
| 信息准确 | 已知事实与身份不乱配，缺失信息不靠猜测补齐 |
| 维护可观察 | 低成本统计已知丢弃、队列积压和派发耗时，不要求每次丢失都向业务发恢复事件 |

读取近期记录、序号和短缓冲可以在成本合适时帮助消化突发或减少重复，但不是所有通知的必经补读协议。ACK、持久化消费位置、强制追赶、完整生命周期重建与可靠恢复不作为本次门槛。

## 范围与边界

主要改动位于插件 SDK、core bus、plugin host/server 和 message plane，既有对话观察继续沿用已有事件。Main/Agent 只增加早期输入、已知回复来源、文本边界和前台播放报告所需的最小观察事件发布、接收转交与关联字段透传，不承担存储、查询、watcher 或插件回调调度，不重构原有路由、session、LLM、记忆、TTS 或播放逻辑。

区分自然播完、取消和异常停止所需的信息如果在当前前台上报中已经丢失，允许讨论最小的播放报告字段扩展与透传；不能仅靠插件侧推断。具体生产点和前台改动清单待实现设计确认。这不扩展为音频流、精确播放进度或播放器重构。

本次重点是读取与监听，不扩展插件调用、消息推送或对话控制能力。以下能力不作为本次重构的默认承诺：

- 完整 LLM messages、最终 system prompt、token 流或思考过程。
- 原始麦克风音频、TTS 音频、合成进度、精确播放进度与逐字音频对齐。基础前台播放报告纳入关联观察，不代表用户一定听到了声音。
- 持久化聊天归档、持久化消费位置、跨重启可靠恢复、ACK 或业务副作用的 exactly-once 保证。短缓冲读取等降低丢失的措施按成本取舍，不承诺在保留范围内必然补齐所有回调。
- 为普通对话重新定义用户问题与角色回复的配对关系。
- 将 `frames`、`memory` 和所有其他 bus 强制改成同一种数据语义。
- 完整附件内容包、逐 token 回复流、工具执行明细、所有外部路由的业务最终结果和完整会话运行监控。本次模式信息仅作为输入与回复的必要上下文。

## 当前实现

### 对话读取路径

```text
宿主已处理的对话观察事件
  → 插件侧接收与转发边界
  → plane_bridge
  → message plane ingest
  → conversations store，topic=all

插件 self.bus.conversations
  → SDK SdkConversationsBus
  → Core ConversationClient
  → MessagePlaneRpcClient
  → bus.get_recent / bus.query
  → conversations store
```

这里的 store 保存单条文本记录，不是包含完整上下文、记忆和播放状态的 conversation 对象。主要记录类型为 `user_message`、`assistant_message`、`proactive_reply`，部分主动回合还包含 `proactive_instruction`。

生产、转发和存储属于 best effort 与有界内存快照。记录没有进入 store 时，插件查询和未来的 watcher 都无法补回该记录。

### 与其他 Bus 的差别

| 项目 | 当前 conversations | 对比与影响 |
| --- | --- | --- |
| 查询参数 | `conversation_id`、`max_count`、`since_ts`、`timeout` | 缺少直接按角色、消息类别查询的参数 |
| 查询计划 | 正常 `get()` 结果没有附带可重放计划 | 不能直接复用现有 watcher 的刷新机制 |
| 链式操作 | 对本次快照进行本地处理 | `where()`、`sort()`、`limit()` 可用，但不会自动更新 |
| 监听 | 不支持 `watch()` | messages、events、lifecycle 支持；frames、memory 也不支持 |
| 单条记录身份 | 底层有事件 ID，SDK record 未完整暴露 | 插件轮询去重、缓存和落库缺少明确主键 |
| 存储与传输 | 查询 message plane | 与 messages、events、lifecycle、frames 共用底座；memory 走另一条控制 RPC |

### 已有订阅设施与实际缺口

现有 `BusSubscriptionService`、订阅登记、`BusSubscriptionManager`、PluginHost 下行及插件命令循环的 `BUS_CHANGE` 接收已经存在。本次优先扩展这些设施，不另建一套对话通知总线。当前仍有以下缺口：

- 订阅支持列表、宿主订阅容器和分发接入均未包含 conversations，仅增加 SDK 方法不能接通监听。
- 现有订阅登记的 rules 等字段不足以表达角色、消息类别和输入来源筛选，需要补充明确契约及实际执行。
- 现有 watcher 收到变化后重查快照、再计算差分；它适合窗口变化，不能直接满足逐条新消息通知。
- 现有分发循环等待一个事件的整批发送完成后才继续处理后续事件；已有超时和并发限制不等于已满足对话所需的慢接收者隔离。

Message plane ingest 在 `Store.publish()` 成功后已经有 PUB 发布出口。接入公开订阅可复用该出口，也可在同进程装配时注入入库观察回调以减少通信；具体衔接见下文，不把两条路同时作为重复的事件来源。

### 开发者目前会遇到的问题

**记录身份与关联 ID 混用。** `conversation_id` 用于关联上下文，不是统一的单条消息 ID。部分主动指令和回复共用同一个 ID；普通消息也不保证用户输入与对应回复共用同一个 ID。SDK record 的 `key()` 优先返回 `conversation_id`，以它作为单条消息缓存键可能覆盖记录。

现有通用 watcher 并不直接调用 SDK record 的 `key()`。它优先识别明确的记录 ID，缺失时回退到整条记录的 dump 指纹。因此不能把上述 SDK 问题直接等同于“watcher 必然合并同回合消息”。重构需要同时明确 SDK 的身份字段与 watcher 的内部识别方式。

**首次读取与条件查询顺序不一致。** 无条件 `get()` 走 `bus.get_recent`，取最近 N 条并按入库先后返回；带正常正值 `since_ts` 或非空 `conversation_id` 时走 `bus.query`，按 store 序号倒序返回。直接遍历追加消息，或把第一条／最后一条当成最新记录，会得到不同结果。

**角色过滤发生在数量截取之后。** 当前 `get(lanlan_name=...)` 不受支持，结构化 `filter(lanlan_name=...)` 也不受支持。`where(lambda r: r.lanlan_name == ...)` 可以使用，但只能从已经取到的全局最近 N 条里筛选，不能表达“该角色最近 N 条”。其他角色消息较多时，目标角色记录可能完全落在窗口之外。

**现有列表不直接支持通用 watcher。** conversations 正常读取只构造快照列表，没有通用 watcher 需要的可重放计划。公共回放代码虽包含 conversations 分支，也不代表正常返回值可以重放。这是复用旧列表监听算法时的限制，不意味着新业务事件必须先重放查询才能交付。

**增量读取不是可靠消费。** `since_ts` 包含边界，重复读取需要去重；条件查询只取最新 N 条，超过上限时没有现成的 seq 翻页与消费确认协议。客户端还有 `since_ts=0` 被按假值分到无条件读取的边界问题。

### 两种时间的意义

`timestamp` 表示转入插件对话通道的时间，当前 `since_ts` 按它查询。`metadata.ts` 表示消息自身的时间，更适合展示；角色文本可能开始较早、收口较晚，两个顺序可以不同。

两种时间都有用途，不应强行合成一个字段。后续应明确命名和排序契约，避免使用展示时间推进读取游标。文本记录的时间也不是 TTS 播放时间。

### 文字与语音路径的异同

当前不同路径最终共用 conversations 的文本记录结构，但其内容来源和进入条件不同。

| 路径 | 用户记录来源 | 角色记录来源 | 需要保留的区别 |
| --- | --- | --- | --- |
| 文字输入与文字模型 | 记录用的用户文字，优先使用清理后的 `memory_text`，否则使用输入正文 | 文字模型输出 | 记录正文不一定等于发给模型的完整输入包装 |
| 原生实时语音 | 通过检查的用户最终转写 | provider 提供的文本或音频输出转写 | 文本到达时间与真实发声、前台播放时间不同 |
| 独立 ASR 加文字模型 | 通过检查的 ASR 最终转写 | 文字模型输出 | 输入来自语音，不代表回复由实时语音模型生成 |

用户消息的 `metadata.is_voice` 区分输入来源，不是回复模型或前台模式的证明。用户语音经过准入、路由归属、接管和回声等检查，不能把 conversations 理解成所有麦克风内容的镜像。

普通角色回复通过共享文本缓存收口后发布，不是逐 token 记录。打断后可以保留部分文本，废弃重试的文本会有清理路径；当前记录没有统一的完整性或结束原因字段，不能凭一条 `assistant_message` 判断它是完整回答。

文字模型的长回复还可能采用完整文本展示、尾部摘要朗读的分流。因此 conversations 的正文不是用户实际听到的逐字稿，`metadata.ts_end` 也不是前台播放结束时间。

### voice_transcript 与 custom_event 的现状

`custom_event` 是按事件类型与处理器 ID 执行插件函数的通用机制。装饰器注册处理器，不会自动生成业务事件；它与 `self.bus.events` 的记录查询和 watcher 不是同一个机制。

当前语音观察路径为：

```text
被接受的非空用户最终转写
  → 异步广播 voice_transcript_observed
  → 插件边界检查 Agent master、user plugin 和生命周期
  → voice_transcript_bridge
  → 查找 event_type=voice_transcript 的已登记处理器
  → PluginDispatchService 并发派发
  → PluginHost / TRIGGER_CUSTOM / EntryExecutor
  → 插件 async custom event 函数
```

handler 当前收到 `transcript`、`lanlan_name`、`metadata`。正常宿主生产路径的 metadata 包含 `session_type` 类名和 `voice_source=True`，不保证提供 session ID、provider、置信度或时间字段。上游广播 UUID 没有作为独立参数投影到 handler；派发中的 `event_id` 和仲裁结果里的 `source_event_id` 指处理器 ID，不能用作每次用户发言的唯一身份。

该路径是 best effort 旁路观察。Main 不等待插件决策；旧请求包装广播后返回 `None`，旧 `voice_bridge_result` 在 Main 侧被忽略。插件服务仍保留 `noop`、`cancel_response`、`prime_context` 的返回值归一化与仲裁，但选中动作不意味着取消回复或注入当前回合上下文。

bridge 默认向各 host 传入一秒处理预算，不是 Main 等待插件的时间，也不是从用户发声到所有 handler 完成的全链路时限。多个处理器并发派发、参数分别深拷贝；相邻语音事件没有按 handler 串行完成的保证，也没有持久化补发或 ACK。

同一有效语音输入还会独立发布 conversations 的 `user_message`。两条路径没有共同透传的消息身份、跨路径到达顺序或原子送达保证，开关条件也不同：语音 custom event 额外受 Agent master 控制。不能按正文与角色猜测合并，也不能收到 custom event 后就假设查询一定已能读到对应记录。

## 已确认的重构方向

### 如无需求勿增实体

新增能力应接走插件本来需要自行完成的轮询、筛选、解码、明确关联和资源清理。先检查现有客户端、存储、订阅和生命周期能否承担，再决定新增模块或对象；不能仅为统一外观或让架构图完整而增加转发层。

继续使用 `self.bus.conversations_v2` 和新的 Memory 客户端，不新增 `ctx.information` 等聚合门面。接口是否容易找到可通过命名、正式导出、文档和示例解决，不作为增加运行时实体的依据。

本次不建设全局 `capabilities()`、支持程度与当前可用性的能力矩阵。操作不支持、订阅不能建立、服务未就绪和调用失败由实际读取或订阅操作明确反馈；成功但无匹配数据返回空结果。没有事件到达不用于推断能力状态，缺失字段按自身契约表达。未来确有跨版本协商需求时再针对具体能力设计。

普通消息、回复详情等需要清楚的数据契约，但职责不要求各占一个类或文件。转换可先用小函数，少量相关业务可位于同一模块；有状态对象只用于实际拥有的订阅、有限关联和资源。客户端、Context、RPC handler 保留必要的公开接口与进程通信边界，不在每层重复业务解释或包装结果。

### conversations_v2 作为新的 SDK 契约

新增 `self.bus.conversations_v2` 作为后续重构计划的一部分。旧 `self.bus.conversations` 继续承担兼容入口；新插件可以显式使用 v2，避免通过插件全局版本开关隐式改变同一段代码的行为。

v2 表示 SDK 读取与监听契约，不意味着另建一套对话业务系统或要求本体重复生产事件。插件侧保存有限的观察副本与派生视图，本体仍负责实际对话；缓存不承担还原完整本体状态的职责。

```text
旧 conversations
  → 旧参数、结果与默认行为适配 ─┐
                              ├→ 共用记录来源、转换与筛选 → 现有普通消息存储
新 conversations_v2            │
  → 新契约适配 ────────────────┘

普通消息入库后的变更
  → 共用订阅与 watcher 机制
  ├→ 使用已有事件内容及时派发给订阅者
  └→ 有视图订阅时维护最近 N 条

输入／回复／播放阶段事实
  → 插件侧有限接纳与必要关联 → 同一订阅机制
```

下文确定公开方法、字段及默认行为；内部读取操作和订阅标记以第 0 步核对记录为准，辅助函数沿用项目约定，不据此增加一层转发。以下示例适用于已接通的 SDK 0.1.0 能力，实际生产路径覆盖见实现记录。

### 兼容集中在入口

本次重构发布保留当前受支持的公开旧入口及其约定行为，不自动要求旧插件迁移。兼容范围以当前公开 SDK 和既有受支持协议为准，不追溯恢复早已删除的 API，也不承诺任意内部模块、私有属性或偶然实现细节不变。旧行为的准确范围应在实现前通过调用盘点和测试固定，重点包括：

- `get()`、`get_by_id()` 的调用方式、参数、默认数量和同步／异步使用方式。
- 旧默认排序和按 ID 查询的返回行为。
- 旧 record 的字段读取、`key()` 和 `dump()` 等可观察行为。
- 旧快照上的本地过滤、排序与限量行为。

旧入口不因引入 v2 自动获得新默认值，也不自动要求旧插件迁移。不需要复制旧查询执行器来实现兼容；应把旧参数和返回结构的差异限制在薄适配层。

旧消息视图与新阶段事件可以通过轻量过滤、索引或派生列表隔离，不因共用来源就把新事件塞进旧消息结果。保留这种适配是正常设计，不以新旧内部结构完全相同为目标。

不预设旧入口的删除版本；若适配成本低可继续保留。后续弃用或删除另行说明影响范围和迁移方式，不因新功能上线自动改变旧插件的加载、初始化或运行行为。

### 旧行为基线与新契约边界

以下是当前源码基线中需要固定的实际行为，不为统一外观在旧入口顺手修整；明确 bug 的例外按后文“已知错误的兼容例外”处理。

| 旧接口或对象 | 当前行为及兼容约束 |
| --- | --- |
| `conversations.get()` | 默认 `max_count=50`、`timeout=5.0`，保留现有参数及返回列表形态 |
| SDK `conversations.get_by_id()` | 默认数量为 10；参数是关联 ID，结果可有多条，未知关联返回空列表 |
| 无条件 get 与条件查询 | 前者按入库先后返回最近窗口，后者按 store 序号倒序；旧入口保留，新接口另定一致顺序 |
| 公开 SDK 的旧读取 | 保留通过 SDK 实际支持的同步／异步调用方式，不将旧调用一律改为异步 |
| 旧 record | 保留 `content`、`lanlan_name`、`turn_type` 等字段及 `key()`、`dump()` 的约定；不以消除重复 DTO 为由直接换成新返回对象 |
| 旧 SDK 缺失底层方法 | 当前部分 Bus 包装返回空列表；本次不通过公共 `_call()` 顺带全面改义，若确认是需修复的问题则单列处理，不永久模拟该行为 |
| 旧通用 watcher | 保留现有 start／stop 使用方式、变化数据格式及窗口差分语义，不自动变为 v2 逐条消息回调 |

新 `get_message()` 等单对象读取的 `None`、明确的不支持错误、新参数校验和异步 watcher 生命周期，只作用于新契约。旧 `get_by_id()` 是按关联返回列表的方法，不能改成单对象读取或无命中时返回 `None`。新 Memory 的 Result 和错误规则也不经共享包装器套到旧 Bus 上。

Core `get_by_id()` 当前默认数量为 50，而 SDK 外层为 10。这是检查公开调用结果时的实现参考，不把未公开的 Core 签名、类路径和默认值升级成永久兼容承诺；内部可重构，公开结果与受支持协议按约定保持。现有测试用于确认基线，不因某个偶然行为已有测试就免除 bug 修复判断。

### 底层记录与混合订阅兼容

当前公开 SDK 的旧 Core 读取路径直接访问 message plane，兼容不能只放在新版 SDK 的出口。普通消息记录继续保留旧解析需要的 `content` 和 metadata 中的 `conversation_id`、`turn_type`、`lanlan_name`、`message_count`，以及原有时间、来源和计数含义；新增可选字段不删改已有字段，不用 `input_id` 或新消息 ID 替换旧关联 ID。旧 `dump()` 的既有字段和结构保持，新增字段是否可见单独确定，不要求兼容层冻结任意未约定的内部内容。

早期提交、回复阶段和播放报告不混入旧普通消息结果，也不挤占旧文字记录的保留容量；仅在读取后过滤阶段事件不足以保证窗口兼容。继续使用现有普通消息存储，阶段资料按需求使用有限关联数据或明确隔离的存储／视图，不为兼容复制完整对话库。

复用 BUS_SUBSCRIBE／BUS_CHANGE 时，旧订阅的缺省值、通知结构与接收路径保持。新契约所需标记只用于选择对应的编码和解码，不强迫旧请求补参数；新事件批次不能直接发给旧 watcher，旧 add／del 也不改成新业务事件语义。新旧订阅应能在同一宿主、同一插件中并存，彼此启停不影响对方。

### 兼容范围与版本要求

| 运行组合 | 承诺与要求 |
| --- | --- |
| 旧插件运行于新宿主，且 SDK 版本声明允许 | 现有公开 API 保持工作，不要求为新功能修改旧插件 |
| 新 SDK 包装旧 Context 或旧宿主能力 | 不使用新能力时旧功能仍可用；实际使用缺失的新能力时明确失败，不扩大旧 Context 的强制属性清单 |
| 依赖新 API 的插件运行于旧 SDK／宿主 | 不承诺可运行，需使用包含新 API 的宿主／SDK 构建；版本保持 0.1.0，不能靠版本范围区分新旧能力；旧 SDK 缺少导出时可能在 import 阶段失败，不能只依赖调用时错误 |
| 旧插件主动改用新入口 | 按新契约迁移字段、空值、错误和监听行为，不假定与旧对象完全相同 |

复用已有 `[plugin.sdk]` 的 supported、recommended 等版本声明及注册检查；按项目约定，SDK 版本保持 0.1.0，不因本次实现调整。版本号不能区分同为 0.1.0 的旧构建与包含新增 API 的构建，使用新增能力需更新后的宿主／SDK；导出缺失与运行时操作缺失分别按现有导入／操作错误处理，不新增能力矩阵或版本路由平台。`conversations_v2` 是对话契约名，不自动要求整个 SDK 跳到不兼容大版本；也不绕过旧插件明确声明的版本范围。

### 已知错误的兼容例外

| 情况 | 处理原则 |
| --- | --- |
| 已公开且正常使用的行为 | 保留原约定，以旧入口用例固定 |
| 有问题但可能被依赖的行为 | 优先在新入口改善；改变旧入口需单列影响和迁移说明 |
| 明确实现错误 | 可单独修复，说明旧／新表现并验证，不将行为变化宣称为完全无影响 |

例如 `since_ts=0` 的分支修复可能同时改变查询路径和排序，需要单独验证；新消息身份不应通过公共旧 record 顺手改变旧 `key()`。`bus.memory` 的包装错误在 Memory 计划中单列。兼容不要求永久模拟 bug，也不为错误结构增加专门的兼容对象；这些修复不阻塞新读取与监听能力。

### 新契约明确身份与查询语义

v2 应暴露独立的单条记录身份，并保留关联 ID 的独立含义。SDK、core 转换和 watcher 应贯通同一身份，不以正文、时间或关联 ID 代替主要消息身份。

v2 使用 character、role、kind、input_source、origin_kind 作为少量结构化条件。先过滤，再按现有普通消息 Store 的创建序号选择最近 N 条，最后按 order 返回；默认 max_count=50、order="asc"、timeout=5.0，单次数量上限沿用现有配置，当前默认上限 1000。order 只改变所选窗口的返回方向，不改成取最早 N 条。

max_count 必须是正整数，超过宿主上限沿用现有服务端限量行为；order 只接受 asc／desc，since_ts 为 None 或有限秒数，0 不按缺省值处理。显式指定的 view_limit 必须为正整数，窗口限量与事件队列容量分别执行。

since_ts 沿用 epoch 秒数，按记录的插件侧 observed_at 做包含边界的筛选，不作为可靠消费位置。observed_at 取现有记录 timestamp 所表示的插件接入观察时间，occurred_at 保留生产端消息时间、可缺失；默认窗口与排序不按 occurred_at 重排。展示时间线可用已有快照排序能力，不先增加多套服务端排序策略。

character 是可选条件；省略时读取当前插件可读范围内各角色，不绑定当前活跃角色，不要求多角色插件逐个拼接。筛选不扩张读取范围。保留 max_count、since_ts 和浮点秒数，不强制引入新的时间参数名或 datetime 调用约定；旧入口仍保留自己的默认值和排序。

查询和视图维护应复用适用的字段定义、过滤与记录转换，避免相同条件由多处业务代码分别解释。事件直接派发与列表更新可以采用不同处理路径，不为追求单一算法而强制全部通知重查询。

任意 lambda 可用于本地快照和回调判断。只有实际选择查询重放的接口才需要限制不可重放条件；不能让该实现限制成为整个事件观察 API 的前提。常用条件是否下沉到框架，按易用性与减少无关传输的收益决定。

### 对话记录的职责与来源语义

v2 应描述这条文字记录代表什么、来自哪里、属于哪个已知角色与回合，以及生产端明确提供的结束状态。输入来源与回复文字来源应分别表达，不以单一的 `mode=voice` 覆盖两种含义。

| 信息 | v2 的责任 | 实现约束 |
| --- | --- | --- |
| 用户提交文字或语音转写 | 表达用户记录的文字来源，并可结构化查询 | 当前可使用已存在的 `is_voice` 信息 |
| 文字生成或语音输出转写 | 保留生产端明确提供的回复文字来源 | 不能由用户输入来源反推；未知时明确缺失或未知 |
| 单条消息与已知回合关联 | 提供稳定身份与已有关系 | 不凭时间接近或正文相同制造配对 |
| 正常结束、中断或失败片段 | 表达生产端明确提供的记录边界 | 发布了一条文本不等于正常生成完成 |
| 消息观察、文本开始、收口与入库时间 | 定义各自含义与排序用途 | 不推断真实发声或播放时刻 |

字段使用下文最小契约，缺失身份、时间和具体来源用 None，已知业务类别的未知值使用 "unknown"。优先接共享的回复归属、首段有效文字和收口出口，已有明确来源直接透传，其余保持缺失。接入时用代码核对和固定样例记录各路径可提供的事实，不建设运行时能力矩阵，也不以填满所有 provider 字段为上线条件。

ASR 如何识别、TTS 如何合成、音频如何送达以及各前台如何播放，分别由其所属模块负责。v2 通过稳定的回复／记录标识关联必要的播放报告，不在同一条对话文本上塞入一个无法解释重播、多音频片段和多窗口播放的全局 `played` 状态。

### 融合语音观察职责并保留旧入口

新插件通过 v2 的用户消息与语音来源条件统一观察对话，不再必须分别接文字快照和语音 custom event。这里融合的是已接受的语音输入事实，不是把通用 custom event 机制搬入 conversations。

通用 custom event 继续负责自定义事件执行。v2 对话观察回调不继承旧的 `cancel_response`、`prime_context` 返回动作契约；改变当前对话回合属于另一项明确的控制能力。

对于已接受的语音消息，v2 以现有 conversations 对话记录为权威来源。不能再把 `voice_transcript_observed` 当成第二个同等权威的入库来源，靠正文、角色和时间去重。两条上游事件当前缺少共同关联 ID，这种合并会误伤连续重复发言。

兼容期保留旧 `@custom_event(event_type="voice_transcript")` 的派发、参数、开关与执行行为。不能直接用 v2 watcher 转调旧 handler，改变其时机、metadata、并发或错误表现。之后是否能将旧入口适配到共同通知基础设施，需要单独验证兼容性。

旧入口暂时并存属于兼容成本；新建第二份语音权威存储、让新插件继续猜测两路关联，则会增加长期维护负担。

### 文字输入早期通知

早期通知服务于“用户发送文字后，插件尽快获得本次提交正文”的需求。它是输入观察，不是等待插件完成的前置处理器，也不允许插件通过返回值拦截或改写本轮输入。

保留原 user_message 发布位置和进入条件，不把它前移来代替早期通知。接入只新增独立的 input.submitted 事实与必要身份透传，不重排 session 准备、打断、命令／路由处理或 TTS 清理，也不为填齐 observed_outcome 补一组成功／失败状态事件。

需要区分三个时刻：

```text
用户点击发送
  → 后端收到提交并通过选定边界的必要检查
  → 输入到达普通对话 user_message 的发布位置
```

当前普通文字路径的 conversations 发布点位于 session 准备／切换、中断旧回复、清理 TTS 和更新本轮状态等操作之后。仅优化插件侧 watcher，不能消除发布之前的等待。前台点击本身也不等于后端已收到输入，网络、前台校验和附件处理均可能影响提交时机。

选定普通对话路由归属明确、连接和格式等必要检查通过之后，session 准备、旧回复清理等昂贵工作之前的边界，非阻塞地产生 input.submitted。首批不在路由未知时观察所有提交，也不默认覆盖游戏、串门等外部路径；扩展来源必须另有明确覆盖需求。

#### Main 和 Agent 的最小改动

| 所属模块 | 允许承担的改动 | 不承担的工作 |
| --- | --- | --- |
| Main 输入入口 | 在选定位置提取必要正文与上下文，记录到达时间，异步发布观察事件；若需要关联后续消息，仅透传必要标识 | 插件 handler 执行、等待插件决策、额外对话存储、watcher 状态 |
| Main 事件发布边界 | 复用既有 Session 事件通道，补充新事件的薄封装 | 新通信系统、独立可靠消息队列或对话控制协议 |
| Main 回复及播放观察边界 | 在已有归属与状态生产点补充来源、文字开始／收口、播放报告的最小事件透传 | 新建生成状态机、改写 TTS 或播放调度 |
| Agent 接收边界 | 识别新事件并转交插件服务 | 按插件维护查询、视图、游标或业务回调 |
| 插件服务与 SDK | 轻量事件归一化与派发、近期观察缓存、已知关联、查询与按需视图、订阅生命周期 | 等待状态齐全、恢复完整本体状态、推断未观察到的生成或播放事实 |

```text
Main 在选定输入边界发布早期观察事件
  → 既有 Session 通道
  → Agent 最小接收分支
  → 插件服务归一化与有限接纳
  → conversations_v2 watcher 交付 input.submitted

后续普通 user_message 仍按原消息链入库，再参与消息通知与视图

Main 的原有输入处理继续进行，不等待上述插件处理完成
```

观察通道失败不得使原有文字对话失败。发送和后台任务应有边界，避免每次提交无界创建工作；不等待插件 handler，不使用其返回值决定是否继续处理。不承诺固定毫秒延迟，也不承诺插件完成处理先于 LLM 开始回复。

当前 `register_text_user_message_hook` 不适合作为这项能力的实现捷径：调用位置偏后，采用第一个有效返回值获胜的规则，而且是进程内机制。它不具备早期、独立旁路广播的语义。

#### 早期提交与用户消息的区别

早期事件表达“后端在选定边界观察到本次提交”，不表达“已经送到 LLM”或“生成一定成功”。后续输入仍可能被其他路由消费、按命令处理、拒绝或因 session 失败而无法产生回复。

早期输入已确定使用 input.submitted，与普通 user_message 分开；消息列表和 change 视图不包含早期事件，避免显示成两条用户发言。事件字段及筛选适用范围按下文契约，共用既有订阅和有限关联，不另建一份重复用户消息的权威来源。

“用户提示词”在这里指本次用户提交的正文，不是拼接系统提示、记忆、知识和其他上下文后的完整模型请求。提交正文与 `memory_text` 等记录用文字可能不同，需要明确其含义，不能静默互换。

#### 输入身份与接入核对

提交正文取选定边界检查后的本次用户文字，不使用 memory_text 静默替代，不携带完整模型请求或附件包。后续 user_message 仍取原记录路径的文字；两者可以正文不同，通过明确的输入身份关联。具体函数位置、检查顺序和原路径的透传点属于接入核对，不再重新选择观察范围。

输入标识先复用已验证作用域和重传语义的 request_id；连接／会话作用域必须明确，不把不同会话的同名请求合并。缺少合适标识时，在输入观察边界生成一次 ID 并向后透传。只有明确证明是同一请求的重传才沿用 ID；无法确认时不声称重试去重。不同提交即使正文相同也不合并，不增加身份管理服务或持久化去重表。

只发送早期通知所需的改动较小；若要求与后续 `user_message` 可靠关联，需要在后续发布点透传必要的输入标识。这属于允许讨论的最小事件契约扩展，不扩展为对本体整个回合身份的重构。

### watch 是本次主要补齐能力

优先复用现有订阅管理、连接和 watcher 生命周期，不另建可靠消息平台。需要补齐的主要能力是业务事件接入、直接派发、必要过滤、近期缓存和 SDK 包装。现有快照差分适合视图更新，不要求作为业务回调的必经路径。

收到有效事实后只做一次归一化。普通消息的 record 通知在现有消息存储接纳后产生；输入、回复和播放阶段事实有限接纳后即可派发，不要求先写入普通消息 Store 或等待普通消息形成。领域服务保留详情读取必需的有限关联，不以先启动 watcher 为条件；未使用的视图和详情不做额外构造，也不建全量阶段日志。回调携带可用内容，不要求插件再查一次；查询只返回当时已有的信息。

减少 store、通知管理器和插件回调之间不必要的线程／事件循环交接，必要交接使用已有稳定机制。旧视图、索引和近期缓存是合理派生数据，不因存在多个读取视图就算重复架构；需要避免的是各自拥有业务判断、分别维护的平行对话系统。

## SDK 业务对象与查询契约

本节记录新契约的公开用法，SDK 0.1.0 已接通的来源见实现记录。记录采用只依赖标准库和已有轻量类型的 dataclass；集合复用现有快照列表的适用能力，不携带旧查询重放或旧 watcher 前提。公开类型从 plugin.sdk.plugin 导出，字段的 wire 编解码在各自契约叶子模块只定义一次，不为转换建立类型注册框架。

### 统一入口与查询方法

以 `self.bus.conversations_v2` 为统一入口，面向不同信息深度提供少量查询方法：

| 目标方法 | 功能 | 结果的边界 |
| --- | --- | --- |
| `get(...)` | 按角色、类别、输入来源、回复来源及观察时间条件读取消息列表 | 已保留的对话文字，含明确标记的主动指令；消息 ID 精确读取由 get_message 提供，不新增列表 ID 查询条件 |
| `get_message(...)` | 按单条消息 ID 精确读取 | 一条消息的正文、来源和已知关联 |
| `get_reply(...)` | 按回复 ID 读取回复详情 | 来源、文字状态和关联播放报告 |
| `get_interaction(...)` | 按输入 ID 整理交互详情 | 输入已观察到的结果、关联回复及各自呈现状态 |
| `watch(...)` | 创建统一观察器 | 支持消息通知、视图变化以及明确的输入／回复／播放事件 |

get 和 watch 共用上述可选筛选字段；get 另接受 max_count、order、since_ts、timeout，watch 另接受 view_limit=None。单对象方法接受相应 ID 和 timeout=5.0。view_limit 仅在订阅 change 时决定窗口，省略时沿用 50；仅订阅事件不会据此启动视图。

列表查询示意：

```python
# SDK 0.1.0 用法。
bus = self.bus.conversations_v2
messages = await bus.get(
    character="YUI",
    role="assistant",
    max_count=20,
    order="asc",
)
for message in messages:
    print(message.id, message.text)
    if message.origin is not None:
        print(message.origin.kind)
    print(message.reply_id)
```

查询结果是观察时点的快照，不会因为底层状态随后变化而自动改写调用方已经拿到的对象。详情由插件侧轻量、有界地汇总已观察事实，不另建一套能决定本体输入、生成或播放行为的业务状态机。事件可以先交付，相关阶段尚未到达或已被淘汰不阻止返回现有信息。

列表优先沿用现有列表或快照列表的使用形式；没有分页或附加读取信息需求时，不新增 `MessagePage`、`has_more_retained` 等包装。新单对象读取没有当前可用记录时返回 `None`，表示未观察到、尚未到达或已经淘汰均有可能，不证明本体对象从未存在；不增加 `Lookup[T]` 或 `not_cached` 状态容器。新契约的操作失败与能力不支持仍明确报错，不折成空值；旧入口继续遵循上文兼容基线。

`get_reply()`、`get_interaction()` 随对应观察事实和关联具备后提供，不为凑齐方法列表先建设空的详情系统，也不让它们阻塞已有消息的读取与监听。

### 消息身份与输入关联

普通消息对象保留直接读取正文的便利，不要求插件先读取全部详情。最小字段如下，新增字段必须对应实际读取需求：

```text
ConversationMessage
  id                 单条消息记录身份
  character          所属角色
  kind               文字记录类别，沿用已知 turn_type 含义
  role               由 kind 派生的业务筛选身份，不是模型 API role
  text               记录正文
  input_id           已知的输入关联，可缺失
  reply_id           已知的回复关联，可缺失
  input_source       用户输入来源，如 text、voice、unknown
  origin             角色回复的业务来源
  observed_at        插件接入观察时间，epoch 秒
  occurred_at        生产端消息时间，可为 None
```

输入提交 ID、消息 ID、回复 ID、观察事件 ID 是不同层次，不能相互代用。一条回复的阶段事件使用同一个回复关联，但每个独立观察事件具有自己的身份。未能可靠建立关联时保持缺失，不能选取最近输入、当前 speech ID 或相同正文补猜。

消息 id 优先贯通现有上游事件 ID；缺少时在接入边界生成本条记录身份，不声称因此能识别未知的上游重传。输入按早期观察一节处理。回复身份只在现有归属对象／明确边界固定一次；经验证唯一且覆盖同一回复的初始 speech ID 值可以冻结复用，后续不随 live speech_id 轮换。已有来源 proof 或客户端路径 ID 也只有生命周期核对通过才复用；不足时补一个观察 ID，不新建 owner／身份服务。该值贯通开始、收口、最终消息及能够明确关联的呈现报告，具体约束见 [非 plugin 最小接入](#非-plugin-改动的最小边界)。

先复用生命周期和作用域合适的已有身份，再补确实缺少的最小透传；身份层次的区别不等于必须新增五套 ID。输入关联用于早期提交与后续记录，回复关联用于文字阶段和播放报告，呈现身份用于区分已纳入需求的多窗口或重播。基础消息插件只需使用记录身份，不必理解全部关联。

kind 保留业务类别字符串，已知值为 user_message、assistant_message、proactive_reply、proactive_instruction。role 由它派生为 user、assistant、instruction 或 unknown，不独立持久化另一套规则；未来未知 kind 保留原字符串，role 回退 unknown。输入与回复文字来源只开放有证据的区分，不要求携带 revision、legacy_conversation_id 或完整来源枚举。

### 回复来源是重点功能

回复来源描述谁或什么已知业务原因引发回复，不是发布模块路径、输入模式或模型后端。`source="main_logic.core"` 不能替代业务来源。

```text
ReplyOrigin
  kind               user_interaction / agent / plugin / avatar / system / unknown
  is_proactive       明确是否主动，未知时为 None
  plugin_id          明确的来源插件，可缺失
  task_id            明确的来源任务，可缺失
```

上述为当前已知类别，kind 使用可扩展字符串，未来未知类别不导致整条数据解码失败。是否主动与业务来源分别保留明确事实；知道来自 Agent 不代表知道具体任务或插件。实际来源标记只在适配处映射一次，接入样例核对代码证据，不在读取时猜测。

来源优先描述这次回复的直接业务触发，不要求追溯完整因果链。例如用户任务经过 Agent 产生回复，直接来源与已知输入关联可以分别表达；是否主动发言与由谁触发也不必争用一个互斥类别。具体字段可保持简单，不为此增加通用因果图。

本次优先贯通当前固定到回合的来源标记及已有关系。来源应在正确的生产／归属边界固定或附加有证据的事实，不能查询时读取全局“当前活动”给旧回复贴标签。异步打断和交错回复不能互相借用来源。

“用户触发的回复”和“回复使用过工具”可以同时成立，工具证据不能覆盖触发来源。此次不因此开放工具调用参数、结果或完整因果追踪，也不让插件直接查询聊天同步数据库取得来源。

业务目标包括区分普通问答与主动发言，识别明确的非用户触发，以及在已有具体来源证据时避免插件响应自身引发的回复。消息、回复详情与相应事件应引用同一回复来源，不出现三套不同解释。

### 输入提交观察与处理结果

早期输入回调的对象示意：

```text
InputSubmission
  id
  character
  text
  input_source
  observed_at
```

提交正文不等于最终完整模型请求，详见文字输入早期通知的边界。后续输入结果只表达已明确观察到的接收、进入普通对话、命令／路由接管、拒绝或准备失败等事实；不同事实不能全部压成一个 `success` 布尔值。

首批 observed_outcome 只表达已有观察明确支持的事实，例如关联 user_message 证明进入普通对话；其余为 unknown，不为填齐结果新增整组路由状态事件。没有回复不判为失败，外部路由接手也不等于其业务成功。

### 交互详情的结构

按输入查询详情的示意：

```python
# 目标用法：按已知输入身份读取关联结果。
interaction = await bus.get_interaction(input_id="input-100")
if interaction is not None:
    for reply in interaction.replies:
        if reply.origin is not None:
            print(reply.origin.kind)
        print(reply.text_state)
        for playback in reply.playbacks:
            print(playback.state, playback.stop_reason)
```

```text
InteractionDetail
  input
    id
    text
    input_source
    observed_outcome

  replies[]
    id
    origin
    text
    text_state
    close_reason
    playbacks[]
      presentation_id
      state
      stop_reason
```

get_reply 返回同一 ReplyDetail 结构，即上面单条 replies 项，并带 character、已知 input_id、audio_expected、已知文字开始／收口时间和 playbacks；不是再定义一份同义 ReplyRecord。集合中的普通消息与详情的当前字段来自同一解释，未知字段遵循 None／unknown 规则。

`replies` 不假定一次输入只有一个回复；`playbacks` 不假定同一回复只播放一次或只在一个窗口播放。呈现端每次播放尝试固定 presentation_id，presenter_id 标识报告端实例；旧报告缺少时保留 None，不用 reply_id 代替呈现身份。没有可靠 reply_id 的报告可以单独交付，但不挂到最近回复的详情里。

输入结果、文字状态和播放状态分别表达，不提供一个同时表示输入处理成功、生成结束和音频播完的 `interaction.completed`。未观察到回复、未收到播放报告、明确不产生音频和报告因断线而未知，也不是同一种状态。

详情是可用信息汇总，不是状态齐全的承诺。可以通过有限关联缓存或按需查询实现，不等待缺失阶段，不为它启动历史扫描、强制补齐或恢复任务。缺失、未知、缓存不存在是正常可表达的结果，不以先实现完整性证明为上线前提。

模式信息作为必要上下文保留，区分输入来自文字／语音、实际回复链路及是否计划产生音频。不能以当前界面模式解释历史回复；模式变化本身也不等于回复或播放终止。本次不额外建设完整会话监控系统。

### 回复文字状态与播放状态

| 观察事实 | SDK 应表达的含义 | 不应推导的结论 |
| --- | --- | --- |
| 首段有效回复文字发布 | 回复已开始输出文字 | 前台已经展示或播放 |
| 文本收口 | 宿主在明确边界关闭本次文本输出，并保留已知原因 | 音频播放结束，或 provider 一定正常完成 |
| 前台播放开始报告 | 指定呈现端报告开始播放 | 所有窗口都在播放 |
| 前台播放停止报告 | 指定呈现端报告停止，并携带已知原因 | 必然自然播完或用户一定听到声音 |

text_state 使用 not_started、started、closed、unknown；只有明确证据才填写 not_started，不从缺少开始事件推断。close_reason 在未收口时为 None，收口后使用 completed、interrupted、discarded、failed、unknown。reply.started 是首段有效文字，reply.closed 是明确文字收口；后续有证据的文字或来源补充通过有限修正处理，不承诺正文从此永久不变。

audio_expected 使用 True、False、None，区分明确计划产生音频、明确不产生与未知。单次播放 state 使用 unreported、playing、stopped、unknown；stop_reason 未停止时为 None，停止后使用 completed、interrupted、canceled、error、fallback、unknown。明确不产生音频不伪造播放对象；文字已 closed 而播放仍 playing 合法。

文字模式可能启用 TTS，语音输入也可能走文字模型；是否需要播放状态取决于这条回复的呈现方式，不能仅凭输入模式决定。

当前前台已经上报 `voice_play_start/end`，但取消路径同样使用 `voice_play_end`，部分兜底也会完成收尾。现有报告最多证明收到“播放停止”的信号，不能直接映射成自然播完。缺少原因的旧前台按未知处理；后端播放门控的超时清零也不是自然结束证据。

播放观察按来源分批适配：旧报告先保留已知开始／停止、缺失身份和未知原因；能补字段的前台在既有报告上增加可选 presentation_id、presenter_id、明确回复关联和 stop_reason。自然结束、取消区分必须由实际路径提供。接入旧报告不代表完成全部播放目标，也不扩展为音频读取或播放器控制。

### 订阅事件与回调对象

同一个 watcher 承载业务事件观察和消息视图。以下事件名及最小数据形式已确定；阶段事件可携带自己的 event_id、observed_at 和生产端时间，不强制使用统一泛型 envelope：

| 订阅名 | 回调主要数据 | 调用时机 |
| --- | --- | --- |
| `input.submitted` | `event.submission`，本次提交正文与身份 | 输入到达选定早期观察边界，事实被插件侧接纳后 |
| `record` | 匹配的新普通文字记录，含明确标记的主动指令 | 入库后被观察到，与 get 的消息范围一致，不含输入提交、回复或播放阶段事件 |
| `message.updated` | 同 ID 的当前消息快照 | 有证据的正文或来源修正被接纳后，不再次触发 record |
| `reply.started` | `event.reply`，回复身份、来源及已观察文字 | 首段有效文字事实被接纳后；不等于开始发声或最终消息已入库 |
| `reply.closed` | `event.reply`，当前文字快照与 close_reason | 宿主明确收口的事实被接纳后；不等待播放停止 |
| `reply.updated` | `event.reply`，修正后的回复快照 | 同一回复的迟到文字或来源补充被接纳后 |
| `playback.started` | 回复关联与呈现端报告 | 前台播放开始报告被插件侧接纳后 |
| `playback.stopped` | 回复关联、呈现身份与已知停止原因 | 前台停止报告被插件侧接纳后 |
| `change` | 当前普通消息视图、差分及初始化标记 | 初始视图建立，或后续消息视图变化 |

消息创建与修正回调直接交付消息；reply 事件交付包含 reply 快照的最小领域数据，playback 数据包含 reply_id、presentation_id、presenter_id、state、stop_reason 及可选 turn_id。turn_id 仅保留原报告上下文，不升级为稳定回复／呈现身份；关联字段缺失仍为 None。change 交付 current、added、updated、removed 和 reason；reason 为 initial 或 update，removed 表示离开视图，不表示底层删除。事件保留当时快照，后续查询可以读取更新后的值。

支持有证据的有限修正，不预建历史版本库。修正沿用对象 ID、不追加第二条普通消息、不改变消息的创建排序位置，消息列表、单条读取和详情使用同一当前值。SDK 用必要的内部顺序或版本防止旧修正覆盖新值，不要求公开 revision；修正改变筛选匹配时重新计算对应窗口，message.updated 与 record 分开去重。

消息修正保留创建序号和初次 observed_at，不把 since_ts 变成修正消费协议。视图需要处理旧值或新值相关的更新：当前不再匹配的项移出，开始匹配的项按同一窗口规则参与选择；可复用当前值和已知视图成员身份，不增关系查询。业务 message.updated 回调交付当前仍匹配的消息，视图移出由 change 表达，内部更新不能被仅按新值过滤而漏掉。

```python
# SDK 0.1.0 用法。
watcher = bus.watch(character="YUI")

@watcher.subscribe(on="input.submitted")
async def on_input(event):
    await inspect_submission(event.submission)

@watcher.subscribe(on="reply.started")
def on_reply_started(event):
    print(event.reply.id)
    if event.reply.origin is not None:
        print(event.reply.origin.kind)

@watcher.subscribe(on="reply.closed")
def on_reply_closed(event):
    print(event.reply.id, event.reply.text, event.reply.close_reason)

@watcher.subscribe(on="playback.started")
def on_playback_started(event):
    print("前台报告开始播放", event.reply_id)

@watcher.subscribe(on="playback.stopped")
def on_playback_stopped(event):
    if event.stop_reason == "completed":
        print("前台报告自然播完")
    elif event.stop_reason == "interrupted":
        print("播放被打断")
    else:
        print("播放停止，原因：", event.stop_reason)

await watcher.start()
# 插件退出或不再观察时：await watcher.stop()
```

该示例不要求插件回调先于 LLM 输出或前台播放完成。回复与播放事件依赖生产端事实，通知顺序不代表跨进程的真实发生顺序；关联必须靠身份，不能靠相邻回调猜测。

### 消息筛选与生命周期筛选

筛选在注册订阅时检查适用性，不让错误组合变成永不触发的静默订阅。角色与类别用同一派生规则；不自动追踪某类用户输入关联的全部回复。适用范围如下：

| 条件 | 适用范围 |
| --- | --- |
| character | 全部事件 |
| role | 消息／视图；input.submitted 固定为 user；reply 事件固定为 assistant；播放事件不使用此条件 |
| kind | 消息创建、修正与视图 |
| input_source | 用户消息、相应视图与 input.submitted；不用于 reply 或 playback |
| origin_kind | 角色消息、相应视图与 reply 事件；不用于用户输入或 playback |

例如 role=user 的 watcher 注册 reply.closed、input_source=voice 的 watcher 注册 playback.stopped，均在订阅注册时明确报参数错误。只有普通消息订阅时，user+voice 正常筛选用户转写。role 和 input_source 校验已定值；kind、origin_kind 接受非空扩展字符串，不因未来数据类别未知而拒绝查询。未知字段、不适用条件或错误参数类型明确报错，不补造匹配值。input.submitted 首批仅普通文字，不代表已有语音早期提交。

```python
# 目标用法：只处理用户语音消息，并维护同条件下最近 20 条。
watcher = bus.watch(
    character="YUI",
    role="user",
    input_source="voice",
    view_limit=20,
)

@watcher.subscribe(on="record")
async def on_voice_message(message):
    await handle_voice_message(message)

@watcher.subscribe(on="change")
def on_view_changed(delta):
    render_messages(delta.current)

await watcher.start()
```

需要同时观察多种事件时，只按角色建立 watcher，再在回调判断所需条件。框架执行已定适用表中的少量筛选，不扩展关系查询语言；近期消息列表不把阶段事件展示成聊天正文。

### 初始化与异步生命周期

v2 使用 `await watcher.start()`、`await watcher.stop()`，并支持异步上下文管理；旧入口不因此改变：

```python
# 目标用法：先注册回调，再进入上下文。
async with watcher:
    await wait_until_plugin_stops()
```

`start()` 返回时，表示宿主订阅与本地接收登记已建立，不表示业务回调已经运行或常驻命令循环已经启动。startup 临时循环与后续常驻接收的衔接按资源所有权一节处理，不相互等待。需要初始视图时异步读取近期快照，不等待业务回调、历史扫描、完整交互状态或补读追赶。

存在 change 订阅时，初始化交付一次 reason="initial"，空视图也通知；纯事件订阅不读取历史。已有历史不触发 record 等业务事件，后续窗口变化使用 reason="update"。

创建 watcher 或仅订阅新消息，不自动加载历史、整理回复详情或维护最近 N 条。只有存在视图订阅时才执行相应的窗口工作，不另外建立通用 ViewService、ViewRepository 或独立视图管理体系。

## 一个 watcher 的两种消息通知

### 查询结果变化与逐条消息到达

v2 的同一个 watcher 应能同时承载以下需求：

- 显示最近 20 条用户语音转写，并随对话更新。
- 对每条新观察到的用户语音记录执行业务处理。

两者共享角色、消息类别、来源等筛选条件，使用不同通知语义。新记录通知描述入库后的新消息；视图变化描述当前查询窗口的变化。

| 通知类别 | 业务含义 | 不应混淆的概念 |
| --- | --- | --- |
| 新记录通知 | 及时交付新观察到的匹配消息内容 | 不是“最终视图里新增的项”，不承诺补齐全部消息 |
| 视图变化通知 | 给出最新视图及进入／移出视图的差分 | 移出窗口不代表底层删除 |

现有 watcher 收到信号后重查快照并计算差分。v2 对业务事件优先直接派发已有内容，不能把快照 `added` 改名后宣称逐条通知，也不要求每条通知先重查缓存。

例如监听最近两条：

```text
原结果：[A, B]
C 到达后的结果：[B, C]
差分：added=C，removed=A
```

A 只是离开查询窗口，不表示从底层删除。若刷新前连续到达 C、D、E，最终结果可能只有 D、E；仅比较快照不能恢复 C。

在事件正常送达、未过载丢弃时，新记录订阅者分别收到 C、D、E，视图订阅者只需更新到 D、E。C 不因显示窗口限量而被有意省略；真实的通道或过载丢失仍按 best effort 处理，不由该示例承诺恢复。

使用形式沿用上文同一个 watcher 的 record／change 示例，v2 不再增加 add／del 别名或第二套监听入口；进入／离开视图由 change.added／removed 表达，不推导存储删除。旧 bus 的现有事件契约保持。

### 直接派发与按需视图维护

目标处理结构为：

```text
观察事实到达插件边界
  → 一次归一化 → 普通消息入库或阶段事实有限接纳
  ├→ 根据订阅及时派发事件内容
  └→ 普通消息有视图需求时更新最近 N 条
       → 合并刷新／差分后通知
```

两条处理路径共用必要的身份、字段与过滤工具，但不要求共用同一套重查询算法。视图允许合并刷新；业务事件允许批量派发以降低开销，不能仅因为最终窗口较小就主动丢掉其余已接收事件。过载时可以有界丢弃。

显示窗口大小与派发批量、队列容量是不同概念。窗口为 20、短时新增 250 条时，批量交付和合理缓冲应尽量吸收突发，最终视图仍为 20 条；不能把显示限量当成通知数量上限，也不因此承诺 250 条必达。具体参数和默认值待实现测量后确定。

短缓冲、序号和一次近期快照读取可用于低成本减少重复或衔接瞬时积压，不是公开 API 必须暴露的消费协议。只有实际采用顺序读取时，才需要相应位置处理；不要求所有调用维护 epoch、游标和重放计划。

优先减少事件生产与派发中的无意义重复，已有稳定 ID 可以支持轻量去重，但不建设无限去重表或 exactly-once 交付。没有订阅者的事件类别不做额外派发，未订阅的视图不持续执行差分或详情重建。

### 初始历史与实时新记录

需要初始列表时读取当前近期快照，不把已有历史自动作为新记录业务回调重新执行。插件可以主动查询近期数据；历史回放若以后确有需要，应单独评估，不作为 watch 默认能力。

启动过程应尽量减少窗口与调度造成的可避免丢失，例如先建立订阅、用已有 ID 合并初始快照等；具体实现按成本选择。新事件不等待历史就绪，不承诺启动时形成一个无遗漏的事务快照。

较旧的初始快照不能覆盖初始化期间已接纳的新消息或修正。接入时若现有 Store 序号可低成本形成同源快照截止位置，优先用它合并后续数据；否则订阅后读取快照，按记录 ID 和必要修正顺序合并有界暂存。两条路径都不阻塞实时事件，不将内部位置暴露为插件必需消费协议，不增加完整性屏障；具体采用哪条由读取接口核对结果确定。

### 有界保留与丢弃

近期消息、关联详情和派发队列都应有界。超过容量、过期、重启或断线时允许丢失；查询只返回仍可用的信息，不能承诺恢复未送达或已淘汰的内容。

排队过载时丢弃较旧的待交付事件以保留较新观察，普通溢出不打断已经运行的回调；视图待更新值合并为最新一份。显示窗口、排队条数、总字节数和在途任务分别限制，具体容量留待实测，不预建公开丢弃策略对象。

### 已知通知遗漏后的视图刷新

普通消息已入 Store，但在宿主待发、发送或 SDK 接收／视图处理之前发生已知遗漏时，仍需避免本地窗口长期落后。对存在 change 订阅且可能受影响的视图，在既有订阅信息或 watcher 中合并一个待刷新标记；宿主侧遗漏利用现有下行在可发送时携带一次合并的视图失效提示，不保存丢失事件清单，也不新增可靠通知通道。

SDK 在通道可用且资源允许时，按相同条件和 view_limit 发起一次合并的近期快照读取，以快照重建窗口，再用初始视图相同的 ID／顺序规则合并期间新数据，不无条件保留旧本地成员。成功后以 change.reason="update" 交付当前窗口，不回放 record、reply 或 playback 业务事件；未入库、已淘汰和未观察到的事实不能因此恢复。

同一视图最多保留一个待刷新需求，重复遗漏不按事件数发查询。失败保留标记，在后续可用信号或既有连接恢复时按有界调度再尝试，合并间隔与退避留待实测；不做固定后台轮询或无限自动追赶。纯事件订阅、业务回调失败、窗口正常移出不触发此读取；stop 清理自身刷新任务和标记。刷新与失效提示仍是 best effort，不承诺识别静默丢失或消除所有缺口。

对已知队列溢出、发送失败等保留低成本计数与适量诊断，用于改进常态丢失率。必要时可以告知连接或缓存重置，但不要求逐次缺口通知、精确缺失区间和调用方恢复握手。

best effort 不意味着任由常态大规模丢失，也不意味着已交付内容可以错配。应优先消除重复中转、阻塞派发和容量不合理等实际原因，而不是用强制补发掩盖它们。

### 回调失败与生命周期

通知交给插件不等于其业务成功完成。框架负责隔离回调异常、限制待处理任务并继续服务，默认不自动重试业务回调。未来确有重试需求再单独约定，不先增加重试策略对象。

宿主派发不等待插件业务回调，异步回调的正常等待不应阻塞其他订阅或独立视图调度。插件回调仍须避免长时间阻塞自身事件循环；本计划不承诺强制中断任意同步 Python 代码，也不为此增加执行器进程。普通排队过载按已定丢旧及视图合并规则处理，不另外增加暂停／结束策略或策略切换接口，不保证最终全部处理完。

串行性以单个 watcher 中的一次处理器登记为单位，按框架接纳顺序执行；不同登记可在总量限制内并行，不跨 watcher 给同一 Python 函数加全局锁，也不承诺跨来源真实发生顺序或处理器完成顺序。复用一个有界调度入口记录必要状态，不要求每个处理器独立队列或常驻 worker；视图合并与业务处理分开调度。

stop 先停止接收并丢弃未运行任务，给运行中回调短暂且有界的收尾时间，超时请求取消；具体等待上限留待测量。返回后不再启动新回调，迟到通知按已移除订阅忽略。协作式异步任务由所属循环收尾；不承诺强行终止阻塞同步代码或回滚副作用。插件退出复用同一清理路径，不由插件自行维护轮询，不增加可配置执行策略或监控状态体系。

插件在回调中已经执行的外部副作用不会因超时或取消自动回滚。需要避免重复执行的业务应使用记录 ID 做幂等；watch 的读取与去重机制不能替代业务幂等。

## 模块归属与实现组织

契约与业务解释集中、兼容适配薄、公共工具小，不在 SDK、Host 和多个 service 分别维护同一规则。以下为当前职责落点，不要求每个职责各建文件、类或实例；内部按业务能力命名，不把 v2 复制为整套 store、manager 或 executor。

### 契约定义与转换

```text
plugin/sdk/shared/contracts/
  conversations.py    新对话 DTO、事件数据与显式 wire 编解码
  memory.py           Memory 目标、结果与显式 wire 编解码

plugin/sdk/shared/conversations/
  client.py          插件侧读取门面
  watcher.py         复用现有订阅与接收，直接交付消息、按需维护近期列表

plugin/server/application/
  conversations.py   单一有限关联与按需详情模块，不作为普通读取必经层
```

contracts 模块只依赖标准库与已有轻量 SDK 基础类型，不导入 Main、Memory 引擎、server、core host 或传输实现，不启动任务或读取用户配置。宿主可直接引用这些叶子模块，插件作者从 `plugin.sdk.plugin` 等正式门面导入，不能要求作者依赖 shared 内部路径。

新 DTO 与 wire 结构在该领域契约模块内定义，使用明确的 `to_payload/from_payload` 或等价小函数；SDK 解码形成公开对象。新契约的 core 传输不再新建一套同义 ConversationRecord，旧返回类型按公开兼容要求保留必要适配。宿主可以使用契约类型或明确内部结构组织索引与详情，不为每个出口重写来源、时间和关联解释。

请求字段及筛选严格校验；响应 DTO 保留必需字段／核心类型检查，但忽略宿主新增的未知附加字段，避免兼容补充元数据时让旧解码器失效。未知类别字符串仍按本契约保留；不借此猜测任意旧对象形状、放宽缺失身份或把畸形结果转成空数据。

Main 的中性观察事件与插件契约不是同一层：Main 不导入插件 SDK。来源事件到插件字段的转换集中于契约叶子的纯转换函数与领域接纳位置，随后按既有传输序列化，SDK 只做契约解码。旧字段别名、旧 metadata 布局和旧 record 形状在旧适配器处理，不让新 DTO 永远兼容任意对象猜测。

集中转换不要求增加 Adapter 接口、工厂或注册体系；当前实现保持纯转换函数和一个领域模块，不为架构图新增 adapters 文件。新 watcher 直接使用现有订阅和接收能力，不再叠一层 `ConversationWatcher → SdkBusWatcher → BusListWatcher` 而继续强制重查快照。旧实现保留兼容，新旧复用适用的字段、差分与生命周期小工具。

### 服务与传输分工

| 位置 | 具体职责 |
| --- | --- |
| Main/Agent 观察边界 | 提供已有事实，Agent 接收后薄转交；来源整理集中在适配位置，不在接收分支计算详情 |
| `application/conversations.py` | 共享来源解释、有限关联与回复／交互详情；只拥有实际需要的状态，不集中所有普通消息读取 |
| contracts/conversations 的纯转换／领域 accept_fact | 每种宿主事实只归一化一次；旧接口继续由原包装处理，不另建同义 adapter 对象 |
| `message_plane` | 现有 ingest、有限存储、RPC 读取与写入后的轻量变更出口；不导入 application 服务 |
| `server/messaging` 与薄 handler | 负责订阅、控制请求和插件连接上的转交，不承接领域计算 |
| `core` 客户端／传输 | 使用现有 RpcPeer、ZMQ 与订阅坐标，传递 payload，不维护第二套 DTO 或来源规则 |
| SDK client／watcher | 解码公开对象、提供回调与按需视图，不直接访问宿主缓存或本体模块 |

近期存储继续复用 message plane 的基础设施，普通消息读取默认沿用现有 message-plane RPC。需要共享关联信息的回复／交互详情通过既有控制 RPC 委托领域服务，不把所有 v2 读取改道到控制 RPC 或 ConversationService。查询与通知可以共用字段、转换和筛选函数，不要求共用同一条调用链。

领域服务通过生命周期装配时注入的读取句柄或已有读取客户端访问数据，不读取 runner 的私有属性、不创建平行 GlobalState 对话列表。通道差异隐藏在传输适配内，查询不触发本体执行。

```text
普通消息读取：SDK → 现有 message-plane RPC → conversations store

对话监听：既有观察 → 一次必要转换 → message plane 接纳记录
  → 入库后通知衔接 → 现有订阅分发 → PluginHost 下行 → 对话 watcher
  ├→ 新消息回调
  └→ 有视图需求时维护最近 N 条

阶段监听：输入／回复／播放事实 → 一次必要转换与有限接纳
  → 同一订阅分发及下行 → 对话 watcher；不写入普通消息窗口

关联详情读取：SDK → 既有控制 RPC → conversations 领域服务
  → 近期消息与有限关联信息

Memory 读取：新 Memory SDK → 既有控制 RPC → 必要的 Memory 适配
  → 当前循环内部 HTTP 池 → 本体正式读取服务
  ├→ search：既有真实检索接口，支持 private／scoped
  └→ get_persona：本体新增 private 当前知识投影，读取本次加载的当前条目
```

当前 PythonMessagePlaneRunner 在宿主进程内构造 ingest、store 和 RPC。同进程消息通知默认由装配层注入中性入库回调，减少一轮通信；只有核对发现既有 PUB 接入能更直接复用时才改用 PUB，仍只选一个出口。阶段事实有限接纳后共用分发，不建全量事件 Store。message plane 不向上导入 server；回调只做线程安全的有界转交，不在 ingest 线程执行插件回调、远端查询或详情重建。桥接队列接纳不等于消息入库。

需要有限关联状态的 ConversationService 由既有 ServerLifecycleService 创建和停止，再向观察入口、详情查询 handler 与通知适配注入所需引用。不要让三个入口各自构造 service，也不通过导入 application 包根来隐式启动它。HTTP 与 Agent 两条启动路径继续使用现有生命周期编排，避免增加独立启动锁和重复任务。

接收方不在同一事件循环时，使用线程安全的有界入队与合并唤醒，不跨线程直接操作 asyncio.Queue 或 ZMQ socket；不为每条事件新建线程、事件循环或无界调度任务。常规同循环路径不增加无意义交接。

BUS_SUBSCRIBE／UNSUBSCRIBE、PluginHost 的下行通知与现有接收注册机制优先复用。新 watcher 接收携带内容的通知，不继承旧 BusListWatcher 的强制重查算法；必要的契约标记保存在订阅信息中，旧订阅不因此改变。

复用需要实际补通 conversations 的支持列表、宿主登记容器、变化入口和常用筛选执行。批次等待造成的后续事件阻塞、有界积压与慢接收者隔离在现有分发职责内修正；按需要采用批量或有限在途发送，不另外建设对话 DispatcherService、独立连接和 supervisor。不得把显示窗口大小当作派发队列容量。

### 共享下行通道的隔离

现有 PluginHost 下行同时承载 BUS_CHANGE、控制 RPC 响应与 STOP 等消息；普通消息的 Message Plane RPC 仍走独立读取路径。继续复用下行连接，但新增观察流不能无限占用共享 socket 的发送队列或阻塞其他插件。观察在进入 socket 前按插件及总量限制待发条数、字节、批次和在途发送；慢插件只消耗自己的有界份额，不让整批等待拖住独立派发。

在既有发送调度中为 STOP 等小型生命周期消息及请求完成保留接纳与发送余量，优先处理尚未发出的必要控制数据；不要一次把大量观察提前塞入底层 HWM。Memory 等 RPC 响应也可能很大，不能把所有响应当作不限额的高优先级控制数据。新增读取结果在进入共享发送队列前限制单响应及总待发字节／在途量；超限或无额度时通过现有错误路径结束请求，不静默丢弃成空结果，也不为大结果增加分片、专用队列平台或另一条连接。

已进入同一 socket 队列的帧不承诺被后来的 STOP 抢占，因此响应大小、应用层接纳与发送截止时间必须实际生效。观察溢出按已定规则丢弃、统计并标记受影响视图；请求失败不能伪装成功。调度调整保持旧协议格式和已承诺的事件顺序语义，新增结果限量不借机全面重设旧 RPC 返回限制。

先通过持续长文本、多订阅、慢接收者及并发搜索／大 Persona 快照负载验证 RPC 响应、STOP 处理、编码解码耗时、积压字节与内存。只有限量后的现有通道仍无法满足测得的控制延迟要求时，才评估最小通道调整；本计划不预建新连接、优先级平台或独立调度服务。

### 消息与详情共用观察信息

消息列表、get_reply 和 get_interaction 使用同一批观察事实。阶段关联及尚未入普通 Store 的已观察回复文字，默认由唯一 conversations 领域服务有限持有；普通消息确认入库后，详情正文从该存储的同一当前值读取。不为复用缓存形式增加阶段 Store，详情按需整理，不各建来源判断、manager 或持久化投影。

Service 的必要性来自共享来源规则、有限关联和详情整理；只转调现有读取而无业务规则或资源所有权的方法不增加 Service 层。禁止的是复制已落盘完整消息库，不排除必要的未收口文字暂存；不按插件创建对话状态机，也不查询 Memory 补齐观察。

ReplyOrigin 在归一化入口形成，有限修正的当前值由既有普通存储或其有界当前值索引统一提供给列表、单条读取与详情，不能只改详情缓存；不建立第二份完整正文。修正通知使用已定义的 message.updated／reply.updated，已交付快照不回写，也不查询当前 session 重贴历史来源。

不为 get_message、get_reply、get_interaction 分别创建独立 manager、repository、数据库或持久化投影。兼容细节集中在前文旧行为与协议边界，旧入口保留薄适配；Context、Host 和通用 Bus 只做必要转交，不复制领域规则。

### 未收口回复文字的归属

reply.started 可能先于普通消息形成，get_reply 仍应能返回该回复已观察到的文字、来源和状态。领域服务以 reply_id 保存最小临时快照，不依赖 watcher 已启动；text 只表示生产端已经明确发布且插件接纳的可用文字，不等于 provider 内部所有 token，也不要求新增逐 token 通道。

| 已观察状态 | 正文及关联的归属 |
| --- | --- |
| 已开始，尚无普通消息 | 领域服务有限保存当前可用文字和阶段事实，查询不必等待最终消息 |
| 已收口，普通消息仍未确认入库 | 继续有限保存已知收口快照；closed 不能当成入库成功信号 |
| 普通消息已确认入库 | 通过明确 reply_id／message_id 关联引用正式当前值，释放临时正文；迟到 started 不把它切回较旧临时版本 |
| 中断、废弃、失败或最终消息未送达 | 保留真实已知原因和仍可用的临时快照，按预算过期／淘汰；不伪造普通消息或补写历史 |

临时文字按单回复字节、总字节、条数和 TTL 有界，取值留待实测。超限或过期后，text 可为 None 或详情按既有 None 语义缺失，不静默截断后仍宣称正文完整；阶段边界也不能证明保留了完整答案。接纳、移交和修正复用同一来源及当前值规则，不维护第二份长期正文或新归属管理器。

### 延迟创建与资源所有权

沿用 SDK shared 的延迟导出习惯。访问 `self.bus.conversations_v2` 或创建 watcher 只创建轻量对象，不加载历史、不建立连接、不启动后台任务。读取发生在 get 等方法调用时；订阅资源在 start 时建立。

SDK watcher 拥有自己的本地回调任务和订阅句柄，停止只释放这些资源。插件 Context 保存已启动资源的少量清理句柄，复用 worker 现有退出收尾流程，在所属事件循环内有界停止；不依赖 `__del__` 执行异步清理。

这些是现有对象的清理责任，不据此增加统一 ResourceManager。停止 watcher 不关闭共享存储、连接或其他领域工作；插件退出清理自己的登记与任务，宿主服务关闭共享设施。

当前 startup 生命周期通过临时 asyncio.run 执行，随后才运行常驻命令循环。startup 中 start 可以完成订阅登记，但不能把长期回调 worker、视图刷新或 socket 绑定到该临时循环。沿用现有生命周期 downlink pump 暂存非响应消息、命令循环处理 BUS_CHANGE 的路径，回调调度使用实际接收时的常驻循环；新增待处理通知保持有界。不能要求插件等常驻循环启动后才能退出 startup，形成互相等待。

包含新模块的新版 SDK 将客户端作为可选能力按需取得，不扩大旧 Context 的强制属性清单；实际使用缺失能力时明确反馈，不影响其他功能。旧宿主自带旧 SDK 缺少导出的情况按前文版本要求处理，不承诺跨版本导入新类型。

宿主订阅与缓存由插件服务生命周期拥有。停止单个插件时移除它的订阅，不关闭共享 message plane；停止服务时先停止接入与派发，再按既有顺序收尾 host、router 和存储资源。新增清理只接到已有生命周期，不另建后台 supervisor。

已知连接断开、服务停止、插件冻结／热重载或 Message Plane 重建时，复用现有关闭与启动路径清理／使旧订阅句柄失效，不能继续把它当有效登记。可报告的失效原因使用既有错误或连接通知；重新启动时取得新订阅 ID 并重建必要接入钩子，迟到旧通知不进入新登记。不新增心跳、状态监控或全量恢复任务，也不承诺静默丢失可被发现；已知失效与期间允许丢失分别处理。

### 从现有工程验证落点

当前 SDK root/shared/core 已有延迟导出；打包测试枚举整个 SDK 子树。新叶子模块需可独立导入，并确保 PyInstaller 收集完整。现有 core 和 SDK 各定义 ConversationRecord 是本次避免延续的重复，不要求把其他旧 DTO 一并迁移。

采用三类有意义的验证：契约编解码与来源适配的固定样例；真实观察数据经过查询／通知后的公开对象一致性；导入、打包、按需启动与退出清理。运行表现仍按 best-effort 的延迟、突发和故障隔离目标验证，不增加完整恢复测试体系。

用普通问答、语音转写、主动／任务回复、打断、播放取消和迟到修正等本批声明支持的真实路径核对强需求。unknown／None 用于缺乏证据或兼容降级，不能替代应有字段的接入完成：普通消息应有角色、正文和消息身份，声明支持的来源／关联／播放路径需以生产证据验证，不能把全部未知当作能力已完成。来源具体插件缺失时，也不声称已保证消除自身回复反馈循环。

另以“只听用户语音”“角色消息加播放停止”“来源筛选窗口发生修正”三个简短插件用例检验已定筛选和回调方式。若常用任务需要反复拆 watcher 或自行拼关联，应重新评审对应契约，不为绕过摩擦增加通用 Query 或隐式关联扩展。

## 非 plugin 改动的最小边界

普通消息读取／record、已有语音转写与 Memory 搜索优先复用现有生产能力，不以 Main 生命周期扩展为前置条件。非 plugin 只补当前通道没有、且已确认需求确实需要的事实；不为插件观察统一本体 owner、改写生成／重试／热切换、读取同步数据库或增加 Main 侧详情存储。Memory 的具体本体边界由 [Memory 计划](/design/plugin-memory-adapter-plan#非-plugin-接入边界) 维护，本节不重复其实现安排。

### 复用点与必要增量

| 需求 | 可复用的实际位置 | 必须补的最小内容 | 不作为前置条件的工作 |
| --- | --- | --- | --- |
| 普通消息与语音最终转写 | 既有 conversation_turn_observed、Main 发布和 Agent 转发 | Agent 保留现有 event_id／必要字段及明确生产时间；本次不另发第二份普通消息 | 新 Main 消息库、另一条语音权威来源、全部输入路由观察 |
| 早期文字输入 | 普通文字路由和已有 Session PUB | 选定边界的提交正文／身份事实，后续普通消息透传已知 input_id | 前移旧消息发布、改变检查或打断顺序、增加输入处理状态机 |
| 普通文字回复归属 | `_ReplyTurn`，streaming／greeting 已绑定的完成／废弃回调 | 在已有 owner 上固定一个稳定观察关联，透传已有 input_id 与已知来源；只增加必要标量，不再维护一套 live 状态 | 把独立 ASR、实时语音、主动路径强行改成 `_ReplyTurn`，改变原 owner 的比较、接管或清理规则 |
| 首段有效文字 | `send_lanlan_response` 的最终有效发布边界及既有 on_published | 原 guard 通过、非空可见文字已被接受发布后，旁路交付首段快照和关联 | provider response.created 即开始、每 token 通知、TTS 专用摘要另算回复、额外 Main 正文缓存 |
| 最终文字收口 | 既有正常完成、中断接管、最终废弃及主动提交出口 | 在原路径已作出最终决定的位置附加关闭事实和已有原因，冻结正文／关联后交接 | 把每个 turn end／discard／text_end 都改名为 reply.closed，或改变原重试／恢复决策来凑完整事件 |
| 回复来源 | 生产端已有内存来源 proof、Agent／主动／avatar 标记及独立工具证据 | 从正确 owner／发布边界取已知来源快照，只由插件适配一次；input 关联与直接触发分别表达 | 为取 ID 提前创建来源 proof、完整因果链、从 callback 名称猜 plugin_id／task_id，或把工具使用当触发来源 |
| 基础播放事实 | 既有 voice_play_start／end、WebSocket 接收及 LifecycleEventBus | 在现有报告出口薄转交 turn_id／已知 meta，不改播放门控；缺失关联与原因保持未知 | 前台先重构、多窗口／重播身份齐全、将 watchdog 自愈伪装为收到停止报告 |
| 准确播放原因与尝试身份 | 前台现有 start／end／cancel 与重播状态、原报告通道 | 按实际需要补可选呈现身份、明确 reply 关联和 stop_reason；字段由原通道透传 | 新播放器、音频二进制协议改造、精确进度或逐字对齐 |

`_ReplyTurn` 当前主要绑定部分 Offline 文字／角色交互回复；独立 ASR、实时语音和主动 `prompt_ephemeral` 各有实际归属，不能因为普通文字可复用就声称已经全覆盖。主动客户端自己发布指令／已提交回复，继续保留该唯一出口；其一次 prompt 内 `_bus_turn_id` 只有在语义核对后才可作该路径关联，不能把所有 legacy conversation_id 升格为回复 ID，也不能迁到 Core 再重复发布。

### 必要字段与观察语义

| 字段或事实 | 最小接入规则 |
| --- | --- |
| message_id／event_id | 普通消息继续用已有观察 event_id 贯通；独立阶段事实各有观察身份，不替代回复身份，不建全局 ID 表 |
| input_id | 普通早期输入复用已验证作用域的 request_id，或一次生成观察 ID；向后透传而不覆盖原 request_id，不要求为所有外部输入立即补齐 |
| reply_id | 固定在现有归属处，后续只透传。初始 speech ID 的值只有经验证唯一才冻结复用；不能读取 current_speech_id 解释迟到回调。proof.recordId 不能无条件等同整条回复身份，复用不足时允许一个新观察 ID |
| character／origin | character 取明确角色；来源读取已有 proof／触发快照。chat、proactive、工具证据不机械一一映射到 SDK kind；具体 plugin_id／task_id 只在有可靠生产字段时填，否则 None |
| started 的 text／时间 | 只观察 guard 后确实发布的首段有效角色文字；`_begin_reply_turn`、provider 建立响应或已有 text_start 本身不证明文字开始。保留原情绪清理、TTS／UI 分流与发布顺序 |
| closed 的正文／原因 | 最终完成、明确中断／最终废弃才发相应关闭事实；will_retry 的一次尝试不关闭整条逻辑回复。恢复分段的 turn end 和 `_ReplyTurn.turn_ended` 先按原用途解释，不能直接成为观察 completed；不能确定时保留 unknown |
| playback 字段 | 基础报告保留实际 turn_id；能明确关联才带 reply_id。7B 再补需要的 presentation_id／presenter_id／stop_reason；可复用有证据的连接身份，不要求另建前台身份系统，旧字段保留 |

Main 的 `mark_turn_origin` 会创建并固定 proof，不是纯读取函数；不得为取得 reply ID 提前调用 `mark_turn_origin(..., "chat")`，抢占后续来源。只复制已有 proof 中允许的事实，不读取聊天同步数据库、改云同步规则或要求用户开启同步。原生 provider response ID 也需连接／会话作用域核对，不直接当成全局身份。

普通文字优先沿用现有回调闭包，必要时只将固定的 owner／reply 关联绑定到文字回调及最终消息发布，不改变回调的原执行条件或结果。不能在迟到文字到达时重新读 `_open_reply_turn`、当前 session 或全局 request_id 来归属；原路径无法提供明确归属时，先如实标缺失并在对应路径增量中核对，不为统一字段改写客户端调度。

首批 started 可携带首段文字，closed 携带已知收口文字；插件详情只承诺已观察到的内容，不承诺每次查询都有最新全部生成中文字。沿用现有文字缓存并在必要边界冻结快照，不在 Main 复制第二份正文或持续发中间片段。现有明确关联的迟到文字可按有限修正接入；持续完整进度、未知分段自动合并和全部 provider 内部尝试追踪均后置，不能为了这些能力改变生成流程。

### 旁路发布与分批覆盖

观察只放在原判断完成后的已有出口，数据在异步交接前冻结为小型事实，不让后台任务再读当前 session／speech／来源。优先复用原 Session PUB 连接及已有有界发布能力；必要薄封装只表达事实，不导入插件 SDK，不新增 Main→plugin 专用连接、观察 Service 或阶段状态机。不等待插件，不把观察结果作为生成、重试、TTS 或播放继续执行的条件，错误仅隔离到旁路；不在逐 token 路径无界 create_task。

LifecycleEventBus 是同步执行订阅处理器的进程内总线，不能在 handler 中执行网络等待、详情重建或插件回调；现有 text_start 位于主动文本投递调用前，text_end 用于投递节奏，二者都不能直接映射成通用 reply 生命周期。播放既有信号可在原接收／信号出口接一次薄转交，避免既直接转发又订阅转发造成重复；不修改原 gate、watchdog、TTS 收尾或信号触发条件。

回复按步骤 6A 普通文字、6B 各自归属的其他已确定路径交付；播放分 7A 基础报告、7B 准确关联／原因。具体顺序仅在下文总实施表维护。6B 和 7B 是已确定能力的后续实施增量，不表示从计划删除；每条路径分别记录已接通事实、可复用身份、未知字段和未完成项，使用固定样例／测试记录即可，不建设运行时能力矩阵。未接通不能用全部 unknown 冒充完成，也不要求 1A／1B／1C 等待这些增量。

## 与 Memory 共用设施而保持独立

公共设施的主要说明集中在 [Memory 适配的公共设施清单](/design/plugin-memory-adapter-plan#公共设施与连接生命周期)。这里只保留两个领域的依赖规则：conversations 不自动调用 Memory，Memory 不依赖 watcher；各自拥有业务模型、缓存和执行任务，插件需要时显式组合。

Memory 首批包括真实 search 与 [private Persona 当前知识快照](/design/plugin-memory-adapter-plan#get_persona)，共用 MemoryClient(self.ctx) 和既有请求设施。快照保留来源、保护与保存的抑制标记，不因读取额外刷新冷却或标记提及；既不代表刚发生的对话已经记住，也不代表 Main 本轮上下文或可直接注入模型的背景。conversations 不拉它补齐消息、回复或关联。Persona 条目的 source 是知识来源，回复的 ReplyOrigin 是业务触发来源，二者不统一成一套来源枚举。scoped Persona、渲染和审计不纳首批，不增加 ctx.information、PersonaService、独立缓存或专用连接。

不创建 BaseObservableDataService 等覆盖两者的业务父类。共享截止时间、RPC、序列化与资源工具，不强制统一查询模型、结果容器、传输路径或 scope。慢 Memory 请求不能拖住对话派发，停止 watcher 也不能顺便取消插件所有独立查询。

`plugin/sdk/shared/transport/message_plane.py` 的 request 当前寻找 plugin_ctx.message_plane_request，现有 PluginContext／SdkContext 没有提供该方法；因此它不是已经接通的普通读取捷径。1A 默认复用 `plugin/core/message_plane_transport.py` 与 Core Context 的既有请求适配，再由 SDK 叶子客户端解码；SDK 不 import Core。原生 request_async 当前只有实例级 socket cache，未区分事件循环，且多个请求各自 recv 并丢弃不匹配 req_id 的响应，不能直接把它视为安全的并发／跨 startup 循环请求入口。这是源码风险核对，不声称已用现有测试复现。

首批新读取沿用现有 Core 异步方法使用默认执行器调用同步请求的方式，明确调用 request_sync，复用其线程本地 socket；在提交执行器前有界接纳，等待和执行共用总截止时间，线程实际开始时重算剩余时间。不新建执行器／线程池，不为异步外观先重写公共传输；取消本次等待不承诺强制中断已执行的阻塞调用。若后续实测证明必须原生异步，再在原传输位置解决循环归属和响应分发，不能直接复用当前 cache 或另建传输系统。以上私有入口不纳入插件作者必须操作的公开 API。

普通读取具体接线采用现有 `_BusHub`／`SdkBusContext` 的边界：集成负责人在 Core hub 接入轻量 conversations_v2 读取适配，Agent A 可将其放在现有 core/bus/conversations.py；它只借用既有 Context／MessagePlaneRpcClient 返回 wire，不再创建一套 Core ConversationRecord。SdkBusContext 将该适配提供的读取能力交给 SDK 叶子客户端解码。创建／取得时均不做 I/O；新 SDK 缺少相应底层适配时明确失败，不能复用公共 _call 的空列表回退。该接线不要求新建通用 message_plane_request 或让 SDK 直接 import Core。


get 的其他已定可选筛选直接位于 args，省略条件不发送；get_message 成功时 result 直接为消息对象。内部 result.items 不增加公开 Page。上述消息身份和关联为合成值，不能根据三条相邻记录推导同一回合；metadata.is_voice 只映射用户 input_source，旧 source 模块字符串不能直接映射 ReplyOrigin。

subscribe_payload 是 BUS_SUBSCRIBE 的业务 payload，外层 request_id、from_plugin、timeout 与剩余 deadline 由既有 RpcPeer／Context 处理，不能与 Message Plane 的 req_id 信封混用。contract 只登记在订阅上，省略时走旧协议；接收按 sub_id 选择 sink，无需改 host 的 BUS_CHANGE 顶层格式。filters 仅包含公开已定字段，不是新 Query DSL；rules 是需接收的事实名。change 在 SDK 生成，存在 change 回调时 SDK 订阅 record／message.updated 并标 view=true，view_limit 留在本地并用于快照读取；纯事件 view=false。已知遗漏使用合并的内部 op=view.invalidated 提示，不新增公开业务回调、gap 清单或重放协议。订阅确认仍复用现有 sub_id 结果，取消使用原有 bus／sub_id。

控制 RPC 的 UNKNOWN_OPERATION 可在新 SDK 边界转换为 CAPABILITY_UNAVAILABLE；Message Plane 旧宿主在 strict 模式可能先以 ERR 拒绝不认识的 op，无法明确识别时保留协议／传输错误，不把任意 ERR、超时或无数据当作能力缺失。不增加探测轮询或为了支持旧宿主另做读取回退。参数错误、未就绪和其他失败仍依各自 code 表达，不能折成 result=null。

### 多 Agent 工作轮次

推荐一个集成负责人加最多三个实施 Agent；并发条件不同可减少人数，不为满并行拆碎同一领域。下表只分配工作范围，各步骤的交付与验收以上表及 Memory 对应工作包为准。各 Agent 负责自己的领域测试，集成负责人复核跨进程、兼容和共享资源结果；不把测试全部留给第四个 Agent。

| --- | --- | --- | --- | --- |

| SDK 打包／公共兼容测试、正式文档和发布声明 | 集成负责人 | A 负责 conversations／Message Plane 回归，B 负责 Memory 插件侧及后续 SDK watcher，C 负责 Persona 原生隔离；不并行修改公共 conftest，plugin/tests 与根 tests 分进程运行 |

以上是代码修改归属，不限制只读核对或独立测试。同一文件的多个需求优先由负责人合并为一次必要调整，不为避免冲突把业务拆成多层 proxy 或新模块。

### 提交与验证边界

每个工作包带必要兼容和相关验证：普通读取、搜索、Persona、共享下行、消息 watcher、窗口修正、早期输入、6A 普通文字、6B 的独立路径和 7A／7B 可分别形成可审阅提交；共享接线随对应能力集成，不拆成多份只靠假上游才能运行的长期中间状态。原生 Persona 与插件适配可独立开发，但在完整链路通过前不宣称 get_persona 已交付。Main 每个增量先证明原生成／重试／打断／TTS／播放语义不变，再验收新增观察；不要求一步一个 PR，也不因本计划自动执行 commit／push。

优先扩展现有 conversations 查询／转发、RPC 进程集成、生命周期、Memory scope／检索和 SDK 打包测试。新测试覆盖新增契约、交错、隔离与资源边界，不镜像实现细节，不建设另一套测试平台。每步相关检查通过后继续集成；只有新改动、失败或未解决问题才扩大或重复测试，最后执行混合场景验收。

旧协议字段、返回形状、默认值与受支持同步／异步方式在对应步骤回归；已知 bug 按前文例外处理，不能冻结错误或扩大成无关旧接口清理。正式导出和文档仅随真实接通能力发布，版本要求沿用现有机制，不预建能力矩阵、阶段开关或空 API。

## 实现验收重点

1. 公开旧 SDK 的默认值、关联 ID 语义、列表、排序、record 与实际支持的同步／异步用法保持；内部重构不以固定未公开 Core 接口为前提。
2. 旧读取链仍可解析普通消息字段，阶段事实不进入旧结果或挤占文字槽位；新 None 和错误规则不顺带改变其他旧 Bus，明确 bug 修复单列。
3. 新旧订阅在同一宿主及插件中并存，旧通知与启停行为保持；停止新 watcher 不影响旧订阅。
4. 使用已有版本声明验证新旧运行组合，新功能不破坏旧 Context 的无关功能，也不承诺旧 SDK 能导入新增类型。
5. 同一关联 ID 的不同消息有不同记录身份，重复读取保持身份；关联只使用明确证据，不要求额外生成全部身份层次。
6. 使用已定的过滤和事件适用表，先过滤再按入库顺序选择窗口；默认 max_count=50、升序，省略角色不绑定当前角色，不适用订阅明确报错。
7. 同 ID 修正更新各读取入口的当前值，已交付快照不变；updated 不再次触发 record，不追加第二条普通消息或改变创建排序位置。
8. 正常未过载时，窗口 A、B 更新到 D、E 期间送达的 C、D、E 仍分别交给新消息订阅者，窗口大小不截断事件通知。
9. 只有 change 订阅维护视图，空视图也有 initial；历史不回放为 record，序号截止或 ID 合并路径均不让旧快照覆盖新消息和修正。
10. start 返回表示订阅登记完成，不等待历史或常驻循环启动；startup 临时循环退出后，通知仍由常驻接收正常处理。
11. stop 停止接收与未运行任务，有界等待后请求取消运行中回调；返回后不启动新回调，退出清理不关闭共享设施或无关查询。
12. 同处理器串行、不同处理器有界并行，慢异步回调不绑住独立视图；无自动重试或每回调常驻 worker，不承诺强制中断同步代码。
13. 缓存、队列和关联有界，过载优先丢较旧待交付事件而不打断运行中回调，视图合并最新；计数可见，不强制追赶或恢复握手。
14. 旧 voice_transcript 保留参数、开关和执行语义；v2 使用普通用户消息来源，不重复入库或应用旧动作返回值。
15. 早期文字在普通路由归属和必要检查后、昂贵准备前发布；提交正文不被 memory_text 替代，与后续记录通过明确输入身份连接，相同正文不误合并。
16. 普通和外部路由按确定的覆盖范围观察，不把早期通知解释成 LLM 已接收或业务成功，不泄漏完整模型上下文。
17. 文字输入、原生语音和独立 ASR 路径的来源解释正确，业务触发与是否主动不互相覆盖，不借用当前状态解释旧回复。
18. reply.started 只表示首段有效文字，reply.closed 不代表播放停止；明确收口原因按证据保留，文字结束但音频仍播放合法。
19. 播放报告按已知呈现身份关联，停止原因未知时保持未知；旧前台、断线和超时清零不伪装成自然播完。
20. 交互详情只汇总有界已观察事实，允许多回复、多播放、未知或 None，不等待缺失阶段或启动历史恢复。
21. Main/Agent 与必要前台只补薄观察边界和标识透传，存储、查询、关联与回调均在插件侧，不重建本体业务。
22. 新契约在轻量叶子模块定义和编解码，SDK 可导入并完整打包；新增来源只改必要适配，新旧入口不复制业务判断。
23. 普通读取沿用 message plane；每条普通消息只用一个入库通知出口，阶段事实有限接纳后共用分发，不强制建全量阶段 Store。
24. 未使用的视图与详情不持续计算，不预建通用门面、能力矩阵、管理体系或每回调独立执行单元；测量延迟、积压、已知丢失和逐订阅重查放大。
25. started 已到而消息未入库时详情可读已观察文字；closed 先到也不提前移交，确认入库后释放临时正文，迟到事件不使归属倒退，超限不伪装完整文本。
26. 长文本、多订阅、慢接收者及并发搜索／大 Persona 快照下，观察发送与新增大 RPC 响应都受相应字节／在途限制，STOP 等小型生命周期消息有余量；共享 socket 已排队帧不被虚假承诺可抢占，不为此新增分片或改义旧 RPC。
27. 已知消息通知遗漏影响 change 视图时，只合并一次当前快照刷新；期间新数据正确合并，不补发业务回调，不为纯事件订阅、业务失败或正常移出启动历史查询。
28. 已知断开或重建使旧句柄失效，重启按已有生命周期重新登记，不留重复钩子；用真实插件路径验证关键字段和易用性，不把全部 unknown 当完成。
29. 与首批 search／private Persona 组合时只复用请求设施，保持独立调用与错误及各自来源含义；不自动读取快照补对话，旧 memory／UI 读取不改成新结果，不新增内部 JSON 兼容层；大快照与观察流并发下共享下行仍受保护。
30. Main 身份附着于现有 owner／明确边界，冻结后的关联不随 speech 轮换；不为取 ID 提前 mark 来源，不统一各 provider owner，不查询同步数据库，不新增 Main 回复正文库。
31. started 只在原 guard 后有效文字确实发布时产生，closed 只在实际最终出口观察；重试中的 discard、恢复分段 turn end 和投递节奏 text_start／end 不被误映射，旁路故障不改变原检查、生成、重试、打断、TTS 或播放门控。
32. 6A、6B、7A、7B 分别按真实路径验收，基础播放可先复用旧报告，准确原因／呈现身份不猜；未完成路径如实列出，持续完整生成进度与完整因果追踪不自动加入本批，不用全部 unknown 冒充已定覆盖。
