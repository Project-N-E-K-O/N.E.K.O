# 猫形态养宠系统首版实施文档（NEKO / NEKO-PC）

> 本文定义实施顺序和验收标准。产品规则以《宠物养成系统方案（修订稿）》为唯一设计基线，接入边界以锁定文档和本轮确认的部署方案为准；数值草案只提供可替换的首版候选配置。
>
> 本文按“用户能看到什么、完成后能验收什么”拆分阶段。阶段 0–9 曾先在本地养成服务镜像上验证业务边界；该镜像随后已经迁出 N.E.K.O。当前本地联调直接运行正式 PetCare 服务代码和隔离数据库，客户端继续使用同一套业务接口。

> **本轮边界确认：** 首版以养成服务、照料、任务、探索、动作链和状态结算为主。养成可用性复用 N.E.K.O 现有 `community_oauth` 统一账号会话，同源薄网关只转交已验证会话，不建立养宠专用登录。账号只有一只猫，绑定账号自己的一个角色，当前角色不是绑定角色时和未登录一样走普通猫路径。用户登录、猫处于猫形态且养成快照完整后，自动进入养成兼容状态，并在首次进入时给出一次提示；只有用户照料、陪玩及探索出发等真实占用猫表现的短窗口才暂时停用冲突的 Cat Mind 自主触发。养成服务负责长期状态、条件、负面状态、探索、库存、奖励和结算；Cat Mind 继续保存自己的短期五维并执行短期自主行为。PetCare 通过版本化只读投影为 Cat Mind 提供输入，但不把养成状态写入 Cat Mind，也不让 Cat Mind 参与长期结算；统一账号会话失效或快照不可用时，撤回投影并继续使用普通猫路径。

## 1. 首版目标与范围

首版完成后，用户可以：

1. 未登录时继续正常使用猫，不显示养成入口、宠物数值或可用养成操作；每次进入猫形态只显示一次轻量账号提示，可直接调用现有 N.E.K.O 统一 OAuth 流程，关闭后本次猫形态期间不再打扰；该提示不是养宠面板，也不建立第二套登录态；
2. 保持 N.E.K.O 统一账号登录后，只有当前角色等于账号绑定角色时才读取该账号唯一宠物；其他角色和未登录一样使用普通猫；
3. 查看饱食、精力、清洁、心情和养成进度；
4. 完成每日任务、喂食、清洁（首版具体操作为梳毛）和用户主动陪玩；
5. 开始一次探索，看到猫离场、猫窝、纸条和来信；
6. 正常等猫回家，或在猫窝面板中结束探索并让猫回到猫形态；用户切回模型时再复用统一模型返回入口完成强制召回；
7. 刷新、重启本地服务、切换角色后仍看到正确数据；
8. 长时间未登录后看到一次离线结算和必要的恢复任务；
9. 通过照料和探索积累进度，达到阈值后看到解锁内容。

首版围绕任务、照料、主动陪玩、一个探索地、负面状态和已有真实消费入口的解锁内容展开，不为达到数量而保留占位解锁。当前确认的首版范围不接商店、钱包或货币结算；锁定文档中的猫薄荷规则保留为未来社区经济接入约束。社交、推送、AIGC、洗澡和更多探索内容安排在后续版本。

实施前已根据实际代码确认以下事实：

| 事项 | 当前实际情况 | 实施要求 |
| --- | --- | --- |

各阶段按所接入的功能验证普通猫回退、当前账号与 `bound_role_id` 校验、请求幂等和服务确认结果；页面侧仍使用当前 `character_uid` 作为角色解析输入。

### 2.1 本地、正式服务与代码结构

养宠是一个独立业务域。阶段 9 的本地后端镜像已经完成差分基线职责并迁出；当前正式数据和结算代码位于 N.E.K.O.Verse 同仓的独立 PetCare 服务包，运行时和数据库边界独立。当前不增加第四个仓库；部署时由实际编排决定是否与 Verse 同一发布项目，但不得因此合并进程、数据库、迁移或领域事务。

社区 PetCare 服务负责账号唯一宠物的状态、任务、探索和结算。API、错误码、幂等和状态版本语义由本地镜像验证后迁移；SQLite 的物理表和 JSON 快照不直接搬入正式库。现有云存档只作隔离、幂等和恢复参考，其角色目录依赖用户主动上传，不能成为宠物绑定的数据源。PetCare 只登记实际用于首次绑定、跨设备关联或官方换绑的角色，不建设完整云角色目录。

账号身份、客户端安装身份和角色身份是三条独立信息：账号来自 N.E.K.O 现有的社区 OAuth／统一账号会话；Verse 校验账号状态、`session_epoch`、安装 proof 持有及 `clients.bound_user_id == users.id` 后得到 `users.id + client_id`；PetCare 再把该安装上的 `character_uid` 别名解析为稳定 `role_id`。安装 proof 是可复制的 bearer 凭据，只证明安装凭据与账号绑定，不证明物理设备或官方二进制完整。账号只有一只宠物；`bound_role_id` 只保存当前 `role_id`，`binding_revision` 只用于换绑并发，`state_version` 只用于宠物聚合版本，三者不能复用。客户端不能声明账号映射、稳定角色、绑定版本或宠物归属。

账号登录与绑定猫可用是两个判断。现有 `/api/card-drop/oauth/status` 已通过实际社区账号服务确认“是谁、会话是否仍有效”。在该结果为已登录时，客户端调用轻量、事件驱动的 `POST /api/pet-care/session/resume`；它只确认当前 N.E.K.O 账号活动，不要求猫形态 active、当前角色匹配或面板打开，也不接受角色、客户端时间、离线时长或结算结果。初始化、`focus`、`pageshow`、页面重新可见和受信账号状态变化先刷新现有账号状态，确认登录后触发 resume。现有跨窗口语义层在成功发送文字、语音转写或 Avatar tool 用户交互时发出 `neko:widget-interaction-start`；连续用户输入也可能发出 `neko:widget-interaction-extend`。客户端只消费这两类事件中 `detail.phase === "waiting"` 的实例：assistant turn／speech 和 settling 也会发 `extend`，但 phase 分别为 `reply`、`speaking` 或 `settling`，不得算用户活动，也不能只凭仍保留的 `detail.source` 判断。符合条件的事件只在内存状态仍为已登录时直接触发 resume，由 edge 再次鉴权，不为每次交互额外调用社区 `/api/users/me`。resume 不上传交互文本或 detail，任意 click、pointermove、失败发送或主动 assistant 输出不算。客户端只按当前账号会话代次 single-flight，并使用服务返回的绝对时间 `resume_not_before` 做流量优化；该提示不得晚于下一服务日边界，也不能成为服务拒绝合法活动的门。`client_id` 继续由网关／edge 受信解析，不暴露给页面。服务日由服务端判断，客户端不靠本地时钟猜“跨日”。当前独立服务、Verse edge、N.E.K.O 网关和客户端均已实现该请求链；真实 OAuth、安装 proof 和生产网络端到端仍留待 staging 验证。

`neko:cat-local-active-change` 只决定是否显示养宠入口和常规宠物快照，不定义账号上线或离线。`session/resume` 返回 `pet_refresh_required` 时，客户端在当前账号会话代次内做本地 latch；不论当前是猫形态还是普通模型，都可对当前 alias 发起一次恢复读取。只有服务确认当前 alias 等于 `bound_role_id` 且快照成功，才清除 latch；非绑定角色或临时失败不清除。活动探索恢复猫窝，服务确认无活动时保持当前普通模型且不展示养宠面板。进程重启后由新 resume 的权威探索状态或切回猫形态时的常规快照重新恢复，不增加服务端 pending／ack 实体。未知 alias、角色不匹配或普通模型继续按普通猫处理，但不会把已经验证的 N.E.K.O 账号活动误判为不上线。无需第二套登录态、轮询、周期心跳、inactive 上报或通用 presence 系统；仅社区网页在线和 Verse `clients.last_seen_at` 仍不足以证明 N.E.K.O 客户端活动。

统一账号的生命周期也必须统一：N.E.K.O 页面、受管的 N.E.K.O.Verse 社区窗口和养宠面板使用同一账号会话边界。社区窗口退出时，必须通过受信窗口桥通知 N.E.K.O 本地会话适配器清理桌面 OAuth 镜像，再由 `/api/card-drop/oauth/status` 重新确认并让养宠入口回到普通猫；不能只清社区页面自己的 `localStorage`，也不能让养宠面板维护第二套登录态。用户在 N.E.K.O 主动退出且存在活动探索时，客户端应在旧会话仍有效时先做一次 best-effort 召回；召回未获服务确认也不得阻止统一 OAuth logout。账号退出确认后立即清除宠物快照、任务、操作和奖励等账号数据，只可保留账号域的不透明探索展示 lease，用于同一账号以后重新登录时恢复读取权威活动；该 lease 不含宠物快照、库存、任务或奖励，也不具备结算权限。若 OAuth logout 本身未获确认，本地仍暂停并清除当前养宠上下文，但不能声称服务端会话已退出。独立浏览器中没有受信 opener 的社区页面不属于这条本地桥，正式服务器接入阶段需提供等价的一次性会话撤销协议。

表现属性只影响外观：模型是角色当前使用的模型；猫档位是同一宠物的不同形态；装扮属于后续纯外观内容。它们都不参与宠物记录主键。本地验收阶段通过切换模型和猫档位验证宠物及 `bound_role_id` 不变，装扮暂不进入首版业务。

`_reserved.character_id` 是数值剧场使用的另一项身份字段；养宠不把它或本机 `_reserved.character_uid` 作为正式宠物主键。

数据流固定为：

```text
Web / NEKO-PC 共用的 NEKO 页面
  → PetCareClient
  → N.E.K.O 本地同源薄网关
  → Verse 公网 edge/BFF（统一账号 + 设备校验）
  → 内网独立 PetCare API
  → PetCare 专用数据库

N.E.K.O 前端契约测试
  → 脱敏 schema / mocked fetch / 黄金行为夹具

PetCare 领域与应用测试
  → 纯领域对象／受控 AsyncSession 替身、假时钟和确定性随机源

PetCare 数据库契约测试
  → 一次性 PostgreSQL 实例执行独立 Alembic 链、约束和触发器验证
```

- **NEKO 页面**负责面板、模式门控、动作适配和统一返回入口。当前实际入口是 `window.NekoPetCareApi` 与 `window.NekoPetCareClient`；页面使用同一客户端读取快照和提交操作，不存在名为 `PetCareBackend` 的当前实现。
- **阶段 9 本地养成后端**曾作为差分基线，负责本地测试期间的规则、补算、结算和持久化。等价行为迁入正式 PetCare 的 `domain/application` 后，N.E.K.O 的业务路由、SQLite 权威和本地会话写入已经删除；当前测试保留领域夹具、会话替身、假时钟和确定性随机输入，不保留第二个可运行结算服务。
- **NEKO-PC**继续只负责窗口、输入、命中区域和 IPC，养成页面复用上述业务接口；不在 preload/bridge 保存账号、宠物状态、规则或结算。只有确有窗口或输入适配需求时，才在现有 pet bridge 中扩展对应能力，通道名集中在 `src/ipc-channels.js`。
- **N.E.K.O 本地网关**运行在用户设备上，只转发用户会话、设备证明、幂等键、版本和关联 ID；它在既有会话文件锁内读取并做结构校验，不为每个 PetCare 请求再次调用社区 `/api/users/me`，也不把本地快照当作账号仍有效的权威证据。它是不可信客户端边界，不能保存服务共享密钥或签发“受信账号上下文”。Verse edge 对每次请求重新校验 token、账号状态、`session_epoch`、安装 proof 和账号绑定后，才向内网 PetCare 签发短期、限定 audience 的内部断言。
- **正式养成后端**位于 N.E.K.O.Verse 同仓的独立服务包，以独立进程／容器部署；使用 `neko_pet_care` 独立数据库、数据库账号、Alembic 链和备份。首发可复用现有 PostgreSQL 集群，但不得使用 Verse 主库 `public` schema。
- **本地测试数据**只存在于隔离测试替身或一次性 PostgreSQL 中；原 `local_state_dir/pet_care` 正式权威路径已从 N.E.K.O 移除。页面和 preload 只保留非权威界面状态及探索重开提示。
- **本地三项目联调**不得把 `NEKO_SOCIAL_BASE_URL` 改成 localhost 来带动 PetCare，因为该变量同时控制社区页面、OAuth callback 和其他社区 API。需要本地 Verse edge 时，只显式设置 `NEKO_PET_CARE_DEV_BASE_URL`；它仅覆盖 N.E.K.O 的 PetCare 固定白名单网关，只接受无凭据、无查询／片段／业务路径的 loopback HTTP(S) origin，非法值直接拒绝。正式发行不设置该变量，仍使用社区 origin；独立 PetCare 服务继续只由 Verse edge 访问，客户端不能用该变量直连服务端口。
- **`.agent` 本地联调夹具**只用于开发且保持不跟踪。它可以在 loopback 上为已经验证、且在隔离 Verse 数据库中精确存在的统一账号身份签发内存短时合成会话，并通过现有前端会话发布入口验证本地社区管理页面；它不能创建账号／身份映射、保存 token、修改正式 OAuth 配置或进入提交、镜像和部署。该路径只证明本地接线，不能替代真实 OAuth callback、安装 proof、撤销传播和管理员授权的 staging 证据。

### 2.2 当前结构和部署结构

```text
  static/avatar/...                    # 猫动作与探索表现

    migrations/                                # 独立 Alembic 链

    scripts/migrate.sh
    alembic.ini
    Dockerfile                                 # 以服务目录为构建上下文
    pyproject.toml / uv.lock                   # 独立最小依赖
```

源码暂与 Verse 同仓管理，但 PetCare 使用独立进程／容器、数据库 URL、Alembic 链和数据库权限。最终是同仓部署还是拆成独立部署项目仍可由运维决定，不改变该运行边界。

`app-pet-care-api.js` 和 `app-pet-care-client.js` 已形成传输与服务端点契约：面板只通过客户端提交养成服务请求；传输适配器统一请求超时、取消信号、凭据和宠物路径，客户端集中上下文、绑定、快照、照料、任务、陪玩和探索端点，二者都不解析业务规则，也不保存账号或宠物状态。当前请求经 N.E.K.O 固定白名单同源网关进入 Verse edge，再由 edge 校验统一账号与安装凭据后访问独立 PetCare。

正式服务通过统一 PetSnapshot 提供公开内容目录、操作包络和确认快照。账号会话沿用 N.E.K.O 现有社区 OAuth；Verse edge 校验当前账号、会话代次和安装凭据后签发请求绑定的短期内部断言。`app-pet-care.js` 遵循“目录 → 操作／终态 → 服务快照 → 表现适配”的边界，不能跨层读写规则或持久化状态。服务目录只公开页面必需的标签、库存、显示增量、CD 和反馈元数据；来源白名单、概率和其他结算权威字段留在服务端。

正式服务代码、独立迁移和 edge/BFF 已完成部署前接入，并已连接隔离本地 PostgreSQL／Redis 完成开发联调；生产密钥、目标网络、staging 和生产部署均未接入。PetCare 不复用 ChatSync 的角色表，不把本机 `character_uid` 设为全局角色主键，也不把 PetCare 迁移加入 Verse 主 Alembic 链。

### 2.3 命名与接口约定

推荐命名：

| 用途 | 命名 |
| --- | --- |
| 业务域 | `pet_care` / `PetCare` |
| API 前缀 | `/api/pet-care` |
| 前端文件 | `app-pet-care-*.js` |
| 服务与数据类型 | `PetCareService`、`PetCareRepository`、`PetCareSnapshot`、`PetCareExploration`；测试使用领域夹具、受控会话替身和一次性 PostgreSQL，不提供第二套 SQLite 运行服务 |
| 数据表 | 以 PetCare 独立迁移中的复数实体名为准，如 `pets`、`pet_roles`、`pet_role_device_aliases`、`pet_role_alias_retirements`、`pet_bindings`、`pet_states`、`pet_inventory`、`pet_tasks`、`pet_play_leases`、`pet_explorations`、`pet_operations`；不沿用 Verse 主库命名空间 |
| 业务标识 | 统一账号 `users.id` + 账号唯一 `pet_id`；稳定角色 `role_id`（快照字段 `bound_role_id`）；设备本地别名 `(client_id, character_uid)` |
| 并发标识 | `binding_revision`（绑定 CAS）、`state_version`（宠物聚合版本） |
| 请求标识 | `idempotency_key`、`request_hash`、`exploration_id`、`request_id` |

当前页面继续传递项目已有的 `character_uid`，但正式服务只在 Verse 已验证的 `users.id + client_id` 上下文中解析它。读取不得创建角色或别名；未知、撤销或不匹配时走普通猫。只有显式的官方首次绑定／换绑用例可以登记 alias。首次绑定使用 expected-absent，`expected_pet_id`、`expected_binding_revision` 和 `expected_state_version` 必须同时为空；官方换绑锁定同一 `pet_id`，要求三者同时等于当前值后才更新绑定。模型、猫档位、改名、异机导入或本地 UID 修改都不能自动复制宠物或改绑。

业务类别和具体内容分层：`feeding`、`cleaning`、`playing`、`exploration` 是稳定的业务类别；小鱼干、梳毛、毛线球、消耗品玩具和探索地点都是可配置的 `item_id` / `content_id`，不能把候选内容写成类别名称。库存由养成服务持有并按账号宠物返回，至少要能表达类别、内容、数量和后续解锁层级；页面不能自行扣库存或把某一个内容当成该类别的唯一实现。当前确认的首版范围不实现商店、钱包或货币结算；锁定文档中的猫薄荷规则保留为未来经济接入约束，届时只能复用社区经济账本，PetCare 不自建第二套余额。小鱼干始终只能由任务获得，不能用猫薄荷购买；付费猫粮仍不在首版。接口和面板为背包与多内容选择保留层级，但阶段 10 不为未来货币预建余额表。

任务是独立的业务记录，不是照料类别的别名，也不是把所有进度、登录和解锁结果塞进一个列表。每个任务必须由服务配置和快照单独标识，至少包含 `task_id`、可配置标题/说明、周期或持续范围、完成条件、当前进度、目标、奖励、状态、可领取标记、进度来源和领取幂等信息。周期和任务类型不能在前端写成固定枚举；页面把任务逐条同级显示。首版没有任务分组消费者，因此配置校验拒绝 `group_id`／`group_label`，不保留“服务接受但无人使用”的死字段。当前候选中的 `daily-work` 先按配置公开的受限 `completion_action` 从 `active` 确认为 `completed`，再单独领取 `small_fish ×1`，完成步骤本身不发奖励；`daily-yarn-play` 只由服务确认的用户主动毛线球操作和猫真实回应推进 `0/3`，不可领取且不携带奖励。每日登录是另一条账号活动结算，不完成这两项任务。恢复任务在当前候选中也复用相同的 `active → completed → claimed` 周期，完成不发物品，领取后才取得药品或逗猫棒。任何当前或历史任务若缺少其所需的受限 `completion_action`，服务一律拒绝完成和领取，不保留绕过完成条件的兼容领取路径。

正式服务把任务实体作为唯一权威集合；PetSnapshot 只返回一个规范列表 `tasks.items`，不再复制 `daily`／`state` 分组投影，防止调用方把同一任务重复渲染或领取。每条记录自身携带周期、进度来源、恢复状态和领取字段，页面仍逐条同级显示。首版实际结算的周期只有配置的服务日；服务日边界一旦已有激活 revision，普通配置激活不得改变时区或起始小时，变更必须走显式数据迁移，避免同一自然时间段重复或漏掉任务／登录周期。

写操作（包括首次绑定和官方换绑）使用 `idempotency_key`，服务保存请求摘要和确认结果；重复请求重放原不可变领域终态，当前认证包络和快照按正式重放契约处理。绑定发现不得建宠：`GET /api/pet-care/context` 和快照读取在账号尚无宠物时只返回 `needs-binding`；账号已有宠物时，读取仍依据 `last_settled_at` 先补算。首次 `POST /api/pet-care/bind` 才按三个 expected 字段同时为空的 expected-absent 语义创建账号唯一宠物，并在同一事务内部复用账号活动恢复用例建立首个无惩罚活动基线和当日唯一登录；绑定失败不得留下基线或登录记录。正式换绑同时校验 `expected_pet_id + expected_binding_revision + expected_state_version`，普通长期业务写使用 `expected_state_version`。账号级 `session/resume` 覆盖没有宠物请求的账号活动；已有宠物的快照和业务入口在服务端复用同一活动前置用例，再按当前角色决定能否返回宠物数据或执行操作。角色和猫形态不作为账号在线条件。

照料、探索出发和陪玩租约签发还必须携带当前完整快照中的 `expected_config_revision`，并把它纳入幂等请求摘要。首次未命中的请求锁定当前 active 配置后先比较 revision；不一致时返回稳定的 `config_revision_conflict` 和 `snapshot_required=true`，且不执行状态补算、账号活动、随机结果、收据或任何库存／任务／探索／状态写入。客户端随后读取新的权威快照并提示用户重新操作，不自动重放旧意图。照料按匹配的当前 revision 执行；已经签发的陪玩租约和已经出发的探索分别按签发／出发时固定的 revision 完成终态，后续激活不能改写在途语义。

首版核心接口：

- `POST /api/pet-care/session/resume`：在现有社区账号校验成功后确认一次 N.E.K.O 账号活动；不接收 `character_uid`、客户端时间、离线时长或活动序号。已有宠物时锁定账号唯一宠物，客户端发送前持久化幂等键，同一账号和安装用同键重试可精确重放稳定领域结果；无宠物时不加账号锁，只按当前事实无状态返回 `needs-binding`，不创建宠物、活动基线或幂等收据，这一分支允许与首次绑定竞态，收到结果后客户端清除 pending key 并按结果继续绑定或重新读取。响应只含通用活动确认、`pet_refresh_required`、`server_time` 和绝对时间 `resume_not_before`；产生每日登录、离线回退或负面状态结果时可带不透明 `settlement_id`，但不直接返回宠物数值或结算详情。客户端以 `resume_not_before - server_time` 建立单调计时，不把本地墙上时钟当权威；该提示只用于节流，不得跨过下一服务日边界，也不是服务端授权门；
- `GET /api/pet-care/context?character_uid=...`：只读当前 alias、绑定和 `needs-binding` 状态，不创建宠物、角色或 alias；
- `POST /api/pet-care/role-aliases/sync`：只同步已提交的本地角色删除事件，写永久 alias 退役围栏；不承担注册、绑定或改绑；
- `POST /api/pet-care/bind`：首次显式绑定要求三个 expected 字段同时为空；已有宠物时仅作为官方换绑用例，并要求当前 `expected_pet_id + expected_binding_revision + expected_state_version`；
- `GET /api/pet-care/pets/{character_uid}`：读取完整宠物快照；
- `POST /api/pet-care/pets/{character_uid}/care-actions`：只提交喂食和清洁操作（首版为小鱼干与梳毛）；
- `POST /api/pet-care/pets/{character_uid}/play-leases` 与 `.../play-leases/{lease_id}/complete`：分别签发短期陪玩授权，并在匹配的真实动作完成终态后结算毛线球或消耗品玩具；
- `POST /api/pet-care/pets/{character_uid}/status-recovery`：只处理已领取恢复任务后的生病用药；赌气恢复必须消费已领取的逗猫棒并走陪玩 lease 与真实动作终态，不能伪装成直接状态写入；
- `POST /api/pet-care/pets/{character_uid}/explorations`：创建探索活动；
- `GET /api/pet-care/pets/{character_uid}/explorations/{exploration_id}`：读取探索状态；
- `POST /api/pet-care/pets/{character_uid}/explorations/{exploration_id}/complete`：正常完成探索并结算；
- `POST /api/pet-care/pets/{character_uid}/explorations/{exploration_id}/recall`：强制召回并结算。

首版接口还需要覆盖任务：

- `GET /api/pet-care/pets/{character_uid}/tasks`：读取服务返回的独立任务项及周期/识别元数据；客户端不得假设固定任务类型，也不得把元数据转换成界面分组；
- `POST /api/pet-care/pets/{character_uid}/tasks/{task_id}/complete`：只执行快照中当前 `active` 任务公开的受限 `completion_action`，按精确 `task_id + cycle_key` 确认为 `completed`，不在这一步发放奖励；
- `POST /api/pet-care/pets/{character_uid}/tasks/{task_id}/claim`：领取已经由服务判定完成且可领取的任务奖励。

任务完成和领取都带 `idempotency_key`、`cycle_key` 与 `expected_state_version`；首次执行并提交时返回完整宠物快照，收据重放只返回原不可变领域终态并要求另读当前快照。每日登录不是面板按钮、任务领取接口或角色级 API，也不存在 `daily-check-in` 接口：服务在每天首个通过账号、设备和 N.E.K.O 客户端来源校验的活动前置事务中按 `(pet_id, service_day)` 唯一处理；独立 `session/resume`、宠物快照和玩家显式发起的新业务请求都复用该事务，纯上下文、旧收据重放和后台／系统结算不重复处理。首次绑定事务内部调用同一用例，因此首日也只产生一次登录和一个无惩罚基线。角色不匹配或普通模型不会阻止账号级登录结算，重复页面恢复、多窗口或多设备请求只读到同一结果。

快照中的 `play_actions.*.minimum_duration_seconds` 只用于签发前预检和展示。实际签发的 lease 与其不可变收据固定当次配置 revision 的 `minimum_duration_seconds`；客户端以 lease 响应值安排动作，完成端按 lease 自己的 revision 重新读取并校验同一值，配置切换不能改变在途 lease。签发请求重放必须返回首次固定值，不能用较新的快照覆盖。

N.E.K.O 本地网关的所有 POST 先签发一个 30 秒、单次消费的本机 capability，并精确绑定当前桌面会话指纹、`POST` method、规范化 path 和请求体 SHA-256；绑定不匹配、会话更换、过期、重复使用或网关重启均 fail-closed。它只阻止其他本机网页直接借回环端口提交写请求，不替代 Verse 的统一账号／安装 proof 校验、内部断言或 PetCare 的权限与事务围栏。

首版可见图片资源随 N.E.K.O 客户端发布，配置中的道具、猫窝和来信图片只允许使用规范的 `/static/assets/neko-idle/` 根相对路径。Verse 在草稿校验和激活时拒绝跨源、其他 scheme、编码分隔符、反斜杠、查询、片段及路径穿越；N.E.K.O 在每个图片展示入口再次执行同一范围校验，失败时使用内置道具／猫窝回退或省略来信缩略图。若以后需要运营 CDN，必须以新版本契约增加受管 HTTPS allowlist 和内容治理，不能把任意 URL 填入 v1 配置。

这些接口中的 `{character_uid}` 只表示当前页面正在校验的角色；服务先从社区认证会话取得账号唯一宠物，再确认当前角色解析出的稳定角色标识是否等于 `bound_role_id`。不匹配时按普通猫返回，不创建第二份宠物记录。

### 2.4 与现有猫行为的兼容边界

Cat Mind 是现有猫行为的一部分，负责猫形态内存中的短期行为驱动力和自主动作选择；养成服务负责按 N.E.K.O 统一账号唯一宠物保存的长期业务状态。两套系统的食欲/困意/精力/社交/刺激与饱食度/精力/清洁度/心情/养成进度不能共用字段、初始值、衰减公式、阈值或结算结果。当前单向适配只消费服务确认、带 revision 和有效时窗的 `client_projection.cat_mind` 动作偏置；失效即撤回，不写回 Cat Mind 五维，也不让 Cat Mind 保存或结算宠物状态。`bound_role_id` 负责正式绑定，`character_uid` 只作为当前页面角色校验。

`client_projection` v3 把两种生命周期分开：`status_rules` 与 `status_seed` 只用于本地只读显示，在承载它们的已授权完整快照仍属于当前账号和绑定角色、且未被后续权威快照替换期间持续有效；`client_projection.cat_mind` 的短期动作偏置只到 `cat_mind_valid_until`，到期或 Cat Mind 拒绝输入时只撤回偏置，不使同一快照的状态显示公式失效。客户端仍兼容 v2 的单一 `valid_until`，其到期会使整份旧投影失效；v3 是尚未发布产品的客户端与服务协调升级，不能把它描述为已存在的滚动兼容保证。配置 revision 激活后不向客户端推送，也不触发轮询；客户端在下一次事件驱动的合法权威快照中采用新 revision，旧投影始终不能授权结算、奖励、扣库存或任何写入。

首版只保留以下兼容约束：

- 首次加载时未登录，或养成快照尚未完整、养成服务不可用时，继续使用普通猫路径，不创建替代存档；若服务已确认当前角色正在探索，则保持猫窝和离场状态，不恢复实体动作。
- 用户已登录、猫处于猫形态且养成快照完整后，自动进入养成兼容状态，并在首次进入时给出一次提示；提示只说明养成入口和边界，不改变业务结算。
- 养成快照完整后，只暂时拦截可能与养成动作冲突的旧自主自动触发；正常的用户照料、陪玩和返回等功能动作仍可由独立适配器调用动作执行器。不要求删除或重写 Cat Mind 的内存需求模型，服务确认结果后才更新长期状态。
- 生病、探索、照料、活动、库存、进度、奖励和结算均由养成服务及独立动作/表现适配器负责，不通过 Cat Mind 决定。
- 单向只读适配器让服务确认的必要派生信号影响 Cat Mind 的自主行为权重；服务不可用、快照过期或角色不匹配时撤回输入并继续普通猫。不得把养成数值直接写入 Cat Mind 五维，也不得让该适配器负责长期状态或结算。

可复用的是 observation 去重、Cat Mind 内存动作请求生命周期、provider 检查、动作终态和清理协议等通用机制；不可复用的是两套数值的业务含义和结算规则。只读适配器是两域之间唯一的数据入口，输入映射要有独立契约和失效清理测试。

旧自主触发不等于所有独立动作来源。当前代码和补充设计中还存在 journey、playground、重力/窗口感知、贴边探头等独立链路；阶段 3 的兼容开关只处理已确认的旧自主触发来源，阶段 7 的探索活动门控必须另外覆盖所有依赖猫实体的输出，不能因为拦截了 `neko:cat-mind:action-request` 就视为全部停止。

## 5. 阶段 1：账号验证、角色识别和入口

### 实施目标

让用户能明确知道养宠复用 N.E.K.O 统一账号登录，并在登录后校验当前角色是否为账号唯一宠物的绑定角色。

### 实施内容

- 按锁定文档的 Q12 保留约 400ms 的悬停触发体验；入口是猫形态独立 surface，不注册现有模型浮动按钮，也不改变 Cat Mind 悬停计数。
- 入口只在当前猫交互语义锚点可见时出现；桌面端采用 demo 的单一透明 surface 和固定坐标几何，rail、状态卡、即时操作和模块卡按同一坐标系围绕猫展开。锚点只提供 `visible`、`busy` 和屏幕矩形作为该 surface 的定位输入；不做默认右侧、左右翻转、候选位置重排、空间不足收缩或底部布局。养成代码不读取 Live2D、VRM、MMD、PNGTuber 的 manager 或容器，入口属于猫形态 surface 的独立养宠入口，不属于模型按钮。
- 未登录或当前角色不匹配时不显示养宠入口、面板、数值和可用操作，继续普通猫；登录由现有 N.E.K.O 统一账号入口承担。已登录、猫形态可见且服务返回 `needs-binding` 时，才允许打开养宠入口并发起一次显式绑定。类别不预设唯一物品，具体食物、清洁操作、玩具和地点由服务配置及库存层级提供。
- 阶段 1 只确认账号、当前角色和绑定上下文；服务尚未返回完整养成快照时继续使用普通 Cat Mind 路径，不提前启用阶段 0 的兼容门。阶段 3 才在登录、猫形态和完整快照同时成立时屏蔽指定 Cat Mind 旧自主请求并清理尾回调，用户主动动作不受影响。
- 未登录进入猫形态时只显示一次轻量登录提示，用户可直接进入现有统一账号流程，也可关闭；提示自动消失且本次猫形态不再重复。它不显示宠物数值、可用操作或养宠面板，也不创建第二套登录入口；登录成功后通过现有 OAuth 状态接口确认账号，并从 `appChatAvatarState` 读取当前角色的 `character_uid`；
- 用受信 OAuth 会话取得当前账号 ID（NEKO 本地实现使用 `local_user_id`），调用 `GET /api/pet-care/context?character_uid=...` 获取服务端绑定状态。
- `GET /api/pet-care/context` 只读绑定状态；账号尚无宠物时返回 `needs-binding`，不创建数据。用户显式提交 `POST /api/pet-care/bind` 后，服务才在事务内创建账号唯一宠物和服务端生成的 `bound_role_id`。绑定写入必须带幂等键；已有宠物换绑还必须匹配最近确认的绑定版本前置条件，并保持同一 `pet_id`。已有宠物且当前角色不匹配时返回普通猫路径，客户端不得复制宠物或推导绑定 ID。
- 处理登出、切换账号和切换角色；服务不可用时提供重试并回退普通猫，不再永久停留在等待文案。

### 用户可见验收

1. 未登录且猫形态可见时没有养宠入口、数值或操作，普通猫仍可正常使用；每次进入猫形态至多出现一次可关闭、会自动消失的统一账号登录提示；
2. 通过现有统一账号入口登录后，养宠入口请求服务端绑定上下文；
3. 登录取消或失败，猫仍可正常使用，养宠入口不出现；
4. 服务返回 `needs-binding` 时允许用户显式绑定当前角色；只读请求不得创建宠物；
5. 首次绑定在服务事务内建立唯一宠物；重复幂等请求返回同一结果。其他角色按普通猫处理，不读取另一份宠物；换绑必须显式提交并通过并发前置条件；
6. 登出后养宠入口、面板、数值和任务信息消失。


## 8. 阶段 4：状态补算和基础照料

### 实施目标

把状态页变成可操作的养宠页面，先完成喂食和清洁类别中的梳毛操作。

### 实施内容

- 按上次结算时间补算状态，并提供仅用于测试的可控时钟或测试种子；测试时间只在测试配置中生效；
- 增加喂食操作，以及清洁类别中的首版梳毛操作；
- 操作前检查统一账号会话、绑定角色、活动状态和库存；只有清洁类别中的梳毛操作检查锁定稿规定的清洁 CD，喂食和消耗品陪玩不新增道具 CD；
- 支持请求标识幂等；
- 照料类操作遵循锁定稿 Q13：请求发出后先启动配置的猫反馈并显示可回滚的状态预览；服务成功后用完整确认快照替换预览，服务拒绝、取消、超时或无回应时清除预览、停止仍在执行的养宠反馈并轻提示；库存扣除、奖励、进度和其他长期变化仍只以服务确认结果为准；
- 用户操作与猫反馈动作分开配置：首版梳毛暂用伸懒腰反馈，后续可替换表现而不改养成结算；
- 服务向页面返回只读的结算参数，页面仅在显示时按同一公式推算当前值，不写回快照、不轮询服务；长期状态仍只由服务结算；
- 使用仅用于测试的固定食品库存或测试种子，让本阶段可以直接验收喂食；测试种子只在测试配置中生效；
- 养成服务返回完整新快照；
- 养成操作由动作适配器调用已有或新增的动作执行器，兼容开关负责屏蔽冲突的旧自主请求；本阶段不把喂食、清洁或服务状态写入 Cat Mind。

### 用户可见验收

1. 点击喂食后立即显示配置的饱食度临时变化并唤醒 CAT1 播放吃零食反馈；服务成功后替换为确认快照并更新小鱼干库存，服务失败时清除临时变化并恢复原快照；
2. 饱食已满时，按钮不可用或点击后显示原因；
3. 梳毛作为首版清洁操作会改变清洁度并受到锁定稿的清洁 CD 限制；
4. 服务拒绝、取消、超时或无回应时，清除临时状态预览、停止仍在执行的本次喂食/梳毛反馈，恢复服务确认前的长期快照，不扣库存、不发奖励；
5. 快速重复点击只产生一次扣除；小鱼干喂食按配置恢复饱食度并结算该内容自己的进度增量，当前候选 revision 的增量为 `0`；梳毛按独立配置结算；
6. 刷新后显示服务确认过的结果。

### 阶段完成条件

- 喂食和梳毛各有成功、失败、重复请求和服务中断验收；
- 所有长期变化都在本地养成服务完成结算；
- 长期数值、库存、奖励和进度统一由服务确认；猫反馈和状态卡临时变化属于可回滚的请求中表现，不能被监听器或其他模块当成业务成功；只有 `action-confirmed` 事件代表服务已确认。

本阶段严格按锁定稿 Q13 实施：喂食、梳毛等照料类操作先播动画和临时数值变化，失败时回滚并轻提示；探索奖励、解锁和货币等“获得类”操作仍等服务确认后才显示。服务器继续是长期状态、扣除和奖励的唯一权威。CAT2/CAT3 被用户主动照料时先按既有交互切到 CAT1；请求失败只回滚临时业务预览和仍在运行的反馈动作，不强行把用户已经唤醒的视觉形态切回睡眠层。

- 侧轨只负责总览、任务、来信、背包、资料等长期模块；具体食物、清洁操作、消耗品玩具和探索地点必须在总览即时操作或对应内容模块中出现，不能把小鱼干、梳毛或某个地点提升成长期导航项；毛线球沿用既有外部互动，服务确认的次数/进度只在任务内容区域显示，不在陪玩内容区复制入口。
- 库存只在相关物品或类别内容中显示；不在账号控件旁重复显示食品数量，也不把库存、任务、来信和解锁项混成一张状态卡。
- 请求处理中保持当前内容区可见并置灰，成功用服务快照更新，失败、取消、超时或上下文失效清除临时表现并回滚。前端只对服务已确认的明确不可用事实做轻量禁用，其他规则仍由服务判断。
- 阶段 5 在内容区增加任务、食品库存、进度和解锁结果；任务列表、领取结果和解锁提示使用独立区域，不把任务占位文案常驻在阶段 4 面板。
- 阶段 6 将毛线球配置为统一任务集合中的每日进度任务项；它由既有毛线球互动产生进度，没有领取按钮，也不在陪玩内容区重复显示。陪玩内容区只显示服务配置的消耗品玩具、库存和处理中状态；没有配置内容时不制造“毛线球”或“消耗品”占位卡。实际毛线球操作沿用现有聊天框最小化和重力 playground 交互，不新增面板点击即触发毛线球反馈的按钮；不能增加未经锁定规则确认的道具 CD。
- 任务页面只使用服务返回的独立任务项和识别元数据。前端不得固定写死“每日任务”“状态任务”等任务类型，也不得按元数据生成分组标题；每个任务独立、同级显示自己的标题、周期/持续范围、条件、进度、奖励、可领取状态和领取结果。每日登录只做后台结算，不显示确认行；毛线球活动进度在同一任务区域以同级、无领取按钮的进度行显示；成长解锁仍是独立结果。
- 阶段 7 在“探索”内容区增加地点、活动中状态、猫窝、纸条、来信和召回；猫离场时内容区和猫窝召回入口仍可用，依赖猫实体的操作统一置灰或隐藏在活动状态下。猫窝召回只结算探索并恢复猫形态，不调用模型返回；用户切回模型、角色切换和模型热重载才使用统一模型返回入口。
- 阶段 8 将生病、赌气等负面状态作为状态区的明确提示和可进入的恢复任务，不以额外常驻按钮污染主面板。

## 9. 阶段 5：每日任务、食品、进度和解锁

### 实施目标

完成第一条可循环的“任务 → 小鱼干 → 当前小鱼干喂食恢复状态；清洁/陪玩/探索/登录按各自规则推动进度 → 解锁”闭环。

### 实施内容

- 增加每日打工任务；
- 用户手动领取任务后发放小鱼干；
- 小鱼干进入食品库存；
- 食品用于喂食；
- 首版当前食物只有小鱼干；小鱼干用于喂食，按候选配置恢复饱食度，当前候选进度增量为 `0`；清洁操作（首版为梳毛）、用户主动陪玩、探索和每日登录按各自独立配置汇入唯一的养成进度字段；不同陪玩类型可以使用独立的次数和基础增量参数，但不能新增第二个进度字段；
- 每日登录完成一次登录结算并按配置增加进度；
- 当前候选提供猫窝信箱和右键撸猫动作两个已有真实消费入口的解锁项及其阈值、可见效果作为可编辑测试配置，用于本阶段验收；撸猫属于客户端表现能力，不写状态、不发奖励，也不复用陪玩租约。后续可在客户端内容和服务能力已适配后通过新 revision 增加解锁，不改变进度存档契约；
- 进度达到配置阈值时，由服务一并记录解锁项、最近存档点并返回解锁结果；
- 增加服务日任务刷新、显式完成、独立领取和每日次数限制；每日打工先执行配置公开的“整理桌面”短操作，完成事务不发奖励，之后的领取事务才按配置发放 1 个小鱼干；毛线球作为同一任务集合中的每日进度项，由既有互动终态推进，不提供领取按钮；
- 本阶段范围覆盖每日任务、食品库存、进度和首批解锁项。

### 用户可见验收

1. 用户能看到当日打工与毛线球两项独立任务，打工未完成时只有完成操作，毛线球只有进度且没有领取操作；
2. 用户完成打工后再手动领取，小鱼干只在领取服务确认后增加 1 个；
3. 小鱼干能用于食品流程；
4. 任务重复领取不会重复发放；
5. 使用小鱼干喂食后食品数量和饱食度在同一服务事务内正确更新，当前候选进度保持不变；其他食物不在本阶段验收；
6. 切换窗口或刷新后，任务和库存保持一致；
7. 达到进度阈值后能看到已解锁内容，刷新后解锁状态仍保留；
8. 每日登录只在当天首次确认时增加一次进度；
9. 同一次操作重试时，解锁记录和奖励仍只有一份。

### 阶段完成条件

- 任务领取、库存、宠物状态在同一结算边界内更新；
- 每日任务产出由服务判定；毛线球按锁定稿每日前 N 次计进度，之后仍可玩但不再计进度；新增消耗品陪玩的每日次数上限由服务判定；两类陪玩都不新增道具 CD；
- 小鱼干、进度和解锁由服务结算并在确认后展示。

### 阶段 5 收口审查（2026-10-17）

按锁定文档第 3.1、3.5、3.7 和第 8 节逐项复核，本阶段闭环成立：

- **任务与食品**：任务首次读取按服务日生成。阶段 5 当时用直接领取占位项验证库存和幂等；当前候选已替换为可配置的每日打工完成动作，服务确认 `active → completed` 后才允许独立领取并增加食品库存。同一任务周期换用新幂等键不能重复完成或重复领取。
- **条件边界**：阶段 5 的无条件占位任务只属于历史过渡，不能继续作为当前产品入口。正式配置中的目录任务必须恰好声明一种推进来源：受限 `completion_action` 或受限 `progress_source`；客户端只呈现服务公开的完成动作，不接受脚本、URL 或客户端奖励规则。
- **进度来源**：锁定文档约束的是喂食类别可以贡献进度，不要求每个食品都提供正进度。当前数值草案把小鱼干设为 `progress_delta = 0`，正式服务保留非负配置字段并在同一事务结算；其他食品若进入后续 revision，可以各自配置进度。
- **进度边界**：饱食度、精力、清洁度和心情保持 `0–100`；养成进度是可配置的非负累计值，不套用状态值的 100 上限，因此当前配置的解锁阈值可以按累计进度到达。
- **解锁**：进度达到可配置阈值后服务记录解锁项和 `unlock_checkpoint`，完整快照返回后页面显示已解锁内容；旧 SQLite 快照可迁移。
- **幂等与配置校验**：任务领取和每日登录的幂等请求哈希包含服务日，跨服务日复用同一键会明确拒绝；已领取任务的拒绝读取仍持久化时间结算和任务日刷新；任务奖励数量必须为正数，避免出现“可领取但无法发放”的配置。
- **失败边界**：领取、每日登录和加载没有前端乐观奖励；失败、超时或上下文变化不会由前端增加奖励、进度或解锁。阶段 5 没有提供任务取消控件，请求处理中相关入口置灰，迟到响应不会覆盖新账号/角色上下文。
- **数据归属**：阶段 5 当时由本地养成服务持有账号、绑定、任务、库存、进度、解锁和幂等结果；当前这些职责已迁到正式 PetCare 独立服务。Web 与 NEKO-PC 继续复用同一接口，PC preload/bridge、Cat Mind 和模型动作链不承担任务规则。
- **周期边界**：当前正式契约只按可配置服务日刷新 `reset_policy=daily` 项；其他周期不能据此宣称已支持。任务身份由 `task_id + cycle_key` 精确确定，完成、领取和恢复操作都必须回传原周期；快照只以 `tasks.items` 返回规范记录，不再维护 `daily/state` 兼容副本。

阶段 5 的任务、库存、幂等和解锁链已闭合；小鱼干只恢复饱食度是当前候选数值，不构成锁定规则差异。阶段 6 的陪玩次数、真实回应和进度事件，以及阶段 7 的探索事件仍不能用占位按钮代替。

### 阶段 5 任务区域体验修订（2026-10-17）

阶段 5 收口后按实际用户操作复核任务区域，确认原先的“查看任务”二次点击、分组层级和低对比度状态文案会把读取动作误认为业务操作，也会让可领取按钮看起来像不可用控件。本次只调整任务区域的交互和表现，不改变任务、奖励、每日登录或服务结算契约：

- 面板打开且服务状态已就绪时自动读取任务；读取完成后所有任务项直接在同一列表中平铺，移除刷新按钮；读取失败只显示错误状态，关闭后重新打开面板自动重试。任务读取期间不阻塞喂食、清洁、陪玩等独立业务操作。
- 任务项始终是同级独立卡片；只有领取按钮可点击，不显示分组标题、每日登录确认行或“当前任务没有可领取奖励”等常驻状态文案。可领取、已领取、未完成、领取中使用明确文字，避免只依赖透明度区分状态。
- 删除没有业务含义的“可领取”和“奖励待配置”默认占位；任务没有说明或奖励时不制造假信息。浅色主题补齐任务日期、进度和领取控件的前景/背景对比度，并为可操作按钮提供键盘焦点轮廓。
- 毛线球作为服务任务集合中的每日进度项，在任务列表中以与其他任务相同的卡片样式显示；它没有领取按钮，进度只由既有互动终态更新，也不在陪玩区域增加毛线球按钮或重复卡片。

验收：前端定向回归 53 项通过；任务自动同步、每日登录确认、任务领取成功/失败、任务加载期间照料操作可用、稀疏任务不生成占位文案均有测试覆盖。桌面宿主最终视觉仍需在已登录且绑定角色的真实 PC 窗口复核，当前浏览器检查未取得登录态。



### 阶段 6 实施前准备记录（2026-10-17）

阶段 6 的陪玩动作和养宠面板职责必须分开。锁定文档规定的是“用户主动拖或点毛线球，并且猫有回应，才算一次陪玩”；面板不是一个点击即播放毛线球反馈的新增按钮。聊天框最小化后的毛线球、重力猫猫模式中的毛线球，以及任务页面中显示的毛线球活动进度，都沿用同一套陪玩业务契约。面板只展示服务确认的任务进度、消耗品库存、处理中状态和结果，不直接把点击转换成陪玩成功，也不在陪玩内容区重复放置一个没有操作意义的毛线球入口。

#### 阶段 6 任务展示与任务契约修订（2026-10-17）

此前把任务区标题、毛线球次数、每日登录和解锁内容放在同一张卡里，或者把“每日任务/状态任务”写成前端固定栏目，都会让任务的周期、领取和完成条件互相污染。本阶段采用以下收口契约：

1. 任务是服务返回的独立记录。任务项拥有稳定 `task_id`，并独立保存标题、说明、周期/持续范围、条件、进度、目标、奖励、状态、可领取标记、进度来源、领取时间和幂等结果。一个任务的刷新、失败、领取或重复请求不能改变另一个任务。
2. 首版任务不提供分组契约，页面按服务返回的独立任务同级平铺显示；服务配置对未消费的 `group_id`、`group_label` 关闭接受，避免运维误以为它们会影响结算或界面。当前正式服务配置只接受 `daily` 的 `reset_policy` 并按服务日刷新；`weekly`、`monthly` 等周期须先补齐周期键、跨周期迁移和幂等边界，再扩展配置 schema，不能让客户端自行解释。
3. `daily_login` 是登录结算记录，不在页面显示确认行；成长解锁是进度结果，不是任务项；毛线球是任务集合中的每日进度项，不提供领取按钮。它与领取小鱼干的每日任务同级显示，进度只能由服务确认的既有用户互动更新，不能由打开面板或点击任务项伪造。
4. 毛线球任务进度只由既有用户互动产生：用户完成聊天框或后续具备独立猫回应终态的毛线球操作，适配层提交统一终态，服务确认后再更新任务页面的毛线球进度。打开任务页、点击进度项或点击陪玩类别都不能增加次数。
5. 养宠面板的陪玩内容区只显示服务配置的消耗品内容及库存。当前没有消耗品配置时，不额外显示毛线球卡片、不显示“毛线球/消耗品”混合占位，也不因为任务页显示毛线球进度而复制一份陪玩入口。

本修订不改变锁定文档关于毛线球“用户主动且猫有回应才算陪玩”、前 N 次计入进度、之后仍可玩但不再计进度的规则；它只明确任务页面、陪玩内容区和服务任务契约的边界。

本地镜像按统一账号会话、规范来源、活动 ID、完成终态和服务事务校验陪玩结算，并以 `content_id + activity_id` 保存幂等回执；代码中的 30 秒窗口统一称为“本地陪玩关联窗（非授权）”，只把用户意图与动作终态关联。浏览器可读取后再回传的一次性票据不能证明猫真实回应，因此不能把本地关联窗包装成安全凭据。正式服务使用独立的短期陪玩动作租约（play action lease），绑定账号、安装、宠物、角色、内容、活动 ID 和有效期，并与历史业务回执分离；受信桌面桥若可用只作为额外证据，不改变服务端次数、库存、幂等和结算权威。

任务目录在同一服务日发生删除或禁用时，服务保留已有记录用于审计，但立即标记为不可领取；下一服务日不再物化该记录。重新启用同一 `task_id` 时只恢复配置元数据，不撤销已经确认的领取结果。客户端只能消费服务返回的任务状态，不能自行把删除的任务恢复为可领取。

现有项目中，聊天框毛线球已有用户拖动事件，动作层也已有毛线球播放和完成/取消终态；CAT1 Playground 现在为用户短点击增加独立猫回应：只有 Playground 活动仍有效、猫和毛线球实体存在、猫未被用户拖动，并且已施加可见扑球速度后，才发送 `neko:pet-care:yarn-click-response` 的完成事实。原有 `neko:idle-cat1-playground-yarn-activate` 恢复聊天语义本身不结算，最小化聊天框的静止点击仍保持原有返回模型行为。养宠动作适配层不读取 Cat Mind 的五维、阈值或自主选择结果；任何来源都不能把原始点击事件冒充猫已回应。`cat1-journey-local` 和没有本地陪玩关联窗的 Cat Mind 自主玩球继续排除。逗猫棒由养宠面板以具体消耗品内容提供入口，调用独立的 `PlayTeaserWandAction`（`play_teaser_wand`）及终态回调。

统一事件链固定为：

```text
已有毛线球交互的用户拖动/点击
→ 记录 source、activity_id 和 user_initiated
→ 现有动作执行器开始
→ 记录 cat_responded
→ 完成 / 取消 / 无回应 / 超时终态
→ 只有 user_initiated + cat_responded + done 才提交服务结算
→ 面板刷新服务确认的次数、进度和状态
```

`source` 只用于区分事件来源和排除自动行为，不为聊天框、重力 playground 和面板建立三套业务规则。面板不新增毛线球直接触发回调；如果后续需要从面板引导用户使用已有毛线球，也只能定位或提示已有交互，不能把一次面板点击直接视为猫已回应。

阶段 6 的代码边界和顺序如下：

1. 在动作层统一用户意图、动作开始和终态适配，确保自动来源不会单独进入养宠结算；聊天框拖球只接受 `chat_yarn_drag_completed` 证据，Playground 点击只接受 `neko:pet-care:yarn-click-response` 的完成事实，原始 activate 事件不计数；`cat1-journey-local` 在没有明确活动标识前保持排除；
2. 再在本地养成服务增加可配置的陪玩内容、服务日次数、毛线球前 N 次进度、消耗品每日次数、状态变化和幂等结算；不增加第二个进度字段，也不新增道具 CD；
3. 扩展现有养宠操作契约，让服务只在统一终态确认后更新陪玩次数、进度、精力、清洁度和消耗品库存；失败、取消、无回应、超时和重复请求保持安全状态；
4. 最后更新面板：任务内容区域直接平铺服务返回的任务项，领取小鱼干的任务显示领取操作，毛线球任务显示服务确认的每日进度但不显示领取按钮；陪玩内容区只显示服务返回的消耗品内容、库存和处理中/结果状态，点击逗猫棒后走 `play_teaser_wand` 独立表现终态，不把面板按钮当作毛线球动作源；
5. 用聊天框毛线球、重力 playground、自动 Cat Mind 玩球、无回应、取消、超时、次数边界、消耗品库存和刷新恢复逐项验收。

## 10. 阶段 6：用户主动陪玩

### 实施目标

在阶段 3 已建立的冲突型 Cat Mind 自主请求门控下，把用户主动陪玩和玩具使用接到独立动作执行器，并形成可结算的业务事件；用户拖动毛线球触发的 Cat Mind 回应仍属于用户活动链，不能与纯自主请求混为一谈；不改变现有 Cat Mind 对普通猫行为的其他职责。

### 实施内容

- 毛线球复用现有 `cat1_play_yarn` 动作；逗猫棒使用独立 `play_teaser_wand` 动作，清洁类别中的梳毛操作暂用伸懒腰反馈；后续替换具体反馈表现不改变业务类别、用户操作、物品消耗和养成结算；其他当前缺少统一终态的动作，由首版补齐独立执行器或基础表现后再接入适配器；
- 逗猫棒是消耗品，首版正常来源为探索掉落和赌气恢复任务的保证获取路径；管理员发放或测试种子只用于隔离开发／验收，不属于用户正常产出链。服务确认使用成功后扣除一次；
- 记录用户发起、猫真实回应、动作完成或取消；
- 只有用户主动且猫有真实回应才提交陪玩结算；
- 猫自主发起的玩耍不计入养成陪玩进度；用户主动毛线球每日前 N 次按自身次数/基础增量配置汇入唯一养成进度，之后仍可玩但不再给进度；消耗品陪玩使用独立的次数和基础增量配置并受服务端每日次数上限约束，不互相污染；
- 养宠面板的陪玩内容区不新增毛线球按钮，也不重复放置毛线球卡片：真实毛线球操作发生在现有聊天框拖动和 CAT1 Playground 点击中；聊天框来源通过统一适配器回传动作终态，Playground 只在猫已做出可见回应后回传独立完成事实。服务确认的毛线球任务进度直接随统一任务集合返回，与其他任务同级显示，不进入陪玩内容项；只有配置为可领取的任务才显示领取操作。服务配置返回的逗猫棒等消耗品作为独立内容项显示库存和次数，点击后调用 `requestCat1PlayTeaserWand` 专用表现桥，仍需等动作终态和服务确认后才扣除；
- 有现成能力的动作复用现有动画、动作和终态事件，新增动作沿用相同的终态契约。

### 用户可见验收

1. 用户通过聊天框主动拖动毛线球，或在 CAT1 Playground 点击毛线球并得到猫的可见扑球回应后，养宠面板显示服务确认的陪玩结果；原始点击／activate 事件、碰撞或最小化聊天框的静止点击不能单独增加次数；
2. 用户使用逗猫棒时，库存、动作终态和陪玩结算一致；
3. 猫没有回应或动作被取消时，不增加养成进度，也不扣除逗猫棒；
4. 服务拒绝或重复提交时，逗猫棒只扣除一次或不扣除；
5. 毛线球前 N 次能按自身配置结算进度，之后仍可玩但不再计进度；消耗品陪玩受库存数量和服务端每日次数上限限制；两者都不新增道具 CD；
6. 退出登录后普通猫恢复原有行为；
7. 刷新后从服务恢复陪玩库存和各类进度。

### 阶段完成条件

- 手动陪玩由养宠适配器调用已有或新增的动作执行器；
- 动作执行器保持独立，养宠只接收统一终态事件；
- 所有陪玩成功、取消、无回应和重复请求场景均可验收；
- 旧自主触发暂时停用后，现有动作能力仍由动作执行器提供。

### 阶段 6 执行记录（2026-10-17）

- **面板结果**：服务返回统一的 `tasks.items` 和陪玩动作配置；页面在任务内容区域以与其他任务相同的卡片样式显示毛线球任务项的确认进度，且没有领取或直接触发动作的按钮；`play_actions` 只提供陪玩动作、次数限制、库存和反馈配置，不承担任务展示。陪玩内容区按配置动态显示带库存的消耗品内容项。消耗品点击后保持处理中状态，只有独立表现终态完成且服务确认才更新库存/次数。陪玩开始前发出的旧任务读取会被代次门控丢弃，不能把服务刚确认的毛线球进度覆盖回旧值。服务失败不会乐观增加进度或扣库存，面板固定内容区不会因等待或结束而跳变；陪玩等待或结算期间，喂食、清洁、任务领取和其他陪玩入口保持置灰，避免多个用户动作争用同一只猫。
- **旧快照收口**：任务面板打开时始终读取任务接口，不因宠物快照已有旧 `tasks` 字段而跳过刷新；服务在同一服务日把新增配置任务补入已有 `tasks.items`，因此旧账号无需等到次日即可看到毛线球任务。若用户在账号/角色绑定尚未完成时已打开面板，绑定完成后也会自动补做任务读取，不要求用户关闭后重新打开。

- **已收口**：毛线球任务和小鱼干任务都作为 `tasks.items` 的独立同级记录返回；毛线球只有服务确认进度，没有领取按钮；每日前 N 次给进度，之后仍可玩但不再给进度。
- **已收口**：锁定稿“拖或点毛线球”已分别由聊天框有效拖球和 CAT1 Playground 点击后的独立猫回应事实覆盖；原始点击、activate、碰撞和最小化聊天框静止点击仍不能冒充业务成功。
- **验证边界**：2026-10-18 重启完整本地后端后，`GET /health` 实际返回 200；当前绑定角色的任务接口实际返回两条同级任务：“领取小鱼干”和“毛线球 0/3”。本地回归已覆盖 CAT1 唤醒适配、内容来源白名单、Playground 点击回应和活动 ID 规范化去重。真实 macOS 窗口端到端和正式社区服务器仍未验证；`user_initiated/cat_responded` 仍来自客户端事件，且前端尚未把 Cat Mind `requestId/runId` 与服务端陪玩动作租约强关联。正式服务器阶段使用一次性短期陪玩动作租约绑定账号会话、安装、宠物、角色、内容、活动 ID 和有效期，并把终态与对应动作请求关联；它保护次数、库存、奖励和重放边界，但不宣称能证明开放客户端上的真人意图或动画真实性。

因此阶段 6 的交付状态记录为：**本地可结算陪玩路径完成；正式服务仍需把客户端终态替换或加固为受信动作证明**。

## 11. 阶段 7：单探索地、猫离场和统一召回

### 实施目标

完成首版最核心的跨会话活动，让用户能看见猫出发、离场、来信、回家和召回。

### 实施内容

- 增加一个探索地点；
- 开始探索前检查饱食、精力、清洁、负面状态和当前活动；心情在出发时保存快照并用于收益计算，首版不把心情单独作为探索前置条件；
- 服务先创建活动并扣除消耗；
- 播放出发动作，完成后隐藏猫形象；
- 清理在跑动作、定时器和尾回调；
- 切换为猫窝命中区域和探索期间素材；素材由探索表现适配器独立管理，不注册为 `cat1/cat2/cat3` 形态，也不交给 Cat Mind 管理。宠物形态通用素材统一放在 `static/assets/neko-idle/`，当前本地验收使用其中的透明 PNG `static/assets/neko-idle/cat-bad.png`，后续可直接替换资源而不改变活动契约；
- 素材切换只发生在服务确认探索活动、出发动作完成并进入离场状态之后。正常完成或召回完成后恢复原猫形态素材和命中区域；素材切换失败不能改变服务活动和结算结果；
- NEKO-PC 只接收页面提供的窗口/命中区域和输入转发变化，不保存探索状态、不判断活动、不执行奖励或结算；
- 展示倒计时纸条和随机来信；
- 提供仅用于验收的可控测试时钟，缩短探索等待；测试时钟不改变正式奖励公式；
- 探索期间由养成活动状态门控所有依赖猫实体的输出，包括旧自主触发、journey、playground、重力/窗口感知、贴边探头、移动、音效、悬停、拖拽、喂食、清洁操作（首版为梳毛）、陪玩及延迟尾回调；这不是 Cat Mind 的业务判断，也不能依赖 Cat Mind 重新计算。猫窝、纸条、来信、探索面板和统一返回入口继续可用；
- 正常完成时由服务结算，恢复猫在场并播放回家动画；
- 用户切回模型时，经现有统一返回入口发起强制召回；
- 正常完成走探索完成接口，强制召回走召回接口；两者共用活动幂等和奖励规则；
- 以 `neko:cat-return-commit` 作为一次召回结算挂点，`neko:cat-return-complete` 只负责表现收尾；
- 召回请求失败或超时可以重试；首次被服务接受时记录服务时间和幂等结果，重试沿用同一结果，不按迟到响应时间重新计算；成功后向用户显示确认的结算信息；
- 奖励和进度只在服务确认后展示。

首版先确定以下可调的奖励语义：正常探索完成按完整时长结算并享受完整探索加成；强制召回按已完成时间比例结算，未完成部分不享受完整加成；两者都使用出发时保存的心情计算收益。具体掉落数量、概率和加成放入配置，后续可调整。

### 用户可见验收

1. 用户开始探索后，先看到出发动作，然后猫形象离场；
2. 原位置出现猫窝或空坐垫、倒计时纸条；
3. 探索期间所有依赖猫实体的输出均停用，猫窝保留状态和返回入口；
4. 用户能看到来信，收获在探索结算后发放；来信数量按锁定稿随机为 1 到 3 次；
5. 猫窝上有探索状态和召回入口；
6. 正常完成后猫回家并显示确认后的收获；
7. 猫窝召回先走探索服务结算并恢复猫形态；用户切回模型时才复用现有模型返回入口，探索强制召回动画不超过 1 秒；
8. 用户切回模型路径的召回未获服务确认时不显示模型与离场猫窝的重叠状态，也不显示未确认奖励；当前活动门和可重试状态保留，服务确认后才完成模型切换；猫窝面板召回失败同样保留猫窝和重试入口；
9. 迟到的召回或探索响应不会把已经切回模型的用户重新切回猫形态；
10. 正常完成与强制召回的奖励差异符合配置，且都使用出发时的心情；
11. 刷新页面或重启本地服务后，探索仍处于正确阶段；服务暂时不可用时，已有探索保留猫窝和离场状态，恢复后继续读取活动。

### 阶段完成条件

- 出发、进行中、正常完成、强制召回、重复召回和服务失败均有验收；
- 猫离场同时切换动作、探索素材、命中区域和延迟回调，回家后恢复原猫形态素材；
- 探索活动跨页面、跨会话存在；
- 用户切回模型、角色切换和模型热重载时，强制召回沿用既有模型/猫切换逻辑；猫窝面板的“召回猫咪”只走探索召回接口并恢复猫形态。角色切换只有在旧活动已获服务确认召回后才提交新角色；服务端换绑在活动仍进行时返回 `409 binding_blocked_by_active_exploration` 并保留原绑定。

### 阶段 7 执行记录与收口结论（2026-10-18）

**阶段 7 召回分流与任务显示纠错记录（2026-10-18）**

本轮复核发现两处实际错误并已修正：

- 猫窝面板的“召回猫咪”曾直接调用 `appUi.returnFromGoodbye`，只要复用可见 return 容器就会进入 `*-return-click`，把猫窝召回错误地变成模型回归。现在面板召回只提交探索 `recall` 并在服务确认后恢复猫形态；用户切回模型、角色切换和模型热重载才进入统一模型返回链。模型已显示时不会因迟到容器事件再次显示猫窝。
- 小鱼干是独立手动领取任务，不定义进度。服务不再为缺少进度配置的奖励任务合成 `progress: 0`，前端也只在 `progress` 与 `target` 都由服务明确返回且为有限数字时渲染进度；毛线球任务仍显示服务确认的 `0/N`。
- 角色切换和模型热重载加入了探索召回前置检查，避免只覆盖一个模型入口；账号显式退出、外部退出和刷新后的重新登录提示沿用统一会话记录。

**阶段 7 历史生命周期与弹窗单主归属修正（2026-10-18；当前探索终态已改为非模态）**

阶段 7 当时的问题是 `/` 模型宿主页和 `/chat`、`/chat_full` 聊天跟随页都曾初始化完整 `app-pet-care.js`。两个 renderer 会各自读取会话、监听探索终态并创建 `common_dialogs.js` modal；窗口级 `sessionStorage` 不能去重跨窗口提示，最终出现两层弹窗并拦截输入。该探索终态 modal 路径现已移除。

- **单一页面职责**：`app-pet-care.js` 现在发布 `nekoPetCareSurface` 契约。模型宿主页拥有养宠入口、服务读取/写入、模型生命周期协调和用户可见确认；聊天跟随页不创建养宠面板、不刷新养宠快照、不执行探索召回、不显示账号或探索弹窗。聊天框毛线球仍由原有跨窗口动作桥回传到模型宿主页的阶段 6 适配器。
- **单一退出协调器**：`nekoPetCareEntry.ensureExplorationEndedBeforeModelExit()` 是模型/猫形态离开前唯一服务召回协调器。`appUi.returnFromGoodbye`、`showCurrentModel()` 以及角色切换前置都复用它；同一活动的并发退出共享同一个 Promise 和 `pet-exploration-recall-{activity_id}` 幂等键，服务未确认时阻止模型显示，确认后才允许旧形态离开。移除了角色变化路径中独立的直接 fallback POST，避免事件召回、补偿请求和模型显示三条链交叉。
- **入口覆盖**：所有复用 `showCurrentModel()` 的会话返回、麦克风/屏幕恢复、WebSocket 重启和教程恢复路径都经过模型显示总入口；聊天跟随页收到角色广播时直接返回，不参与模型资源和养宠生命周期。猫窝“召回猫咪”仍是独立的猫形态回家操作，不经过该模型退出协调器。
- **当时的 modal 去重**：模型宿主页内确需确认的流程使用串行队列，不再追加多个遮罩；探索完成／召回现已改用非模态短提示，不进入该队列。刷新仍按锁定稿保留服务活动和猫窝／门控，已成功展示的终态不因恢复页面再次提示。

**阶段 7 生命周期再审与可扩展边界（2026-10-18）**

本轮不是给单个入口加补丁，而是把“离开当前猫形态上下文”和“加载新账号/角色上下文”收敛到同一层级的生命周期协调器：

- **退出前置**：模型显示、统一返回、模型热重载、角色显示变化、猫形态主动离开和本地显式退出，都先调用 `ensureExplorationEndedBeforeModelExit()`；账号/会话变化再经 `ensureExplorationEndedBeforeAuthChange()` 串行等待。未获服务确认时不清理旧快照、不清除探索离场展示租约、不提交新角色/登出，并保留可重试错误；服务确认后才释放旧上下文。刷新和 `pageshow` 不属于退出，仍按锁定稿恢复进行中的活动。
- **服务端兜底**：客户端预检之外，`LocalPetCareBindingService.bind()` 在同一事务读取旧宠物快照；活动进行中拒绝换绑并回滚，避免任何迟到的前端请求把探索活动带到新角色。召回或正常完成确认后才能重新绑定。
- **内容目录**：照料面板不再维护小鱼干/梳毛的固定前端列表。服务快照返回的 `care_actions` 是当前内容目录，前端只负责展示类别下的具体内容、库存和服务确认结果；小鱼干当前候选进度为 `0`，未来食物和清洁操作继续通过目录和配置 revision 扩展。
- **层级与职责**：模型宿主页是养宠业务和提示的唯一 owner；聊天跟随页只转发已有互动。生命周期协调器只负责活动终态与上下文切换，探索表现适配器只负责离场/猫窝/纸条/来信，养成服务只负责状态、库存、任务、活动和结算，NEKO-PC 仍只处理窗口、输入和 IPC。

这次再审补充了角色切换失败保留旧活动、显式退出先召回、服务端活动中拒绝换绑以及动态照料目录的回归。外部窗口已经先完成 OAuth 注销、导致旧服务凭证不可用的极端情况只能保留本地探索离场展示租约并等待下一次统一会话恢复，不能伪造“已召回”；正式社区服务器仍需提供同一幂等召回契约。

本轮新增/更新回归：任务小鱼干不显示 `0/0`，毛线球保留 `0/3`；猫窝召回与模型返回事件分流；模型热重载、角色切换和外部退出后重新登录提示有静态/运行时契约覆盖。
本轮按锁定稿 Q11/Q11a、Q13 和本节契约补齐并收口了本地代码闭环，锁定文档未修改。阶段 7 的本地服务、页面契约、活动门控、形态分流、探索离场展示租约和提示去重已经完成；真实 PC 生命周期、视觉时序和长时间活动仍列为阶段 9 的实机验收项，不能用静态契约测试代替。长期状态、活动条件、消耗、心情快照、来信计划、奖励、掉落和幂等结果均由本地养成服务持有；前端只提交开始/完成/召回请求并显示服务确认的快照。

### 历史开发调试工具

阶段 4–7 的本地镜像曾在显式开发开关下提供“三项状态加满”，只用于反复验收满值边界。该调试接口、开关和面板入口已经随本地权威一起删除；正式 PetCare 服务、N.E.K.O 网关和官方客户端都不提供任意填值接口。当前边界测试使用隔离数据库、可控时钟、配置 simulation 和测试夹具，不把调试写入口带入运行时。

- **服务与接口**：本地服务增加可配置单探索地点、`POST /explorations`、按 ID 读取、正常完成、强制召回四条 HTTP 接口；当前活动随宠物快照的 `current_exploration` 返回。开始活动在同一事务中检查当前活动、饱食度、精力、清洁度和生病状态，保存出发心情并扣除消耗；完成按完整时长结算，召回按服务时间比例结算，掉落按配置和比例处理；重复请求按幂等记录重放，SQLite 重启后仍能读取活动。
- **页面闭环**：养宠面板从服务响应恢复活动 ID、代次、地点、已确认来信和倒计时；面板只显示探索摘要、状态、来信、收获和召回入口，不重复放置桌面猫窝素材。喂食、清洁、陪玩及重复探索入口按活动状态置灰。正常完成和召回都沿用同一结算适配器，奖励、进度和掉落只在完整服务快照确认后显示；失败、超时和旧代次响应保留活动并允许重试。
- **离场与门控**：服务确认后发布探索活动门，门控独立覆盖 Cat Mind、journey、playground、重力/窗口感知、贴边、移动、音效、悬停、拖拽和延迟回调；猫窝、纸条、来信、面板和统一返回入口不被清理广播关闭。活动 ID 与本地门代次用于拒绝旧活动的迟到释放，账号、角色或绑定上下文切换会 fail-closed 清理旧门。服务活动代次只作为跨模块身份传递，不直接当成本地门代次比较。
- **离场表现、素材与召回**：服务确认后先进入独立的 260ms 有界离场表现适配器，完成后才切换通用透明资源 `static/assets/neko-idle/cat-bad.png`；该资源只属于桌面离场期间的猫窝/空坐垫表现，不进入养宠面板的地点卡或来信兜底。适配器同时挂载可撤销的纸条、倒计时和带可配置图片的来信气泡，不注册新猫形态、不调用 Cat Mind、不参与结算。素材和原命中区域由同一表现适配器恢复。猫窝面板的“召回猫咪”只调用探索 recall 接口，服务确认后恢复猫形态；模型已经显示或当前处于模型形态时，迟到的返回容器状态不能再次显示猫窝或召回猫。用户切回模型、角色切换和模型热重载才接入 `appUi.returnFromGoodbye`，由养成适配器在模型返回提交点发起服务召回；只有重新进入猫形态后才恢复猫窝表现。没有新增模型按钮，也没有把素材或规则交给 Cat Mind。
- **生命周期收口**：角色、模型或猫形态切换前先进入上述统一召回协调器；模式适配器在收到显示角色变化时只发出 context-change-request，保持旧探索门和 Cat Mind 屏蔽，直到 owner 确认服务召回后才提交新 context。若切换让原返回容器暂时不可见，协调器仍以活动 ID、账号会话代次和同一幂等键完成一次服务请求，不能把旧活动带到新角色。完成请求与主动召回竞争时由服务端事务和活动幂等结果决定终态：若完成先获服务确认，完成终态和完整奖励保持最终状态；完成未确认且活动仍在进行时，主动召回沿用同一活动幂等契约重试。刷新或 `pageshow` 时，服务短暂不可用则用 session-scoped 探索离场展示租约保留猫窝、倒计时和门控；该租约只含已确认离场的表现事实，不含状态、库存、奖励且不开放写操作。服务端权威事实始终称为探索活动记录；服务恢复后必须重新读取权威快照。刷新不伪造召回，也不把跨会话活动提前结束。

- **统一召回时长和结果提示**：普通模型返回沿用既有过渡锁；只有用户切回模型时的探索强制召回接入模型返回事件链并使用探索专用的不超过 900ms 过渡上限，猫窝面板召回不触发模型过渡。首次确认召回、正常完成或此前未成功展示的终态使用非模态短提示，不能用全窗确认框阻塞导航；正常完成只显示“探索已完成，收获：”和实际收获，召回显示“猫已召回”及存在时的实际收获，不出现服务实现、机器字段或异常正文。终态提示按账号和探索活动 ID 在设备本地持久去重，同一活动从 `completed`、`recalled` 或 `returned` 变化也只提示一次；模型／角色／退出前置召回可抑制中间终态提示，由最终会话提示统一说明。显式退出、服务确认的外部退出以及刷新后重新确认的退出，均通过同一会话提示记录在下一次登录时说明；网络失败不伪造退出成功。没有服务确认时不伪造收获。
- **探索中来信读取**：严格遵循锁定稿 Q4，客户端不做周期轮询。阶段 7 原实现只在打开探索面板或用户主动触发时读取一次；当前正式链路还可按服务返回的 `next_letter_at` 安排一次状态读取，同一提示不能因页面反复隐藏／恢复而重复重排，并发读取合并。倒计时只由服务时间戳和本地显示计时更新，完成／召回结算时再读取权威结果。桌面表现适配器只消费已确认的来信，不自行揭示、结算或变更数值。

## 12. 阶段 8：离线结算、负面状态和角色切换

> 本节的会话 invalid→valid 边沿只记录阶段 8 本地 SQLite 镜像当时的过渡实现和验收，不是当前运行契约。该镜像已经迁出；正式服务由第 13–15 节定义的“社区账号校验后账号级 `session/resume` + `last_verified_neko_activity_at`”语义替代，不再要求或保留第二套本地 resume／离线结算实现。

### 实施目标

在不引入 Cat Mind 业务依赖、不给 PC/Web 增加第二份存档的前提下，验证养宠状态可以跨统一账号会话、时间和角色正确恢复。阶段 8 的核心是服务端一次性离线结算，不是前端计算离线时长，也不是增加几个状态按钮。

### 实施内容

- **会话边沿契约**：统一账号适配层向养成服务提供受信的 `account_id`、稳定会话边沿/离线段标识、会话是否从明确失效恢复等信息。`session_generation` 不能直接复用会因 token refresh 变化的 OAuth 计数；网络暂不可用、已保存凭证和普通 token refresh 都不能触发离线结算。前端不得提交离线开始时间、随机种子或结算结果。
- **状态补算**：普通读取仍只按 `last_settled_at` 补算服务配置中的基础状态；`last_settled_at` 是状态游标，不是统一账号会话失效时间。服务同时持久化配置化的 `interaction_index` 和其衰减游标，并在服务事务内由三项状态与互动指数重算心情；阶段 8 的负面判定只使用补算后的快照值和离线段确定性抽样，重复读取不重新随机。前端只显示服务返回的心情，不能自行重算。
- **一次性恢复事务**：只有明确的“会话失效 → 重新有效”边沿触发 `reconcile_on_session_restore`。事务顺序固定为：补算状态 → 按配置执行长期未登录进度回退 → 使用补算后的状态值一次判定生病/赌气 → 生成恢复任务 → 保存可重复读取的结算回执 → 返回完整快照。药品和逗猫棒只在任务成功领取后进入库存；重复请求按离线段幂等，不重复回退、抽样、扣除或发奖。
- **长期未登录回退**：连续 5 天不登录后才允许回退，回退下限为最近解锁存档点；已经解锁的内容永不删除。5 天、回退速度和边界全部配置化，数值草案中的 48 小时、概率公式和每日回退点数只作为可替换本地测试配置。
- **负面状态**：生病与赌气是可并存的独立状态，同一离线段各自最多判定一次；所有状态值达到锁定稿保护条件时不触发。生病只禁止探索，普通清洁、照料、左键返回模型和悬停入口继续可用；赌气通过成功的陪玩恢复，不得擅自扩大成探索禁用。
- **恢复任务和物品**：恢复任务作为服务返回的普通同级任务记录，不增加固定“状态任务”分组或常驻按钮。生病路径由求药任务、领取药品和确认用药清除；赌气路径要求使用该恢复任务 revision 指定的逗猫棒并由猫真实回应，已有合格库存可直接执行，缺少时由任务领取提供保证获取路径。失败、取消、超时不扣物品、不清除状态。任务、奖励、物品 ID 和数量全部配置化。
- **角色和请求边界**：同一账号只有一只宠物；绑定角色继续读取该宠物，其他角色走普通猫。账号、角色、会话和请求代次都参与响应围栏，迟到响应不能覆盖当前页面。角色改名、模型切换和猫档位变化不改变稳定绑定关系。
- **探索和断线**：非探索状态断线时停止养成写入，恢复后重读服务结果；活动探索按阶段 7/8 的探索离场展示租约继续保持离场并恢复猫窝、纸条和来信。主动退出、账号切换、角色切换等会导致离开猫形态的链路统一走探索结束/召回确认，不能由各模块分别处理。模型形态和猫形态始终互斥，猫窝召回不进入模型返回链。
- **架构边界**：养成服务持有状态、规则、库存、任务、奖励、探索和结算回执；NEKO-PC 只处理窗口、输入、命中区域和 IPC；Cat Mind 不保存养成五维、负面状态或长期结算，只接收服务按配置 revision 派生、带有效期的只读行为偏置。偏置缺失或失效时立即撤回，不影响普通猫短期五维。阶段 8 记录本地过渡闭环；阶段 10 用账号级 resume 与正式活动 sequence 取代本地 session invalid→valid 离线边沿。

### 用户可见验收

1. 修改测试时间或等待离线窗口后重新登录，状态正确补算；
2. 同一离线段重复登录，不重复触发负面状态；
3. 生病时出现求药任务，完成任务领取药品，使用药品并确认扣除后恢复；
4. 赌气时出现取得逗猫棒的恢复路径，取得后完成猫真实回应的逗猫棒陪玩，服务确认扣除后恢复；
5. 生病期间探索入口不可用；
6. 切换到绑定角色继续读取账号唯一宠物，切换到其他角色按普通猫处理，迟到响应不会覆盖当前页面；
7. 绑定角色改名、换模型或换猫档位后仍通过原稳定角色标识读取同一只宠物；
8. 非探索状态断线时普通猫和统一返回模型可用，养成写操作停止；已有探索仍保持猫窝和离场状态；
9. 恢复后重新读取确认结果，探索状态不被错误结束；
10. 连续 5 天不登录后，进度最多退到最近存档点，已解锁内容仍可用。

### 阶段完成条件

- 有可控的服务端时间和会话边沿测试方式，能够区分普通读取、网络暂不可用和明确失效后恢复；
- 状态补算、长期回退、负面判定、恢复任务、物品使用和结算回执可重复验证；
- 同一离线段重复读取、刷新、重新登录和重试都不改变结果；
- 账号、角色、会话和请求代次均参与响应校验；
- 断线期间仍只有一份可写存档，恢复后只重读服务确认结果；
- 本阶段不修改锁定文档，不把 Cat Mind 或 PC 变成养成业务依赖。

### 实施顺序与阶段性收口

1. **会话适配和边沿契约**：先补齐统一账号适配返回值，明确 invalid→valid、网络不可用、token refresh 和显式退出的区别；完成后只验会话边沿，不执行负面结算。
2. **存储和一次性结算回执**：增加离线段游标/回执和迁移，保证状态补算、回退、抽样和任务物化在服务事务内幂等；完成后验重复请求和失败重试。
3. **负面状态、回退和恢复任务**：实现配置驱动的补算、回退、生病/赌气判定、同级任务、药品/逗猫棒领取与使用；完成后逐项验收生病、赌气、并存和保护条件。
4. **角色、探索和断线恢复**：接入角色/请求代次围栏、活动探索恢复和统一退出链；完成后验角色切换、刷新、断线、召回和迟到响应。
5. **前端确认结果接入**：显示服务确认的状态和同级任务，提供服务确认的恢复操作，保持普通照料、返回模型和悬停入口；完成后验 Web/PC 共用契约且不写本地存档。
6. **阶段 8 总验收**：按本节 10 项用户可见验收和服务幂等矩阵复跑，并在本节记录修改内容、测试结果、失败路径、未验证内容和剩余风险。

- **验证**：覆盖首次会话、同会话读取、重复新会话、显式退出时间起点、事务回退和旧库迁移。

#### 步骤 3：回退、负面状态和恢复任务（已完成）

- **修改内容**：实现配置驱动的连续未登录回退、最近解锁存档点下限、生病/赌气独立一次判定、同段确定性抽样和普通同级任务记录；增加任务领取后的药品/逗猫棒发放、服务确认的物品使用和成功逗猫棒陪玩清除赌气。
- **目标核对**：生病和赌气可同时存在；生病只阻止探索，普通喂食、清洁、陪玩和左键返回继续可用；恢复物品不在判定时直接写入库存；失败、取消、超时和无回应不扣物品、不清状态、不发奖励。所有阈值、概率、回退速度、任务和物品均来自可编辑配置。
- **验证**：覆盖保护状态不触发、两种状态并存、回退不越过 `unlock_checkpoint`、任务领取幂等、物品使用幂等、生病探索拒绝及赌气成功陪玩恢复；补充验证恢复任务在“领取 → 使用/完成 → 使用新幂等键再次领取”时仍拒绝重复发放，并验证互动指数按服务配置衰减、动作成功后增加且重开服务仍读取同一心情结果。

#### 步骤 4：角色、探索和断线恢复（已完成）

- **写入竞态**：各写入和依赖当前会话的读取方法在 SQLite 事务内再次校验不透明 `session_id`；如果路由预检后会话已注销或被新会话替换，服务返回 `session_stale`（409），不提交旧请求的状态、任务、库存或探索变化。

## 13. 阶段 9：本地首版完整验收

### 实施前准备（2026-10-18）

阶段 9 的性质是本地首版总验收和必要的小修收口，不新增产品规则、不新增一个与锁定稿无关的业务层，也不提前接入正式社区服务器。验收目标是证明阶段 0–8 已落地的同一套服务契约能够在真实用户路径中完成一次可恢复的养宠循环，并且失败、退出、刷新和跨端切换不会污染普通猫或账号数据。

本阶段以《宠物养成系统方案（修订稿）》为目标，以阶段 0–8 的实现、测试和记录为事实依据；数值草案只提供可替换测试配置。发现实现与锁定目标不一致时，先记录差异并做最小范围修正，不能用本阶段验收反向修改锁定文档或扩大首版范围。

### 范围与排除项

必须验收的范围：

- N.E.K.O 统一账号会话、账号唯一宠物、服务确认的绑定角色，以及未登录/非绑定角色的普通猫回退；
- 基于 `last_settled_at` 的读取和操作补算、每日首次登录一次性结算、基础状态和可配置的独立任务项；
- 每日任务手动领取小鱼干；小鱼干只是当前基础食物，不把它当成喂食类别或任务进度条；
- 喂食、清洁类别中的梳毛、用户主动陪玩和服务确认后的库存/状态/进度变化；毛线球必须来自现有用户拖动或点击互动并得到猫的真实回应，Cat Mind 自主玩耍不得计入；
- 小鱼干在首版只从配置的每日任务奖励获得；喂食小鱼干按候选配置恢复饱食度，当前候选进度增量为 `0`。其他食物和内容仍通过可配置目录扩展，不能把小鱼干或梳毛写成类别本身；
- 单探索地点的出发、猫离场、猫窝和纸条、来信、正常完成、猫窝召回，以及切回模型、角色切换、离开猫形态和统一账号退出的召回链；刷新只恢复服务确认的活动，关闭面板只收起表现；
- 生病、赌气和状态任务的读取、恢复和探索禁用；一次离线段只能由服务结算一次；
- 可配置进度达到阈值后的解锁显示；不把占位名称、资源或阈值固化为产品规则；
- Web 与真实 NEKO-PC 窗口通过同一个养成接口读取同一账号、同一角色和同一宠物快照。PC 只验收窗口、输入、命中区域和 IPC，不保存养成状态或执行结算。

本阶段明确排除：正式社区服务器和生产数据库、跨设备正式部署、正式经济服务及其商店/付费猫粮/社区货币结算、社交/推送/AIGC、洗澡和复杂小游戏，以及把养成数值写进 Cat Mind 或让 Cat Mind 参与结算。锁定设计文档中的社区货币条款由后续正式经济服务和配置版本核对；本地阶段不以它作为已实现功能。阶段 10 的服务、数据库、迁移和部署边界见第 14 节及 Verse ADR。

### 长期运营数据基线

阶段 9 不把“本地能跑”直接等同于“可以长期运营”。验收时先冻结业务逻辑契约，再明确本地镜像的物理结构、正式服务的逻辑结构和迁移方向。所有时间使用服务端 UTC 时间保存；服务日时区、开始小时、数值、概率、次数、CD、奖励和解锁目录都属于带版本的配置，不能从客户端时间或页面文本推导。

#### 阶段 9 本地 SQLite 镜像的历史结构

阶段 9 的实现曾集中在 `services/pet_care/binding_service.py`，当时本地数据库包含以下表。该结构是正式服务迁移输入和差分测试向量，不是当前 N.E.K.O 的运行权威。

| 表 | 当前字段/变量 | 约束和用途 |
| --- | --- | --- |
| `pet_care_accounts` | `account_id`、`pet_id`、`bound_role_id`、`bound_character_uid`、`created_at`、`updated_at` | `account_id` 主键；`pet_id`、`bound_role_id` 唯一；`bound_character_uid` 只是本地角色解析字段，不是跨设备角色主键。一个账号只能有一只宠物 |
| `pet_care_snapshots` | `pet_id`、`account_id`、`bound_role_id`、`schema_version`、`last_settled_at`、`status_values_json`、`negative_status_json`、`inventory_json`、`tasks_json`、`unlocks_json`、`exploration_json`、`cleaning_cooldowns_json`、`activity_counters_json`、`interaction_state_json`、`unlock_checkpoint`、`created_at`、`updated_at` | 一只宠物一行；状态、负面状态、库存、任务、解锁、探索、CD、陪玩次数和互动指数从快照恢复。JSON 读取后必须通过服务端 schema/range 校验 |
| `pet_care_operation_results` | `account_id`、`idempotency_key`、`request_hash`、`result_json`、`created_at` | 主键为 `(account_id, idempotency_key)`；同键同请求返回原结算结果，同键不同请求体拒绝，不能重复扣除或发奖 |
| `pet_care_session_state` | `account_id`、`last_session_id`、`last_valid_at`、`last_invalid_at`、`invalid_session_id`、`last_reconciled_segment_id`、`updated_at` | 保存统一账号会话围栏和离线段去重游标；不保存 OAuth token，不成为第二套登录状态 |
| `pet_care_offline_settlements` | `segment_id`、`account_id`、`pet_id`、`bound_role_id`、`session_id`、`previous_session_id`、`invalid_at`、`valid_at`、`duration_seconds`、`config_version`、`result_json`、`created_at` | `(account_id, segment_id)` 唯一；同一离线段只能结算一次，并保存配置版本和决定结果，读取不能重新抽概率 |
| `pet_care_schema_meta` | `schema_name`、`schema_version`、`migrated_at` | 当前本地存储版本标记；未知未来版本拒绝降级并 fail-closed，非法或半建库结构拒绝读写；当前版本为 `1` |

该历史镜像还建立了 `idx_pet_care_operations_created_at`（操作回执保留/查询入口）和 `idx_pet_care_offline_account_valid_at`（账号离线段查询入口）两个索引。建库和迁移在 SQLite `BEGIN IMMEDIATE` 内串行执行；服务启动先检查已存在的 schema 版本，再执行必要的低版本迁移，不能把未来版本静默改回当前版本。快照读取会将 JSON 中的 `pet_id/account_id/bound_role_id` 与关系表交叉校验，损坏的幂等回执直接 fail-closed，不返回伪造的成功结果。

当前 SQLite 的声明类型也属于契约的一部分：ID、时间、配置版本和 JSON 字段为 `TEXT`；schema/检查点/数量等离散值为 `INTEGER`；离线时长为 `REAL`。正式服务迁移时，ID 仍保持不透明字符串或 UUID，数量、状态、进度和版本使用有范围约束的整数，时间统一为带时区的 UTC 时间；不能因为换数据库而把数量、状态或进度改成浮点数。

快照中的逻辑变量必须保持以下含义：`status_values.satiety/energy/cleanliness/mood` 为受配置约束的整数状态，`status_values.progress` 为非负累计进度；`interaction_index` 和 `interaction_last_settled_at` 属于养成服务自己的互动指标；`negative_status.sick/sulk` 各自有独立状态和恢复任务；`inventory` 按 `item_id` 保存数量；`tasks` 按独立 `task_id` 和服务周期保存进度、目标、奖励、状态和领取幂等信息；`exploration` 保存地点、活动 ID、状态、服务开始时间、时长、消耗、来信计划、随机结果和结算结果；`unlock_checkpoint` 只表示进度回退下限，已解锁内容不能被删除。

探索的随机种子、完整候选纸条和其他结算输入属于服务私有字段。探索进行中，任何普通快照、任务或上下文读取都只能返回已经达到揭示条件的纸条；活动快照只可额外返回服务计算的下一封可见时间 `next_letter_at`，不得返回未来内容、预选计划、剩余数量、掉落或奖励。只有服务确认活动进入终态后，才返回完整纸条和奖励结果。客户端不能以快照字段推导随机结果或提前展示奖励。

该历史 JSON 快照适合阶段 9 的隔离验收，但不能默认是正式服务的最终查询结构。需要查询、并发更新、审计或独立生命周期管理的内容，正式服务不得继续无限堆进一个 JSON 字段。

#### 阶段 9 历史配置结构和版本要求

阶段 9 本地 `DEFAULT_PET_CARE_SNAPSHOT_CONFIG` 及 `pet_care.json` 的顶层结构当时包含：`schema_version`、`initial_status_values`、`initial_negative_status`、`item_catalog`、`initial_inventory`、`initial_tasks`、`initial_unlocks`、`initial_exploration`、`mood_formula`、`action_progress_mood_multiplier`、`exploration`、`playing`、`service_day`、`task_catalog`、`daily_login`、`offline_settlement`、`unlock_catalog`、`settlement` 和 `care_actions`。`item_catalog` 是库存 ID 的闭合目录，所有初始库存、任务奖励、照料／陪玩消耗、恢复物品和探索掉落都必须解析到该目录；标签和资源仍由各自内容／动作目录负责。这些是历史配置边界和迁移输入，不是第二份产品规则。

每个配置块都必须有明确的 schema、类型、范围和默认处理：状态上限/下限、时间单位、服务日时区、任务周期键、奖励物品、库存数量、探索地点、信件计划、概率和解锁阈值都由服务端校验；客户端只能读取服务返回的目录。配置发布产生不可变的 `config_revision`、内容摘要和服务端 `effective_at`。宠物状态保存结算 revision 游标；当 `last_settled_at` 跨过一个或多个配置生效边界时，服务按时间区间逐段补算，不能用当前 revision 追溯覆盖旧区间。操作按接受时 revision 固定，探索按出发时 revision 固定，任务实例按创建的周期 revision 固定，离线段按协议明确的分段 revision 固定；历史结果不能因当前配置修改而重算。已有库存或历史回执仍引用的 `item_catalog` ID 不能直接删除；必须保留稳定 ID，或先完成可回滚的数据迁移并验证历史回放。配置缺失、激活历史断裂或内容非法时拒绝写入或进入只读安全状态，不能用半套默认值覆盖正式配置。

#### 当前本地结构与长期结构的差异

以下差异必须在阶段 9 报告中单列，不能用“测试通过”掩盖：

- 本地快照把状态、库存、任务、探索和解锁放在 JSON 字段；正式服务需要把可查询、可并发和有独立生命周期的实体拆出；
- 本地操作结果表没有过期/归档字段，正式服务需要定义幂等结果保留期、归档和重复请求查询策略；
- 本地快照没有独立的 `state_version`/乐观锁字段，正式服务需要用行版本或等价事务机制防止并发覆盖；
- 当前没有正式审计表、配置修订表和统一请求关联 ID，阶段 9 先在验收日志中记录，阶段 10 正式服务必须落地；
- 当前 `LocalPetCareBindingService` 同时承载 schema、迁移、规则和存储操作，阶段 9 不做大规模重写，但新增接口不得继续绕过边界；阶段 10 迁移时按应用用例、领域规则和仓储端口拆分。

#### 正式服务的逻辑数据模型

阶段 10 迁移时，保持 API 和业务含义不变，按正式数据库能力拆成以下最小逻辑实体；具体表名由部署项目的迁移规范决定，不能在阶段 9 擅自绑定某个社区仓库。

| 逻辑实体 | 必备字段 | 关键约束 |
| --- | --- | --- |
| 宠物身份 `pets` | `pet_id`、`owner_user_id`、创建时间、可空删除时间 | `owner_user_id` 唯一；显式换绑保持同一 `pet_id`；不把当前角色或可变状态塞进身份行 |
| 官方角色 `pet_roles` | `role_id`、`owner_user_id`、状态、创建／更新时间 | `(owner_user_id, role_id)` 唯一；只登记首次绑定、跨设备关联或换绑涉及的角色 |
| 设备角色别名 `pet_role_device_aliases` | `owner_user_id`、`role_id`、`client_id`、`character_uid`、状态、登记／撤销时间 | `(owner_user_id, client_id, character_uid)` 唯一；以 `(owner_user_id, role_id)` 复合外键保证同账号；读取不得创建；当前 `client_id` 不允许静默跨账号复用 |
| 角色别名退役 `pet_role_alias_retirements` | `owner_user_id`、`client_id`、`character_uid`、固定删除来源、退役时间 | `(owner_user_id, client_id, character_uid)` 永久唯一；可先于角色登记写入；后到绑定 fail-closed |
| 当前绑定 `pet_bindings` | `owner_user_id`、`pet_id`、`role_id`、`binding_revision`、更新时间 | `pet_id` 唯一；以 `(owner_user_id, pet_id/role_id)` 复合外键保证同账号；换绑保持 `pet_id` 并递增 revision |
| 宠物状态 `pet_states` | 四项状态、进度、互动指标、负面状态、`state_version`、`activity_sequence`、`activity_epoch`、解锁存档点、`last_settled_at`、`last_verified_neko_activity_at`、结算 revision、CD／次数游标 | 与宠物一对一；范围约束；账号活动与角色绑定解耦；activity sequence 独立于 `state_version`；跨配置生效点分段补算 |
| 背包 `pet_inventory` | `pet_id`、`item_id`、数量、更新时间 | `(pet_id, item_id)` 唯一；数量不能为负；扣除与操作结算同一事务；来源由不可变 operation receipt、追加 audit、任务／探索／租约记录及其固定配置 revision 组合追溯，不另存重复摘要 |
| 任务实例 `pet_tasks` | `pet_id`、`task_id`、周期键、条件、进度／目标、状态、奖励、配置 revision、领取时间 | `(pet_id, task_id, cycle_key)` 唯一；任务逐条独立；实例固定创建时 revision |
| 每日登录 `pet_daily_logins` | `pet_id`、服务日、活动 sequence、稳定 `settlement_id`、进度结果摘要、配置 revision | `(pet_id, service_day)` 唯一；只由账号活动恢复用例创建，首次绑定在创建宠物的事务内调用同一用例；有实际效果时保存该活动 sequence 的结算标识 |
| 解锁记录 `pet_unlocks` | `pet_id`、`content_id`、来源 revision、解锁时间 | `(pet_id, content_id)` 唯一；进度回退不撤销已解锁内容 |
| 探索活动 `pet_explorations` | 活动 ID、`pet_id`、地点、状态、服务时间、时长、消耗、来信、固定结果、配置 revision、召回时间 | 每宠物最多一个活动探索；完成／召回互斥；出发时固定 revision 和结果 |
| 陪玩租约 `pet_play_leases` | 账号、宠物、角色、安装、活动／动作、签发版本、配置 revision、签发／过期／消费时间、消费操作 | `(owner_user_id, client_id, activity_id)` 唯一；换绑 revision、时限和消费状态共同围栏；完成读取签发 revision 的规则 |
| 操作幂等 `pet_operations` | `owner_user_id`、`pet_id`、受信 `client_id`、来源 `session_epoch`、幂等键、业务请求摘要、类别、可空活动 sequence、状态、领域结果、创建／归档时间 | `(owner_user_id, idempotency_key)` 唯一；无宠物 resume 不建操作行；业务请求摘要纳入服务端解析的 `client_id`、method、path 和规范化 payload，但不纳入可因重新认证变化的 `session_epoch`。同一账号和安装可在新认证代次用原键恢复同一请求，不同安装或不同业务请求冲突；收据保存不可变领域结果，不把可随角色变化的完整响应快照作为无条件重放内容；大结果可归档，最小 key＋hash tombstone 在账号保留期内不得删除或复用 |
| 离线结算 `pet_offline_segments` | `owner_user_id`、`pet_id`、离线段 ID、前后 `activity_sequence`、`activity_request_id`、`source_kind`、稳定 `settlement_id`、数据库时间、`activity_epoch`、配置 revision、负面状态和回退结果摘要 | `(pet_id, previous_sequence, current_sequence)` 唯一；客户端不得自报游标、时间、来源或离线段 ID；同一活动 sequence 产生的每日登录和离线记录共用结算标识，绑定角色快照从这些现有记录组合最近一次有实际效果的摘要，无效果活动不能覆盖它 |
| 服务可用性 `pet_service_state` | 当前 `activity_epoch`、已知维护／故障区间、更新时间 | epoch 单调且变更可审计；候选区间跨越已知 auth／edge／PetCare 故障时不执行回退或负面判定 |
| 配置版本 `pet_care_config_revisions` | schema、revision、hash、状态、服务端 `effective_at`、操作者 | 不可变；激活历史连续可查；当前最多一个 active |
| 审计记录 `pet_audit_events` | 请求 ID、脱敏主体、操作类别、结果、前后版本、配置 revision、服务时间 | 追加写入；不记录 token／proof／角色正文；只用于排查和对账 |

库存、任务、探索、解锁和审计实体可以继续保留扩展 JSON 用于内容配置，但业务主键、数量、状态、时间、版本和唯一性不能只存在不可查询的 JSON 文本中。正式服务应建立 `pet_id`、账号、绑定角色、活动状态、周期键、幂等键和创建/更新时间索引；索引名和具体数据库语法由阶段 10 的部署项目决定。

#### 数据不变量和事务边界

- 账号、宠物、角色 alias 和绑定关系的唯一性及同账号归属必须由数据库复合约束和服务事务共同保证；当前角色不匹配只返回普通猫路径，不创建第二个宠物。设备解绑、换绑账号或安装凭据撤销时，旧 alias 必须被撤销，不能继续解析到宠物。
- 官方换绑锁定宠物并同时校验 `expected_pet_id`、`expected_binding_revision` 和 `expected_state_version`；首次绑定则要求三者同时为空。宠物 ID、`bound_role_id`、绑定版本和状态版本不得互相替代。探索进行中必须先完成或召回，换绑请求不能暗中结束活动。
- 宠物快照和领域读写入口在处理前由服务按 `last_settled_at` 和配置激活历史补算；这类读取触发的补算也必须锁定宠物、推进 `state_version` 并返回新版本，读取请求不要求客户端预先提供版本。只读上下文不触发补算。客户端时间只用于显示，不能提交未来时间、概率或奖励结果。
- 状态变化、库存扣除、任务领取、进度、解锁和探索结算必须在同一业务事务内完成。动作在发出服务请求前取消、无回应或超时，以及服务明确拒绝时，不产生该业务的副作用；独立成功的账号活动以前置后快照作为比较基线。请求已发出后的传输超时属于 unknown outcome，客户端只回滚乐观显示并冻结依赖该版本的新写入；同一账号和安装在当前或重新认证后的有效会话中都使用原幂等键与原业务请求重试，当前状态另读绑定快照。不能把“没收到响应”写成“服务必然回滚”。
- Verse edge 只为当时有效的账号会话签发短 TTL、绑定请求的内部断言；PetCare 在接纳请求时校验断言签名、`exp`、audience 和请求绑定，随后用有界锁等待／事务 deadline 重新检查 `binding_revision`、`state_version`／行版本与幂等收据。到达时已经过 `exp` 的请求不得接纳；在到期前已经接纳的请求即使执行期间跨过 `exp`，仍可在 deadline 内完成，超时则在可变副作用前失败。因此登出后的在途窗口上界是断言剩余 TTL 加有界锁等待／事务时间，而不是实时撤销。独立 PetCare 数据库不能实时读取 Verse 当前 `session_epoch`；登出或换代会阻止新断言，版本、绑定和幂等围栏保证已接纳请求不能覆盖较新的角色或状态。若产品以后要求即时取消在途请求，必须另建 PetCare 可见的撤销围栏，不能在当前方案中假装已经具备。幂等结果超过在线查询期后可以归档，但旧 key 的请求摘要 tombstone 仍须拒绝再次执行。
- 探索开始原子扣除消耗并创建唯一活动；探索进行中拒绝依赖猫实体的操作；正常完成和召回使用同一活动记录但不同终态，奖励按首次服务接受时间计算。
- 当前本地镜像只在统一账号会话 invalid→valid 时生成离线段，每日登录又由任务面板读取触发；二者都与锁定稿的账号级“上线／回来”不等价。正式服务建立一个高内聚的账号活动前置用例：独立 `session/resume` 用它覆盖普通模型、非绑定角色和聊天等没有宠物请求的场景；已通过账号、安装凭据、scope 和请求格式校验的宠物快照，以及由玩家显式发起的新业务请求，也在服务端复用它，因此不需要“先 resume 再调业务”的近期门。上下文发现、既有幂等收据重放和后台／系统结算不产生新的账号活动；探索正常完成、超时重试、故障恢复重放和懒终结等路径按服务端固定用例类型排除，不能相信客户端传来的 `automatic` 或类似布尔值。带 alias 的绑定／业务写收据必须在当前绑定版本、库存等可变前置条件之前查询；命中后只重放不可变领域结果，不再执行活动或业务，使用当前认证与 alias 生成脱敏包络并返回 `snapshot_required=true`，不拼接保存过的旧快照或无锁读取当前快照。客户端需要当前状态时再发起一次合法快照读取；非绑定角色不能获得宠物数值、结算摘要或完整快照。`session/resume` 收据重放仍只使用自身的通用活动包络和 `pet_refresh_required`，不返回 `snapshot_required`。
- 新业务写首次查询收据未命中后，先取得账号／宠物锁并在锁内再次查询；仍未命中才记录账号活动前置步骤执行前的当前版本，随后按独立 `last_settled_at`、数据库时间、`last_verified_neko_activity_at` 和单调 `activity_sequence` 完成普通补算、离线／负面判定及 `(pet_id, service_day)` 每日登录，再把 `expected_state_version` 与此前记录的输入版本比较。并发唯一冲突必须回滚后读取赢家收据，不能执行第二次。首次绑定在账号锁内同样复查幂等键。只有期望版本匹配时才在更新后的内部状态上判断并执行本次业务；不匹配时返回版本冲突，但已验证账号活动仍可提交。业务因满值、CD、库存、活动或其他领域条件被拒绝时同理：这是一份成功的 `activity_result` 加一份被拒绝的 `operation_result`，不是失败操作改变长期数值；以活动前置后的状态为基线，本次业务的库存、奖励、任务、探索、绑定和操作效果必须为零。认证、安装凭据、scope、请求格式或活动前置本身失败时整次请求不提交长期变化。首次绑定在创建宠物的同一事务内部调用该用例，建立首个无惩罚基线和当日唯一登录；绑定失败不留下任何一项。无宠物 `session/resume` 直接按当前事实返回 `needs-binding`，不建宠物、活动基线或操作行，也不承诺以后仍重放该读结果；它与并发首次绑定允许竞态，客户端按返回结果继续绑定或重新读取即可，不为这个无状态读增加账号锁。
- unknown outcome 始终由原账号、原安装使用原幂等键和原业务请求重试。pending key 由本地网关按账号和安装命名空间隔离，页面不读取受信 `client_id`；切换账号或安装后绝不沿用旧 key。`session_epoch` 仍进入当前内部断言的请求绑定摘要并写入来源审计，但不进入持久化的业务请求摘要；两种摘要不能混用。因此同一安装重新认证后可用新断言继续对账原请求，原请求若仍在途，与重试在同一账号／宠物锁下竞争并二次查收据，只会有一个提交；不同安装或不同 payload 使用同键时稳定冲突且不执行。跨认证代次重放旧 `session/resume` 只对账旧活动，不代表新代次已经活动；新认证事件仍以新 key 发起一次 resume。
- 数据库迁移与尚未发生首次账号活动的记录必须让 `last_verified_neko_activity_at` 保持 `NULL`，不得用建宠、迁移、客户端时间或 Verse 通用活动时间回填。首次无可信基线、身份／设备不匹配、顺序无法串行化或区间跨越已知 auth／edge／PetCare 故障 epoch 时不执行离线惩罚；角色不匹配只阻止宠物数据和业务操作，不否定已验证账号活动。回退不低于 `unlock_checkpoint`，已解锁内容不回收。客户端在有状态请求发送前持久化幂等键；同一账号和安装在当前或重新认证后的有效会话中用原键重试，精确重放领域终态，返回投影仍按当前 alias 脱敏。绑定角色快照返回最近一次有实际结算效果的稳定 `settlement_id/summary`，较新的无效果活动不能覆盖它，客户端按 `(account_id, settlement_id)` 持久化展示去重。该摘要只用于恢复当前最新结果，不承诺历史通知队列；权威状态始终来自快照。该行为必须由当前正式服务、客户端及其仓储替身／故障测试共同覆盖时间、故障、响应丢失和多设备场景后才能放量；历史本地镜像只保留差分向量，不作为第二个运行权威。

#### 迁移、备份和恢复

本地镜像继续使用显式 schema 迁移，不删除未知列、不静默覆盖旧数据；每次迁移记录 `schema_version`、配置版本、执行时间和结果。阶段 9 必须用阶段 1/2 的旧库、包含阶段 7 探索字段的库和包含阶段 8 互动/离线字段的库做向前迁移测试，并验证失败时原库可恢复。

阶段 9 的验收夹具必须使用临时数据库、临时配置和临时端口；执行前后保存正式本地存档哈希，验收后逐字节确认未被污染。正式部署前另需确定备份频率、恢复演练、保留期限、RPO/RTO、迁移回滚方式和数据清理策略；这些是阶段 10 的部署门槛，不能在本地验收中假定已满足。

### 阶段 9 历史结构与长期运营依赖方向

阶段 9 本地镜像当时的实现事实是：`main_routers/pet_care_router.py` 负责 HTTP、`services/pet_care/account_session.py` 负责统一账号适配、`services/pet_care/binding_service.py` 同时包含本地 SQLite schema、配置校验、快照转换、规则和事务；前端由 `app-pet-care-api.js`、`app-pet-care-client.js` 和 `app-pet-care.js` 组成；生命周期由 `app-character.js`、`surface-floating-controls.js`、`return-transitions.js` 和 `app-pet-care-mode.js` 协同；猫动作和既有毛线球来源分布在 `static/avatar/avatar-ui-buttons/` 与聊天窗口脚本中。NEKO-PC 只提供窗口、输入和 IPC。该段记录迁移输入，不描述当前正式结构；当前结构见 2.2 和 14.1。

面向长期运营的依赖层次如下，当前正式服务代码已按这一方向落地：

```text
HTTP / WebSocket 适配层
  → 认证与请求上下文适配（只提供统一账号、会话、请求 ID）
  → PetCare 应用用例层
       bind / snapshot / session-resume / care / task / play / exploration / recovery
  → 领域规则层
       补算、状态转移、任务周期、库存、幂等、奖励、解锁、负面状态
  → 仓储端口与事务端口
  → 受控测试替身 或 正式 PostgreSQL 适配器
  → 审计、指标、结构化日志和配置版本记录
```

依赖方向必须保持单向：规则层不能导入 FastAPI、浏览器、Electron、OAuth 私有实现或具体数据库适配器；路由不能直接修改数据库；前端不能计算奖励／概率／绑定；NEKO-PC 不能保存宠物状态；Cat Mind 不能调用养成结算。历史 `LocalPetCareBindingService` 已移除，新增业务只能通过正式应用用例和仓储边界进入。

阶段 9 的代码结构检查还要确认：

- 请求上下文包含账号、当前 `character_uid`、会话 ID、请求 ID和取消/超时信号；账号和角色身份不能从浏览器正文伪造；
- 服务返回稳定的错误码、操作状态、确认快照和配置版本；前端只渲染服务目录与确认结果，不把错误文本、任务周期或内容名称写死成规则；
- 写请求统一携带 `Idempotency-Key`/`idempotency_key`，路径中的 `character_uid` 只用于当前角色解析；业务正文中的账号、`pet_id`、`bound_role_id`、奖励、概率和服务时间均不可信，不能覆盖认证上下文或服务计算结果；
- 统一响应至少能关联 `request_id`、操作状态、`pet_id`、`bound_role_id`、确认快照、结果码和配置版本；奖励、库存、任务、探索和解锁的显示必须能区分预览、处理中、确认和失败；
- 历史本地镜像确认的业务向量、错误码和幂等契约已迁入当前正式服务测试；远端地址、认证适配和存储实现仍由正式边界提供；
- 规则、存储、传输和表现动作各自可单测；动作终态只产生表现事件，`action-confirmed`/结算结果才产生业务成功；
- 失败路径统一经过服务错误包络和前端回滚/保留策略，不在多个模块分别弹窗、分别清理或分别结束探索。

### 长期运营的测试层次

阶段 9 的“完整验收”不是只跑一组接口测试。每一层验证不同事实，上一层通过不能替代下一层：

| 层次 | 目标 | 必须留下的证据 |
| --- | --- | --- |
| 领域/规则单测 | 补算、状态边界、任务周期、心情、概率、奖励、回退和解锁不变量 | 输入配置、服务时间、输出快照和边界结果 |
| 存储/迁移集成测 | 历史 SQLite 镜像的旧库迁移向量，以及当前 PostgreSQL 的事务、唯一约束、正式迁移、回滚、并发冲突和幂等结果 | 迁移前后 schema、行数/唯一性、失败恢复和数据库 hash |
| HTTP 契约测 | 认证、当前角色、错误码、请求摘要、确认快照、缓存控制和接口兼容 | 请求/响应摘要、状态码、`request_id`、错误包络 |
| 浏览器契约测 | API/client 只传输，页面只应用服务确认，代次/取消/回滚正确 | DOM 状态、事件顺序、旧响应被丢弃的记录 |
| 真实 NEKO-PC 验收 | 猫形态入口、窗口、输入、命中区域、模型/猫互斥、探索离场/回家和视觉时序 | 操作录像或截图、窗口日志、IPC 记录；不能用 IAB 代替 |
| 跨端一致性测 | Web 与 PC 使用同一账号和同一服务快照，写入后互相读取 | `account_id`、`pet_id`、`bound_role_id`、状态、任务、库存、探索和解锁逐字段比较 |
| 运行恢复测 | 服务重启、网络中断、超时、重复提交、迁移失败、临时数据库恢复 | 前后快照、幂等结果、日志关联 ID、存档 hash |

阶段 9 可以新增只读验收脚本和临时夹具，但不得把夹具、真实账号、token、正式数据库副本或诊断日志加入普通功能提交。阶段 10 还要补正式数据库并发、负载、备份恢复、滚动迁移和故障注入测试。

### 运营安全、观测和维护要求

阶段 9 至少要为长期运行留下可接入的观测点，即使本地只写结构化测试日志：请求 ID、操作类别、账号/宠物脱敏标识、当前角色校验结果、活动 ID、幂等命中、状态码、耗时、配置版本和结果码。日志不得包含 OAuth token、Cookie、完整请求凭证或完整个人资料。

服务应能区分认证失败、角色不匹配、服务不可用、业务拒绝、幂等重放、并发冲突、迁移失败和内部异常；前端提示只面向用户，诊断细节留在结构化日志。长期部署需要健康检查、依赖检查、慢请求/错误率/幂等冲突/活动卡住/数据库锁等待指标，以及告警和降级策略：养成服务不可用时普通猫继续可用，不能伪造奖励或清除尚未确认的探索。

配置发布必须带版本、来源、校验结果和服务端生效时间；激活历史不可变。`last_settled_at` 跨越配置边界时按各 revision 有效区间分段补算，操作、任务实例和探索固定其采用的 revision，不能通过修改当前配置重算旧区间或旧奖励。内容、激活历史或数值配置校验失败时服务拒绝写入或进入只读安全状态，不使用半套默认值覆盖正式配置。

长期维护还需要明确账号生命周期和运维工具边界：注销只撤销统一会话，不删除宠物；显式换绑、账号删除、数据导出和数据清理必须由正式服务提供可审计的业务用例，不能直接改表。修复脚本必须支持 dry-run、幂等重试、变更前后摘要和审计记录；禁止通过手工 SQL 修改库存、进度、奖励或探索状态来“修数据”。

正式 API 在阶段 10 接入前要先清零已知锁定规则差异，再冻结请求/响应语义、错误码和版本化投影输入。小鱼干 `progress_delta = 0` 属于当前候选配置，不是锁定差异；Cat Mind 版本化只读输入和上述心情收益映射已经进入正式契约。新增字段只能向后兼容地加入，删除或改变含义必须经过迁移和客户端兼容期。

### 前置条件和现状差异

阶段 0–8 的服务和页面契约必须保持可调用；阶段 8 的临时 SQLite、固定时钟、HTTP 矩阵和桌面验收夹具可以复用，但阶段 9 每次执行都要使用隔离的临时存储和可回滚配置，不修改正式本地存档。当前已知仍需补证据的内容包括：真实 PC 的完整探索生命周期和视觉时序、正常完成与强制召回两条分支、自然两小时探索和五天离线边界、刷新恢复／关闭收起／共享猫窝重开，以及模型退出、角色切换和账号退出召回。静态测试或网页端操作不能替代这些桌面验收。

进入阶段 9 验收前必须处理或证明以下已知风险，否则不能标记阶段完成：

- OAuth 外部退出后刷新页面，如果服务尚未确认探索召回，不能直接丢弃探索离场展示租约；重新登录后必须能恢复或明确收口；
- `app-pet-care-mode.js` 发出的 `context-change-request` 必须有唯一 owner 消费，角色切换不能依赖未验证的旁路事件；
- 真实 NEKO-PC 中养宠入口的语义锚点必须可见、可点击并正确避让猫，不能用网页端通过替代桌面证据；
- 伸懒腰、吃零食、玩球等表现动作不能被错误当作锁定稿未列出的 busy 状态，导致入口消失；同时仍要保持移动、拖拽、重力下坠和贴边探头的忙态门控。

### 本地端到端验收顺序

每次验收使用一个临时账号、一个绑定角色、一个非绑定角色和一套临时可编辑配置；所有写请求带唯一幂等键，记录请求、服务响应、快照和数据库前后摘要。

1. **普通猫与入口**：未登录打开猫，行为保持现状且不显示养成入口、数值或操作。登录失败、服务不可用或当前角色不匹配时仍回普通猫；已登录且服务返回 `needs-binding` 时才显示可进入显式绑定的入口。
2. **身份和绑定上下文**：登录统一账号后先只读 `context`；无宠物时返回 `needs-binding`，经显式 bind 才创建账号唯一宠物。已有宠物这里只返回绑定／不匹配上下文，不提前读取完整快照；切换到非绑定角色不能读取或创建第二只宠物。
3. **账号活动、初始快照、每日登录和任务**：现有社区账号状态确认登录后提交 `session/resume` 并重复提交；宠物快照和玩家显式发起的新业务请求也必须在服务端复用同一账号活动前置用例，旧收据重放、探索正常完成、后台探索终态重试／故障恢复重放不得新增活动。覆盖同一长期会话、普通模型、非绑定角色、成功文字／语音／Avatar 交互、assistant turn／speech／settling 排除、业务拒绝、首次绑定和跨服务日，服务每天只产生一次登录结果，猫形态和面板开关不参与判定。绑定 alias 确认后读取同一完整快照；任务逐条同级显示，周期、完成动作、目标和奖励来自服务目录。每日打工先按原 `task_id + cycle_key` 完成，再单独领取小鱼干；毛线球只显示真实回应推进的 `0/3` 且不可领取；每日登录不推进二者。重复完成或领取不重复发放，页面不出现虚假 `0/0` 或前端分组。
4. **照料和主动陪玩**：在服务确认允许时验证喂食、梳毛和真实毛线球互动。依据锁定稿 Q13，照料可先显示反馈和临时数值变化，明确失败时回滚；库存、任务奖励、解锁和探索收益等“获得类”结果只在服务确认后显示。满值、库存为零、梳毛 CD、动作提交前取消／超时、无猫回应和服务明确拒绝均不扣除、不加进度；请求发出后的传输超时先按 unknown outcome 以原幂等键对账。逗猫棒等消耗品由服务确认库存和次数，不能擅自增加道具 CD。
5. **探索两条分支**：从家中出发后猫离场，喂食/清洁/陪玩和所有依赖猫实体的自动输出被活动门控；猫窝、纸条、来信、面板和统一返回入口保持可用。分别验收服务确认的正常完成和按已完成比例结算的强制召回，奖励在确认后才显示。猫窝召回回到猫形态；用户切回模型时只走统一模型返回入口，不同时显示猫实体或猫窝。
6. **生命周期和互斥**：探索中刷新或页面重载只恢复服务确认的同一活动；关闭面板只收起表现，不结束活动、不召回，桌面共享猫窝仍可悬停重开。模型切换、角色切换、离开猫形态和统一账号退出才必须按统一召回契约收口，并显示一次清晰的结果确认；迟到的快照、动作、召回和旧角色响应不能覆盖新代次或已确认终态。模型与猫形态不能同时成为可见实体，猫窝图片只属于离场表现，不进入养宠面板内容。`cat1`、`cat2`、`cat3` 是同一 `pet_id` 的外观/睡眠形态；用户对 `cat2`/`cat3` 进行喂食、梳毛或陪玩等主动操作时切回 `cat1`，服务返回的 `pet_id` 和 `bound_role_id` 必须保持不变，装扮也不能创建第二只宠物；不能把猫窝召回误走模型召回链。
7. **离线和负面状态**：用可控时钟模拟短时、超过回退门槛和超过负面状态门槛的账号无活动段；下一次已确认账号活动（独立 `session/resume`、宠物快照或玩家显式发起的新业务请求）只判定一次，生病/赌气任务独立呈现，生病禁止探索但清洁和恢复操作仍按服务契约可用。重复读取、刷新和服务重启不能重复回退、重掷概率或发放恢复物品；已知 auth／edge／PetCare 故障区间必须 fail-safe 不处罚。
8. **跨端和恢复**：在 Web 与真实 NEKO-PC 中用同一临时账号执行读取和关键写操作，比较服务返回的账号、`pet_id`、`bound_role_id`、状态、库存、任务、探索和解锁字段；停止/重启本地养成服务、断开网络再恢复后，服务记录仍是唯一长期来源，成功结果可恢复，失败请求不留下半次结算。

### 必须通过的失败与边界矩阵

- 未登录、登录失败、统一会话失效、服务不可用、非绑定角色和非法 `character_uid`；
- 状态已满、库存不足、梳毛 CD、探索中照料/陪玩、重复任务领取、重复每日登录、重复消耗品使用；
- 毛线球无回应、用户取消、动作超时、旧自主触发、迟到动作终态和出发时已有动作；
- 重复点击、相同幂等键不同请求体、不同幂等键重复请求、召回迟到和正常完成/召回竞态；
- 切换角色、切换猫形态/模型、刷新、重载、关闭窗口、账号退出、重新登录和本地服务重启；
- 生病/赌气与探索冲突、离线段重复结算、进度回退低于存档点、已解锁内容被回收；
- 所有动作提交前失败都必须验证长期状态完全不变。服务完成独立账号活动前置、随后明确拒绝业务时，以前置完成后的快照为基线，验证该业务的库存、状态增量、任务、进度、探索、奖励和绑定关系没有副作用；认证、格式或活动前置失败则整次请求不提交。请求发出后的传输超时先标记 unknown outcome：原账号、原安装在当前或重新认证后的有效会话中都用原幂等键和原业务请求重试，再验证唯一合法结果，不能把客户端超时直接算作服务回滚。

### 数据隔离、证据和完成门槛

- 阶段 0–9 的历史矩阵使用临时 SQLite；当前正式服务测试使用隔离 PostgreSQL／仓储替身、临时配置、可控时钟和独立服务端口。任何开发账号的现存本地数据都不作为夹具写入目标。
- 每条关键路径保存请求/响应摘要、服务快照前后差异、幂等结果、必要的路由日志、Web 契约结果、真实 PC 截图/操作记录和数据库前后哈希。奖励和解锁必须能从服务记录恢复，不能只凭页面显示判定成功。
- PC 是最终的视觉和点击验收基线；Web 只用于证明同一接口契约，不用 IAB 或静态页面替代桌面操作。现有来源没有真实猫回应终态的操作不计入毛线球陪玩，必须记录为未验证或不适用，不能伪造成功。
- 阶段 9 只有在正常完整循环、两种探索结束分支、失败矩阵、刷新/重启/断线/角色切换、Web-PC 同快照和临时数据恢复全部有证据后才收口。报告分为“已通过、失败路径、未验证内容、剩余风险”，不把阶段 10 正式服务器接入写成完成。

### Electron/NEKO-PC 的实际接入边界

NEKO-PC 当前不是普通的局部 BrowserWindow：`src/window-manager.js` 的 `createPetWindow()` 创建透明、无边框、不可调整大小、覆盖工作区的 Pet 窗口，继续加载 N.E.K.O 共享页面 URL。Windows/macOS 启动时由主进程设置整窗鼠标穿透；Linux/Wayland/X11 则由 `pet-window-lifecycle.js`、原生 input region 和 `pet-input-region-bridge.js` 的 DOM 命中区域协同处理。养宠总览的即时操作应在这个现有透明窗口中围绕猫的语义锚点绘制，不能另开一个 Electron 养宠窗口，也不能把 BrowserWindow 缩成 demo 的固定 1180×730 画布。

实现时遵循以下约束：

- 新浮层根节点保持 `pointer-events: none`；中央猫自由区、装饰背景和透明留白继续穿透桌面及现有猫输入；有实际底色的侧轨、状态卡、模块卡、操作卡及独立按钮分别发布可命中区域并启用 `pointer-events: auto`；
- 养宠页面通过现有 `nekoCatInteractionAnchor` 的 `visible/busy/rect` 得到猫的语义位置，以锚点中心计算 scene 中心和即时操作环，不读取 Live2D/VRM/MMD/PNGTuber manager、容器边界或模型按钮；
- 按 demo 的实际几何把 rail、状态卡、即时操作和模块卡映射到猫锚点周围的固定自由区；每个组件保留猫与可交互卡片的间距，使用单一坐标系和透明留白，不实现空间不足时的响应式折叠、候选位置、左右翻转或底部布局。不能把整块 surface 固定到右侧，也不能只把旧 panel 的左上角贴到 `anchor.rect.right`；
- DOM 结构更新后，养宠控件使用 `data-neko-pet-care-interactive`，有底色但不一定可操作的界面块使用 `data-neko-pet-care-input-surface`，二者进入 PC 现有 input-region 白名单；根节点、布局包装层、scene 和猫区域不得使用这两个标记。不得只依赖 CSS `pointer-events` 期待原生 input region 自动更新，也不得让整窗恢复可点击而遮住猫和桌面；
- 页面 resize、滚动、猫形态切换、窗口重载、显示器变化和模块切换都重新提交命中区域与浮层位置；滚动内容的区域必须裁到当前可见视口，没有可见界面块或控件时恢复整窗穿透；
- 允许在 PC preload 的现有命中选择器、区域刷新和对应契约测试中做最小同步修改，使有底色的养宠界面块和其中控件不把点击漏到桌面；不在 preload、bridge 或 `window-manager.js` 中保存宠物状态、执行养成规则、扣库存或决定服务结果。PC 仍只负责窗口、命中区域、输入转发和必要的布局/穿透协作。

Electron 官方 API 的边界也决定了实现方式：`BrowserWindow#setIgnoreMouseEvents()` 是整窗级别的穿透开关，官方提供的 `forward` 选项只用于在整窗忽略鼠标时继续转发鼠标移动，不能替代页面内的分区命中；透明无框窗口需要结合页面 CSS 与输入区域管理。实现前后应以 Electron 官方的 [BrowserWindow API](https://www.electronjs.org/docs/latest/api/browser-window)、[Custom Window Interactions](https://www.electronjs.org/docs/latest/tutorial/custom-window-interactions) 和 [webContents input events](https://www.electronjs.org/docs/latest/api/web-contents) 对照验证，不引入第二套窗口穿透机制。

### 本次整体检查结论（2026-10-21）

阶段 0–9 的本地镜像完成了行为闭环和迁移基线，随后按照正式边界完成了迁出。当前官方 N.E.K.O 源码不再包含 `pet_care_router.py`、`LocalPetCareBindingService`、PetCare SQLite 创建路径或登出直写；这些历史模块和对应本地权威测试已移除。它们留下的价值是已验证的行为与失败边界，不是要随客户端发布的第二套服务。

当前三个项目的代码责任如下：

- **N.E.K.O：** `PetCareClient`、同源薄网关、账号／角色门控、养宠界面、猫动作与 Cat Mind 单向只读输入。网关只有固定路径白名单，只转发已经验证的统一账号会话和安装凭据；它不保存规则、宠物数据库或内部服务密钥。
- **N.E.K.O-PC：** 透明窗口、输入区域、桌面命中和现有宿主能力。它不保存宠物状态，不计算奖励，也不创建第二套 API。
- **N.E.K.O.Verse 主进程：** 复用统一账号和安装凭据校验，提供玩家 edge 与管理员 BFF；管理员页面负责候选配置的校验、草稿、模拟、审批、CAS 激活、回退草稿和审计查看。
- **独立 PetCare 运行单元：** 源码聚合在 N.E.K.O.Verse 的 `services/pet_care/`，通过自己的 ASGI 入口、镜像、数据库 URL 和 Alembic 链运行。它是长期状态、懒结算、库存、任务、解锁、陪玩租约、探索、负面状态、恢复、幂等、配置 revision 和审计的唯一权威；Verse 主进程只保留 `app/modules/pet_care/edge/`。

客户端先调用 `/context` 做脱敏绑定发现；只有服务确认当前 alias 已绑定，才读取完整宠物快照。普通猫响应不泄露长期状态。完整快照统一携带 `item_directory`、`care_actions`、`play_actions`、`exploration_locations`、`content_directory`、`client_projection` 和 `service_capabilities`；成功写操作返回同一快照结构，客户端不从响应顶层维护第二份内容目录。`item_directory` 提供服务 revision 确认的物品名称、类别、说明、资源路径和玩家获取来源，库存、任务奖励和探索掉落仍只携带 ID 与数量；`content_directory` 的解锁项同时返回服务配置确认的 `threshold`、`display_name` 和 `unlocked`，总览用它计算“当前累计值 ÷ 下一解锁阈值”的进度条。旧 revision 的首版物品字符串目录保持可读，客户端只对仍存在的 schema-v1 物品 ID 使用兼容显示；已经移除的占位 ID 不保留名称或资源兜底。新物品必须使用完整结构化目录，不能借旧字符串形态绕过名称、类别、资源和来源校验。

锁定文档的“喂食能涨进度”描述的是来源类别能力，不等于每种食品都必须提供正进度。当前数值草案明确小鱼干只恢复饱食度，`progress_delta = 0`；正式校验允许非负配置，不强制零值或正值。任务领取只增加服务确认的库存，不顺带增加进度。候选数值仍需通过运营面板在 staging 调试和审批，不能写成产品定稿。

## 14. 阶段 10：正式服务接入

### 14.1 部署前代码现状

- 独立 PetCare 的领域、应用、仓储和 PostgreSQL 模型已经建立；`services/pet_care/` 提供独立 Docker 构建上下文和最小依赖锁，不安装 Verse 的图像、搜索等无关依赖；账号唯一宠物、稳定 `role_id`、设备 alias、`binding_revision` 和 `state_version` 分开处理。该构建上下文此前已完成本地镜像内容和非 root 运行检查，但当前工作树此后仍有变化，旧 digest 不再代表当前代码。冻结提交后必须重建、扫描并生成 SBOM、注册表 digest 和 release manifest。
- 首次绑定、官方换绑、状态补算、照料、任务、库存、解锁、每日登录、账号活动、陪玩租约、探索正常完成／召回、来信、离线结算、生病／赌气／恢复、操作幂等和审计均进入正式服务用例。角色不匹配时仍是普通猫，只开放不含宠物数值的显式换绑确认入口；换绑保持同一 `pet_id` 并同时校验 `expected_pet_id + expected_binding_revision + expected_state_version`。
- 玩家 edge 验证现有社区账号、账号状态、会话代次、安装凭据及账号绑定，再签发短期、限定 audience/scope 且绑定 method/path/body 的内部断言。浏览器和 N.E.K.O 网关不接触内部签名私钥。
- 正式服务使用 `services/pet_care/alembic.ini`，当前独立线性**代码 head** 为 `petcare_0010`，不向 Verse 主数据库或 ChatSync 角色表写入 PetCare 数据。`petcare_0007` 在数据库写入边界约束设备 alias 为 32 位小写十六进制，并在发现非法存量时阻断迁移等待人工核对，不自动改写或删除；`petcare_0008` 同样先阻断任何非空的旧库存来源摘要，再删除未实际承载证据的重复列；`petcare_0009` 增加配置工作流、角色删除 tombstone 和完整操作收据的数据库写入围栏；`petcare_0010` 在严格预检后派生离线可见性和恢复任务查询字段，并为审计、离线结算、当前任务和恢复任务增加匹配索引。任何不能从合法历史 JSON／cycle key 唯一派生的行都会阻断迁移，不能猜值或吞掉异常。ChatSync 仅提供设计参考，不是角色或宠物权威。
- 配置使用不可变 revision、payload hash、maker-checker、CAS 激活和审计；候选文件不会在导入或启动时自动激活。源码中的当前候选为 `draft-stage10-15`，尚未自动替换隔离本地数据库已激活的旧 `draft-stage10-12`，staging／生产也未激活；两者都不能写成产品数值定稿。
- 普通配置激活只能调整不破坏历史解释的运营数值：不得删除既有物品、照料／陪玩动作、地点或解锁 ID，不得改变动作的共享冷却组、前置解锁或消耗物品，不得改变地点的前置解锁、物品类别，以及解锁的类型、能力／地点／内容／物品／记录来源／反馈动作或发放物品身份。服务日边界同样不能通过普通激活改变；这些持久语义需要显式数据迁移和相应回滚方案。
- 内容扩展分为三个边界：结构化物品目录记录稳定 ID、用户名称、类别、本地资源和真实玩家获取来源；服务配置分别描述饱食、精力、清洁、互动和成长效果，并关联库存、解锁、任务、地点、可选共享冷却及每个动作自身的每日成长次数。毛线球、逗猫棒和未来玩具分别按自己的规则结算，不共享成长预算。独立 PetCare 服务用代码能力表注册可执行的业务动作、反馈动作与终态来源，N.E.K.O 则交付对应资源和客户端动作适配。配置可以增加额外任务、地点、解锁和已适配动作，但 schema v1 仍强制首版两条 canonical 任务，以及猫窝信箱与右键撸猫动作两项 canonical 解锁；缺失或改写固定语义、未知能力、缺失获取来源、类别不匹配、非法资源路径或会破坏持久化键的 ID 均在激活前拒绝。服务端执行时再次检查解锁、库存、冷却、动作自身的次数限制和活动冲突；前端目录只负责展示和预检，不成为结算权威。配置校验对来源和可执行链只做保守的结构闭包证明；概率分布、长期资源净流和有限次数下的动态经济必须继续由 draft simulation 与 staging 隔离账号验证，不能由该闭包外推。
- 管理页面只结构化编辑、校验、模拟和发布当前源码已经定义的现有内容，不提供任意新增／删除内容的入口。新内容的发布顺序固定为：先交付 N.E.K.O 客户端资源和动作适配，再发布 PetCare 服务代码侧能力注册，最后才创建、审批并激活引用这些能力的配置 revision。只改变已有条目的运营数值仍走现有 maker-checker 流程；两条路径不能混成一次无代码发布。候选 JSON 只登记当前已经交付的真实物品和内容；隔离环境中已激活的旧 revision 不能冒充更新后候选，必须按 maker-checker 流程重新激活后再验收。本轮不为目录迁移伪造尚不存在的药品资源。
- N.E.K.O 已切换为固定白名单同源网关并删除本地权威；前端只接受服务确认快照、服务结果和版本前置条件，失败、取消、超时和活动冲突不会由客户端写入长期状态。降级时仍保持普通猫并在总览显示简短原因和重试入口；机器错误码、源码路径和异常正文只留在诊断状态，不直接呈现给用户。账号状态暂时无法确认时，旧快照立即失效；用户重新打开降级面板或点击重试只触发一次去重的账号确认。纯 PetCare 故障则只重试绑定／快照，不额外刷新账号；明确退出永远不会借此恢复旧宠物上下文，也没有轮询。
- N.E.K.O 与 Verse 复用同一套统一账号主体，不增加养宠专用登录或第二套 OAuth；环境不一致时继续拒绝会话转交。本地页面是否呈现登录外观不作为 PetCare 业务闭环证据，正式同环境链路仍由既有一次性票据与环境隔离保护。
- N.E.K.O 写操作先在账号范围的单一持久 pending registry 中固化请求正文、幂等键、版本和绑定上下文；未知结果只能以同一请求重试，明确确认／拒绝后才清除。PetCare UI 只通过 `PetCareClient → PetCareApi` 这一条传输链访问业务接口，缺少任一层时 fail-closed，不回退到页面原始 `fetch`。
- Cat Mind 继续保存自己的短期五维；PetCare 只通过版本化 `client_projection.cat_mind` 提供动作权重偏置。v3 偏置按 `cat_mind_valid_until` 单独到期；状态显示投影继续随当前已授权完整快照和账号／绑定角色上下文存在，直到上下文失效或下一次事件驱动权威快照替换。v2 保持原单一 `valid_until` 的整份投影到期语义。任何投影都不授权客户端结算或写入，也不增加轮询。
- v3 的 Cat Mind 偏置窗口由服务领域构造器、响应 schema 和客户端共同限制为最多 5 分钟；状态投影必须完整携带合法边界、阈值、探索暂停和心情权重，否则整份养宠快照按不完整处理并回退普通猫。当前配置激活仍以服务端即时 `effective_at` 为准，客户端也不接收配置变更推送；因此一个持续打开且没有发生服务请求的面板，可能在下一次用户触发的权威读取前继续显示旧 revision 的只读推算。服务端写入和结算不会采用该旧投影。staging 必须验证并记录这段显示滞后；若产品要求配置激活后立即改变所有已打开页面，只能另行设计可审计的配置变更推送或预先调度的生效点，不能用轮询绕过锁定约束。
- 逗猫棒通过 `PlayTeaserWandAction` 的真实完成终态提交陪玩租约；毛线球保持独立互动和任务来源，客户端不再保留会把两者混成同一业务入口的通用陪玩桥。签发响应和不可变收据固定当次 revision 的动作、消耗、时序与任务语义；完成端按该 revision 校验并结算动作经济，但以当前 active revision 校验可用精力、裁剪长期状态边界并重算最终心情，避免旧 revision 的较高下限把负增量反向抬高为增益。租约通过身份、绑定、活动、状态版本和最短时长校验后，一旦进入领域结算，成功或稳定业务拒绝都会在同一事务绑定不可变回执并终态化；原幂等键只重放原结果，新键不能复用该动作，条件改变后必须重新签发。过早完成、格式错误、身份／活动不匹配和配置故障不会消费租约。快照值只作签发前预检；租约能防过期、重放、错安装和错动作，但不把开放客户端动画伪装成可信硬件证明。
- 每日打工、毛线球进度和每日登录保持三条独立链；当前恢复任务与每日打工复用通用任务完成接口，均在完成后另行领取，只有领取事务发放相应物品。生病在领取药品后走 `status-recovery`；赌气使用恢复任务 revision 指定的逗猫棒并走受限陪玩 lease，已有合格库存可直接恢复，任务在缺少时提供保证获取路径。赌气恢复始终校验活动冲突、来源、库存和解锁，不受普通陪玩的精力不足、既有 CD 和每日硬上限阻断；它仍消费库存、累计次数，并以较晚的既有／新 CD 为准。若执行前已经达到硬上限，本次恢复不给进度、不推进任务也不触发解锁。
- 正式写入口已收窄为一条链：`care-actions` 只接受喂食／清洁，全部 `playing` 必须使用陪玩 lease；`status-recovery` 只接受生病，赌气不能直接改状态；首版任务配置拒绝未消费的分组字段。这样删除了三个能够绕过或混淆正式动作语义的旧兼容口。
- 探索快照只按服务时间公开已经到达的纸条；活动期间仅附带服务计算的下一封可见时间 `next_letter_at`，不泄露未来内容、计划、剩余数量、掉落或奖励。N.E.K.O 对正式探索 DTO 做 fail-closed 校验：身份、地点、时间别名与持续时间必须互相一致，活动／终态字段、纸条、掉落、进度、比例和固定地点投影必须符合各自状态；简化对象或夹带未来内容都使整份养成快照不可用并回退普通猫。N.E.K.O 对每个提示最多安排一次状态读取，页面隐藏时取消未触发的计时，恢复可见时只补排同一次读取并合并并发；不做周期轮询，也不在客户端生成来信或终态。探索事件同时携带账号、角色和模式代次上下文，迟到的旧账号／旧角色事件不能重开或结束当前猫实体门；正式快照恢复时若发现活动仍在而本地门已丢失，会按同一活动重新建立门控。正常完成与强制召回仍由服务端结算并持久化结果。
- 探索终态使用非模态短提示，不能用全窗遮罩阻塞养宠面板或左侧导航。正常完成只显示“探索已完成，收获：”加实际道具名称、数量和进度；不出现“服务已确认”、`teaser_wand` 等内部字段或异常正文。已知内容 ID 必须通过服务目录映射到用户名称，未知道具只显示通用名称。任务奖励和普通操作结果不因此重复展示道具大图。
- Verse 管理员页面和 BFF 已接入配置全流程。激活／退役要求 superadmin；创建人与审批人必须分离；写接口独立限流并产生审计。资源发放也仅允许 superadmin 选择当前激活目录中的道具，按统一账号、数量、原因和幂等键提交，不允许任意修改宠物数值。审计列表使用稳定的 `(created_at,id)` keyset cursor，可按 actor、action、subject 和时间范围精确过滤并继续加载更早记录；旧首页数组接口保留兼容。配置页面按业务模块结构化编辑，默认视图只显示本地化业务名称，不显示 schema 字段名、道具／任务／地点内部 ID、UUID 或完整 hash；完整追溯标识只在折叠的“技术详情”中显示。未知 schema 或字段 fail-closed，上游失败映射为面向管理员的短提示，不直接显示 `detail`、Traceback 或源码路径。

### 14.2 保持不变的产品与安全边界

- 未登录、角色不匹配、快照不完整或服务不可用时，不显示养宠入口、数值和可用操作，继续普通猫。
- 每个统一账号只有一只宠物；换绑保持同一 `pet_id`，要求最新 `expected_pet_id + expected_binding_revision + expected_state_version`。本地修改 `character_uid` 不能自动得到服务认可。
- 读取和写操作按 `last_settled_at` 懒结算，不运行宠物定时任务；客户端不轮询、不发奖、不扣库存、不生成概率结果。
- 所有概率、CD、消耗、奖励、阈值、任务、地点和解锁条件属于服务端配置 revision。前端只消费完整快照和公开内容目录。
- 官方发行版不提供本地 PetCare 权威模式。功能尚未发布，因此没有用户本地存档迁移；开发 SQLite 数据不进入正式库。
- 宠物数值、库存和进度不做自创的“加密计算”。可信边界来自 TLS、服务端时间和随机数、最小权限、数据库约束、事务、版本、幂等收据、审计、磁盘／备份加密与密钥管理。

## 15. 验证口径

自动化测试只证明各自实际覆盖的代码层；部分测试使用一次性真实 PostgreSQL，但仍不等于 staging 或生产。正式验收必须分别保留：N.E.K.O 网关与前端回归、Cat Mind／Avatar 回归、N.E.K.O-PC 命中契约、Verse 正式服务与管理面板测试、独立 Alembic 离线和在线迁移、真实 PostgreSQL 并发与恢复、Windows／macOS 实机记录。某一层通过不能替代另一层证据。

当前独立 PetCare **代码 head** 与隔离开发库均为 `petcare_0010`，数据库与候选 revision 口径见 14.1。一次性 PostgreSQL 16 已验证有效非空样例从 `0008` 前进到 `0010`、派生列回填、恢复 task ID 演进和新索引；另以非法离线摘要形状和非法恢复 cycle key 分别验证升级会失败并保持 `0009`。这些构造样本尚未替代 staging 的实际历史分布预检、锁时间、备份恢复和回滚演练。Verse 测试已覆盖跨 revision 陪玩中“签发规则与当前状态边界”分离、恢复路径例外和真实 PostgreSQL 约束；N.E.K.O 前端测试已覆盖正式探索 DTO fail-closed、一次性纸条读取、迟到事件上下文围栏、门控恢复和 Cat Mind／Avatar 相关回归。14.1 的计数和运行记录是本轮实际证据；PC 历史全量仍有 5 个已归因的非 PetCare 失败，因此不得把整体状态写成全绿。自动化和当前启动状态仍不能替代真实 OAuth／安装凭据、透明 Pet 窗口内完整业务动作、管理员窄屏视觉或 staging／生产迁移证据。发布清单必须保留实际命令、原始输出、跳过项和失败归因。当前工作树尚未从冻结提交重建发布镜像，不能写成“发布镜像通过”。
