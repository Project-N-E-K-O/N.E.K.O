# 猫形态养宠系统首版实施文档（NEKO / NEKO-PC）

> 本文定义实施顺序和验收标准。产品规则以《宠物养成系统方案（修订稿）》为唯一设计基线，接入边界以锁定文档和本轮确认的部署方案为准；数值草案只提供可替换的首版候选配置。
>
> 本文按“用户能看到什么、完成后能验收什么”拆分阶段。所有阶段先在本地养成服务镜像上跑通；之后接入社区服务器，客户端继续使用同一套业务接口。

> **本轮边界确认：** 首版以养成服务、照料、任务、探索、动作链和状态结算为主。养成可用性复用 N.E.K.O 统一账号会话；当前本地适配器沿用 `community_oauth`，它是会话来源而不是产品账号的归属。账号只有一只猫，绑定账号自己的一个角色，当前角色不是绑定角色时和未登录一样走普通猫路径。用户登录、猫处于猫形态且养成快照完整后，自动进入养成兼容状态，并在首次进入时给出一次提示；阶段 3 只暂时停用可能与养成动作冲突的 Cat Mind 自主自动触发，正常的用户照料、陪玩和返回等功能动作不因此停用。养成服务负责长期状态、条件、负面状态、探索、库存、奖励和结算；Cat Mind 继续负责现有猫形态的短期自主行为。首版不把养成值写入 Cat Mind。基础闭环稳定后，再按锁定文档通过独立适配让养成快照作为 Cat Mind 的输入，但 Cat Mind 不负责长期状态结算；统一账号会话失效或快照不可用时，继续使用现有普通猫路径。

## 1. 首版目标与范围

首版完成后，用户可以：

1. 未登录时继续正常使用猫；猫形态可见时只可显示不可用的登录提示/快捷入口，不显示养成入口、宠物数值或可用养成操作；
2. 保持 N.E.K.O 统一账号登录后，只有当前角色等于账号绑定角色时才读取该账号唯一宠物；其他角色和未登录一样使用普通猫；
3. 查看饱食、精力、清洁、心情和养成进度；
4. 完成每日任务、喂食、清洁（首版具体操作为梳毛）和用户主动陪玩；
5. 开始一次探索，看到猫离场、猫窝、纸条和来信；
6. 正常等猫回家，或在猫窝面板中结束探索并让猫回到猫形态；用户切回模型时再复用统一模型返回入口完成强制召回；
7. 刷新、重启本地服务、切换角色后仍看到正确数据；
8. 长时间未登录后看到一次离线结算和必要的恢复任务；
9. 通过照料和探索积累进度，达到阈值后看到解锁内容。

首版围绕任务、照料、主动陪玩、一个探索地、负面状态和 3 到 5 个解锁项展开。社区货币与购买型道具、社交、推送、AIGC、洗澡和更多探索内容安排在后续版本。

## 2. 当前项目事实和实施边界

实施前已根据实际代码确认以下事实：

| 事项 | 当前实际情况 | 实施要求 |
| --- | --- | --- |
| 统一账号会话 | 当前由 NEKO OAuth / `community_oauth` 适配器保存和校验统一账号身份；养成页面沿用该会话，NEKO-PC preload/bridge 不负责会话 | 养宠请求从受信统一账号会话取得账号；社区只是当前接入来源 |
| 角色身份 | 项目已有本机 `_reserved.character_uid`；新建或导入生成，改名保留 | 宠物按已认证 N.E.K.O 统一账号唯一定位；宠物记录保存跨设备稳定的 `bound_role_id`；当前 `character_uid` 只用于页面角色解析和当前角色校验，不作为正式宠物主键；不按每个角色建宠物 |
| Cat Mind | app-cat-mind.js 是现有猫行为的一部分，会发起 `neko:cat-mind:action-request`；当前没有完整 pause/disable API；五维和动作评分属于猫形态短期运行态 | 作为现有短期自主行为系统接入兼容层：养成快照完整后暂时停用可能冲突的自主请求，并单独清理已运行动作；首版不向其中写入养成值，也不让它负责养成状态和结算 |
| 动作执行 | 当前已有 cat1 吃零食、移动、毛线、音效和收尾模块；梳毛、逗猫棒及其他形态的业务反馈尚未形成统一执行器 | 养宠适配器复用已有能力，并为首版缺少的动作补齐独立执行器或基础表现，统一等待完成、取消或失败回报 |
| 探索离场 | 现有清理方法可收尾桌面动作和离场表现 | 出发动作完成后隐藏猫；探索期间停止依赖猫实体的所有动作和尾回调 |
| 返回模型 | surface-floating-controls.js 有统一返回入口和 neko:cat-return-commit / neko:cat-return-complete 事件 | 仅用户切回模型、角色切换和模型热重载时的强制召回接入既有模型返回链；猫窝面板召回只走探索 recall 并恢复猫形态 |
| NEKO-PC | Pet preload/bridge 负责窗口、输入、命中区域和 IPC 桥接，不负责账号会话或养成业务 | 长期状态和结算由养成服务管理；养成页面沿用 NEKO 的会话和业务接口 |
| 社区侧现状 | 已有统一账号和基础服务，但尚无宠物快照、任务、探索和养成结算模块 | 首版先做本地养成服务镜像；本地闭环通过后接入社区服务器，具体模块、接口和数据归属另行确认 |

各阶段按所接入的功能验证普通猫回退、当前账号与 `bound_role_id` 校验、请求幂等和服务确认结果；页面侧仍使用当前 `character_uid` 作为角色解析输入。

### 2.1 本地、正式服务与代码结构

养宠是一个独立业务域。第一版先实现本地后端镜像，正式数据和结算固定接入社区服务器；F2 没有规定社区服务器的具体模块、接口或数据库表，这些接入细节保留到本地闭环通过后确认，不把独立部署作为另一条正式方案。

社区服务器负责账号唯一宠物的状态、任务、探索和结算。API、数据结构、错误码和幂等语义在本地镜像与社区服务器之间保持一致；本地只用于开发、验收和可回退验证。账号仍来自 N.E.K.O 统一账号会话，宠物另记录一个跨设备稳定的 `bound_role_id`。未来自有云存档复用同一账号、宠物和绑定关系，不另建一套互相冲突的宠物身份。

账号身份与角色身份是两条独立信息：账号来自 N.E.K.O 统一账号会话，当前页面角色由 NEKO 的 `character_uid` 表示，正式绑定使用跨设备稳定的 `bound_role_id`。账号只有一只宠物；当前 `character_uid` 只用于解析和校验当前页面角色，不写入账号认证对象，也不按每个角色创建宠物。NEKO 当前会话字段为 `local_user_id`，它在本地是统一账号主键的适配镜像，不是社区专属主键。N.E.K.O.Verse 当前已有稳定的认证主体映射：`AuthPrincipal` 的 `(issuer, subject)` 通过 `UserAuthIdentity` 定位 `user_id`；后续正式服务器接入须把该统一 `user_id` 映射到本地 `local_user_id`，不能再创建养宠专用账号。

统一账号的生命周期也必须统一：N.E.K.O 页面、受管的 N.E.K.O.Verse 社区窗口和养宠面板使用同一账号会话边界。社区窗口退出时，必须通过受信窗口桥通知 N.E.K.O 本地会话适配器清理桌面 OAuth 镜像，再由 `/api/card-drop/oauth/status` 重新确认并让养宠入口回到普通猫；不能只清社区页面自己的 `localStorage`，也不能让养宠面板维护第二套登录态。独立浏览器中没有受信 opener 的社区页面不属于这条本地桥，正式服务器接入阶段需提供等价的一次性会话撤销协议。

表现属性只影响外观：模型是角色当前使用的模型；猫档位是同一宠物的不同形态；装扮属于后续纯外观内容。它们都不参与宠物记录主键。本地验收阶段通过切换模型和猫档位验证宠物及 `bound_role_id` 不变，装扮暂不进入首版业务。

`_reserved.character_id` 是数值剧场使用的另一项身份字段；养宠不把它或本机 `_reserved.character_uid` 作为正式宠物主键。

数据流固定为：

```text
Web / NEKO-PC 共用的 NEKO 页面
  → PetCareBackend 接口
    → 本地模式：NEKO 本地养成 API → LocalPetCareStore
    → 正式模式：正式养成 API → PetCare 数据库
```

- **NEKO 页面**负责面板、模式门控、动作适配和统一返回入口。前端的 `PetCareBackend` 封装本地与远端请求，页面使用相同方法读取快照和提交操作。
- **本地养成后端**负责本地测试期间的规则、补算、结算和持久化。作为 NEKO 内独立模块接入本地 API，由 `app/main_server/web_app.py` 注册路由。
- **NEKO-PC**继续只负责窗口、输入、命中区域和 IPC，养成页面复用上述业务接口；不在 preload/bridge 保存账号、宠物状态、规则或结算。只有确有窗口或输入适配需求时，才在现有 pet bridge 中扩展对应能力，通道名集中在 `src/ipc-channels.js`。
- **正式养成后端**接收本地已验证的业务规则，适配正式认证和数据库。本地与正式环境用同一组业务用例核对结果。
- **本地测试存储**放在现有 `local_state_dir` 下的 `pet_care` 数据目录，采用 SQLite 支持事务和幂等记录；页面和 preload 保留面板开合、显示偏好等界面状态。正式服务使用部署环境的数据库。

> **结构状态说明（按当前代码校准）：** 上表是阶段 0–10 的目标分层，不代表这些文件已经全部存在。当前仓库的实际落点以本节下一段为准；目标文件只有在迁移或拆分实际发生后才能写入“已实现”。

当前阶段已落地 `app-pet-care-api.js` 的传输边界和 `app-pet-care-client.js` 的服务端点契约：面板只通过客户端提交养成服务请求；传输适配器统一请求超时、取消信号、凭据和宠物路径，客户端集中绑定、快照、照料、任务、陪玩和探索端点，二者都不解析业务规则，也不保存账号或宠物状态。当前本地 API 仍由同一适配器访问，后续切换社区服务时只替换部署端点/适配实现，不能把社区认证或结算逻辑下沉到 NEKO-PC 或面板。

服务端同时提供公开的 `catalog_for_snapshot()` 内容目录契约，路由只返回目录、操作包络和确认快照，不调用本地实现的私有方法。账号会话也通过 `account_session` 适配层使用认证提供方的公开函数；当前提供方仍是 N.E.K.O 现有 OAuth，后续正式服务器只替换提供方，不让养宠业务依赖社区 OAuth 私有实现。当前 `app-pet-care.js` 仍是旧页面的组合入口，但新增能力必须遵循“目录 → 操作/终态 → 服务快照 → 表现适配”的边界，不能继续跨层直接读写规则或持久化状态。

当前正式服务尚未接入，社区侧不能假定存在 `schemas.py`、`service.py`、`rules.py` 或指定表路径。阶段 10 应从当前本地组合服务中提取已验证的业务语义，按社区项目实际模块、认证和迁移规范落地；`N.E.K.O.Verse` 的候选目录只能作为调查入口，不能作为已确定部署位置。

#### 当前代码保留与正式迁移边界

- **继续保留在客户端的代码：** `static/app/app-pet-care.js`（页面组合与渲染）、`app-pet-care-mode.js`（模式/生命周期门控）、`app-pet-care-api.js`（传输适配）和 `app-pet-care-client.js`（请求契约），以及现有 CSS、猫动作、统一返回链、探索表现和 NEKO-PC 的窗口/输入/IPC 桥接。客户端只发送当前角色 `character_uid` 和操作参数，展示服务确认的快照与结果。
- **仅用于本地镜像的代码：** `main_routers/pet_care_router.py`、`services/pet_care/binding_service.py` 的 SQLite、迁移、测试时钟和本地 OAuth 适配。它们支持开发、验收和回退验证，不能直接作为正式数据库结构或正式认证实现。
- **迁移到正式服务的责任：** 账号唯一宠物、`bound_role_id` 绑定、补算/结算、任务、库存、解锁、探索、负面状态、离线段去重、幂等、并发控制、审计和配置版本。迁移的是业务语义和接口契约，不是把本地 SQLite 的 JSON 快照原样搬到生产库。
- **必须保持兼容的边界：** `PetCareClient` 的请求/响应包络、错误码、`idempotency_key` 语义和普通猫回退。正式服务地址和认证适配可以替换；页面、NEKO-PC 和 Cat Mind 不得获得正式结算或宠物存档职责。

### 2.3 命名与接口约定

推荐命名：

| 用途 | 命名 |
| --- | --- |
| 业务域 | `pet_care` / `PetCare` |
| API 前缀 | `/api/pet-care` |
| 前端文件 | `app-pet-care-*.js` |
| 服务与数据类型 | `PetCareService`、`PetCareRepository`、`LocalPetCareStore`、`PetCareSnapshot`、`PetCareExploration` |
| 数据表 | `pet_care_*` |
| 业务标识 | 已认证 N.E.K.O 统一账号 ID（当前适配字段 `local_user_id`）+ 账号唯一 `pet_id`；宠物记录附带一个稳定的 `bound_role_id`，不按角色复制宠物；请求中的当前 `character_uid` 只用于校验 |
| 请求标识 | `idempotency_key`、`request_hash`、`exploration_id` |

当前页面继续传递项目已有的 `character_uid`。账号 ID 由统一账号认证上下文提供；服务先按统一账号取唯一宠物，再通过角色解析得到稳定的 `bound_role_id` 并校验当前角色。首次绑定只建立一只账号宠物；换绑必须是显式操作，更新同一宠物的绑定关系，不创建第二只记录；角色改名、模型切换、猫档位切换、异机导入或角色删除都不能自动复制宠物。

业务类别和具体内容分层：`feeding`、`cleaning`、`playing`、`exploration` 是稳定的业务类别；小鱼干、梳毛、毛线球、消耗品玩具和探索地点都是可配置的 `item_id` / `content_id`，不能把候选内容写成类别名称。库存由养成服务持有并按账号宠物返回，至少要能表达类别、内容、数量和后续解锁层级；页面不能自行扣库存或把某一个内容当成该类别的唯一实现。首版不加入商店、货币或付费猫粮，但接口和面板必须为背包与多内容选择保留层级。

任务是独立的业务记录，不是照料类别的别名，也不是把所有进度、登录和解锁结果塞进一个列表。每个任务必须由服务配置和快照单独标识，至少包含 `task_id`、可配置标题/说明、周期或持续范围、完成条件、当前进度、目标、奖励、状态、可领取标记、进度来源和领取幂等信息。周期、分组和任务类型不能在前端写成固定枚举；服务返回的这些元数据只用于结算和识别，页面把任务逐条平铺为同级记录，不增加分组标题或不同层级。小鱼干领取和毛线球互动都是独立的服务任务项：小鱼干任务通过手动领取获得奖励，毛线球任务由服务确认用户主动操作且猫完成回应后推进；毛线球仍不是养宠面板里的直接操作按钮。

写操作使用 `idempotency_key`，服务保存请求内容摘要和结算结果；重复请求返回已确认的结果。账号主体从认证上下文取得，页面传递当前角色的 `character_uid` 和操作参数。

首版核心接口：

- `GET /api/pet-care/pets/{character_uid}`：读取完整宠物快照；
- `POST /api/pet-care/pets/{character_uid}/care-actions`：提交喂食、清洁操作（首版为梳毛）、用户主动陪玩和物品使用；
- `POST /api/pet-care/pets/{character_uid}/explorations`：创建探索活动；
- `GET /api/pet-care/pets/{character_uid}/explorations/{exploration_id}`：读取探索状态；
- `POST /api/pet-care/pets/{character_uid}/explorations/{exploration_id}/complete`：正常完成探索并结算；
- `POST /api/pet-care/pets/{character_uid}/explorations/{exploration_id}/recall`：强制召回并结算。

首版接口还需要覆盖任务和每日登录：

- `GET /api/pet-care/pets/{character_uid}/tasks`：读取服务返回的独立任务项及周期/识别元数据；客户端不得假设固定任务类型，也不得把元数据转换成界面分组；
- `POST /api/pet-care/pets/{character_uid}/tasks/{task_id}/claim`：完成并领取任务奖励；
- `POST /api/pet-care/pets/{character_uid}/daily-check-in`：提交当天首次登录结算。

任务领取和每日登录同样带 `idempotency_key`，返回完整宠物快照。

这些接口中的 `{character_uid}` 只表示当前页面正在校验的角色；服务先从社区认证会话取得账号唯一宠物，再确认当前角色解析出的稳定角色标识是否等于 `bound_role_id`。不匹配时按普通猫返回，不创建第二份宠物记录。

### 2.4 与现有猫行为的兼容边界

Cat Mind 是现有猫行为的一部分，负责猫形态内存中的短期行为驱动力和自主动作选择；养成服务负责按 N.E.K.O 统一账号唯一宠物保存的长期业务状态。两套系统的食欲/困意/精力/社交/刺激与饱食度/精力/清洁度/心情/养成进度不能共用字段、初始值、衰减公式、阈值或结算结果。锁定方案规定养成数值后续可以作为 Cat Mind 的输入；首版暂不接入该输入，`bound_role_id` 负责正式绑定，`character_uid` 只作为当前页面角色校验。

首版只保留以下兼容约束：

- 首次加载时未登录，或养成快照尚未完整、养成服务不可用时，继续使用普通猫路径，不创建替代存档；若服务已确认当前角色正在探索，则保持猫窝和离场状态，不恢复实体动作。
- 用户已登录、猫处于猫形态且养成快照完整后，自动进入养成兼容状态，并在首次进入时给出一次提示；提示只说明养成入口和边界，不改变业务结算。
- 养成快照完整后，只暂时拦截可能与养成动作冲突的旧自主自动触发；正常的用户照料、陪玩和返回等功能动作仍可由独立适配器调用动作执行器。不要求删除或重写 Cat Mind 的内存需求模型，服务确认结果后才更新长期状态。
- 生病、探索、照料、活动、库存、进度、奖励和结算均由养成服务及独立动作/表现适配器负责，不通过 Cat Mind 决定。
- 基础养成闭环稳定后，如确有价值，再新增只读适配器让快照少量影响自动行为或短期心情；不得把养成数值直接写入 Cat Mind 五维，也不得让该适配器负责长期状态、结算或成为养成闭环的前置条件。

可复用的是 observation 去重、动作请求租约、provider 检查、动作终态和清理协议等通用机制；不可复用的是两套数值的业务含义和结算规则。这样可以在不重写现有 Cat Mind 的前提下，先完成养成闭环，再单独评估是否增加行为提示适配。

旧自主触发不等于所有独立动作来源。当前代码和补充设计中还存在 journey、playground、重力/窗口感知、贴边探头等独立链路；阶段 3 的兼容开关只处理已确认的旧自主触发来源，阶段 7 的探索活动门控必须另外覆盖所有依赖猫实体的输出，不能因为拦截了 `neko:cat-mind:action-request` 就视为全部停止。

## 7.1 阶段 0–3 首个大阶段收口（2026-10-16）

阶段 0–3 作为首个大阶段的交付物，是“统一身份和状态读取可以安全进入猫形态兼容模式，并能失败回到普通猫”的基础闭环；它不是完整养宠业务周期。完整的时间补算、照料、任务、主动陪玩、探索、离线结算和负面状态仍按阶段 4–8 逐步接入，阶段 9 才做本地首版完整验收。

### 当前闭环

```text
N.E.K.O 统一账号会话
  → 当前角色 character_uid
  → 本地 PetCare 服务确认账号唯一宠物和 bound_role_id
  → 完整只读快照
  → 猫形态活动
  → 阶段 3 Cat Mind 兼容门
  → 离开猫形态、登出、角色/绑定变化或服务失效时清理并回到普通猫
```

## 9. 阶段 5：每日任务、食品、进度和解锁

### 实施目标

完成第一条可循环的“任务 → 小鱼干 → 当前小鱼干喂食恢复状态；清洁/陪玩/探索/登录按各自规则推动进度 → 解锁”闭环。

### 实施内容

- 增加每日打工任务；
- 用户手动领取任务后发放小鱼干；
- 小鱼干进入食品库存；
- 食品用于喂食；
- 首版当前食物只有小鱼干；小鱼干只用于喂食并只恢复饱食度，不直接增加进度，其他食物不在本阶段预设；进度结算保留按食物/操作配置扩展的入口，本阶段仅实现小鱼干配置为 `0`；清洁操作（首版为梳毛）、用户主动陪玩、探索和每日登录按各自独立配置汇入唯一的养成进度字段；不同陪玩类型可以使用独立的次数和基础增量参数，但不能新增第二个进度字段；
- 每日登录完成一次登录结算并按配置增加进度；
- 按数值草案提供 5 个占位解锁项及其阈值、可见效果作为本地可编辑测试配置，用于本阶段验收；草案不构成锁定规则，后续可替换名称、资源、内容和数值而不改变进度存档契约；
- 进度达到配置阈值时，由服务一并记录解锁项、最近存档点并返回解锁结果；
- 增加服务日任务刷新、手动领取和每日次数限制；初版可领取任务不设置条件，领取成功固定由配置发放 1 个小鱼干，任务条件字段只保留扩展位；毛线球作为同一任务集合中的每日进度项，由既有互动终态推进，不提供领取按钮；
- 本阶段范围覆盖每日任务、食品库存、进度和首批解锁项。

### 用户可见验收

1. 用户能看到当日可领取项；
2. 用户手动领取后，小鱼干只在服务确认后增加 1 个；
3. 小鱼干能用于食品流程；
4. 任务重复领取不会重复发放；
5. 使用小鱼干喂食后食品数量和饱食度正确更新，小鱼干喂食不增加进度；其他食物不在本阶段验收；
6. 切换窗口或刷新后，任务和库存保持一致；
7. 达到进度阈值后能看到已解锁内容，刷新后解锁状态仍保留；
8. 每日登录只在当天首次确认时增加一次进度；
9. 同一次操作重试时，解锁记录和奖励仍只有一份。

### 阶段完成条件

- 任务领取、库存、宠物状态在同一结算边界内更新；
- 每日任务产出由服务判定；毛线球按锁定稿每日前 N 次计进度，之后仍可玩但不再计进度；新增消耗品陪玩的每日次数上限由服务判定；两类陪玩都不新增道具 CD；
- 小鱼干、进度和解锁由服务结算并在确认后展示。

### 阶段 5 收口审查（2026-10-17）

按锁定文档第 3.1、3.5、3.7 和第 8 节逐项复核，本阶段闭环成立：

- **任务与食品**：任务首次读取按服务日生成；用户手动领取；服务事务确认后才增加食品库存；同一任务换用新幂等键不能再次领取。
- **条件边界**：本阶段默认任务没有条件；若配置误填非空条件，服务明确拒绝领取，不把条件任务伪装成已完成。条件事件记录器留给后续阶段接入。
- **进度来源**：小鱼干配置强制 `progress_delta = 0`；梳毛沿用服务配置增加唯一进度；每日登录按服务日只增加一次；陪玩和探索没有被提前伪造为阶段 5 结果。
- **进度边界**：饱食度、精力、清洁度和心情保持 `0–100`；养成进度是可配置的非负累计值，不套用状态值的 100 上限，因此草案中的高阈值占位解锁不会永久不可达。
- **解锁**：进度达到可配置阈值后服务记录解锁项和 `unlock_checkpoint`，完整快照返回后页面显示已解锁内容；旧 SQLite 快照可迁移。
- **幂等与配置校验**：任务领取和每日登录的幂等请求哈希包含服务日，跨服务日复用同一键会明确拒绝；已领取任务的拒绝读取仍持久化时间结算和任务日刷新；任务奖励数量必须为正数，避免出现“可领取但无法发放”的配置。
- **失败边界**：领取、每日登录和加载没有前端乐观奖励；失败、超时或上下文变化不会由前端增加奖励、进度或解锁。阶段 5 没有提供任务取消控件，请求处理中相关入口置灰，迟到响应不会覆盖新账号/角色上下文。
- **数据归属**：账号、绑定角色、任务、库存、进度、解锁和幂等结果由本地养成服务持有；Web 与 NEKO-PC 继续复用同一接口，PC preload/bridge、Cat Mind 和模型动作链没有新增阶段 5 规则。
- **周期边界**：本地镜像当前只按可配置服务日刷新 `reset_policy=daily` 项；其他非空策略只保留跨服务日状态，不能据此宣称已支持 weekly/monthly/once 调度。正式开放新周期前要补周期键、状态迁移和幂等测试；`tasks.items` 是规范记录，`daily/state` 仅为旧快照兼容别名。

因此阶段 5 标记为“本地闭环完成”，下一实施入口为阶段 6。阶段 6 的陪玩次数、真实回应和进度事件，以及阶段 7 的探索事件不能在本阶段补写或用占位按钮代替。

### 阶段 5 任务区域体验修订（2026-10-17）

阶段 5 收口后按实际用户操作复核任务区域，确认原先的“查看任务”二次点击、分组层级和低对比度状态文案会把读取动作误认为业务操作，也会让可领取按钮看起来像不可用控件。本次只调整任务区域的交互和表现，不改变任务、奖励、每日登录或服务结算契约：

- 删除没有业务含义的“可领取”和“奖励待配置”默认占位；任务没有说明或奖励时不制造假信息。浅色主题补齐任务日期、进度和领取控件的前景/背景对比度，并为可操作按钮提供键盘焦点轮廓。
- 毛线球作为服务任务集合中的每日进度项，在任务列表中以与其他任务相同的卡片样式显示；它没有领取按钮，进度只由既有互动终态更新，也不在陪玩区域增加毛线球按钮或重复卡片。

### 阶段 6 实施前准备记录（2026-10-17）

阶段 6 的陪玩动作和养宠面板职责必须分开。锁定文档规定的是“用户主动拖或点毛线球，并且猫有回应，才算一次陪玩”；面板不是一个点击即播放毛线球反馈的新增按钮。聊天框最小化后的毛线球、重力猫猫模式中的毛线球，以及任务页面中显示的毛线球活动进度，都沿用同一套陪玩业务契约。面板只展示服务确认的任务进度、消耗品库存、处理中状态和结果，不直接把点击转换成陪玩成功，也不在陪玩内容区重复放置一个没有操作意义的毛线球入口。

#### 阶段 6 任务展示与任务契约修订（2026-10-17）

此前把任务区标题、毛线球次数、每日登录和解锁内容放在同一张卡里，或者把“每日任务/状态任务”写成前端固定栏目，都会让任务的周期、领取和完成条件互相污染。本阶段采用以下收口契约：

1. 任务是服务返回的独立记录。任务项拥有稳定 `task_id`，并独立保存标题、说明、周期/持续范围、条件、进度、目标、奖励、状态、可领取标记、进度来源、领取时间和幂等结果。一个任务的刷新、失败、领取或重复请求不能改变另一个任务。
2. 任务类型和任务分组由服务配置返回，不在客户端固定枚举。`group_id`、`group_label`、`reset_policy` 等元数据只供服务识别和结算，页面不据此生成分组标题或不同视觉层级；所有任务同级平铺显示。当前本地镜像只实现 `daily` 按服务日刷新，以及非 `daily` 项保留已确认状态的兼容语义；`weekly`、`monthly` 等名称目前只是服务识别元数据，不代表已经实现对应周期调度。要开放新的周期，必须先补周期键、跨周期迁移和幂等边界，不能让客户端自行解释。
3. `daily_login` 是登录结算记录，不在页面显示确认行；成长解锁是进度结果，不是任务项；毛线球是任务集合中的每日进度项，不提供领取按钮。它与领取小鱼干的每日任务同级显示，进度只能由服务确认的既有用户互动更新，不能由打开面板或点击任务项伪造。
4. 毛线球任务进度只由既有用户互动产生：用户完成聊天框或后续具备独立猫回应终态的毛线球操作，适配层提交统一终态，服务确认后再更新任务页面的毛线球进度。打开任务页、点击进度项或点击陪玩类别都不能增加次数。
5. 养宠面板的陪玩内容区只显示服务配置的消耗品内容及库存。当前没有消耗品配置时，不额外显示毛线球卡片、不显示“毛线球/消耗品”混合占位，也不因为任务页显示毛线球进度而复制一份陪玩入口。

本修订不改变锁定文档关于毛线球“用户主动且猫有回应才算陪玩”、前 N 次计入进度、之后仍可玩但不再计进度的规则；它只明确任务页面、陪玩内容区和服务任务契约的边界。

现有项目中，聊天框毛线球已有用户拖动事件，动作层也已有毛线球播放和完成/取消终态；重力 playground 的短点击则只发送恢复聊天框的语义事件、移除毛线球 body，按当前代码和辅助设计文档没有猫回应终态，也不产生 Cat Mind observation。阶段 6 必须增加独立的养宠动作适配层，不读取 Cat Mind 的五维、阈值或自主选择结果；任何来源都不能把“用户点击”本身冒充猫已回应。`cat1-journey-local` 这类来源本身不能证明用户陪玩，当前终态没有明确活动标识，因此继续排除；没有活动租约的自动 journey 和 Cat Mind 自主玩球均排除。逗猫棒没有现成用户来源，因此由养宠面板以具体消耗品内容提供入口，复用玩球表现的独立终态回调；这不等于新增毛线球直点按钮。

统一事件链固定为：

```text
已有毛线球交互的用户拖动/点击
→ 记录 source、activity_id 和 user_initiated
→ 现有动作执行器开始
→ 记录 cat_responded
→ 完成 / 取消 / 无回应 / 超时终态
→ 只有 user_initiated + cat_responded + done 才提交服务结算
→ 面板刷新服务确认的次数、进度和状态
```

`source` 只用于区分事件来源和排除自动行为，不为聊天框、重力 playground 和面板建立三套业务规则。面板不新增毛线球直接触发回调；如果后续需要从面板引导用户使用已有毛线球，也只能定位或提示已有交互，不能把一次面板点击直接视为猫已回应。

阶段 6 的代码边界和顺序如下：

1. 先在动作层补齐统一的用户意图、动作开始和终态适配，确保自动来源不会单独进入养宠结算；对 Cat Mind 仅放行带 `chat_yarn_drag_completed` 用户触发证据的毛线球请求，现有 `cat1-journey-local` 终态在没有明确活动标识前保持排除；重力 playground 只有在补出“用户点击后猫真实回应”的独立终态后才能接入，当前短点击恢复链路先保持不结算；
2. 再在本地养成服务增加可配置的陪玩内容、服务日次数、毛线球前 N 次进度、消耗品每日次数、状态变化和幂等结算；不增加第二个进度字段，也不新增道具 CD；
3. 扩展现有养宠操作契约，让服务只在统一终态确认后更新陪玩次数、进度、精力、清洁度和消耗品库存；失败、取消、无回应、超时和重复请求保持安全状态；
4. 最后更新面板：任务内容区域直接平铺服务返回的任务项，领取小鱼干的任务显示领取操作，毛线球任务显示服务确认的每日进度但不显示领取按钮；陪玩内容区只显示服务返回的消耗品内容、库存和处理中/结果状态，点击消耗品后走独立玩球表现终态，不把面板按钮当作毛线球动作源；
5. 用聊天框毛线球、重力 playground、自动 Cat Mind 玩球、无回应、取消、超时、次数边界、消耗品库存和刷新恢复逐项验收。

## 10. 阶段 6：用户主动陪玩

### 实施目标

在阶段 3 已建立的冲突型 Cat Mind 自主请求门控下，把用户主动陪玩和玩具使用接到独立动作执行器，并形成可结算的业务事件；用户拖动毛线球触发的 Cat Mind 回应仍属于用户活动链，不能与纯自主请求混为一谈；不改变现有 Cat Mind 对普通猫行为的其他职责。

### 实施内容

- 毛线球优先复用现有动作；逗猫棒首版暂用玩球反馈，清洁类别中的梳毛操作暂用伸懒腰反馈；后续替换具体反馈表现不改变业务类别、用户操作、物品消耗和养成结算；其他当前缺少统一终态的动作，由首版补齐独立执行器或基础表现后再接入适配器；
- 逗猫棒是消耗品，首版用测试种子提供库存，正式来源在探索掉落阶段接入；服务确认使用成功后扣除一次；
- 记录用户发起、猫真实回应、动作完成或取消；
- 只有用户主动且猫有真实回应才提交陪玩结算；
- 猫自主发起的玩耍不计入养成陪玩进度；用户主动毛线球每日前 N 次按自身次数/基础增量配置汇入唯一养成进度，之后仍可玩但不再给进度；消耗品陪玩使用独立的次数和基础增量配置并受服务端每日次数上限约束，不互相污染；
- 养宠面板的陪玩内容区不新增一个点击即触发毛线球反馈的按钮，也不重复放置一个没有操作意义的毛线球卡片：真实毛线球操作继续发生在现有聊天框最小化和重力 playground 交互中；聊天框来源当前通过统一适配器回传终态，重力 playground 现有短点击仍只有恢复聊天的终态，待补出独立的猫回应契约后再接入养宠结算。服务确认的毛线球任务进度直接随统一任务集合返回，与其他任务同级显示，不进入陪玩内容项；只有配置为可领取的任务才显示领取操作。服务配置返回的逗猫棒等具体消耗品则作为独立内容项显示库存和次数，点击后调用养宠专用玩球表现桥，仍需等动作终态和服务确认后才扣除；
- 有现成能力的动作复用现有动画、动作和终态事件，新增动作沿用相同的终态契约。

### 用户可见验收

1. 用户通过已有聊天框毛线球交互主动拖动或点击，猫执行动作并返回完成结果；养宠面板同步显示服务确认的陪玩结果，不直接触发毛线球动作。重力 playground 当前只验证原有恢复聊天链路，未把点击或碰撞当作猫回应或陪玩结算；
2. 用户使用逗猫棒时，库存、动作终态和陪玩结算一致；
3. 猫没有回应或动作被取消时，不增加养成进度，也不扣除逗猫棒；
4. 服务拒绝或重复提交时，逗猫棒只扣除一次或不扣除；
5. 毛线球前 N 次能按自身配置结算进度，之后仍可玩但不再计进度；消耗品陪玩受库存数量和服务端每日次数上限限制；两者都不新增道具 CD；
6. 退出登录后普通猫恢复原有行为；
7. 刷新后从服务恢复陪玩库存和各类进度。

### 阶段完成条件

- 手动陪玩由养宠适配器调用已有或新增的动作执行器；
- 动作执行器保持独立，养宠只接收统一终态事件；
- 所有陪玩成功、取消、无回应和重复请求场景均可验收；
- 旧自主触发暂时停用后，现有动作能力仍由动作执行器提供。

### 阶段 6 执行记录（2026-10-17）

本阶段已完成当前可证明来源的本地闭环：聊天框毛线球的有效拖动、养宠面板中的消耗品操作 → 猫响应终态 → 服务确认陪玩结算。阶段 6 不能标记为所有锁定来源无条件完成：现有最小化聊天框毛线球的静止点击会恢复聊天窗口，现有 CAT1 playground 毛线球短点击也只恢复聊天并移除毛线球 body，两者都没有“猫回应完成”终态，因此不计入陪玩结算；在不改变既有恢复功能的前提下，必须等后续补出独立的猫回应终态后再接入。养宠面板的“陪玩”不新增点击即播放毛线球的业务按钮，也不重复放置毛线球内容项；毛线球任务每日进度直接随统一任务集合返回，与领取小鱼干的任务同级显示；只有小鱼干任务提供领取操作。服务配置中的逗猫棒等具体消耗品以内容项显示，并在独立动作终态完成后提交结算。

- **实际代码通路**：聊天框最小化毛线球的既有拖动适配器在完整用户手势结束后产生 `chat_yarn_drag_completed`，适配层只接受带 `userInitiated=true` 且 `endedNearCat=true` 的用户手势，建立短时活动租约；用户从 CAT2/CAT3 发起这类操作时，适配器先通过 `wakeCat1ForCare` 切回 CAT1，再等待既有 `cat1_play_yarn` 终态，唤醒只改变表现层，不参与业务结算。现有 Cat Mind 若因该用户触发作出 `cat1_play_yarn` 请求，适配层才等待其完成终态并提交服务。重力 playground 当前短点击只产生 `neko:idle-cat1-playground-yarn-activate`，恢复聊天框并移除毛线球 body，不产生猫回应终态，因此本阶段不会把它结算为陪玩；已有 `cat1-journey-local` 终态没有用户活动标识，继续作为自动表现，不参与养宠结算；没有用户租约的 Cat Mind 自主结果同样不会结算。
- **门控边界**：阶段 3 的 Cat Mind 兼容门控仍屏蔽自主动作；仅带 `chat_yarn_drag_completed` 证据的毛线球请求放行给既有 Cat Mind 决策链，不能把用户触发的响应误判为自主行为。养宠逻辑不读取 Cat Mind 五维、阈值或选择结果。
- **服务结算**：本地服务新增可配置 `playing` 内容、允许来源、服务日计数、毛线球前 N 次进度、消耗品库存与每日上限、能量/清洁度变化和幂等活动事件。只有 `user_initiated + cat_responded + terminal_status=done` 且来源命中该内容的服务白名单时，才更新计数、状态和进度；取消、无回应、超时、失败、自动/未知来源和库存/次数拒绝都不扣除或发奖。陪玩写入使用 `content_id + activity_id` 的服务规范化幂等键，同一活动换客户端幂等键也不会重复结算。请求开始时页面按服务返回的同一配置生成临时能量、清洁度和进度预览，终态非成功或服务拒绝即清除，库存和次数不做客户端预扣。
- **面板结果**：服务返回统一的 `tasks.items` 和陪玩动作配置；页面在任务内容区域以与其他任务相同的卡片样式显示毛线球任务项的确认进度，且没有领取或直接触发动作的按钮；`play_actions` 只提供陪玩动作、次数限制、库存和反馈配置，不承担任务展示。陪玩内容区按配置动态显示带库存的消耗品内容项。消耗品点击后保持处理中状态，只有独立表现终态完成且服务确认才更新库存/次数。服务失败不会乐观增加进度或扣库存，面板固定内容区不会因等待或结束而跳变；陪玩等待或结算期间，喂食、清洁、任务领取和其他陪玩入口保持置灰，避免多个用户动作争用同一只猫。
- **旧快照收口**：任务面板打开时始终读取任务接口，不因宠物快照已有旧 `tasks` 字段而跳过刷新；服务在同一服务日把新增配置任务补入已有 `tasks.items`，因此旧账号无需等到次日即可看到毛线球任务。若用户在账号/角色绑定尚未完成时已打开面板，绑定完成后也会自动补做任务读取，不要求用户关闭后重新打开。

### 阶段 6 收口审查（2026-10-17）

## 11. 阶段 7：单探索地、猫离场和统一召回

### 实施目标

完成首版最核心的跨会话活动，让用户能看见猫出发、离场、来信、回家和召回。

### 实施内容

- 增加一个探索地点；
- 开始探索前检查饱食、精力、清洁、负面状态和当前活动；心情在出发时保存快照并用于收益计算，首版不把心情单独作为探索前置条件；
- 服务先创建活动并扣除消耗；
- 播放出发动作，完成后隐藏猫形象；
- 清理在跑动作、定时器和尾回调；
- 切换为猫窝命中区域和探索期间素材；素材由探索表现适配器独立管理，不注册为 `cat1/cat2/cat3` 形态，也不交给 Cat Mind 管理。宠物形态通用素材统一放在 `static/assets/neko-idle/`，当前本地验收使用其中的透明 PNG `static/assets/neko-idle/cat-bad.png`，后续可直接替换资源而不改变活动契约；
- 素材切换只发生在服务确认探索活动、出发动作完成并进入离场状态之后。正常完成或召回完成后恢复原猫形态素材和命中区域；素材切换失败不能改变服务活动和结算结果；
- NEKO-PC 只接收页面提供的窗口/命中区域和输入转发变化，不保存探索状态、不判断活动、不执行奖励或结算；
- 展示倒计时纸条和随机来信；
- 提供仅用于验收的可控测试时钟，缩短探索等待；测试时钟不改变正式奖励公式；
- 探索期间由养成活动状态门控所有依赖猫实体的输出，包括旧自主触发、journey、playground、重力/窗口感知、贴边探头、移动、音效、悬停、拖拽、喂食、清洁操作（首版为梳毛）、陪玩及延迟尾回调；这不是 Cat Mind 的业务判断，也不能依赖 Cat Mind 重新计算。猫窝、纸条、来信、探索面板和统一返回入口继续可用；
- 正常完成时由服务结算，恢复猫在场并播放回家动画；
- 用户切回模型时，经现有统一返回入口发起强制召回；
- 正常完成走探索完成接口，强制召回走召回接口；两者共用活动幂等和奖励规则；
- 以 `neko:cat-return-commit` 作为一次召回结算挂点，`neko:cat-return-complete` 只负责表现收尾；
- 召回请求失败或超时可以重试；首次被服务接受时记录服务时间和幂等结果，重试沿用同一结果，不按迟到响应时间重新计算；成功后向用户显示确认的结算信息；
- 奖励和进度只在服务确认后展示。

首版先确定以下可调的奖励语义：正常探索完成按完整时长结算并享受完整探索加成；强制召回按已完成时间比例结算，未完成部分不享受完整加成；两者都使用出发时保存的心情计算收益。具体掉落数量、概率和加成放入配置，后续可调整。

### 用户可见验收

1. 用户开始探索后，先看到出发动作，然后猫形象离场；
2. 原位置出现猫窝或空坐垫、倒计时纸条；
3. 探索期间所有依赖猫实体的输出均停用，猫窝保留状态和返回入口；
4. 用户能看到来信，收获在探索结算后发放；来信数量按锁定稿随机为 1 到 3 次；
5. 猫窝上有探索状态和召回入口；
6. 正常完成后猫回家并显示确认后的收获；
7. 猫窝召回先走探索服务结算并恢复猫形态；用户切回模型时才复用现有模型返回入口，探索强制召回动画不超过 1 秒；
8. 用户切回模型路径的召回未获服务确认时不显示模型与离场猫窝的重叠状态，也不显示未确认奖励；当前活动门和可重试状态保留，服务确认后才完成模型切换；猫窝面板召回失败同样保留猫窝和重试入口；
9. 迟到的召回或探索响应不会把已经切回模型的用户重新切回猫形态；
10. 正常完成与强制召回的奖励差异符合配置，且都使用出发时的心情；
11. 刷新页面或重启本地服务后，探索仍处于正确阶段；服务暂时不可用时，已有探索保留猫窝和离场状态，恢复后继续读取活动。

- 猫离场同时切换动作、探索素材、命中区域和延迟回调，回家后恢复原猫形态素材；

### 阶段 7 执行记录与收口结论（2026-10-18）

**阶段 7 召回分流与任务显示纠错记录（2026-10-18）**

本轮复核发现两处实际错误并已修正：

- 猫窝面板的“召回猫咪”曾直接调用 `appUi.returnFromGoodbye`，只要复用可见 return 容器就会进入 `*-return-click`，把猫窝召回错误地变成模型回归。现在面板召回只提交探索 `recall` 并在服务确认后恢复猫形态；用户切回模型、角色切换和模型热重载才进入统一模型返回链。模型已显示时不会因迟到容器事件再次显示猫窝。
- 小鱼干是独立手动领取任务，不定义进度。服务不再为缺少进度配置的奖励任务合成 `progress: 0`，前端也只在 `progress` 与 `target` 都由服务明确返回且为有限数字时渲染进度；毛线球任务仍显示服务确认的 `0/N`。
- 角色切换和模型热重载加入了探索召回前置检查，避免只覆盖一个模型入口；账号显式退出、外部退出和刷新后的重新登录提示沿用统一会话记录。

**阶段 7 生命周期与弹窗单主归属修正（2026-10-18）**

本轮针对真实双窗口结构复核后，确认 `/` 模型宿主页和 `/chat`、`/chat_full` 聊天跟随页都曾初始化完整 `app-pet-care.js`。这会让两个 renderer 各自读取会话、监听探索终态并创建 `common_dialogs.js` modal；窗口级 `sessionStorage` 不能去重跨窗口提示，最终表现为退出或探索结束后出现两层弹窗，关闭上层后下层仍拦截输入。

- **单一页面职责**：`app-pet-care.js` 现在发布 `nekoPetCareSurface` 契约。模型宿主页拥有养宠入口、服务读取/写入、模型生命周期协调和用户可见确认；聊天跟随页不创建养宠面板、不刷新养宠快照、不执行探索召回、不显示账号或探索弹窗。聊天框毛线球仍由原有跨窗口动作桥回传到模型宿主页的阶段 6 适配器。
- **单一退出协调器**：`nekoPetCareEntry.ensureExplorationEndedBeforeModelExit()` 是模型/猫形态离开前唯一服务召回协调器。`appUi.returnFromGoodbye`、`showCurrentModel()` 以及角色切换前置都复用它；同一活动的并发退出共享同一个 Promise 和 `pet-exploration-recall-{activity_id}` 幂等键，服务未确认时阻止模型显示，确认后才允许旧形态离开。移除了角色变化路径中独立的直接 fallback POST，避免事件召回、补偿请求和模型显示三条链交叉。
- **入口覆盖**：所有复用 `showCurrentModel()` 的会话返回、麦克风/屏幕恢复、WebSocket 重启和教程恢复路径都经过模型显示总入口；聊天跟随页收到角色广播时直接返回，不参与模型资源和养宠生命周期。猫窝“召回猫咪”仍是独立的猫形态回家操作，不经过该模型退出协调器。
- **提示不叠层**：模型宿主页内的养宠确认使用串行队列；同一时刻只存在一个可确认 modal，后续不同状态消息等待前一个关闭，不再追加多个遮罩。刷新仍按锁定稿保留服务活动和猫窝/门控；刷新本身不是“切回模型”，已成功展示过的服务终态不因恢复页面再次提示，只有尚未成功展示的首次终态才补提示。

**阶段 7 生命周期再审与可扩展边界（2026-10-18）**

本轮不是给单个入口加补丁，而是把“离开当前猫形态上下文”和“加载新账号/角色上下文”收敛到同一层级的生命周期协调器：

- **退出前置**：模型显示、统一返回、模型热重载、角色显示变化、猫形态主动离开和本地显式退出，都先调用 `ensureExplorationEndedBeforeModelExit()`；账号/会话变化再经 `ensureExplorationEndedBeforeAuthChange()` 串行等待。未获服务确认时不清理旧快照、不清除离场租约、不提交新角色/登出，并保留可重试错误；服务确认后才释放旧上下文。刷新和 `pageshow` 不属于退出，仍按锁定稿恢复进行中的活动。
- **服务端兜底**：客户端预检之外，`LocalPetCareBindingService.bind()` 在同一事务读取旧宠物快照；活动进行中拒绝换绑并回滚，避免任何迟到的前端请求把探索活动带到新角色。召回或正常完成确认后才能重新绑定。
- **内容目录**：照料面板不再维护小鱼干/梳毛的固定前端列表。服务返回的 `care_actions` 是当前内容目录，前端只负责展示类别下的具体内容、库存和服务确认结果；小鱼干的“只恢复饱食度、不增加进度”仍在服务端配置校验中保留，未来食物和清洁操作可通过目录扩展。
- **层级与职责**：模型宿主页是养宠业务和提示的唯一 owner；聊天跟随页只转发已有互动。生命周期协调器只负责活动终态与上下文切换，探索表现适配器只负责离场/猫窝/纸条/来信，养成服务只负责状态、库存、任务、活动和结算，NEKO-PC 仍只处理窗口、输入和 IPC。

这次再审补充了角色切换失败保留旧活动、显式退出先召回、服务端活动中拒绝换绑以及动态照料目录的回归。外部窗口已经先完成 OAuth 注销、导致旧服务凭证不可用的极端情况只能保留本地活动租约并等待下一次统一会话恢复，不能伪造“已召回”；正式社区服务器仍需提供同一幂等召回契约。

本轮新增/更新回归：任务小鱼干不显示 `0/0`，毛线球保留 `0/3`；猫窝召回与模型返回事件分流；模型热重载、角色切换和外部退出后重新登录提示有静态/运行时契约覆盖。
本轮按锁定稿 Q11/Q11a、Q13 和本节契约补齐并收口了本地代码闭环，锁定文档未修改。阶段 7 的本地服务、页面契约、活动门控、形态分流、刷新租约和提示去重已经完成；真实 PC 生命周期、视觉时序和长时间活动仍列为阶段 9 的实机验收项，不能用静态契约测试代替。长期状态、活动条件、消耗、心情快照、来信计划、奖励、掉落和幂等结果均由本地养成服务持有；前端只提交开始/完成/召回请求并显示服务确认的快照。

### 开发调试工具（本地验收辅助）

为便于阶段 4 以后反复验收状态边界，增加一个独立的开发调试操作：服务进程显式设置 `NEKO_PET_CARE_DEV_TOOLS=1` 后，已绑定角色的养宠面板才显示“开发工具 / 三项状态加满”。按钮调用 `POST /api/pet-care/pets/{character_uid}/debug/fill-status`，由本地养成服务在事务内确认账号、角色、探索状态和幂等键，然后只把饱食度、精力、清洁度设为状态上限。

该操作不改变心情、养成进度、库存、任务、解锁、奖励或 Cat Mind，也不能在探索期间使用；未显式开启开关时能力字段和接口均不可用。前端只应用服务返回的完整快照，不直接改写数值。该开关和接口属于本地开发/验收辅助，不进入正式社区服务契约。

- **服务与接口**：本地服务增加可配置单探索地点、`POST /explorations`、当前状态和按 ID 读取、正常完成、强制召回五条接口。开始活动在同一事务中检查当前活动、饱食度、精力、清洁度和生病状态，保存出发心情并扣除消耗；完成按完整时长结算，召回按服务时间比例结算，掉落按配置和比例处理；重复请求按幂等记录重放，SQLite 重启后仍能读取活动。
- **页面闭环**：养宠面板从服务响应恢复活动 ID、代次、地点、已确认来信和倒计时；面板只显示探索摘要、状态、来信、收获和召回入口，不重复放置桌面猫窝素材。喂食、清洁、陪玩及重复探索入口按活动状态置灰。正常完成和召回都沿用同一结算适配器，奖励、进度和掉落只在完整服务快照确认后显示；失败、超时和旧代次响应保留活动并允许重试。
- **离场与门控**：服务确认后发布探索活动门，门控独立覆盖 Cat Mind、journey、playground、重力/窗口感知、贴边、移动、音效、悬停、拖拽和延迟回调；猫窝、纸条、来信、面板和统一返回入口不被清理广播关闭。活动 ID 与本地门代次用于拒绝旧活动的迟到释放，账号、角色或绑定上下文切换会 fail-closed 清理旧门。服务活动代次只作为跨模块身份传递，不直接当成本地门代次比较。

- **开始/结束竞态**：开始探索要求当前仍在猫形态且没有喂食、清洁、陪玩、任务领取或另一探索写入；服务确认开始后 CAT2/CAT3 只唤醒为同一只宠物的 CAT1 表现。正常完成、猫窝召回和模型切换召回均绑定活动 ID；回家先隐藏旧素材并等待有界恢复表现，再释放探索门，旧活动的回家定时器和迟到的容器状态不能重显猫窝覆盖新模型。探索活动门的各个实体监听也校验活动 ID，旧活动的迟到 active/inactive 广播不会重开或解除新活动的门；正常完成失败后的自动重试采用退避，猫窝仍保留手动重试入口。
- **服务响应边界**：活动进行中只返回服务已揭示的 `letters_revealed`，不把完整随机来信池或随机种子泄露给前端；活动终态确认后才返回完整来信和奖励。探索地点的 `asset_url` 只供桌面离场表现，来信图片使用来信自身的可编辑字段，前端不把猫窝资源当地点或来信图。
- **统一召回时长**：普通模型返回沿用既有过渡锁；只有用户切回模型时的探索强制召回接入模型返回事件链并使用探索专用的不超过 900ms 过渡上限，猫窝面板召回不触发模型过渡。首次确认召回、正常完成或此前未成功展示的终态，都通过可确认的养宠提示展示服务已确认结算信息；共享页面优先调用 `common_dialogs.js` 的 `showAlert`，脚本尚未挂载时才退回原生可确认提示，不能只显示右上角短 toast。终态提示按账号和探索活动 ID 在设备本地持久去重，同一活动从 `completed`、`recalled` 或 `returned` 变化也只提示一次；模型/角色/退出前置召回可抑制中间终态提示，由最终会话提示统一说明。显式退出、服务确认的外部退出以及刷新后重新确认的退出，均通过同一会话提示记录在下一次登录时说明；网络失败不伪造退出成功。没有服务确认时不伪造收获。

## 12. 阶段 8：离线结算、负面状态和角色切换

### 实施目标

在不引入 Cat Mind 业务依赖、不给 PC/Web 增加第二份存档的前提下，验证养宠状态可以跨统一账号会话、时间和角色正确恢复。阶段 8 的核心是服务端一次性离线结算，不是前端计算离线时长，也不是增加几个状态按钮。

### 实施内容

- **会话边沿契约**：统一账号适配层向养成服务提供受信的 `account_id`、稳定会话边沿/离线段标识、会话是否从明确失效恢复等信息。`session_generation` 不能直接复用会因 token refresh 变化的 OAuth 计数；网络暂不可用、已保存凭证和普通 token refresh 都不能触发离线结算。前端不得提交离线开始时间、随机种子或结算结果。
- **状态补算**：普通读取仍只按 `last_settled_at` 补算服务配置中的基础状态；`last_settled_at` 是状态游标，不是统一账号会话失效时间。服务同时持久化配置化的 `interaction_index` 和其衰减游标，并在服务事务内由三项状态与互动指数重算心情；阶段 8 的负面判定只使用补算后的快照值和离线段确定性抽样，重复读取不重新随机。前端只显示服务返回的心情，不能自行重算。
- **一次性恢复事务**：只有明确的“会话失效 → 重新有效”边沿触发 `reconcile_on_session_restore`。事务顺序固定为：补算状态 → 按配置执行长期未登录进度回退 → 使用补算后的状态值一次判定生病/赌气 → 生成恢复任务 → 保存可重复读取的结算回执 → 返回完整快照。药品和逗猫棒只在任务成功领取后进入库存；重复请求按离线段幂等，不重复回退、抽样、扣除或发奖。
- **长期未登录回退**：连续 5 天不登录后才允许回退，回退下限为最近解锁存档点；已经解锁的内容永不删除。5 天、回退速度和边界全部配置化，数值草案中的 48 小时、概率公式和每日回退点数只作为可替换本地测试配置。
- **负面状态**：生病与赌气是可并存的独立状态，同一离线段各自最多判定一次；所有状态值达到锁定稿保护条件时不触发。生病只禁止探索，普通清洁、照料、左键返回模型和悬停入口继续可用；赌气通过成功的陪玩恢复，不得擅自扩大成探索禁用。
- **恢复任务和物品**：恢复任务作为服务返回的普通同级任务记录，不增加固定“状态任务”分组或常驻按钮。求药、药品使用、取得逗猫棒、逗猫棒使用和状态清除均由服务确认；失败、取消、超时不扣物品、不清除状态。任务、奖励、物品 ID 和数量全部配置化。
- **角色和请求边界**：同一账号只有一只宠物；绑定角色继续读取该宠物，其他角色走普通猫。账号、角色、会话和请求代次都参与响应围栏，迟到响应不能覆盖当前页面。角色改名、模型切换和猫档位变化不改变稳定绑定关系。
- **探索和断线**：非探索状态断线时停止养成写入，恢复后重读服务结果；活动探索按阶段 7/8 的活动租约继续保持离场并恢复猫窝、纸条和来信。主动退出、账号切换、角色切换等会导致离开猫形态的链路统一走探索结束/召回确认，不能由各模块分别处理。模型形态和猫形态始终互斥，猫窝召回不进入模型返回链。
- **架构边界**：养成服务持有状态、规则、库存、任务、奖励、探索和结算回执；NEKO-PC 只处理窗口、输入、命中区域和 IPC；Cat Mind 不接收养成五维、负面状态或长期结算。阶段 8 继续使用本地服务完成闭环，正式社区服务在阶段 10 按同一契约接入。

### 用户可见验收

1. 修改测试时间或等待离线窗口后重新登录，状态正确补算；
2. 同一离线段重复登录，不重复触发负面状态；
3. 生病时出现求药任务，完成任务领取药品，使用药品并确认扣除后恢复；
4. 赌气时出现取得逗猫棒的恢复路径，取得后使用并确认扣除后恢复；
5. 生病期间探索入口不可用；
6. 切换到绑定角色继续读取账号唯一宠物，切换到其他角色按普通猫处理，迟到响应不会覆盖当前页面；
7. 绑定角色改名、换模型或换猫档位后仍通过原稳定角色标识读取同一只宠物；
8. 非探索状态断线时普通猫和统一返回模型可用，养成写操作停止；已有探索仍保持猫窝和离场状态；
9. 恢复后重新读取确认结果，探索状态不被错误结束；
10. 连续 5 天不登录后，进度最多退到最近存档点，已解锁内容仍可用。

### 阶段完成条件

- 有可控的服务端时间和会话边沿测试方式，能够区分普通读取、网络暂不可用和明确失效后恢复；
- 状态补算、长期回退、负面判定、恢复任务、物品使用和结算回执可重复验证；
- 同一离线段重复读取、刷新、重新登录和重试都不改变结果；
- 账号、角色、会话和请求代次均参与响应校验；
- 断线期间仍只有一份可写存档，恢复后只重读服务确认结果；
- 本阶段不修改锁定文档，不把 Cat Mind 或 PC 变成养成业务依赖。

### 实施顺序与阶段性收口

1. **会话适配和边沿契约**：先补齐统一账号适配返回值，明确 invalid→valid、网络不可用、token refresh 和显式退出的区别；完成后只验会话边沿，不执行负面结算。
2. **存储和一次性结算回执**：增加离线段游标/回执和迁移，保证状态补算、回退、抽样和任务物化在服务事务内幂等；完成后验重复请求和失败重试。
3. **负面状态、回退和恢复任务**：实现配置驱动的补算、回退、生病/赌气判定、同级任务、药品/逗猫棒领取与使用；完成后逐项验收生病、赌气、并存和保护条件。
4. **角色、探索和断线恢复**：接入角色/请求代次围栏、活动探索恢复和统一退出链；完成后验角色切换、刷新、断线、召回和迟到响应。
5. **前端确认结果接入**：显示服务确认的状态和同级任务，提供服务确认的恢复操作，保持普通照料、返回模型和悬停入口；完成后验 Web/PC 共用契约且不写本地存档。
6. **阶段 8 总验收**：按本节 10 项用户可见验收和服务幂等矩阵复跑，并在本节记录修改内容、测试结果、失败路径、未验证内容和剩余风险。

## 13. 阶段 9：本地首版完整验收

### 实施前准备（2026-10-18）

阶段 9 的性质是本地首版总验收和必要的小修收口，不新增产品规则、不新增一个与锁定稿无关的业务层，也不提前接入正式社区服务器。验收目标是证明阶段 0–8 已落地的同一套服务契约能够在真实用户路径中完成一次可恢复的养宠循环，并且失败、退出、刷新和跨端切换不会污染普通猫或账号数据。

本阶段以《宠物养成系统方案（修订稿）》为目标，以阶段 0–8 的实现、测试和记录为事实依据；数值草案只提供可替换测试配置。发现实现与锁定目标不一致时，先记录差异并做最小范围修正，不能用本阶段验收反向修改锁定文档或扩大首版范围。

### 范围与排除项

必须验收的范围：

- N.E.K.O 统一账号会话、账号唯一宠物、服务确认的绑定角色，以及未登录/非绑定角色的普通猫回退；
- 基于 `last_settled_at` 的读取和操作补算、每日首次登录一次性结算、基础状态和可配置的独立任务项；
- 每日任务手动领取小鱼干；小鱼干只是当前基础食物，不把它当成喂食类别或任务进度条；
- 喂食、清洁类别中的梳毛、用户主动陪玩和服务确认后的库存/状态/进度变化；毛线球必须来自现有用户拖动或点击互动并得到猫的真实回应，Cat Mind 自主玩耍不得计入；
- 小鱼干在首版只从配置的每日任务奖励获得；喂食小鱼干只恢复饱食度，不直接增加养成进度。其他食物和内容仍通过可配置目录扩展，不能把小鱼干或梳毛写成类别本身；
- 单探索地点的出发、猫离场、猫窝和纸条、来信、正常完成、猫窝召回，以及切回模型、角色切换、离开猫形态、刷新和关闭等导致离开猫形态的统一召回链；
- 生病、赌气和状态任务的读取、恢复和探索禁用；一次离线段只能由服务结算一次；
- 可配置进度达到阈值后的解锁显示；不把占位名称、资源或阈值固化为产品规则；
- Web 与真实 NEKO-PC 窗口通过同一个养成接口读取同一账号、同一角色和同一宠物快照。PC 只验收窗口、输入、命中区域和 IPC，不保存养成状态或执行结算。

本阶段明确排除：正式社区服务器和生产数据库、跨设备正式部署、商店/货币/付费猫粮、社交/推送/AIGC、洗澡和复杂小游戏，以及把养成数值写进 Cat Mind 或让 Cat Mind 参与结算。社区服务器的模块归属、迁移和部署属于阶段 10。

### 长期运营数据基线

阶段 9 不把“本地能跑”直接等同于“可以长期运营”。验收时先冻结业务逻辑契约，再明确本地镜像的物理结构、正式服务的逻辑结构和迁移方向。所有时间使用服务端 UTC 时间保存；服务日时区、开始小时、数值、概率、次数、CD、奖励和解锁目录都属于带版本的配置，不能从客户端时间或页面文本推导。

#### 当前本地 SQLite 的实际结构

当前实现集中在 `services/pet_care/binding_service.py`，本地数据库已经有以下表。阶段 9 要把字段和唯一性作为验收断言，不能只比较页面上的数值。

| 表 | 当前字段/变量 | 约束和用途 |
| --- | --- | --- |
| `pet_care_accounts` | `account_id`、`pet_id`、`bound_role_id`、`bound_character_uid`、`created_at`、`updated_at` | `account_id` 主键；`pet_id`、`bound_role_id` 唯一；`bound_character_uid` 只是本地角色解析字段，不是跨设备角色主键。一个账号只能有一只宠物 |

当前实现还建立了 `idx_pet_care_operations_created_at`（操作回执保留/查询入口）和 `idx_pet_care_offline_account_valid_at`（账号离线段查询入口）两个索引。建库和迁移在 SQLite `BEGIN IMMEDIATE` 内串行执行；服务启动先检查已存在的 schema 版本，再执行必要的低版本迁移，不能把未来版本静默改回当前版本。快照读取会将 JSON 中的 `pet_id/account_id/bound_role_id` 与关系表交叉校验，损坏的幂等回执直接 fail-closed，不返回伪造的成功结果。

当前 SQLite 的声明类型也属于契约的一部分：ID、时间、配置版本和 JSON 字段为 `TEXT`；schema/检查点/数量等离散值为 `INTEGER`；离线时长为 `REAL`。正式服务迁移时，ID 仍保持不透明字符串或 UUID，数量、状态、进度和版本使用有范围约束的整数，时间统一为带时区的 UTC 时间；不能因为换数据库而把数量、状态或进度改成浮点数。

快照中的逻辑变量必须保持以下含义：`status_values.satiety/energy/cleanliness/mood` 为受配置约束的整数状态，`status_values.progress` 为非负累计进度；`interaction_index` 和 `interaction_last_settled_at` 属于养成服务自己的互动指标；`negative_status.sick/sulk` 各自有独立状态和恢复任务；`inventory` 按 `item_id` 保存数量；`tasks` 按独立 `task_id` 和服务周期保存进度、目标、奖励、状态和领取幂等信息；`exploration` 保存地点、活动 ID、状态、服务开始时间、时长、消耗、来信计划、随机结果和结算结果；`unlock_checkpoint` 只表示进度回退下限，已解锁内容不能被删除。

当前 JSON 快照适合本地镜像和阶段 9 的隔离验收，但不能默认是正式服务的最终查询结构。需要查询、并发更新、审计或独立生命周期管理的内容，正式服务不得继续无限堆进一个 JSON 字段。

#### 当前配置结构和版本要求

本地 `DEFAULT_PET_CARE_SNAPSHOT_CONFIG` 及 `pet_care.json` 的顶层结构目前包含：`schema_version`、`initial_status_values`、`initial_negative_status`、`initial_inventory`、`initial_tasks`、`initial_unlocks`、`initial_exploration`、`mood_formula`、`exploration`、`playing`、`service_day`、`task_catalog`、`daily_login`、`offline_settlement`、`unlock_catalog`、`settlement` 和 `care_actions`。这些是配置边界，不是第二份产品规则。

每个配置块都必须有明确的 schema、类型、范围和默认处理：状态上限/下限、时间单位、服务日时区、任务周期键、奖励物品、库存数量、探索地点、信件计划、概率和解锁阈值都由服务端校验；客户端只能读取服务返回的目录。配置发布需要产生不可变的 `config_version` 和内容摘要，操作、探索、离线结算和任务实例保存采用的配置版本，历史结果不能因当前配置修改而重算。配置缺失或非法时拒绝加载或进入只读安全状态，不能用半套默认值覆盖正式配置。

#### 当前本地结构与长期结构的差异

以下差异必须在阶段 9 报告中单列，不能用“测试通过”掩盖：

- 本地快照把状态、库存、任务、探索和解锁放在 JSON 字段；正式服务需要把可查询、可并发和有独立生命周期的实体拆出；
- 本地操作结果表没有过期/归档字段，正式服务需要定义幂等结果保留期、归档和重复请求查询策略；
- 本地快照没有独立的 `state_version`/乐观锁字段，正式服务需要用行版本或等价事务机制防止并发覆盖；
- 当前没有正式审计表、配置修订表和统一请求关联 ID，阶段 9 先在验收日志中记录，阶段 10 正式服务必须落地；
- 当前 `LocalPetCareBindingService` 同时承载 schema、迁移、规则和存储操作，阶段 9 不做大规模重写，但新增接口不得继续绕过边界；阶段 10 迁移时按应用用例、领域规则和仓储端口拆分。

| 背包 `pet_inventory` | `pet_id`、`item_id`、数量、来源、更新时间 | `(pet_id, item_id)` 唯一；数量不能为负；扣除与操作结算同一事务 |
| 任务实例 `pet_task` | `pet_id`、`task_id`、服务周期键、标题/说明配置版本、条件来源、进度/目标、状态、奖励、领取时间 | `(pet_id, task_id, cycle_key)` 唯一；任务逐条独立，前端不能按周期或类型重组为固定分组 |
| 探索活动 `pet_exploration` | 活动 ID、`pet_id`、地点、状态、服务开始/接受/结束时间、时长、消耗快照、来信计划、随机种子或结果、奖励结果、召回时间 | 每只宠物最多一项活动处于活动状态；完成/召回只能成功一次；结果在开始或首次接受结算时固定，重试不能重抽 |
| 操作幂等 `pet_operation` | 账号、宠物、幂等键、请求摘要、操作类别、状态、结果、创建/过期时间 | `(account_id, idempotency_key)` 唯一；摘要不一致返回冲突；保留期和归档策略可配置 |
| 离线结算 `pet_offline_settlement` | 离线段 ID、会话前后标识、开始/结束时间、时长、配置版本、负面状态和回退结果 | `(account_id, segment_id)` 唯一；同一段不重复判定、不重复回退 |
| 审计记录 `pet_audit_log` | 请求 ID、账号/宠物脱敏标识、操作类别、结果码、状态前后摘要、配置版本、服务时间 | 追加写入；不记录 token、完整凭证或不必要的个人信息；用于排查和对账，不能反向驱动业务 |

库存、任务、探索、解锁和审计实体可以继续保留扩展 JSON 用于内容配置，但业务主键、数量、状态、时间、版本和唯一性不能只存在不可查询的 JSON 文本中。正式服务应建立 `pet_id`、账号、绑定角色、活动状态、周期键、幂等键和创建/更新时间索引；索引名和具体数据库语法由阶段 10 的部署项目决定。

#### 数据不变量和事务边界

- 账号、宠物和绑定角色的唯一性必须由数据库约束和服务事务共同保证；当前角色不匹配只返回普通猫路径，不创建第二个宠物。
- 读取或写入前由服务按 `last_settled_at` 补算；客户端时间只用于显示，不能提交未来时间、概率或奖励结果。
- 状态变化、库存扣除、任务领取、进度、解锁和探索结算必须在同一业务事务内完成；失败、取消、超时、无回应和活动冲突回滚整笔写入。
- 会话围栏、`state_version`/行版本和幂等检查必须在同一写事务内再次确认，不能只依赖路由预检；迟到响应不能覆盖新会话、新角色或新状态版本。
- 探索开始原子扣除消耗并创建唯一活动；探索进行中拒绝依赖猫实体的操作；正常完成和召回使用同一活动记录但不同终态，奖励按首次服务接受时间计算。
- 负面状态只在统一账号会话重新有效时对同一离线段判定一次；回退不低于 `unlock_checkpoint`，已解锁内容不回收。

#### 迁移、备份和恢复

本地镜像继续使用显式 schema 迁移，不删除未知列、不静默覆盖旧数据；每次迁移记录 `schema_version`、配置版本、执行时间和结果。阶段 9 必须用阶段 1/2 的旧库、包含阶段 7 探索字段的库和包含阶段 8 互动/离线字段的库做向前迁移测试，并验证失败时原库可恢复。

阶段 9 的验收夹具必须使用临时数据库、临时配置和临时端口；执行前后保存正式本地存档哈希，验收后逐字节确认未被污染。正式部署前另需确定备份频率、恢复演练、保留期限、RPO/RTO、迁移回滚方式和数据清理策略；这些是阶段 10 的部署门槛，不能在本地验收中假定已满足。

### 长期运营代码层次和依赖方向

当前本地实现事实是：`main_routers/pet_care_router.py` 负责 HTTP、`services/pet_care/account_session.py` 负责统一账号适配、`services/pet_care/binding_service.py` 同时包含本地 SQLite schema、配置校验、快照转换、规则和事务；前端由 `app-pet-care-api.js`、`app-pet-care-client.js` 和 `app-pet-care.js` 组成；生命周期由 `app-character.js`、`surface-floating-controls.js`、`return-transitions.js` 和 `app-pet-care-mode.js` 协同；猫动作和既有毛线球来源仍分布在 `static/avatar/avatar-ui-buttons/` 与聊天窗口脚本中。NEKO-PC 只提供窗口、输入和 IPC，当前相关模块包括 `src/main/pet-window-lifecycle.js`、`input-region-controller.js`、`pet-document-reload-fence.js`、`pet-model-control-bridge.js`、`pet-interaction-bridge.js`、`pet-input-region-bridge.js` 和 `pet-widget-mode-host-bridge.js`。阶段 9 不为“看起来分层”而重写这些代码，但必须用契约测试锁住边界。

面向长期运营的目标层次如下，阶段 10 迁移时按部署项目的实际模块系统落地：

```text
HTTP / WebSocket 适配层
  → 认证与请求上下文适配（只提供统一账号、会话、请求 ID）
  → PetCare 应用用例层
       bind / snapshot / check-in / care / task / play / exploration / recovery
  → 领域规则层
       补算、状态转移、任务周期、库存、幂等、奖励、解锁、负面状态
  → 仓储端口与事务端口
  → 本地 SQLite 适配器 或 正式数据库适配器
  → 审计、指标、结构化日志和配置版本记录
```

依赖方向必须保持单向：规则层不能导入 FastAPI、浏览器、Electron、OAuth 私有实现或 SQLite；路由不能直接修改数据库；前端不能计算奖励/概率/绑定；NEKO-PC 不能保存宠物状态；Cat Mind 不能调用养成结算。`LocalPetCareBindingService` 在本地阶段可以继续作为组合服务，但新增业务必须通过独立用例和仓储边界进入，不能继续从页面或路由追加第二套规则。

阶段 9 的代码结构检查还要确认：

- 请求上下文包含账号、当前 `character_uid`、会话 ID、请求 ID和取消/超时信号；账号和角色身份不能从浏览器正文伪造；
- 服务返回稳定的错误码、操作状态、确认快照和配置版本；前端只渲染服务目录与确认结果，不把错误文本、任务周期或内容名称写死成规则；
- 写请求统一携带 `Idempotency-Key`/`idempotency_key`，路径中的 `character_uid` 只用于当前角色解析；业务正文中的账号、`pet_id`、`bound_role_id`、奖励、概率和服务时间均不可信，不能覆盖认证上下文或服务计算结果；
- 统一响应至少能关联 `request_id`、操作状态、`pet_id`、`bound_role_id`、确认快照、结果码和配置版本；奖励、库存、任务、探索和解锁的显示必须能区分预览、处理中、确认和失败；
- 本地与未来正式服务共享业务用例测试、错误码和幂等契约；远端地址、认证适配和存储实现可替换；
- 规则、存储、传输和表现动作各自可单测；动作终态只产生表现事件，`action-confirmed`/结算结果才产生业务成功；
- 失败路径统一经过服务错误包络和前端回滚/保留策略，不在多个模块分别弹窗、分别清理或分别结束探索。

### 长期运营的测试层次

阶段 9 的“完整验收”不是只跑一组接口测试。每一层验证不同事实，上一层通过不能替代下一层：

| 层次 | 目标 | 必须留下的证据 |
| --- | --- | --- |
| 领域/规则单测 | 补算、状态边界、任务周期、心情、概率、奖励、回退和解锁不变量 | 输入配置、服务时间、输出快照和边界结果 |
| 存储/迁移集成测 | SQLite 事务、唯一约束、旧 schema 迁移、回滚、并发冲突和幂等结果 | 迁移前后 schema、行数/唯一性、失败恢复和数据库 hash |
| HTTP 契约测 | 认证、当前角色、错误码、请求摘要、确认快照、缓存控制和接口兼容 | 请求/响应摘要、状态码、`request_id`、错误包络 |
| 浏览器契约测 | API/client 只传输，页面只应用服务确认，代次/取消/回滚正确 | DOM 状态、事件顺序、旧响应被丢弃的记录 |

| 运行恢复测 | 服务重启、网络中断、超时、重复提交、迁移失败、临时数据库恢复 | 前后快照、幂等结果、日志关联 ID、存档 hash |

### 运营安全、观测和维护要求

阶段 9 至少要为长期运行留下可接入的观测点，即使本地只写结构化测试日志：请求 ID、操作类别、账号/宠物脱敏标识、当前角色校验结果、活动 ID、幂等命中、状态码、耗时、配置版本和结果码。日志不得包含 OAuth token、Cookie、完整请求凭证或完整个人资料。

服务应能区分认证失败、角色不匹配、服务不可用、业务拒绝、幂等重放、并发冲突、迁移失败和内部异常；前端提示只面向用户，诊断细节留在结构化日志。长期部署需要健康检查、依赖检查、慢请求/错误率/幂等冲突/活动卡住/数据库锁等待指标，以及告警和降级策略：养成服务不可用时普通猫继续可用，不能伪造奖励或清除尚未确认的探索。

配置发布必须带版本、来源、校验结果和生效时间；读取历史操作时可以根据 `config_version` 解释结果，不能通过修改当前配置重算旧奖励。内容和数值配置校验失败时服务拒绝启动或进入只读安全状态，不使用半套默认值覆盖正式配置。

长期维护还需要明确账号生命周期和运维工具边界：注销只撤销统一会话，不删除宠物；显式换绑、账号删除、数据导出和数据清理必须由正式服务提供可审计的业务用例，不能直接改表。修复脚本必须支持 dry-run、幂等重试、变更前后摘要和审计记录；禁止通过手工 SQL 修改库存、进度、奖励或探索状态来“修数据”。

正式 API 在阶段 10 接入前要冻结当前请求/响应语义和错误码，必要时由部署端提供版本前缀或兼容适配；阶段 9 不为了版本化擅自改动现有本地路径。新增字段只能向后兼容地加入，删除或改变含义必须经过迁移和客户端兼容期。

### 前置条件和现状差异

阶段 0–8 的服务和页面契约必须保持可调用；阶段 8 的临时 SQLite、固定时钟、HTTP 矩阵和桌面验收夹具可以复用，但阶段 9 每次执行都要使用隔离的临时存储和可回滚配置，不修改正式本地存档。当前已知仍需在本阶段补证据的内容包括：真实 PC 的完整探索生命周期和视觉时序、正常完成与强制召回两条分支、自然两小时探索和五天离线的时间边界、所有退出/刷新/角色切换链，以及现有 OAuth 外部页面注销后的统一会话表现。静态测试或网页端操作不能替代这些桌面验收。

进入阶段 9 验收前必须处理或证明以下已知风险，否则不能标记阶段完成：

- OAuth 外部退出后刷新页面，如果服务尚未确认探索召回，不能直接丢弃活动租约；重新登录后必须能恢复或明确收口；
- `app-pet-care-mode.js` 发出的 `context-change-request` 必须有唯一 owner 消费，角色切换不能依赖未验证的旁路事件；
- 真实 NEKO-PC 中养宠入口的语义锚点必须可见、可点击并正确避让猫，不能用网页端通过替代桌面证据；
- 伸懒腰、吃零食、玩球等表现动作不能被错误当作锁定稿未列出的 busy 状态，导致入口消失；同时仍要保持移动、拖拽、重力下坠和贴边探头的忙态门控。

### 本地端到端验收顺序

每次验收使用一个临时账号、一个绑定角色、一个非绑定角色和一套临时可编辑配置；所有写请求带唯一幂等键，记录请求、服务响应、快照和数据库前后摘要。

1. **普通猫与入口**：未登录打开猫，行为保持现状；养成入口只可显示锁定稿允许的不可用登录提示，不显示数值和可用养成操作。登录失败、服务不可用或当前角色不匹配时仍回普通猫。
2. **身份和初始快照**：登录统一账号，服务确认当前角色绑定关系后只读取账号唯一宠物；切换到非绑定角色不能读取或创建第二只宠物。首次进入、刷新和重新打开面板只重读同一快照。
3. **每日登录和任务**：提交当天首次登录结算并重复提交；服务只产生一次结果。任务逐条同级显示，周期、条件、目标和奖励来自服务目录；手动领取小鱼干成功后库存增加，重复领取不重复发放，页面不出现虚假 `0/0` 或前端分组。
4. **照料和主动陪玩**：在服务确认允许时验证喂食、梳毛和真实毛线球互动。依据锁定稿 Q13，照料可先显示反馈和临时数值变化，失败必须回滚；库存、任务奖励、解锁和探索收益等“获得类”结果只在服务确认后显示。满值、库存为零、梳毛 CD、取消、超时和无猫回应均不扣除、不加进度。逗猫棒等消耗品由服务确认库存和次数，不能擅自增加道具 CD。
5. **探索两条分支**：从家中出发后猫离场，喂食/清洁/陪玩和所有依赖猫实体的自动输出被活动门控；猫窝、纸条、来信、面板和统一返回入口保持可用。分别验收服务确认的正常完成和按已完成比例结算的强制召回，奖励在确认后才显示。猫窝召回回到猫形态；用户切回模型时只走统一模型返回入口，不同时显示猫实体或猫窝。
6. **生命周期和互斥**：探索中刷新、重载、关闭面板、模型切换、角色切换、离开猫形态和统一账号退出都必须结束活动或按统一召回契约收口，并显示一次清晰的结果确认；迟到的动作、召回和旧角色响应不能覆盖新代次。模型与猫形态不能同时成为可见实体，猫窝图片只属于离场表现，不进入养宠面板内容。`cat1`、`cat2`、`cat3` 是同一 `pet_id` 的外观/睡眠形态；用户对 `cat2`/`cat3` 进行喂食、梳毛或陪玩等主动操作时切回 `cat1`，服务返回的 `pet_id` 和 `bound_role_id` 必须保持不变，装扮也不能创建第二只宠物；不能把猫窝召回误走模型召回链。
7. **离线和负面状态**：用可控时钟模拟短时、超过回退门槛和超过负面状态门槛的离线段；重新建立统一账号会话时只判定一次，生病/赌气任务独立呈现，生病禁止探索但清洁和恢复操作仍按服务契约可用。重复读取、刷新和服务重启不能重复回退、重掷概率或发放恢复物品。

NEKO-PC 当前不是普通的局部 BrowserWindow：`src/window-manager.js` 的 `createPetWindow()` 创建透明、无边框、不可调整大小、覆盖工作区的 Pet 窗口，继续加载 N.E.K.O 共享页面 URL。Windows/macOS 启动时由主进程设置整窗鼠标穿透；Linux/Wayland/X11 则由 `pet-window-lifecycle.js`、原生 input region 和 `pet-input-region-bridge.js` 的 DOM 命中区域协同处理。养宠总览的即时操作应在这个现有透明窗口中围绕猫的语义锚点绘制，不能另开一个 Electron 养宠窗口，也不能把 BrowserWindow 缩成 demo 的固定 1180×730 画布。

实现时遵循以下约束：

- 新浮层根节点保持 `pointer-events: none`；中央猫自由区、装饰背景和透明留白继续穿透桌面及现有猫输入；总览中喂食、清洁、陪玩、探索四个按钮、侧轨、状态卡、模块卡和关闭按钮单独启用 `pointer-events: auto`；
- 养宠页面通过现有 `nekoCatInteractionAnchor` 的 `visible/busy/rect` 得到猫的语义位置，以锚点中心计算 scene 中心和即时操作环，不读取 Live2D/VRM/MMD/PNGTuber manager、容器边界或模型按钮；
- 按 demo 的实际几何把 rail、状态卡、即时操作和模块卡映射到猫锚点周围的固定自由区；每个组件保留猫与可交互卡片的间距，使用单一坐标系和透明留白，不实现空间不足时的响应式折叠、候选位置、左右翻转或底部布局。不能把整块 surface 固定到右侧，也不能只把旧 panel 的左上角贴到 `anchor.rect.right`；
- DOM 结构更新后，养宠交互控件必须进入当前 PC input-region 的可识别命中集合；建议统一使用专用的 `data-neko-pet-care-interactive` 标记，并在 `DESKTOP_FLOATING_INTERACTIVE_SURFACE_SELECTORS`/现有 `[data-neko-sidepanel]` 白名单中增加该标记。不得只依赖 CSS `pointer-events` 期待 Linux 原生 input region 自动更新，也不得让整窗恢复可点击而遮住猫和桌面；
- 页面 resize、滚动、猫形态切换、窗口重载、显示器变化和模块切换都重新提交命中区域与浮层位置；没有可用交互控件时恢复整窗穿透；
- 允许在 PC preload 的现有命中选择器、区域刷新和对应契约测试中做最小同步修改，使新侧轨、总览四个即时操作、任务领取、模块卡按钮和召回按钮可点击；不在 preload、bridge 或 `window-manager.js` 中保存宠物状态、执行养成规则、扣库存或决定服务结果。PC 仍只负责窗口、命中区域、输入转发和必要的布局/穿透协作。

Electron 官方 API 的边界也决定了实现方式：`BrowserWindow#setIgnoreMouseEvents()` 是整窗级别的穿透开关，官方提供的 `forward` 选项只用于在整窗忽略鼠标时继续转发鼠标移动，不能替代页面内的分区命中；透明无框窗口需要结合页面 CSS 与输入区域管理。实现前后应以 Electron 官方的 [BrowserWindow API](https://www.electronjs.org/docs/latest/api/browser-window)、[Custom Window Interactions](https://www.electronjs.org/docs/latest/tutorial/custom-window-interactions) 和 [webContents input events](https://www.electronjs.org/docs/latest/api/web-contents) 对照验证，不引入第二套窗口穿透机制。

### 阶段 9.1 验收标准

- 普通模型态不显示养宠浮层；cat1/cat2/cat3 只在锚点可见且非忙态时显示入口；

## 14. 阶段 10：接入正式养成服务

### 实施目标

将已经在本地跑通的宠物服务镜像接入社区服务器，由社区服务器承担正式存储和结算。社区服务器的具体模块入口、接口注册和数据库归属在本阶段确认。

### 实施内容

- 先确认社区服务器仓库、模块入口、接口注册、数据库归属、部署环境和认证接入方式；在这些事实确认前，不创建猜测性的模块路径、表名或配置；
- 从 `binding_service.py` 提取已验证的业务语义和接口契约，按正式服务的应用用例、领域规则、仓储/事务边界拆分后接入正式数据库，不直接搬运本地 SQLite JSON schema；
- 保存宠物、库存、任务、解锁、活动和操作幂等记录；
- 通过现有社区认证的 `(issuer, subject) → user_id` 映射取得稳定账号主体，再解析并校验 `bound_role_id`；禁止创建养宠专用账号或信任客户端提交的账号、宠物、奖励和服务时间；
- 账号只有一只宠物，使用稳定的 `bound_role_id` 绑定角色，并由当前 `character_uid` 解析后校验；
- 将本地 `PetCareClient` 请求/响应包络、错误码、确认快照和 `idempotency_key` 语义与正式服务保持兼容，正式地址通过配置切换；
- 增加数据库迁移、事务边界、`state_version`/并发、活动唯一性、请求幂等、审计和重复请求测试；
- 在测试环境完成账号/绑定/存档迁移样例、健康检查、备份恢复、回滚和失败后安全状态验证后，再把客户端服务地址和认证配置切换到正式候选环境；
- 保留普通猫回退和养成不可用提示。

### 正式服务验收

1. 同一个N.E.K.O 统一账号在绑定角色上于 Web、NEKO-PC 读取到同一只宠物，其他角色不读取宠物；
2. 正式模式以社区服务器作为宠物数据来源；
3. 正式服务重启后宠物、任务、活动和库存可恢复；
4. 并发重复请求只产生一次结算；
5. 探索活动跨客户端、跨会话恢复；
6. 首次加载或非探索状态服务不可用时普通猫可用，养成写操作停止；已有探索保持猫窝和离场状态，统一返回模型仍可用；
7. 使用本地测试样例在社区服务器测试环境验证迁移，账号、绑定角色和宠物关系保持正确；
8. 配置版本、请求 ID、审计记录和幂等结果可追溯，且不记录 token、Cookie 或完整个人资料；
9. 正式服务健康检查、迁移、备份恢复和回滚验证通过后，才开放正式入口。
