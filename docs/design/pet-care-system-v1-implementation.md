# 猫形态养宠系统首版实施文档（NEKO / NEKO-PC）

> 本文定义实施顺序和验收标准。产品规则以《宠物养成系统方案（修订稿）》为唯一设计基线，接入边界以锁定文档和本轮确认的部署方案为准；数值草案只提供可替换的首版候选配置。
>
> 本文按“用户能看到什么、完成后能验收什么”拆分阶段。所有阶段先在本地养成服务镜像上跑通；之后接入社区服务器，客户端继续使用同一套业务接口。

> **本轮边界确认：** 首版以养成服务、照料、任务、探索、动作链和状态结算为主。养成可用性复用 N.E.K.O 统一账号会话；当前本地适配器沿用 `community_oauth`，它是会话来源而不是产品账号的归属。账号只有一只猫，绑定账号自己的一个角色，当前角色不是绑定角色时和未登录一样走普通猫路径。用户登录、猫处于猫形态且养成快照完整后，自动进入养成兼容状态，并在首次进入时给出一次提示；阶段 3 只暂时停用可能与养成动作冲突的 Cat Mind 自主自动触发，正常的用户照料、陪玩和返回等功能动作不因此停用。养成服务负责长期状态、条件、负面状态、探索、库存、奖励和结算；Cat Mind 继续负责现有猫形态的短期自主行为。首版不把养成值写入 Cat Mind。基础闭环稳定后，再按锁定文档通过独立适配让养成快照作为 Cat Mind 的输入，但 Cat Mind 不负责长期状态结算；统一账号会话失效或快照不可用时，继续使用现有普通猫路径。

## 1. 首版目标与范围

首版完成后，用户可以：

1. 未登录时继续正常使用猫；猫形态可见时养宠入口只提供灰色登录快捷方式，不显示宠物数值或可用养成操作；
2. 保持 N.E.K.O 统一账号登录后，只有当前角色等于账号绑定角色时才读取该账号唯一宠物；其他角色和未登录一样使用普通猫；
3. 查看饱食、精力、清洁、心情和养成进度；
4. 完成每日任务、喂食、清洁（首版具体操作为梳毛）和用户主动陪玩；
5. 开始一次探索，看到猫离场、猫窝、纸条和来信；
6. 正常等猫回家，或从猫窝触发统一返回模型入口完成召回；
7. 刷新、重启本地服务、切换角色后仍看到正确数据；
8. 长时间未登录后看到一次离线结算和必要的恢复任务；
9. 通过照料和探索积累进度，达到阈值后看到解锁内容。

首版围绕任务、照料、主动陪玩、一个探索地、负面状态和 3 到 5 个解锁项展开。社区货币与购买型道具、社交、推送、AIGC、洗澡和更多探索内容安排在后续版本。

## 2. 当前项目事实和实施边界

实施前已根据实际代码确认以下事实：

| 事项 | 当前实际情况 | 实施要求 |
| --- | --- | --- |
| 统一账号会话 | 当前由 NEKO OAuth / `community_oauth` 适配器保存和校验统一账号身份；养成页面沿用该会话，NEKO-PC preload/bridge 不负责会话 | 养宠请求从受信统一账号会话取得账号；社区只是当前接入来源 |
| 角色身份 | 项目已有本机 `_reserved.character_uid`；新建或导入生成，改名保留 | 宠物按已认证 N.E.K.O 统一账号唯一定位；宠物记录保存跨设备稳定的 `bound_role_id`；当前 `character_uid` 只用于页面角色解析和当前角色校验，不作为正式宠物主键；不按每个角色建宠物 |
| Cat Mind | app-cat-mind.js 是现有猫行为的一部分，会发起 `neko:cat-mind:action-request`；当前没有完整 pause/disable API；五维和动作评分属于猫形态短期运行态 | 作为现有短期自主行为系统接入兼容层：养成快照完整后暂时停用可能冲突的自主请求，并单独清理已运行动作；首版不向其中写入养成值，也不让它负责养成状态和结算 |
| 动作执行 | 当前已有 cat1 吃零食、移动、毛线、音效和收尾模块；梳毛、逗猫棒及其他形态的业务反馈尚未形成统一执行器 | 养宠适配器复用已有能力，并为首版缺少的动作补齐独立执行器或基础表现，统一等待完成、取消或失败回报 |
| 探索离场 | 现有清理方法可收尾桌面动作和离场表现 | 出发动作完成后隐藏猫；探索期间停止依赖猫实体的所有动作和尾回调 |
| 返回模型 | surface-floating-controls.js 有统一返回入口和 neko:cat-return-commit / neko:cat-return-complete 事件 | 强制召回挂接既有模型/猫切换链路 |
| NEKO-PC | Pet preload/bridge 负责窗口、输入、命中区域和 IPC 桥接，不负责账号会话或养成业务 | 长期状态和结算由养成服务管理；养成页面沿用 NEKO 的会话和业务接口 |
| 社区侧现状 | 已有统一账号和基础服务，但尚无宠物快照、任务、探索和养成结算模块 | 首版先做本地养成服务镜像；本地闭环通过后接入社区服务器，具体模块、接口和数据归属另行确认 |

各阶段按所接入的功能验证普通猫回退、当前账号与 `bound_role_id` 校验、请求幂等和服务确认结果；页面侧仍使用当前 `character_uid` 作为角色解析输入。

### 2.1 本地、正式服务与代码结构

养宠是一个独立业务域。第一版先实现本地后端镜像，正式数据和结算固定接入社区服务器；F2 没有规定社区服务器的具体模块、接口或数据库表，这些接入细节保留到本地闭环通过后确认，不把独立部署作为另一条正式方案。

社区服务器负责账号唯一宠物的状态、任务、探索和结算。API、数据结构、错误码和幂等语义在本地镜像与社区服务器之间保持一致；本地只用于开发、验收和可回退验证。账号仍来自 N.E.K.O 统一账号会话，宠物另记录一个跨设备稳定的 `bound_role_id`。未来自有云存档复用同一账号、宠物和绑定关系，不另建一套互相冲突的宠物身份。

账号身份与角色身份是两条独立信息：账号来自 N.E.K.O 统一账号会话，当前页面角色由 NEKO 的 `character_uid` 表示，正式绑定使用跨设备稳定的 `bound_role_id`。账号只有一只宠物；当前 `character_uid` 只用于解析和校验当前页面角色，不写入账号认证对象，也不按每个角色创建宠物。NEKO 当前会话字段为 `local_user_id`，它在本地是统一账号主键的适配镜像，不是社区专属主键。N.E.K.O.Verse 当前已有稳定的认证主体映射：`AuthPrincipal` 的 `(issuer, subject)` 通过 `UserAuthIdentity` 定位 `user_id`；后续正式服务器接入须把该统一 `user_id` 映射到本地 `local_user_id`，不能再创建养宠专用账号。

统一账号的生命周期也必须统一：N.E.K.O 页面、受管的 N.E.K.O.Verse 社区窗口和养宠面板使用同一账号会话边界。社区窗口退出时，必须通过受信窗口桥通知 N.E.K.O 本地会话适配器清理桌面 OAuth 镜像，再由 `/api/card-drop/oauth/status` 重新确认并让养宠入口回到普通猫；不能只清社区页面自己的 `localStorage`，也不能让养宠面板维护第二套登录态。独立浏览器中没有受信 opener 的社区页面不属于这条本地桥，正式服务器接入阶段需提供等价的一次性会话撤销协议。

表现属性只影响外观：模型是角色当前使用的模型；猫档位是同一宠物的不同形态；装扮属于后续纯外观内容。它们都不参与宠物记录主键。本地验收阶段通过切换模型和猫档位验证宠物及 `bound_role_id` 不变，装扮暂不进入首版业务。

`_reserved.character_id` 是数值剧场使用的另一项身份字段；养宠不把它或本机 `_reserved.character_uid` 作为正式宠物主键。

数据流固定为：

```text
Web / NEKO-PC 共用的 NEKO 页面
  → PetCareBackend 接口
    → 本地模式：NEKO 本地养成 API → LocalPetCareStore
    → 正式模式：正式养成 API → PetCare 数据库
```

- **NEKO 页面**负责面板、模式门控、动作适配和统一返回入口。前端的 `PetCareBackend` 封装本地与远端请求，页面使用相同方法读取快照和提交操作。
- **本地养成后端**负责本地测试期间的规则、补算、结算和持久化。作为 NEKO 内独立模块接入本地 API，由 `app/main_server/web_app.py` 注册路由。
- **NEKO-PC**继续只负责窗口、输入、命中区域和 IPC，养成页面复用上述业务接口；不在 preload/bridge 保存账号、宠物状态、规则或结算。只有确有窗口或输入适配需求时，才在现有 pet bridge 中扩展对应能力，通道名集中在 `src/ipc-channels.js`。
- **正式养成后端**接收本地已验证的业务规则，适配正式认证和数据库。本地与正式环境用同一组业务用例核对结果。
- **本地测试存储**放在现有 `local_state_dir` 下的 `pet_care` 数据目录，采用 SQLite 支持事务和幂等记录；页面和 preload 保留面板开合、显示偏好等界面状态。正式服务使用部署环境的数据库。

### 2.3 命名与接口约定

推荐命名：

| 用途 | 命名 |
| --- | --- |
| 业务域 | `pet_care` / `PetCare` |
| API 前缀 | `/api/pet-care` |
| 前端文件 | `app-pet-care-*.js` |
| 服务与数据类型 | `PetCareService`、`PetCareRepository`、`LocalPetCareStore`、`PetCareSnapshot`、`PetCareExploration` |
| 数据表 | `pet_care_*` |
| 业务标识 | 已认证 N.E.K.O 统一账号 ID（当前适配字段 `local_user_id`）+ 账号唯一 `pet_id`；宠物记录附带一个稳定的 `bound_role_id`，不按角色复制宠物；请求中的当前 `character_uid` 只用于校验 |
| 请求标识 | `idempotency_key`、`request_hash`、`exploration_id` |

当前页面继续传递项目已有的 `character_uid`。账号 ID 由统一账号认证上下文提供；服务先按统一账号取唯一宠物，再通过角色解析得到稳定的 `bound_role_id` 并校验当前角色。首次绑定只建立一只账号宠物；换绑必须是显式操作，更新同一宠物的绑定关系，不创建第二只记录；角色改名、模型切换、猫档位切换、异机导入或角色删除都不能自动复制宠物。

业务类别和具体内容分层：`feeding`、`cleaning`、`playing`、`exploration` 是稳定的业务类别；小鱼干、梳毛、毛线球、消耗品玩具和探索地点都是可配置的 `item_id` / `content_id`，不能把候选内容写成类别名称。库存由养成服务持有并按账号宠物返回，至少要能表达类别、内容、数量和后续解锁层级；页面不能自行扣库存或把某一个内容当成该类别的唯一实现。首版不加入商店、货币或付费猫粮，但接口和面板必须为背包与多内容选择保留层级。

写操作使用 `idempotency_key`，服务保存请求内容摘要和结算结果；重复请求返回已确认的结果。账号主体从认证上下文取得，页面传递当前角色的 `character_uid` 和操作参数。

首版核心接口：

- `GET /api/pet-care/pets/{character_uid}`：读取完整宠物快照；
- `POST /api/pet-care/pets/{character_uid}/care-actions`：提交喂食、清洁操作（首版为梳毛）、用户主动陪玩和物品使用；
- `POST /api/pet-care/pets/{character_uid}/explorations`：创建探索活动；
- `GET /api/pet-care/pets/{character_uid}/explorations/{exploration_id}`：读取探索状态；
- `POST /api/pet-care/pets/{character_uid}/explorations/{exploration_id}/complete`：正常完成探索并结算；
- `POST /api/pet-care/pets/{character_uid}/explorations/{exploration_id}/recall`：强制召回并结算。

首版接口还需要覆盖任务和每日登录：

- `GET /api/pet-care/pets/{character_uid}/tasks`：读取今日任务和状态任务；
- `POST /api/pet-care/pets/{character_uid}/tasks/{task_id}/claim`：完成并领取任务奖励；
- `POST /api/pet-care/pets/{character_uid}/daily-check-in`：提交当天首次登录结算。

任务领取和每日登录同样带 `idempotency_key`，返回完整宠物快照。

这些接口中的 `{character_uid}` 只表示当前页面正在校验的角色；服务先从社区认证会话取得账号唯一宠物，再确认当前角色解析出的稳定角色标识是否等于 `bound_role_id`。不匹配时按普通猫返回，不创建第二份宠物记录。

### 2.4 与现有猫行为的兼容边界

Cat Mind 是现有猫行为的一部分，负责猫形态内存中的短期行为驱动力和自主动作选择；养成服务负责按 N.E.K.O 统一账号唯一宠物保存的长期业务状态。两套系统的食欲/困意/精力/社交/刺激与饱食度/精力/清洁度/心情/养成进度不能共用字段、初始值、衰减公式、阈值或结算结果。锁定方案规定养成数值后续可以作为 Cat Mind 的输入；首版暂不接入该输入，`bound_role_id` 负责正式绑定，`character_uid` 只作为当前页面角色校验。

首版只保留以下兼容约束：

- 首次加载时未登录，或养成快照尚未完整、养成服务不可用时，继续使用普通猫路径，不创建替代存档；若服务已确认当前角色正在探索，则保持猫窝和离场状态，不恢复实体动作。
- 用户已登录、猫处于猫形态且养成快照完整后，自动进入养成兼容状态，并在首次进入时给出一次提示；提示只说明养成入口和边界，不改变业务结算。
- 养成快照完整后，只暂时拦截可能与养成动作冲突的旧自主自动触发；正常的用户照料、陪玩和返回等功能动作仍可由独立适配器调用动作执行器。不要求删除或重写 Cat Mind 的内存需求模型，服务确认结果后才更新长期状态。
- 生病、探索、照料、活动、库存、进度、奖励和结算均由养成服务及独立动作/表现适配器负责，不通过 Cat Mind 决定。
- 基础养成闭环稳定后，如确有价值，再新增只读适配器让快照少量影响自动行为或短期心情；不得把养成数值直接写入 Cat Mind 五维，也不得让该适配器负责长期状态、结算或成为养成闭环的前置条件。

可复用的是 observation 去重、动作请求租约、provider 检查、动作终态和清理协议等通用机制；不可复用的是两套数值的业务含义和结算规则。这样可以在不重写现有 Cat Mind 的前提下，先完成养成闭环，再单独评估是否增加行为提示适配。

旧自主触发不等于所有独立动作来源。当前代码和补充设计中还存在 journey、playground、重力/窗口感知、贴边探头等独立链路；阶段 3 的兼容开关只处理已确认的旧自主触发来源，阶段 7 的探索活动门控必须另外覆盖所有依赖猫实体的输出，不能因为拦截了 `neko:cat-mind:action-request` 就视为全部停止。

## 3. 实施阶段总览

| 阶段 | 目标 | 用户可见验收 |
| --- | --- | --- |
| 0 | 建立基线和可回退门控 | 未登录普通猫行为与当前一致 |
| 1 | N.E.K.O 统一账号、绑定角色和养成入口 | 独立入口能提示登录；登录后由服务确认当前角色是否为账号绑定角色 |
| 2 | 本地养成服务和基础状态页 | 能看到并持久化账号唯一宠物的基础数值 |
| 3 | 养成与旧自主触发兼容 | 进入养成后会冲突的旧自主动作停止，退出后恢复 |
| 4 | 状态补算和基础照料 | 喂食、清洁（首版为梳毛）可用，成功和失败都能看见正确结果 |
| 5 | 每日任务、食品、进度和解锁 | 任务获得小鱼干，清洁/陪玩/探索/登录按各自配置推动进度，达到阈值后解锁 |
| 6 | 用户主动陪玩 | 手动陪玩可验收，取消和无回应不计进度 |
| 7 | 单探索地、猫离场和统一召回 | 能看到出发、猫窝、来信、回家和召回 |

## 7. 阶段 3：养成与旧自主触发兼容

### 实施目标

在任何养成动作接入前，先让系统能安全地从普通猫模式切换到首版养成模式，并暂时停用可能冲突的旧自主自动触发。登录、猫形态和完整快照同时成立时自动进入；首次进入给一次提示，不增加额外的用户开关。

### 实施内容

- 快照完整且当前处于猫形态后启用养成模式兼容开关，并记录一次性首次提示状态；
- 只暂时拦截旧自主自动触发产生的 `neko:cat-mind:action-request`，不向现有猫行为逻辑注入养成快照或新的业务数值；正常用户发起的照料、陪玩和返回动作不被该开关拦截；
- 清理已经运行的吃、走、玩、伸展、音效和延迟尾回调；

3. 切换到养成模式时，已经开始的动作能安全收尾，不残留定时器或尾回调；

6. 首次快照加载失败或尚未进入养成时，普通猫可用，养成写操作不启动。

## 7.1 阶段 0–3 首个大阶段收口（2026-10-16）

阶段 0–3 作为首个大阶段的交付物，是“统一身份和状态读取可以安全进入猫形态兼容模式，并能失败回到普通猫”的基础闭环；它不是完整养宠业务周期。完整的时间补算、照料、任务、主动陪玩、探索、离线结算和负面状态仍按阶段 4–8 逐步接入，阶段 9 才做本地首版完整验收。

### 当前闭环

```text
N.E.K.O 统一账号会话
  → 当前角色 character_uid
  → 本地 PetCare 服务确认账号唯一宠物和 bound_role_id
  → 完整只读快照
  → 猫形态活动
  → 阶段 3 Cat Mind 兼容门
  → 离开猫形态、登出、角色/绑定变化或服务失效时清理并回到普通猫
```

- 入口是独立猫形态 surface，默认在猫右侧并避让猫体；它只使用 `visible`、`busy`、`rect` 语义锚点，不读取 Live2D、VRM、MMD、PNGTuber 的 manager、容器边界或模型按钮。`busy` 只对应锁定文档列出的移动、拖拽、重力下坠和贴边探头；伸懒腰等表现动作不能额外把入口隐藏。锚点无效或处于这些忙态时保持隐藏，避免入口脱离猫形态悬空。
- 未登录或当前角色不匹配时不显示宠物数值和可用操作；未登录入口保留灰色登录快捷方式。登录态、账号变更、角色变更、服务异常和快照失败都清空旧宠物上下文，推进 generation，禁止迟到响应复活旧状态。
- 阶段 3 只拦截已确认的六个 `source: 'cat_mind'` 自主 action id，并用现有来源过滤清理已运行的动作、音效、气泡和尾回调。Cat Mind 调度器仍运行，用户主动动作、返回入口和未列入本阶段的独立链路不由该门控取消。
- 同一绑定快照的重复读取不递增 generation；快照和本地可编辑配置都做 schema、字段类型和 `0–100` 范围校验；认证 401 或共享会话不可用时先失效旧上下文，再重新读取 N.E.K.O 账号状态。
- 本地服务持有账号唯一宠物、绑定角色、快照和 SQLite 持久化；NEKO-PC preload/bridge 不保存养成状态、不执行规则和结算。正式社区服务器接入必须复用同一业务契约和账号主体，不另建社区专属账号。

### 周期与数据边界

阶段 0–3 不启动宠物数值的在线衰减、时间补算、操作结算、任务奖励或库存扣除；`last_settled_at` 只作为服务快照字段保存，后续由服务端补算流程使用。Cat Mind 的自主调度周期与养宠服务周期保持分离，不能把 Cat Mind 的短期驱动力当作养宠结算时钟。

当前快照尚未实现心情公式所需的 `interaction_index` 或负面状态所需的离线段去重标记；这两个字段及其服务端语义留给阶段 8 的契约设计，不能在客户端推导，也不能写入 Cat Mind。

### Web 与 NEKO-PC 的运行边界

## 9. 阶段 5：每日任务、食品、进度和解锁

### 实施目标

完成第一条可循环的“任务 → 小鱼干 → 当前小鱼干喂食恢复状态；清洁/陪玩/探索/登录按各自规则推动进度 → 解锁”闭环。

### 实施内容

- 增加每日打工任务；
- 任务完成后发放小鱼干；
- 小鱼干进入食品库存；
- 食品用于喂食；
- 首版当前食物只有小鱼干；小鱼干只用于喂食并只恢复饱食度，不直接增加进度，其他食物不在本阶段预设；进度结算保留按食物/操作配置扩展的入口，本阶段仅实现小鱼干配置为 `0`；清洁操作（首版为梳毛）、用户主动陪玩、探索和每日登录按各自独立配置增加进度；不同陪玩类型不共用进度值；
- 每日登录完成一次登录结算并按配置增加进度；
- 按数值草案提供 5 个占位解锁项及其阈值、可见效果作为本地可编辑测试配置，用于本阶段验收；草案不构成锁定规则，后续可替换名称、资源、内容和数值而不改变进度存档契约；
- 进度达到配置阈值时，由服务一并记录解锁项、最近存档点并返回解锁结果；
- 增加任务刷新、完成、领取和每日次数限制；
- 本阶段范围覆盖每日任务、食品库存、进度和首批解锁项。

### 用户可见验收

1. 用户能看到今日任务和完成条件；
2. 完成任务后，小鱼干只在服务确认后增加；
3. 小鱼干能用于食品流程；
4. 任务重复提交不会重复发放；
5. 使用小鱼干喂食后食品数量和饱食度正确更新，小鱼干喂食不增加进度；其他食物不在本阶段验收；
6. 切换窗口或刷新后，任务和库存保持一致；
7. 达到进度阈值后能看到已解锁内容，刷新后解锁状态仍保留；
8. 每日登录只在当天首次确认时增加一次进度；
9. 同一次操作重试时，解锁记录和奖励仍只有一份。

### 阶段完成条件

- 任务、库存、宠物状态在同一结算边界内更新；
- 每日任务产出由服务判定；毛线球按锁定稿每日前 N 次计进度，之后仍可玩但不再计进度；新增消耗品陪玩的每日次数上限由服务判定；两类陪玩都不新增道具 CD；
- 小鱼干、进度和解锁由服务结算并在确认后展示。



## 10. 阶段 6：用户主动陪玩

### 实施目标

在旧自主触发暂时停用后，把用户主动陪玩和玩具使用接到独立动作执行器，并形成可结算的业务事件。

### 实施内容

- 毛线球优先复用现有动作；逗猫棒首版暂用玩球反馈，清洁类别中的梳毛操作暂用伸懒腰反馈；后续替换具体反馈表现不改变业务类别、用户操作、物品消耗和养成结算；其他当前缺少统一终态的动作，由首版补齐独立执行器或基础表现后再接入适配器；
- 逗猫棒是消耗品，首版用测试种子提供库存，正式来源在探索掉落阶段接入；服务确认使用成功后扣除一次；
- 记录用户发起、猫真实回应、动作完成或取消；
- 只有用户主动且猫有真实回应才提交陪玩结算；
- 猫自主发起的玩耍不计入养成陪玩进度；用户主动毛线球每日前 N 次给进度，之后仍可玩但不再给进度；消耗品陪玩使用独立进度配置并受服务端每日次数上限约束，不互相污染；
- 有现成能力的动作复用现有动画、动作和终态事件，新增动作沿用相同的终态契约。

### 用户可见验收

1. 用户主动操作毛线球，猫执行动作并返回完成结果；
2. 用户使用逗猫棒时，库存、动作终态和陪玩结算一致；
3. 猫没有回应或动作被取消时，不增加养成进度，也不扣除逗猫棒；
4. 服务拒绝或重复提交时，逗猫棒只扣除一次或不扣除；
5. 毛线球前 N 次能按自身配置结算进度，之后仍可玩但不再计进度；消耗品陪玩受库存数量和服务端每日次数上限限制；两者都不新增道具 CD；
6. 退出登录后普通猫恢复原有行为；
7. 刷新后从服务恢复陪玩库存和各类进度。

### 阶段完成条件

- 手动陪玩由养宠适配器调用已有或新增的动作执行器；
- 动作执行器保持独立，养宠只接收统一终态事件；
- 所有陪玩成功、取消、无回应和重复请求场景均可验收；
- 旧自主触发暂时停用后，现有动作能力仍由动作执行器提供。

## 12. 阶段 8：离线结算、负面状态和角色切换

- 登出、换账号、换角色和断线恢复都校验统一账号会话代次；

- 恢复连接后读取未确认操作结果，结算以服务记录为准。

3. 生病时出现求药任务，完成任务领取药品，使用药品并确认扣除后恢复；

### 阶段完成条件

- 有可控的时间推进测试方式，能够验证探索等待、每日限制和离线窗口；

### 必须通过的失败场景

- 未登录点击养成入口；
- 登录失败或服务不可用；
- 状态已满、库存不足、梳毛 CD 中；
- 探索中重复照料；
- 旧自主触发或迟到的普通动作响应不能改变生病、探索和养成结算结果；
- 陪玩无回应；
- 重复点击、重复提交、重复召回；
- 猫出发时已有动作或延迟回调；
- 召回响应晚到；
- 切换角色后旧请求晚到；
- 本地服务重启；
- 网络中断后恢复。

### 阶段完成条件

- 所有阶段 1 至 8 的用户可见验收通过；
- 本地宠物服务是唯一长期数据来源；
- Web 和 NEKO-PC 通过同一业务接口看到同一角色数据；
- 奖励、扣除、角色关系和探索状态均能从服务记录恢复；
- 本阶段通过后才开始正式养成服务接入与部署验证。



## 14. 阶段 10：接入正式养成服务

### 实施目标

将已经在本地跑通的宠物服务镜像接入社区服务器，由社区服务器承担正式存储和结算。社区服务器的具体模块入口、接口注册和数据库归属在本阶段确认。

### 实施内容

- 确定社区服务器的模块入口、接口注册、数据库归属和认证接入方式；
- 迁移已验证的 pet_care 业务模块，并接入正式数据库；
- 保存宠物、库存、任务、解锁、活动和操作幂等记录；
- 通过现有社区认证取得稳定账号主体，养成服务校验请求凭据；
- 账号只有一只宠物，使用稳定的 `bound_role_id` 绑定角色，并由当前 `character_uid` 解析后校验；
- 将本地服务接口和正式服务接口保持一致；
- 增加数据库迁移、事务边界、并发和重复请求测试；
- 把客户端服务地址和认证配置切换到测试环境；
- 保留普通猫回退和养成不可用提示。

### 正式服务验收

1. 同一个N.E.K.O 统一账号在绑定角色上于 Web、NEKO-PC 读取到同一只宠物，其他角色不读取宠物；
2. 正式模式以社区服务器作为宠物数据来源；
3. 正式服务重启后宠物、任务、活动和库存可恢复；
4. 并发重复请求只产生一次结算；
5. 探索活动跨客户端、跨会话恢复；
6. 首次加载或非探索状态服务不可用时普通猫可用，养成写操作停止；已有探索保持猫窝和离场状态，统一返回模型仍可用；
7. 使用本地测试样例在社区服务器测试环境验证迁移，账号、绑定角色和宠物关系保持正确；
8. 正式服务健康检查、迁移和回滚验证通过后开放入口。



## 15. 每阶段开发记录格式

每个阶段完成时只需要记录以下内容：

- 阶段编号和完成日期；
- 已实现的用户可见结果；
- 通过的验收场景；
- 未通过或暂缓的场景；
- 涉及的代码、接口和数据迁移；
- 下一阶段依赖；
- 未验证风险。

阶段完成以该阶段用户可见结果和验收证据为准；涉及持久化的阶段同时提供刷新、重启恢复和失败路径的证据。
