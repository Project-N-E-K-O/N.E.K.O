# 个人资料库与成品知识包分享开发方案

> 文档性质：实施中的设计与验收基线。产品范围见第 1 节，当前审查结论及发布门槛见第 11 节，模块实施与整改记录见第 13 节，PR 拆分分析见第 14 节。模块已有代码或曾通过直接测试，不代表真实模型、跨平台和线上发布门槛已满足。
>
> 代码核查基线：NEKO `origin/main` 的 `72120988d`，市场 `origin/main` 的 `3214a85`；实施与审查对象为两仓 `Knowledge_Base` 工作树。现有公共知识系统合同见[知识库架构](/architecture/knowledge-architecture)。本文只定义新增个人资料库及分享建设，不覆盖或改写现有公共知识、聊天与记忆合同。

## 1 已确认目标与阶段边界

### 1.1 产品目标

用户可以建立自己的资料库，导入文档、查看解析内容、检索资料，并将选定资料构建为成品知识包。作者把成品包发布到 NEKO 市场，其他用户下载、安装后即可检索，不再重复文档解析、OCR、分块或整库向量计算。

本阶段需要交付独立资料库页面、资料管理、成品包构建与校验、市场发布及下载生命周期。知识库自身的检索用于资料查找和验证，不生成 NEKO 对话回复。

### 1.2 明确不做

- 不接入日常聊天、实时语音、主动搭话、角色设定、群聊、串门和游戏。
- 不注册新的对话工具，不修改提示词、聊天消息协议、引用气泡或会话上下文。
- 不把个人资料、市场新成品包或检索结果写入当前公共知识检索池及用户记忆。
- 不更改已有公共知识包的导入、订阅、自动上下文和历史兼容行为。
- 不训练或微调回答大模型；不要求下载者部署 Dify、RAGFlow 或额外本地回答模型。
- 不建设多人协同、云盘同步、网页爬虫、付费交易或通用工作流平台。
- 不做功能插件，不在仓库根新增独立业务包；按小剧场模式归入 `services/`，配套本体 API 与独立模板页面。

允许复用主服务宿主、受控计算适配、存储根解析、模板与静态资源、HTTP 鉴权和市场连接基础设施；为新页面提供独立领域 API 所需的接线属于本阶段。复用基础设施不等于接通聊天业务。后续对话接入需另立方案，本阶段不预埋启用开关或隐式激活流程。

### 1.3 完成标准

1. 用户可在独立页面创建资料库，导入、查看、更新、删除资料并检索到真实原文片段。
2. 作者可从明确选定的资料版本构建、校验和导出成品包；没有完整向量产物的任务不能报告构建成功。
3. 兼容成品包可在另一台电脑安装、检索、重启恢复；安装和派生索引重建均不调用文档解析、OCR 或批量向量生成。
4. 通过真实市场完成作者发布、版本查询、他人下载、安装与更新；本地导出或模拟市场通过不能替代这一项。
5. 新功能的全部操作均不改变现有公共知识工具的可用性、检索结果及记忆数据。

## 2 当前基础与缺口

本节记录 `72120988d` 基线已有能力与当时缺口，供理解复用边界；变更后的模块状态见第 13 节，不应把基线缺口误认为仍未开发。

| 领域 | 当前能力与证据 | 本阶段缺口 |
| --- | --- | --- |
| 公共知识 | `knowledge/service.py`、`store.py`：知识包、分块、SQLite FTS5、向量快照、检索与后台任务 | 个人资料库和文件生命周期；独立存储与可追溯来源 |
| 包格式 | `knowledge/models.py`：严格 schema-v1 JSON，只有原始文本，拒绝附加向量等字段 | 独立的成品格式、兼容性声明及持久向量产物 |
| 本地模型 | `app/memory_server/knowledge_routes.py::_SharedEmbedder`：借用进程内 EmbeddingService | 显式构建任务、固定构建规格、不能依赖聊天触发模型就绪 |
| 文档解析 | `utils/document_parser.py`：PDF、DOCX、XLSX、PPTX 文本提取；`document_upload.py`：有界上传和后台线程 | 面向完整资料入库的结构化输出、长文档处理、来源定位 |
| 文本解码 | `static/avatar/avatar-drop-parser.js`：TXT/Markdown 的编码识别、解码及乱码检查，当前属于头像附件流程 | 提取可复用规则，补服务端持久导入校验；不依赖整个 avatar 模块 |
| 管理界面 | `frontend/plugin-manager/src/views/KnowledgeManager.vue`：总览、条目、包管理、诊断及市场入口 | 面向资料库与文件的页面、成品构建、作者发布 |
| 市场下载 | `plugin/server/routes/knowledge_market.py`：下载校验、订阅安装、退订；v1 忽略预生成索引 | 成品包下载校验、新安装目标、新协议协商 |
| 市场发布 | 仓库内有插件投稿工作台，但字段及任务围绕 `plugin.toml` 和 `neko-plugin publish` | 知识包作者创建、上传、发布及版本管理；远端源码与合同待核实 |

当前文档解析有 16 MiB 输入、32,000 字符输出、PDF 40 页等限制。它们属于现有附件路径，不能通过直接放大共享常量来获得完整入库。新导入流程应保留现有调用方行为，并明确报告超限、部分处理或不支持；不能将截断结果显示为完整入库。

现有知识包的单份 JSON 限制为 10 MiB，总条目和分块均有独立容量约束。这些不自动成为新资料库或成品包的容量合同，亦不能未经测量就取消限制。

### 2.1 复用落点与适配责任

新业务归属 `services/knowledge_library/`，分层禁止其导入 `knowledge`；不放宽禁边，也不注入旧领域对象绕过边界。当前已将纯文本能力下沉到 `utils`，新领域另建持久存储和编排；下表区分已实施复用与参考边界，不再把已落地的计算接口列为“执行位置待冻结”。

| 链路与现有入口 | 复用方式 | 新领域适配及禁止事项 |
| --- | --- | --- |
| `KnowledgeStore(database_path)` 及其 SQLite schema-v3 | 参考存储隔离与索引恢复思路，不直接复用旧 Store | 新 `LibraryStore` 独立实现 JSON 清单及不可变文档/向量版本，SQLite 仅为可重建 FTS；并非复制旧 SQLite schema。领域事务留在各自业务，通用文本规则由 `utils` 单点维护 |
| `knowledge/chunking.py`、`knowledge/text.py` | 已提取 `utils/text_chunking.py`、`utils/knowledge_text.py`，旧入口保留兼容导出 | 新 `make_chunks()` 调用 `source_windows()`，不走旧 `derive_chunks()` 的 96 块限制；新旧输入拼接和来源语义分别维护，token 边界缺口见第 4.2 节 |
| 旧关键词候选、向量排序、RRF 与片段选择 | 复用合法下层的分词、归一化和安全 FTS 表达式；新领域实现自己的候选与排序编排 | 不直接 import 旧检索模块，不解析旧 `_render()` 提示词文本；未来提取只限两方真正相同的纯算法，不把业务 Store 下沉到 `utils` |
| `EmbeddingService` 与新计算 API | 已由 Memory 所属路由提供 HTTP `/internal/knowledge-library/embeddings/{spec,plan,batch}`，Main 通过 `host.py` 注入适配 | 规格读取也走 HTTP，`services` 不 import `memory.embeddings`。单例、调度与准入见第 13.15 节，真实 TCP 故障验证见第 13.19 节；跨硬件质量与低配预算仍待验收 |
| `utils/document_upload.py::parse_uploaded_document()` 与 `utils/document_parser.py` | 复用受限读取、类型校验、可注入 parser/runner 及现有格式解析 | 先保留受管理原件；现返回值不含原始 bytes，上传对象会关闭；新增结构化完整解析合同 |
| `plugin/server/infrastructure/` 的 `package_sources.download_candidates()`、`package_transfer.download_package()`；现知识市场下载校验 | 镜像偏好、选路、流式落盘、超时、取消、切换及续传是复用候选；经市场进程的受限接口使用，或先完成合法下层提取 | 新 services 不直接导入 `plugin.*`；候选 URL 不等于受信来源，仍须逐跳来源与最终大小/摘要校验，并适配新格式、限额和安装目标 |
| 后端 `_authenticated_market_token()`、既有配对/市场连接 API；`useMarketAuth` 等管理页消费者 | 通过运行中市场连接服务的接口复用账号、凭据刷新与配对合同，参考小剧场的调用方式 | Main 不重导入市场模块获取另一进程状态；Vue composable 不直接加载到模板，不调用插件 CLI，不把 JSON 投稿代理当大文件上传器 |
| `utils/file_utils.py` 的 `atomic_write_text()`、`atomic_write_json()`、`atomic_write_bytes()` | 复用落盘、临时文件清理及 Windows 文件替换重试 | 单文件原子替换不等于多文件安装提交；仍需领域安装清单和恢复顺序 |

`KnowledgeService(root, embedder=...)` 虽然支持独立实例，但这不解除 `services/ → knowledge` 的禁边。它的 `start()` 会自动启动旧导入 runner 和补向量循环，旧导入及恢复固定消费 schema-v1 文本；不能把旧实例直接注入新业务充当安装器，也不能用旧 `import_pack()` 或 `_reconcile_blocking()` 代替冻结成品的安装恢复。

`services/chat_sync/model_package.py::install_model()` 可参考成员校验、保留原 artifact 和暂存切换次序；它绑定 Live2D 协议与限额，且读取成员到内存，不能直接作为资料包安装器或照搬其内存策略。当前任务 store 与发布器也有专属状态，任务恢复边界见第 9.1 节。

## 3 职责与隔离设计

### 3.1 领域划分

| 部分 | 责任 | 不负责 |
| --- | --- | --- |
| 个人资料库 | 文档保存、版本、解析、分块、索引、原文查看、检索 | 聊天工具注册、角色记忆、市场审核 |
| 成品包构建器 | 冻结所选资料版本、生成兼容向量、校验与导出不可变产物 | 发布账号认证、调用插件发布命令 |
| 成品包安装器 | 校验、兼容选择、事务安装、更新、卸载、派生索引恢复 | 自动重算不兼容包、激活公共知识工具 |
| 前端资料页 | 展示资料与任务状态，操作本地领域 API，发起市场操作 | 在浏览器生成向量、持有长期市场凭据 |
| 市场客户端适配层 | 使用已有连接基础设施，交互真实市场接口 | 实现或假定远端市场已有上传服务 |
| 远端市场 | 作者与作品身份、发布版本、artifact 托管及可下载状态 | 替下载者执行本地安装 |

按小剧场的“本体路由 → services 领域 → 模板页面”组织：业务由主服务宿主加载，领域实例、任务与数据保持独立，不新增功能插件或常驻业务服务。`host.py` 负责运行根、可写栅栏和计算适配，路由不重写领域规则。当前分层禁止 `main_routers/`、`services/`、`plugin/` 和 `app/main_server/` 直接导入 `knowledge`，新目录不改变这一约束。

当前模块按以下结构组织；实际入口与验证状态见第 13 节：

```text
services/knowledge_library/
├── __init__.py
├── host.py                 # 本体适配、实例生命周期、写入与计算能力注入
├── models.py               # 资料、版本、来源及成品合同
├── service.py              # 资料库编排
├── documents.py            # 原件保存、解析与预览
├── store.py                # 持久元数据、版本清单及提交
├── indexing.py             # 索引与检索适配
├── package_build.py        # 冻结输入、生成成品
├── package_validate.py     # 格式、向量、身份与摘要校验
├── package_install.py      # 安装、更新、恢复与卸载
├── jobs.py                 # 检查点、取消与恢复
└── paths.py                # 当前用户数据根解析

main_routers/knowledge_library_router.py       # 本体资料 API
main_routers/knowledge_library_market_router.py # 市场操作薄适配
main_routers/pages_router.py                  # 登记独立页面
templates/knowledge_library.html
static/js/knowledge_library.js
static/css/knowledge_library.css
tests/unit/knowledge_library/
```

参照 `services/theater/` 的功能归属和 `templates/theater.html` 的页面链路，不机械复制小剧场的全部文件。`services/theater_workshop/` 是无界面作者 SDK，当前没有正式页面或 HTTP 调用方；个人库本阶段没有独立 SDK 需求，不另建 `knowledge_workshop/sdk`。

小剧场也使用 `plugin/server/routes/theater_market.py` 作为外部市场到 Main 的受限桥接。知识包可复用必要的市场基础设施，但资料、检索、构建和安装业务仍归本体；不将功能实现放入插件目录或插件管理器。

### 3.2 必须独立于当前运行态公共知识

`KnowledgeService.availability()` 不检查每包的 `auto_context`，主动查询 `_allowed_pack_ids()` 也不以该开关隔离资料。把新资料写入当前 `knowledge/registry.json` 后，即使关闭自动上下文，仍可能注册并被 `query_public_knowledge` 查询。

因此，本阶段新增资料、草稿、导出的成品及新下载包：

- 使用独立的资料目录、清单与派生数据库，不写当前 `knowledge/registry.json`、`knowledge/packs/`、`knowledge/knowledge.db`。
- 不调用现有 `subscriptions/apply` 或既有 subscribe 的最终安装动作；可复用鉴权、下载校验等基础能力，但安装目标必须区分。
- 不参与现有 `tool_available`、全局公共知识统计、被动检索和模型工具参数生成。
- 不用修改公共检索过滤规则来补偿错误的数据混入。

旧 `knowledge_routes.py` 持有公共服务单例，Main 的 `public_knowledge_router.py::_relay()` 还会转发可用性通知。新领域可以复用鉴权与受限传输能力，但不得把独立实例挂到旧单例、旧代理回复或旧 availability 通知链。

现有已经安装的公共知识包继续由原链路管理。个人库与新成品包在新页面管理，不对同一对象建立两套启停、删除与任务权威。

### 3.3 存储要求

数据目录由 `ConfigManager.app_docs_dir` 解析，禁止写死平台路径。参照小剧场的 `<app_docs>/theater/`，新领域采用自己的 `<app_docs>/knowledge_library/`，由 `paths.py` 统一解析；不复用旧公共知识目录。新根已登记到运行数据迁移清单；未因此新增云同步，也不自动搬移旧公共知识数据。备份、暂存清理与发行资源仍按各自合同验证，不能以目录登记代替完整验证。

```text
<app_docs>/knowledge_library/
├── libraries/              # 持久资料元数据、原件、解析结果与版本
├── artifacts/              # 构建或下载的不可变成品
├── indexes/                # 可重建索引
├── jobs/                   # 任务记录、冻结清单与检查点
└── staging/                # 未确认预览及未提交安装
```

需要区分两类数据：

- **持久资料**：资料库与文档的稳定身份、版本清单、来源和片段映射、本地导入的原件副本、完整解析结果、所选版本快照、成品 artifact、安装清单、任务可恢复检查点。
- **派生索引**：当前实现的 SQLite FTS 可由保留正文和片段恢复；文档版本中的原始向量属于持久资料，不能按索引缓存回收。

历史保留策略已确认：保留受管理原件、正文、全部不可变文档版本、成品包、任务记录及重试输入，只自动回收可重建的旧 SQLite 索引。此策略不回溯删除历史快照，也不扩展为磁盘配额或历史资料自动过期；资料持续积累仍会占用磁盘。用户明确放弃未确认预览及传输暂存的原有清理另按其任务所有权处理。

导入保留应用管理的副本，用户删除库外原文件后不应导致已完成的资料失效。删除操作只影响应用管理的对象，不删除用户最初选择的外部文件。不得自动搬移或覆盖旧公共知识目录。

`KnowledgeStore` 的本地行号不是包内永久身份，领域映射须由持久清单恢复。现有 Store 在 schema 正确时允许额外表，但版本不符、缺表或完整性失败会抛错，旧 Service 随后删除整份派生 DB。稳定资料元数据不能仅存在其中；索引内映射只能是可重建投影，新领域的持久元数据不能交给旧恢复路径删除。

## 4 个人资料库最小闭环

### 4.1 首版输入范围

建议首版支持 TXT、Markdown、DOCX 和文字型 PDF。DOCX/PDF 复用后端解析能力；TXT/Markdown 的现成解码规则在头像附件前端，后端 `document_parser.py` 本身不接受这两类文件，需要补服务端持久导入。可提取编码与质量检查规则，但不依赖整个 avatar 模块、不复制其附件限额，也不把浏览器回传正文当作已校验原件。XLSX、PPTX、扫描件 OCR 和复杂版面保留为独立增量。

本阶段不接大模型改写、自动摘要或问答生成。文本清理与分块采用确定性规则，不把模型生成内容替换为原始资料。

### 4.2 文档生命周期

```text
选择资料库与文件
  -> 保存受限大小的原件副本
  -> 提取完整可支持的正文与位置
  -> 预览并确认解析结果
  -> 生成分块与索引
  -> 可检索
```

资料库内维护稳定的文档身份和内容版本；文件名不是唯一标识。同一文件重复导入应识别并告知，不静默覆盖同名不同内容。

上传时先保存受管理的原件与预览记录。现解析 helper 和路由会关闭 `UploadFile`/multipart form，确认请求必须使用服务端预览对象标识及冻结内容版本/摘要，不能重读原 HTTP 上传对象。未确认预览不进入检索池，放弃预览的暂存资料按独立且有界的清理规则回收。

更新采用新版本准备、校验后替换的方式。解析或索引失败时保留原可用版本，并展示失败与重试入口。只处理实际变化的文档或片段，不因编辑资料库名称就重算全部向量。

解析输出应保留文档、页码或章节、段落等实际可获得的位置。DOCX 没有可靠页码时使用章节或段落，不能制造固定页码。无可读文本的扫描 PDF 应明确提示首版不支持，不把空文档标记为完成。

分块与编码输入使用同一份 token 预算，计入文件名、必要前缀和特殊 token。当前先生成最多 1,200 字符的来源预窗口，再经 Memory `/plan` 用独立的真实无截断 tokenizer 规划连续完整字符范围，每段实际输入不超过 1,024 token；`/batch` 也在加载/推理前检查并明确拒绝溢出，不依赖模型自身截断。新构建使用 `neko-paragraph-token-windows-v2-title-v1`，缺失或漏尾规划不能生成成品；旧 v1 包继续可读，其原向量 token 覆盖不能由新版本背书。已通过罕见字、emoji、长标题和连续范围直接回归，真实本机 tokenizer 样本也通过；跨平台和恶意来源映射的进一步审查仍按第 11 节收口。

### 4.3 本地检索与查看

检索必须显式指定资料库，返回片段、文档名、位置、匹配方式及可打开的原文引用；不调用回答大模型。支持精确/关键词检索，并在兼容向量模型就绪时提供语义检索。

当前实现分别取最多 40 个关键词候选与 40 个兼容的正余弦向量候选，使用 RRF 融合；融合分相同时先按实际语义相似度，再按稳定身份排序。没有把未经本模型/语料校准的固定余弦值当作相关性概率或拒答门槛。正相似度但无关的片段仍可能进入结果，用户需要查看原文；这只适用于独立资料查找，未来接入对话前必须另做召回质量和无结果策略验收，不能把当前候选规则直接作为上下文准入规则。

页面显示文字可检索、向量准备中、完整可用等实际状态；关键词可用不能冒充成品包已具备可发布的向量产物。语义检索仍需要生成问题向量，不属于下载后免模型或零计算承诺。

## 5 成品知识包构建合同

### 5.1 构建位置与版本冻结

首版由发布者本机执行显式构建任务，市场负责接收、校验、保存与分发成品；当前实现没有建设市场端文档计算集群，也没有让下载者重新生成整库向量。

构建开始时冻结所选文件列表和受管理的持久版本副本，任务检查点引用同一快照。构建期间编辑资料不改变此次产物；冻结副本缺失或损坏时任务失败，恢复时不得转读最新版本。用户删除库外原文件不影响已经保存的副本。

冻结副本和检查点不放在旧公共知识 `.staging` 或旧包版本清理范围内。删除库内目标时，使未提交的关联任务失效，防止晚到任务重新写入已删除对象；已保留的历史版本、构建快照和重试输入不随删除自动回收。新快照冻结正文、片段与来源，不再重复存储构建器本来就会重新计算的缓存向量；旧含向量快照继续可读和重试，不迁移或改写历史文件。

构建器经 `host.py` 注入的适配器显式申请计算能力就绪，不依赖进入聊天或公共知识 warmup 的副作用。硬件不支持、模型缺失或加载失败时说明原因，不能生成缺向量却标记为成品的包。不得为每个资料库重复加载同一模型。

现有 EmbeddingService 是进程内单例，profile、维度和量化在实例构造时固定，调用接口没有逐任务规格参数。源码模式可分进程运行 Main/Memory，冻结发行物默认合并，不能用合并模式证明主服务总能直接借用 Memory 单例。现实现使用第 2.1 节的受限 HTTP 计算接口，两种运行模式保持同一合同；单机资源基线见第 13.17 节，完整桌面及跨平台成本仍待验收。只有匹配规格的实例可以借用，禁止临时修改属性、全局配置或调用测试 reset；取消构建不关闭共享模型。

构建任务入队前取得并持久绑定首次编码规格，每批和结束再次核对；重试必须使用原规格，不能重新选择当前档位。生产适配器每次显式接收 `expected_spec`，并发查询刷新缓存也不能改变任务请求。旧任务缺失规格时明确拒绝，不冒充可复现重试。单实例加载锁、冷单例构造锁、前台异步读取及计算预处理准入已有直接并发回归；独立进程被终止后的原输入重试也已通过，仍不承诺完整发行启动链验收。

### 5.2 最小内容

包为单独可校验的数据产物，禁止直接上传整份 `knowledge.db`、个人资料目录或运行时模型文件。现实现已冻结独立 ZIP 后缀、内部格式标识和第 1 版合同，见第 13.6 节；不向现有 schema-v1 JSON 偷加字段。

| 内容 | 最低要求 |
| --- | --- |
| 作品清单 | 包内稳定作品身份、展示名称、发布版本、来源与许可说明、格式版本、最低消费能力 |
| 文档记录 | 包内文档身份、名称、内容版本/哈希、原文结构与位置映射 |
| 最终片段 | 稳定片段身份、所属文档与位置、完整片段正文、实际 embedding 输入哈希 |
| 向量产物 | 向量与片段的一一映射、编码、形状、维度、数量及摘要 |
| 兼容规格 | 实际权重/外部数据/tokenizer 的 SHA-256、运行 profile、量化、输出维度、最大长度和处理规则版本 |
| 文件清单 | 每个产物的角色、相对路径、字节数与摘要，供安装前校验 |

包必须携带完整的可检索正文和来源结构，不能只有向量或摘要。当前固定四成员格式不包含原始 PDF/Word 附件，原件仅保存在作者本地；下载者查看的是包内保存的正文和来源位置，不能声称可以下载不存在的原文件。原件附件及其元数据清理属于后续格式扩展，不是本版已实现能力。

包内作品身份在首次构建前稳定生成，离线导出也使用该身份。市场作品 ID 在发布时另行分配或绑定，由版本描述映射到包内身份；不能在上传后回填冻结包并继续沿用原摘要。

不打包绝对路径、账号令牌、任务日志、查询历史、本地开关、未选定资料、代码或可执行安装钩子。新容器的成员路径、解压总量及数据结构必须有界校验；向量以数据读取，不反序列化可执行对象。

### 5.3 兼容性与完整性

当前 `model_id` 由 profile、维度、量化、最大输入长度组成，不能仅靠该字符串证明模型完全相同。第 1 版实现以实际权重、外部数据和 tokenizer 的 SHA-256 固定资源身份，未伪造现有资源没有记录的上游 revision。当前会按 RAM 自动选择 64/128/256 维，作者与下载者不一定一致。

新合同需要同时绑定：

- 检索模型及固定权重版本、量化、输出维度、分词/截断/池化/归一化规则。
- 分块算法和版本、标题/摘要/正文的输入拼接规则，以及实际送入 embedding 的文本 SHA-256。
- 向量存储编码与数值约束；模型 INT8 量化与向量存储 dtype 是不同字段，当前知识向量为 float32。

当前实现只接受本地编码器合同与实际资源哈希，具体字段见第 13.3 节；不支持发布者任意指定未知模型。自动维度在 4–8 GiB 为 64、8–16 GiB 为 128、16 GiB 及以上为 256；自动量化路径选择受支持的 INT8 或禁用，FP32 是显式配置，不是自动降级档。低于 4 GiB 默认禁用。原完整规格匹配已扩展为下述共同前缀视图；跨量化、不同权重或不同处理规则仍不兼容。

已实现共同前缀派生检索视图：在权重、tokenizer、量化、最大长度和固定预处理一致时，将文档与查询向量截取到共同支持的较低维度，并重新 L2 归一化；检查有限数值、原形状及非零前缀，不补零冒充高维。原 artifact、摘要、向量和编码规格保持不可变。固定的 last-token → prefix-truncate → L2 规则下，这一转换在数学上等价于直接输出共同低维，已做直接回归；该结论不等于检索质量或跨 CPU 数值验收。当前模型的[固定版本官方说明](https://huggingface.co/jinaai/jina-embeddings-v5-text-nano-retrieval/blob/ac5d898c8d382b17167c33e5c8af644a3519b47d/README.md)也列出 32/64/128/256/512/768 维 Matryoshka 支持；真实 ONNX 单机结果见第 13.17 节，跨平台仍另行验证。

另一选项是固定规范规格并按需加载专用查询实例，例如 256 维 INT8。它需要实例或池化合同、额外会话与内存预算，不能临时修改共享单例，也不能解决默认禁用模型的低配设备。本次审查建议先验证能复用现有编码器的派生视图，再依据实测决定是否需要第二实例；未将兼容扩展方案标为最终验收通过。保持现有严格匹配可避免错误混用，但无法兑现跨档位语义分享目标，不应作为该目标的最终验收结果。

兼容性实验须分别测试同 INT8 权重在 VNNI/AVX2 等执行路径的差异、INT8 与 FP32 的差异，以及各维度截取结果；记录余弦偏差、Recall@k、前列结果重合与资源成本。没有实测基线前不编造统一数值阈值；跨量化暂不放行，资源哈希一致也不单独构成检索质量证明。输出维度是在模型推理后截取，不能承诺它会按比例降低模型本体的计算或内存。

构建成功前检查片段唯一性、映射一一对应、输入哈希、向量行数和维度、有限数值、归一化要求及成员摘要。只允许校验通过的冻结产物进入发布步骤。

## 6 安装 更新与恢复

```text
取得市场冻结版本描述
  -> 下载指定字节并核对摘要
  -> 校验包格式、成员与资源上限
  -> 选择客户端兼容向量产物
  -> 在暂存区建立本地索引
  -> 原子提交安装清单与版本
  -> 页面显示可用
```

下载完成、包校验完成和安装成功是不同状态。原市场任务的 `staged` 只表示已交给导入器，不能直接沿用为新页面的完成依据。

- 安装保留经过校验的成品 artifact，派生索引通过已有向量恢复，不进入本地批量 embedding 队列。
- 缺少兼容产物时显示不兼容或提供兼容版本；不静默重算。关键词模式可用于浏览，但必须标明语义检索不可用。
- 相同作品、版本和摘要重复安装应幂等；同版本不同摘要必须拒绝，不能覆盖已发布的不可变版本。
- 更新先安装并校验新版本，再切换当前版本；提交前失败、取消、进程退出或磁盘不足时保留原可用版本，提交后按已提交清单恢复真实版本。
- 重启后根据已提交清单恢复；暂存状态不能成为已安装事实。重新下载或重建均使用原冻结版本和摘要。
- 派生数据库缺失或损坏时，从保留的成品包恢复文本、分块与向量，不重新解析作者原件，不调用 embedder 重算文档。
- 原 artifact 本身损坏或丢失时应重新获取同一冻结版本，或明确不可用；不得伪装成普通数据库重建并全量向量化。
- 市场作品身份与本地草稿身份分开。卸载市场副本不删除作者草稿或用户外部原文件；市场本地安装状态由本地提交结果决定。

更新只复用底层事务机制，不照搬旧 Service 的“先替换 DB、registry 写失败后从旧原文重新导入”补偿。该路径可能已丢失旧向量；新流程需保留旧文本、映射与向量版本直到新安装清单提交成功，失败恢复不依赖重算。取消在提交前生效；进入不可取消的提交阶段后拒绝取消并查询真实结果，不把一次取消申请显示成已回到旧版本。

### 6.1 提交点与崩溃恢复

当前 `LibraryStore._activate_library_revision()` 依次写不可变版本 JSON、建立本 revision 的 FTS、通过提交闸门、原子替换 manifest；manifest 本身就是唯一激活指针，不再另造一个指针权威。安装器先保留校验过的 artifact。下表定义应达到的恢复行为，不代表所有崩溃点已实测：

| 阶段 / 崩溃点 | 恢复动作与验收要求 |
| --- | --- |
| 接收或校验中，尚未保留完整 artifact | 不产生已安装状态；任务标明中断，仅从原冻结版本重试；回收本任务未完成文件 |
| artifact 已保留，版本文件写到一半 | 保留旧 manifest；完整 artifact 可复用，不信任半写版本；清理仅限能确认归属的未提交文件 |
| 新版本与索引就绪，manifest 尚未替换 | 旧库仍可读；新版本必须通过与正式读取相同的大小、结构及可读性检查，失败不得切换 |
| manifest 替换前后 | 替换前认旧 revision，替换后认新 revision；任务显示从提交事实恢复，不能因 HTTP 超时再切回旧版 |
| 提交后、响应或任务完成记录前 | 重试识别作品/版本/摘要幂等；不能重复创建安装；新索引缺失时从保留数据恢复 |
| 提交后旧索引回收中 | 只删除规范数字命名且 revision 小于当前 manifest 的普通 `.sqlite`；正文、向量版本、artifact、任务和快照不动。清理失败不改变提交结果，下次启动重试 |

旧索引回收在成功替换 manifest 后，或宿主取得单写者锁、完成任务恢复后执行；同用 Store 锁及存储写栅栏。须先核对受支持 manifest、库身份、文档引用和当前索引存在；当前或更高 revision、未知文件/目录、损坏清单、相关层级符号链接及 Windows 非零重解析点均保留。当前索引缺失时先留存，检索仍可从持久资料重建，不因启动清理调用 embedding。墓碑库同样保留当前索引与全部资料。

新领域使用 `persistence.write_json()` 流式编码、限制与正式读取相同的 128 MiB，先 fsync 文件再原子替换，在支持的平台同步父目录；新建目录项也按层持久化。激活前通过正式 reader 再核对持久版本，已有损坏候选不能跳过检查。成品保留补充目录同步，索引与构建 artifact 同步随对应模块验证。Windows 保留文件 fsync 与已有 busy-file 替换重试，Python 没有等价的可移植目录 fsync；不能宣称其断电保证已验证。

已在 macOS 隔离根验证写版本后、manifest 替换前、替换后三处实际子进程强杀，重启只读取已提交版本，并可从已保存正文/向量恢复缺失索引。其他崩溃点、Windows/Linux 与断电仍待验证；SIGKILL 通过不能单独宣称断电安全。

### 6.2 新旧协议隔离

成品包格式版本、市场版本描述协议版本、派生数据库 schema 版本分别演进。旧 schema-v1 文本包的旧入口保留，不把旧包伪装成免计算成品；新客户端的新资料库流程应明确拒绝或提示另行制作。旧客户端不得把新格式解释为 v1 原文包。

现 v1 版本描述使用 `extra="ignore"`，只增加最低客户端能力或向量字段会被旧端忽略。新成品必须通过显式协议/产物类型协商隔离，不能遇到未知协议就降级为 `artifacts.knowledge` 或旧 `subscriptions/apply`。安装还须核对远端描述与包内身份、发布版本及 artifact 摘要的完整绑定，不能只分别验证各字段格式合法。

## 7 市场发布与外部合同

### 7.1 旧公共知识消费合同

旧公共知识客户端下载以下远端合同，与本次个人成品包分享分别维护：

- `GET /api/v1/knowledge/packages/{package_id}/versions/{version}?channel=...`：读取版本描述。
- `POST /api/v1/me/knowledge-subscriptions` 与 `DELETE /api/v1/me/knowledge-subscriptions/{package_id}`：尽力上报订阅信息，不是安装事实的权威。
- 当前描述为 `protocol_version=1`，artifact 提供 URL、字节数与 SHA-256；现下载器仅支持受限 GitHub/Release/CDN/镜像来源和 `.neko-knowledge.json`。

新个人成品通过 `/api/v1/shares` 流程发布和下载，显式声明 `format=neko.personal-knowledge-package` 与 `format_version=1`；旧 `protocol_version=1` 描述不承担新成品发现或安装。两处版本数字相同不代表协议相同。测试须验证旧端安全拒绝新 ZIP、新端保留旧 JSON 入口；不能只在旧描述里增加会被 `extra="ignore"` 吞掉的向量字段。

### 7.2 新发布流程

```text
选择通过校验的本地成品
  -> 展示拟公开文件范围、名称、版本、来源与许可
  -> 使用市场账号提交
  -> 市场核验作品所有权与成品格式
  -> 完成实际市场要求的审核或发布步骤
  -> 取得市场作品 ID 与包内身份的绑定、冻结版本描述及分享地址
```

私有资料入库、生成成品和公开发布是三个独立动作。未明确选入发布范围的资料不上传；后续本地编辑不自动更新市场版本。失败重试应查询既有提交结果，避免一次不确定响应创建重复作品或版本。

发布与导出确认读取所选不可变 artifact 的实际文档列表、来源与许可，而不是当前库的最新勾选状态；导出提示这些内容包含在包中，发布进一步提示下载者可读取。已实现本机预览、明确确认、取消不下载及晚到响应保护；本机预览与上传复用有界准入，页面复用操作互斥，取消等待真实校验线程退出后再释放。公开市场预览继续只展示允许的包统计信息，不默认公开文件名或正文。

## 9 资源与故障控制

- 本地作者导入与构建是主要计算阶段，采用小批量、受限并发、可取消与可恢复任务；普通查看和检索不应被长任务阻塞。
- 向量适配在其实际执行宿主内复用模型，并隔离单份坏资料的推理失败；分别验证源码分进程与冻结合并模式，不假定两个子系统永远共享单例，也不静默增加模型副本。
- 完整成品包不要求下载端重新做文档 embedding；查询向量与检索自身仍消耗资源。安装写入与完整性校验也不是零开销。
- 文件、解析输出、片段、包压缩与展开大小、数量、内存中的向量快照均须有界；限制根据样本测试冻结，不机械沿用旧文本包限额。
- 原件和包产物尽量流式读取；原子切换时评估新旧索引并存的峰值，不能只计算最终向量矩阵大小。
- OCR 首版不强制启用，不下载回答大模型，不对外承诺固定内存占用或节省比例。

8 GB 内存、普通四核 CPU、SSD 可作为建议适配机型，16 GB 作为更宽裕的对照；这不是经过验证的最低配置。需要分别记录导入、构建、安装、索引恢复和查询的时间、峰值内存、CPU 与磁盘临时空间。

### 9.1 任务恢复与取消边界

前端 `marketInstallTask` 是插件安装单槽，后端 `_install_task_store.py` 限定特定工具安装，公共知识 `_jobs` 也仅保存在内存；这些不能直接实现新领域的恢复承诺。复用阶段展示、取消申请和提交闸门模式，资料领域维护自己的最小任务记录，不扩展为通用任务平台。

任务记录需持久绑定目标对象和版本、冻结输入/产物、构建规格、阶段检查点与提交事实。页面重载后恢复展示、进程重启后找回记录、重新执行未提交阶段是三个独立验收点；重启恢复只能使用原冻结输入，不能仅依据一个旧进度百分比继续执行。

解析、构建、安装各自声明提交点。取消是申请，提交闸门在持有目标写入所有权时核对任务是否有效；提交后返回实际结果，不反向宣称取消成功。`asyncio.to_thread` 的等待被取消或浏览器请求超时，不证明同步解析已经停止；需丢弃晚到结果，并将并发额度、输入和临时资源持有到实际 worker 退出。不能取消后立即释放额度并无限重试，亦不能让晚到写入重新创建已删除资料。

当前服务重启将未完成任务标为 `interrupted`，需要显式重试，不承诺自动续跑。Memory 未启动、重启或请求超时时，构建明确失败且不得发布半成品；查询回退关键词；资料入库可能仅完成关键词索引，当前没有自动补齐向量的保证。应为这些状态提供可理解的原因和恢复入口。

### 9.2 计算调度与容量预算

构建按 4 个输入一批 RPC，计算 API 的 16 输入、2,000 字符和 256 KiB 仍是单请求上限。现已在编码器所属层串行实际推理，前台/后台分别最多 32/4 个等待者，前台优先且连续 8 次后给后台一次防饥饿；另按服务 app 限制前台 2、后台 1 个计算 RPC，覆盖规格指纹、分词、冷构造、加载与推理。超额明确返回忙，不把队列压力变成模型粘性故障；取消等真实线程结束后才释放名额。不在 Main 加载第二模型。后台在每个文本推理后释放名额并让出事件循环，前台原批处理保持。第 13.17 节的单机复测记录了延迟、RSS 与吞吐取舍，不能仅凭优先队列测试宣称低配实时性能已达标。

| 场景 | 整改前计算量 | 整改后计算量 / 验证边界 |
| --- | --- | --- |
| 入库及构建 | 入库编码 N 个片段，构建再编码约 N 个；构建约 `ceil(N/4)` 批 RPC，可能截断 | 原预窗口 W 经约 `ceil(W/16)` 个规划 RPC 得到新 N；每阶段仍编码其实际 N，长文本可能增加片段和总工作量。当前构建不复用入库向量；新增独立 tokenizer 缓存，不增加 ORT 会话或回答模型调用 |
| 安装、索引恢复 | 文档向量调用为 0，校验、解包与索引有 CPU/磁盘成本 | 仍为 0；记录 JSON/向量展开、新旧版本并存的内存与磁盘峰值 |
| 单次语义查询 | 生成一次查询向量，无回答大模型 | 共同前缀视图不增加查询编码次数或改原包；真实单机跨维度小样本已通过，跨 CPU 与召回质量仍待测 |
| 另开固定规格实例 | 当前没有第二实例 | 额外加载、会话内存及冷查询成本未知；未测量前不纳入默认方案 |

| 输入容量样本 | 当前字符分块结果 | 限额含义 |
| --- | --- | --- |
| 单段 256,000 字符 | 237 个字符来源预窗口 | 最终 token 片段数由 `/plan` 决定，不能当作固定容量承诺 |
| 单文 12,000 个单字段落，含段间分隔共约 35,998 字符 | 12,000 片段 | 字符很少也能超过成品 10,000 片段上限 |
| 10 文档，各 1,960 个百字段落 | 约 1,999,180 字符、19,600 片段 | 可在本地 20,000 片段限额内，却不能构建成品；需明确发布预检或统一上限 |

现行 16 MiB 原件、40 页 PDF、单文 256,000 字符、库总 2,000,000 字符及包 64/128 MiB 是不同层的独立上限，不因其中一个未达到就放过其他上限。它们是试运行边界，不是以实测确定的最低硬件或耗时预算。

目标典型包的基准夹具定为 50 份文档、总正文约 1,000,000 字符，按段落结构覆盖约 2,000–5,000 片段；另设 10,000 片段边界和密集短段落夹具。在 8 GiB/普通四核/SSD 与 16 GiB 对照机上，记录冷/热加载、构建总时长与每批时长、构建时前台查询/记忆延迟、安装/恢复耗时、各进程 RSS 峰值和临时磁盘峰值。token 分块改变片段数时先记录实际数量，不伪造固定数量或耗时。现有基线只覆盖 16 GiB ARM64 隔离进程：50 文档、1,003,900 字符、2,000 片段在单文本后台微批下入库约 241 秒、构建约 387 秒、安装约 0.83 秒，采样 RSS 峰值约 650 MiB；构建期间前台向量查询 P95 约 240 ms。完整测试条件及首轮对照见第 13.17 节；这些数据不构成 8 GiB 最低配置、完整桌面资源或延迟达标承诺。

已修复的持久化容量缺口：格式允许 10,000 × 768 维，float32 原始向量仅 30,720,000 字节；安装会展开为浮点列表，合法等分量单位向量的紧凑 JSON 仅数值数组就约 153,720,000 字节，超过正式 reader 的 128 MiB 上限。现已由流式有界写入及激活前正式读取拒绝超限，不再先切换后发现不可读，也没有扩大读上限。该包格式的上限不保证每种数据布局都能安装，用户会收到明确容量原因。第 13.20 节已实跑 10,000 片段的 256 维成功安装与 768 维大 JSON 拒绝保旧版，均用合成向量；64/128 MiB 其他边界布局及完整客户端峰值仍待测。

### 9.3 安全、隐私与日志边界

包始终是外部不可信数据：摘要证明所收字节与声明一致，不证明作者诚实、向量确由所报模型生成或知识正确。市场账号用于归属追溯，审核用于既有发布政策；当前前三次投稿可自动发布，已发布作品更新也不是一律重新人工审核，不能将“市场审核 + 账号”写成安全或语义真实性保证。任意满足单位范数的恶意向量仍可能影响排序，本版不以全库重算验证作者正确性。

校验器限制固定成员集合、重复成员名、`external_attr` 中符号链接/特殊文件、加密及不支持压缩方式、实际流式展开字节数/摘要、JSON 重复键、NaN/Infinity/全零与异常范数。第 13.21 节已补显式恶意夹具并修复真实反例：标准 ZIP 读取器会按作者声明长度截取，伪造该前缀的 CRC 可隐藏真实展开尾部；现独立按最多 64 KiB 输出解码全部压缩流，核对真实大小、EOF 和尾部，不按压缩率猜测。成员名按未截断的原始名称校验，拒绝 NUL 隐藏后缀。重算摘要后的非法向量也须被拒绝；有限且单位范数仍只是数值安全，不是排序可信证明。

资料正文、原文片段、文件名、检索词、绝对路径及完整请求/响应不得进入应用日志、遥测或错误上报。只记录必要对象/任务身份、阶段、稳定原因码和计数；市场凭据继续不出既有连接层。解析与共享推理异常已用唯一标记合成资料做日志 canary 回归。另以真实 PDF 复现 pypdf 页解析警告泄漏私有对象名；个人 PDF 解析期间仅对当前解析线程的该日志源替换稳定诊断，清除参数、异常和缓存文本，保持其他线程附件日志与正文提取语义。此处只覆盖已核实的日志源，全局异常、其他第三方诊断、遥测与错误上报仍未完整覆盖，不能据此声称整条链零泄漏。

导出的包包含选定正文、文档名及作者填写的来源信息，公开发布后下载者可读取；本地导出本身不等于上传或公开。两者均按第 7.2 节确认实际 artifact 范围。本版不带 PDF/DOCX 原件，因此没有原件元数据清理功能；以后增加原件附件时，需明确 PDF 元数据、DOCX 作者字段等隐私，并提供适合格式的去元数据选项及独立测试。

用户可见错误由稳定原因码映射 i18n key，未知码显示已翻译的通用失败，不回传原异常正文。八语已补 `view` / `replace`、范围确认、容量/token 原因和提交后同步警告；检查覆盖 `button(key)` 间接调用，删除 key 的进程内变异也能使指定测试失败。作者填写的包名、文件名、来源和许可原文不自动翻译，协议字段名也不作 UI 翻译。

### 10.1 必测行为
