## 1. 文档目的与规范用语

本文用于：

- 快速理解功能解决的问题、边界和用户体验；
- 修改迁移、启动、恢复、窗口编排或存储目录时判断影响范围；
- 定位各状态文件、接口、进程和 UI 的职责；
- 作为回归测试、发布验收和故障排查的基线。

本文使用以下规范用语：

- **必须 / 不得**：数据安全或进程一致性约束，修改时不可绕过；
- **应 / 不应**：默认设计，偏离时需要明确理由和测试；
- **可**：兼容或体验增强，不是主链路成立的前提。

本文不把以下内容定义为本功能的一部分：

- Steam Workshop 外部安装目录自身的迁移；
- 运行中无重启热切换根目录；
- 自动删除迁移源目录；
- 将 cloudsave 跟随用户选择的运行时目录迁移。

---

## 2. 一句话结论

存储位置迁移不是普通的目录复制，而是一次受启动屏障保护的运行时根目录切换事务：用户可以在应用内选择路径；路径不变时原会话继续，路径变化时先冻结写入并关闭当前后端，再由 launcher 在新服务初始化前复制、校验和提交；失败则恢复旧根；cloudsave 和状态文件始终留在固定锚点目录。

---

## 3. 业务目标与核心约束

### 3.1 业务目标

1. 新安装用户可以确认默认位置或选择其他存储位置。
2. 升级用户可以继续使用历史数据，并在需要时迁移到新位置。
3. 配置、记忆、模型、插件等用户数据可以迁移，Steam Auto-Cloud 的固定同步位置不受影响。
4. 迁移中断、目标不可用或目标磁盘断开时，系统仍有明确的恢复路径。
5. 桌面端迁移期间只保留必要窗口，避免其他窗口继续访问受限服务。

### 3.2 不可破坏的设计约束

- 不支持对已经创建的 `ConfigManager` 热重绑定。
- 真正的复制和切根必须发生在旧服务退出之后、新服务初始化之前。
- 新策略只能在目标数据复制并校验成功后提交。
- `cloudsave/`、云存档暂存/备份和迁移控制状态必须固定在 `anchor_root`；`anchor_root/state/` 内的用户功能状态不能继续按整个目录固定。
- 迁移源默认保留，只有用户明确清理时才删除。
- 已提交的自定义根不可用时，不得把临时回退根静默提交为新的稳定选择。
- Main Server 和 Memory Server 必须共同受启动屏障约束。
- 多进程不能依赖父进程内存传递布局，必须使用持久化策略和启动环境变量。

这些约束共同防止两类严重问题：

- 同一会话同时向新旧目录写入，形成两套相互分叉的数据；
- 运行时目录已经移动，但 cloudsave 或子进程仍绑定旧位置。

## 4. 术语与所有权模型

| 术语 | 含义 |
| --- | --- |
| `anchor_root` | 平台标准应用数据目录。固定保存迁移控制状态、cloudsave、暂存和备份；其中 `state/` 当前还混有待拆分的功能状态。 |
| `selected_root` | 用户已正式提交的运行时数据根，可等于 anchor，也可位于其他磁盘。 |
| `effective_root` | 当前进程实际使用的运行时根。正常时等于 `selected_root`；恢复时可能暂时等于 anchor。 |
| `committed_selected_root` | 策略文件里记录的稳定选择，即使该路径暂时离线也不会被静默改写。 |
| `reported_current_root` | 恢复界面向用户展示的原正式路径，避免把临时 fallback 误报成稳定选择。 |
| legacy root | 历史版本可能使用过的 Documents、可执行文件目录或工作目录下的 `N.E.K.O`。 |
| retained source | 用户主动迁移成功后保留的原始目录。当前实现直接保留原位置，不另搬到备份目录。 |
| startup barrier | 阻止正常业务初始化和写入，直到存储选择或恢复完成的双服务屏障。 |

### 4.1 默认锚点位置

| 平台 | `anchor_root` |
| --- | --- |
| Windows | `%LOCALAPPDATA%/N.E.K.O` |
| macOS | `~/Library/Application Support/N.E.K.O` |
| Linux | `$XDG_DATA_HOME/N.E.K.O`；未设置时为 `~/.local/share/N.E.K.O` |

标准目录无法解析时，才使用当前可用根作为兜底。

### 4.2 目录归属

固定在 `anchor_root`：

- `state/` 中的 `storage_policy.json`、`storage_migration.json`、`root_state.json`、写保护锁及 cloudsave 控制状态；
- `cloudsave/`；
- `.cloudsave_staging/`；
- `cloudsave_backups/`。

历史版本的 `ConfigManager.local_state_dir` 曾把部分用户功能状态写入 `anchor_root/state/`。这些文件不属于迁移控制面，必须先按实际读写链路拆到 selected/effective state。拆分完成后，功能状态位于 `selected_root/state/`（正常运行时），而主动迁移清单、空间估算、诊断和 retained-source 清理对该目录的纳入属于后续迁移更新维护，不在本次拆分本身完成。

当前用户主动迁移清单定义在 `utils/storage/migration.py::MIGRATED_RUNTIME_ENTRY_NAMES`：

- `config/`
- `memory/`
- `plugins/`
- `live2d/`
- `vrm/`
- `mmd/`
- `workshop/`
- `character_cards/`
- `card_faces/`
- `jukebox/`
- `avatar_tools/`

不随用户主动迁移：

- 固定锚点目录；
- `logs/`、`logs/diagnostics/` 等可重新生成内容；
- Steam Workshop 实际安装目录及其他外部绝对路径。

当前 `ConfigManager` 还定义了 `pngtuber/`，但它没有进入主动迁移清单，详见“已知实现差异与维护风险”。

## 5. 总体架构

本功能由四层协作完成：

| 层 | 职责 | 主要实现 |
| --- | --- | --- |
| 路径与策略层 | 计算 anchor、校验选择、读取稳定策略、导出本次启动布局 | `utils/storage/policy.py`、`utils/storage/layout.py`、`utils/config_manager/storage_roots.py` |
| 事务与保护层 | 保存迁移检查点、复制校验、写栅栏、失败恢复、旧源清理 | `utils/storage/migration.py`、`utils/cloudsave_runtime/`、`utils/root_state_lock.py` |
| 服务编排层 | 受限启动、API、双服务屏障、受控关闭、launcher 接力和自动重启 | `app/main_server/__init__.py`、`app/memory_server/runtime.py`、`main_routers/storage_location_router.py`、`launcher_core/runtime.py` |
| 显示与桌面宿主层 | 应用内选择/维护/完成界面、Memory Browser 管理入口、桌面窗口隐藏恢复 | `static/app/app-storage-location.js`、`static/js/memory_browser.js`、`N.E.K.O.-PC/src/main/storage-gate.js` |

权威边界：

- 后端是存储状态和迁移决策的唯一真源；
- Web UI 只提交选择、展示状态并等待结果；
- NEKO-PC 只编排桌面窗口和原生目录操作，不自行迁移数据。

## 6. 持久化状态模型

三份控制状态文件位于 `anchor_root/state/`，职责不得混用。当前 `local_state_dir` 还被部分功能模块复用，因此该目录实际混有用户功能状态；这属于待修正的实现边界，不改变迁移目的。后续先按实际读写链路完成 anchor 功能状态拆分，再执行迁移清单和完整性维护。

### 6.1 `storage_policy.json`：稳定路由

用途：记录已经正式生效的长期选择。

| 字段 | 语义 |
| --- | --- |
| `version` | 当前为 `1` |
| `anchor_root` | 固定锚点 |
| `selected_root` | 已提交运行时根 |
| `selection_source` | `default`、`user_selected` 或 `recovered` |
| `cloudsave_strategy` | 固定为 `fixed_anchor` |
| `first_run_completed` | 是否已完成首次选择 |
| `updated_at` | 更新时间 |

约束：

- 用户仅预览或请求迁移时不得提前修改 `selected_root`；
- 只有保持当前路径、恢复提交或迁移校验成功后才能保存策略；
- `selection_source` 会被规范化，选中 anchor 记为 `default`。

### 6.2 `storage_migration.json`：迁移事务检查点

用途：让当前后端关闭后，launcher 仍知道需要执行什么；同时向重启后的 UI 提供结果和旧源清理信息。

主要字段：

- `version`、`txid`
- `status`
- `source_root`、`target_root`
- `selection_source`
- `confirmed_existing_target_content`
- `backup_root`、`retained_source_root`、`retained_source_mode`
- `error_code`、`error_message`
- `requested_at`、`started_at`、`updated_at`、`committed_at`、`completed_at`

| 状态 | 含义 |
| --- | --- |
| `pending` | 已接受请求，等待旧服务退出后执行 |
| `preflight` | launcher 正在重新验证源和目标 |
| `copying` | 正在复制运行时条目 |
| `verifying` | 正在校验目标快照 |
| `committing` | 正在提交策略和 root state |
| `retaining_source` | 已定义的保留源阶段；当前成功路径不单独落此状态 |
| `rollback_required` | 已定义的回退阶段；当前实现主要直接进入 `failed` |
| `failed` | 迁移失败，等待用户恢复决策 |
| `completed` | 迁移完成，检查点继续保留以支持完成提示和旧源清理 |

`pending` 至 `rollback_required` 属于活跃状态，会阻断正常启动。`failed` 本身不属于活跃迁移，但会配合 `root_state.mode=deferred_init` 进入恢复态。

### 6.3 `root_state.json`：运行状态与写栅栏

主要字段：

- `mode`
- `current_root`
- `last_known_good_root`
- `last_migration_source`
- `last_migration_result`
- `last_migration_backup`
- `last_successful_boot_at`
- `legacy_cleanup_pending`

| 模式 | 语义 |
| --- | --- |
| `normal` | 正常读写 |
| `bootstrap_importing` | 正在导入或修复旧数据，阻止冲突写入 |
| `bootstrap_readonly` | bootstrap 只读保护 |
| `deferred_init` | 需要用户恢复决策，正常业务不得启动 |
| `maintenance_readonly` | 已接受重启迁移请求，旧实例进入只读维护 |

`root_state.mode` 是写保护真源。`storage_migration.status` 只描述事务进度，不能代替写栅栏。

### 6.4 本次启动的环境变量

launcher 解析最终布局后导出：

- `NEKO_STORAGE_SELECTED_ROOT`
- `NEKO_STORAGE_ANCHOR_ROOT`
- `NEKO_STORAGE_CLOUDSAVE_ROOT`

环境变量只保证当前 launcher 及子进程的一致性；持久化真源仍是策略和状态文件。

## 7. 两类迁移必须分开理解

### 7.1 启动期历史数据导入

`bootstrap_local_cloudsave_environment()` 会调用 `import_legacy_runtime_root_if_needed()`，扫描历史候选根并将旧数据导入当前标准运行根。

特点：

- 发生在首次选择 UI 之前；
- 服务于旧版本升级和历史目录修复；
- 导入清单包含运行时目录，也包含旧 cloudsave、备份和暂存结构；
- 原历史数据仍保留；
- 结果写入 `root_state`。

因此升级用户可能经历：

```text
历史 Documents 根 -> 自动导入默认 anchor/runtime 根 -> 用户选择自定义根 -> 主动迁移到自定义根
```

这是当前真实行为，不应误写成“UI 选择后才首次触碰旧数据”。

### 7.2 用户主动更换存储位置

由存储位置 UI、API、launcher 和 `run_pending_storage_migration()` 协作完成。

特点：

- 必须由用户选择触发；
- 当前会话不热切根；
- 只迁移 `MIGRATED_RUNTIME_ENTRY_NAMES`；
- cloudsave 和状态目录不移动；
- 成功后源目录以 `manual_retention` 模式保留。

两类迁移使用不同清单和不同触发条件，维护时不得把 legacy import 清单直接当作用户主动迁移清单。

## 8. 完整启动与迁移时序

### 8.1 每次 launcher 启动的早期顺序

1. 清除继承的存储布局环境变量并重置 `ConfigManager` 缓存。
2. 创建轻量 `ConfigManager`，检查 `storage_migration.json`。
3. 若存在活跃检查点，执行待迁移事务。
4. 再次重置 `ConfigManager`，从最终策略解析布局。
5. 导出 `NEKO_STORAGE_*` 环境变量。
6. 执行 cloudsave phase-0 bootstrap 和必要的 legacy import。
7. 启动 Main Server、Memory Server 等服务。

关键保证：待迁移事务在新服务首次按运行根初始化之前完成。

### 8.2 服务启动屏障

Main Server 和 Memory Server 都读取统一的阻断原因：

- `selection_required`
- `migration_pending`
- `recovery_required`

存在任一原因时：

- 两个服务只开放健康检查、静态资源、系统状态、存储位置 API 和必要内部接口；
- 正常业务路由返回受限状态；
- 模型、记忆后台任务、页面配置及其他存储相关初始化不继续执行。

选择当前根成功后，Main Server 先通知 Memory Server 继续初始化，再初始化自身运行时。如果后续初始化失败，会重新封锁 Memory Server 并恢复受限模式。

### 8.3 正常启动

```text
launcher 解析布局
  -> 无活跃迁移
  -> cloudsave bootstrap
  -> Main/Memory 无阻断原因
  -> /api/system/status 返回 ready
  -> Web 放行页面配置与业务初始化
  -> NEKO-PC 放行附属窗口
```

### 8.4 首次选择且保持当前路径

1. `/api/system/status` 返回 `migration_required` 和 `selection_required`。
2. Web 获取 `/api/storage/location/bootstrap` 并显示应用内选择层。
3. 用户选择当前根或默认推荐根。
4. `POST /api/storage/location/select` 原子保存 policy。
5. 后端释放 Memory/Main 启动屏障。
6. 返回 `continue_current_session`，前端关闭引导并继续原会话。

此分支不创建迁移检查点，也不重启。

### 8.5 选择不同路径

1. `POST /api/storage/location/select` 校验路径并返回 `restart_required`、预检结果和 `restart_mode=migrate_after_shutdown`；此时不保存新策略，也不创建检查点。
2. UI 显示源、目标、数据量、空间、警告及“旧数据保留”说明。
3. 目标已有用户数据时，必须再次确认替换目标中的同名运行时条目。
4. 用户确认后调用 `POST /api/storage/location/restart`。
5. 后端重新校验，原子写入 `pending` 检查点和 `maintenance_readonly`，然后请求受控关闭。
6. 如果关闭请求未被接受，后端恢复 policy、migration 和 root state 的写前快照。
7. 服务退出并完成资源清理后，launcher 运行迁移事务。
8. launcher 发出迁移事件并启动下一代 launcher；桌面宿主继续等待新后端。
9. 新后端 ready 后，Web 自动恢复并显示完成提示。

### 8.6 原自定义路径恢复后的仅重绑定

已提交的自定义根暂时不可用时，进程可以用 anchor 建立受限恢复环境，但仍报告原 committed root。

如果原路径重新连接且可用：

- 选择原路径返回 `restart_mode=rebind_only`；
- 不复制数据；
- 保存策略并写入维护状态；
- 受控关闭后按原路径重新启动。

### 8.7 迁移失败

1. 检查点写为 `failed`，记录错误码和消息。
2. 如果源根已解析，policy 恢复并指向源根，`selection_source=recovered`。
3. `root_state` 进入 `deferred_init`，最后可用根和备份均指向源根。
4. launcher 仍拉起下一代后端。
5. Web 进入恢复界面，用户可以继续源根、重试可用路径或重新选择。

失败不得删除源根，也不得提交目标根为稳定选择。

## 9. 主动迁移算法

`run_pending_storage_migration()` 的实际步骤如下：

1. 规范化 anchor、源根和目标根。
2. 拒绝源目标相同、互相嵌套、源根不存在等情况。
3. 写入 `preflight`。
4. 检查目标是否已有用户数据：
   - `legacy` 或 `recovered` 场景可直接重绑定已有目标；
   - 普通选择必须带显式确认标记。
5. 创建目标并检查读、写、执行权限。
6. 写入 `copying`，逐个迁移存在的运行时条目：
   - 删除目标中的同名条目；
   - 使用 `copy2/copytree` 复制；
   - 目标中的无关文件和目录保留。
7. 重写 `config/workshop_config.json` 中与运行时根绑定的路径。
8. 写入 `verifying`，比较每个条目的类型、文件数量和总字节数。
9. 写入 `committing`，保存新 policy，并把 root state 切回 `normal`。
10. 写入 `completed`，记录源根为 retained source。

当前校验是结构统计校验，不计算逐文件哈希。源条目或内部文件涉及符号链接时不支持自动迁移。

## 10. 路径选择与预检规则

### 10.1 阻断规则

目标路径必须：

- 非空且为绝对路径；
- 经 `expanduser()` 和 `resolve(strict=False)` 规范化；
- 不是文件；
- 可创建并可写；
- 不位于项目源码目录内；
- 不位于 anchor 的 `cloudsave/`、`state/`、`.cloudsave_staging/`、`cloudsave_backups/` 内；
- 不是 anchor 的其他子目录；目标等于 anchor 本身允许；
- 与源根不存在父子嵌套关系。

自定义选择如果末级目录名不是 `N.E.K.O`，后端会自动追加该目录名。

### 10.2 非阻断警告

预检会针对以下位置给出风险提示：

- OneDrive、iCloud、Google Drive 等同步目录；
- 网络共享；
- 外置卷；
- 路径链中的符号链接；
- 目标已有数据；
- 可用空间接近或小于预计迁移数据量。

预检数据量只计算主动迁移清单中的现有条目。真正迁移时仍会重新执行关键校验，不能把 UI 预检当作事务提交依据。

## 11. 后端接口契约

存储路由前缀为 `/api/storage/location`。

| 方法与路径 | 职责 | 是否修改状态 |
| --- | --- | --- |
| `GET /api/system/status` | 最轻量的启动哨兵，返回 `ready` 或 `migration_required` | 否 |
| `GET /bootstrap` | 当前根、推荐根、legacy roots、阻断原因、迁移摘要 | 否 |
| `GET /status` | UI/桌面宿主轮询的生命周期状态和完成通知 | 否 |
| `GET /diagnostics` | 当前布局及运行时条目读写根诊断 | 否 |
| `GET /retained-source` | 已完成迁移及旧源清理能力 | 否 |
| `POST /pick-directory` | 无桌面 bridge 时调用系统目录选择器 | 否 |
| `POST /open-current` | 在文件管理器打开当前运行根 | 外部 UI 动作 |
| `POST /select` | 校验选择；同根时提交策略并释放屏障，不同根时返回重启预览 | 可能 |
| `POST /preflight` | 已完成启动后的设置页预检 | 否 |
| `POST /restart` | 创建迁移/重绑定状态并请求受控关闭 | 是 |
| `POST /exit` | 受限状态下退出；要求 `X-Neko-Storage-Action: exit` | 是 |
| `POST /retained-source/cleanup` | 显式删除迁移源并更新完成状态 | 是且具有删除性 |

所有状态 GET 响应都应禁止缓存。存储变更路由在 cloudsave 因本地状态不可用而被禁用时不得继续执行。

## 12. 并发、原子性与取消语义

### 12.1 原子落盘与互斥

- policy、migration 和 root state 使用原子 JSON 写入。
- 涉及多文件状态转换时，路由先保存写前快照，失败后精确恢复。
- 存储变更路由使用进程内 mutation lock。
- root state 的读—改—写使用 `root_state_transaction()`。
- cloudsave 写入另有跨进程 fence。
- 锁顺序必须保持 cloud apply lock 在外、root state lock 在内，避免死锁。

### 12.2 工作线程和请求取消

复制、删除、状态落盘等阻塞操作在工作线程中执行。即使 HTTP 请求被取消，路由也必须等工作线程到达确定终态后才释放 mutation lock，防止下一请求看到半写入状态。

受控关闭存在特殊边界：

- 关闭回调尚未成功时请求取消，必须回滚迁移状态；
- 关闭回调已经被 launcher 接受后才收到取消，不得回滚已经提交的 pending 检查点。

### 12.3 读接口不得偷偷写状态

`GET /bootstrap`、`GET /status` 等轮询接口只计算派生状态，默认不回写 `legacy_cleanup_pending`。需要协调写入时，只能在持有 mutation lock 的变更路径中执行，避免轮询覆盖变更路由的回滚结果。

## 13. Web 显示与交互

### 13.1 主页面启动门

`templates/index.html` 在主应用脚本前加载 `app-storage-location.js`。`static/app/app.js` 的 `ready()` 必须等待存储 gate 完成，之后才能加载页面配置和启动主要业务。

Web 流程：

1. 轮询 `/api/system/status`，后端短暂启动中时有限重试。
2. ready 时不显示遮罩，直接放行。
3. 阻断时获取 bootstrap 并显示首次说明、位置选择、确认、维护或恢复界面。
4. 后端离线期间保留维护页并继续重连。
5. 新后端 ready 后重载或恢复应用。

维护进度条根据检查点阶段映射为固定百分比，不是实时字节级进度。

### 13.2 完成提示和旧源清理

迁移完成后，检查点继续保留。主页面在启动屏障释放后显示完成卡片：

- 当前生效路径；
- 旧数据目录；
- 打开两个目录；
- 显式清理旧目录；
- 本次会话暂不处理。

用户选择清理时：

- 若旧源等于 anchor，只删除主动迁移清单中的运行时条目，保留 anchor 控制状态和 cloudsave；已拆分的功能状态按其 selected/effective 归属处理；
- 若旧源是独立目录，安全校验通过后删除整个旧源；
- 当前根、目标根、包含当前/目标/anchor 的父目录都不得作为清理目标。

### 13.3 跨页面协调与 Memory Browser

从 Memory Browser 发起变更时，页面通过 `BroadcastChannel` 和 `postMessage` 通知其他 NEKO 页面进入维护状态。

Memory Browser 是首次启动之后的持续管理入口，可查看并打开当前路径、选择新位置、执行 preflight、确认关闭迁移并处理恢复状态。它优先使用桌面宿主目录选择器，不可用时回退后端选择器。

## 14. NEKO-PC 桌面宿主协作

### 14.1 Storage Gate

`N.E.K.O.-PC/src/main/storage-gate.js` 将后端状态归纳为：

- `unknown`
- `checking`
- `selection_required`
- `maintenance`
- `recovery_required`
- `ready`
- `backend_unreachable`

阻断期间每秒轮询，ready 后每三秒轮询。

### 14.2 窗口编排

存储未 ready 时不得创建或显示正常附属窗口。进入 maintenance 后，桌面宿主会隐藏并记录 React Chat compact/full、subtitle、Agent HUD 和 jukebox 的可见状态。

宠物主窗口保持可见并承载存储遮罩。后端恢复后，宿主重载宠物页并按维护前状态恢复窗口。

### 14.3 原生 bridge

`window.nekoHost` 提供：

- `pickDirectory()`
- `openPath()`
- `closeWindow()`

preload 还会观察存储遮罩阶段，使遮罩区域获得完整交互能力，并通过 `neko:storage-location-phase` 通知主进程进入 maintenance。

### 14.4 后端代际重启

launcher 在迁移期间发送：

- `storage_migration_processing`
- `storage_migration_completed`
- `storage_migration_failed`
- `storage_migration_restart`

NEKO-PC 收到 restart 事件后清空当前 launch id，使下一代 launcher 的事件能被接受。

当前 NEKO-PC 没有设置 `NEKO_OWNER_RELAUNCH`，因此实际主路径是 launcher 自行启动下一代 launcher，而不是 Electron 主进程重新拉起。用户看到的“自动重启”主要是后端运行时代际重启，Electron 应用本身通常保持运行。

## 15. 恢复与异常场景

| 场景 | 当前行为 |
| --- | --- |
| 首次安装，无 policy | 进入 `selection_required`，用户确认当前/推荐根后原会话继续 |
| 已有有效 policy | 直接使用 committed selected root |
| 自定义根离线 | effective root 暂时回退 anchor，保留 committed root，进入 `deferred_init` |
| 自定义根重新可用 | `rebind_only` 重启，不复制数据 |
| 上次迁移仍为活跃状态 | launcher 在服务初始化前继续执行该事务 |
| 迁移失败 | policy 恢复源根，checkpoint=`failed`，root state=`deferred_init` |
| 目标已有数据 | 普通迁移要求二次确认；legacy/recovered 可使用现有目标 |
| 目标空间或权限不足 | preflight 或迁移阶段阻断，不提交新策略 |
| 受控关闭调度失败 | 精确恢复 policy、checkpoint 和 root state 快照 |
| 维护状态遗留 | 无 pending checkpoint 时可恢复部分 stale mode；`deferred_init` 不自动绕过 |

恢复原则：宁可保持受限并要求用户确认，也不静默产生第二套可写数据。

## 16. 诊断与可观测性

可用证据源：

- `/api/system/status`：是否允许业务启动；
- `/api/storage/location/status`：生命周期、迁移阶段、最后错误和完成通知；
- `/api/storage/location/bootstrap`：当前、推荐、anchor、cloudsave、legacy roots 和阻断原因；
- `/api/storage/location/diagnostics`：effective/committed/reported 根和各运行时条目的读写位置；
- `storage_policy.json`：最终稳定选择；
- `storage_migration.json`：事务最后阶段和错误；
- `root_state.json`：写栅栏与最后可用根；
- launcher 的 `NEKO_EVENT`：跨进程重启进度；
- NEKO-PC Storage Gate 日志：桌面窗口状态和后端可达性。

排障顺序：

1. 确认 committed、effective、reported 三个根。
2. 查看 `root_state.mode` 和 blocking reason。
3. 查看 migration checkpoint 是否活跃、失败或完成。
4. 核对 launcher 是否处理检查点并产生下一代事件。
5. 核对 Main/Memory 两边的启动屏障是否同时释放。
6. 最后检查前端遮罩或桌面窗口恢复。

## 19. 已知实现差异与维护风险

以下是当前代码事实，不应在文档中伪装成已经解决：

### 19.1 `pngtuber/` 未进入主动迁移清单

`ConfigManager` 将用户 PNGTuber 资源写入 `selected_root/pngtuber`，但 `MIGRATED_RUNTIME_ENTRY_NAMES` 没有包含它，诊断清单也没有包含它。

影响：切换到自定义根后，用户 PNGTuber 资源可能留在旧根且不被诊断接口发现。

### 19.2 诊断清单与迁移清单不一致

迁移包含 `card_faces`，但 `/diagnostics` 当前不报告它；`pngtuber` 两边都缺失。

维护要求：新增运行时目录时必须同步检查 ConfigManager、迁移清单、legacy import、诊断接口、清理逻辑和测试，不能只添加目录属性。

### 19.3 校验强度有限

当前只比较条目类型、文件数量和总字节数，没有逐文件哈希。相同统计值不能严格证明内容一致。

### 19.4 部分状态只存在于协议层

`retaining_source` 和 `rollback_required` 已被状态协议及 UI 识别，但当前迁移实现通常从 `committing` 直接到 `completed`，失败则直接到 `failed`。

### 19.5 首屏展示未使用全部 bootstrap 信息

bootstrap 返回 `legacy_sources`、`anchor_root`、`cloudsave_root`，当前首屏主要展示当前、推荐和自定义路径，没有完整展示历史来源和固定 cloudsave 位置。

### 19.6 桌面重启所有权仍有技术债

NEKO-PC 尚未启用 owner-driven relaunch，实际由 launcher 自拉起下一代。Windows 为避免 Job Object 在旧 launcher 退出时杀死新 launcher，会在清理后放宽 kill-on-close；这可能使后续失控进程不再自动随 Job 关闭，需要继续关注进程所有权和残留清理。

### 19.7 通用配置读取仍保留项目回退语义

`get_config_path()`、`get_memory_path()` 的通用接口仍可能回退项目目录；关键运行时链路应使用明确的 runtime 真源 API。诊断接口当前把 config/memory 视为 effective root 内读取，不能据此推断所有历史调用点都已完全消除回退。

### 19.8 `anchor/state` 的拆分边界

历史版本的 `ConfigManager.local_state_dir` 指向 `anchor_root/state`，使 voice identity、人格、greeting、locale、topic 等功能状态与迁移控制状态混在一起。拆分后的所有权是：

- `anchor_root/state/`：迁移策略、迁移检查点、root 状态、写保护和 cloudsave 控制状态；
- `selected_root/state/`：上述功能模块的运行状态；默认 selected 与 anchor 相同时两者物理路径可以相同，但逻辑所有权仍按文件类型区分。

本节只定义状态归属和运行时读写边界。将 `selected_root/state/` 纳入主动迁移、目标内容检测、校验、诊断、空间估算和 retained-source 清理，属于拆分完成后的迁移更新维护阶段，不能与本次拆分混为一项已完成能力。

## 20. 维护规则

### 20.1 修改目录结构时

新增、删除或重命名用户数据目录，必须同时检查：

1. `ConfigManager` 属性和目录创建；
2. `MIGRATED_RUNTIME_ENTRY_NAMES`；
3. legacy import 清单；
4. `/diagnostics` 运行时条目；
5. retained source 清理逻辑；
6. 路径重写规则；
7. 自动化测试和本文目录表。

### 20.2 修改状态或接口时

必须同步检查：

- launcher 是否仍能在服务初始化前恢复；
- Main/Memory 两个屏障是否理解同一状态；
- Web 维护轮询和固定进度映射；
- NEKO-PC Storage Gate 状态归一化；
- 请求取消、关闭已接受和状态回滚边界；
- 旧版本遗留 checkpoint 的兼容处理。

### 20.3 修改重启方式时

必须明确回答：

- 谁拥有并拉起下一代 launcher；
- 单实例锁如何交接；
- Windows Job/process group 如何保证新旧代不互杀；
- NEKO-PC 如何识别新的 launch id；
- 失败后由谁负责重新进入恢复 UI。

### 20.4 文档维护要求

- “当前行为”和“计划改进”必须分章记录；
- 不得保留已经落地功能的“建议新增”措辞；
- API、字段和状态名必须来自实际代码；
- 每次更改迁移清单、状态机、启动时序、窗口编排或恢复策略时同步更新本文；
- 尚未验证的发布环境必须明确写为未验证，不得用单元测试代替打包态结论。

## 21. 完成定义

一次存储位置功能改动只有同时满足以下条件，才可认为完成：

- 选择当前根能在原会话安全放行；
- 选择不同根只在旧服务退出后迁移；
- policy 只记录已成功提交的稳定根；
- cloudsave 和迁移控制状态始终固定在 anchor；`anchor/state/` 中的用户功能状态必须先完成归属拆分，再按 selected/effective 迁移；
- Main/Memory/NEKO-PC 对阻断状态理解一致；
- 失败不会删除源数据或留下半提交策略；
- 下一代服务在首次运行时路径绑定前已经拿到最终布局；
- 完成提示和旧源清理只作用于后端确认的 retained source；
- 自动化测试与受影响平台的手工验收通过；
- 已知未验证项和剩余风险被明确记录。

## 22. 当前不确定性

截至最后核对日期，代码级链路和相关自动化测试已经确认；以下仍需依赖真实发布环境验证：

- Steam 启动下的完整升级和自动重启体验；
- Windows 外置盘、CFA、OneDrive 与 Job Object 交接；
- macOS 目录授权和外置卷重连；
- Linux 不同桌面环境下的原生目录选择器；
- 大体量数据、符号链接和迁移中断时的耗时与恢复体验。

这些不确定性不改变当前设计事实，但限制了对所有发布环境“完全无风险”的结论。
