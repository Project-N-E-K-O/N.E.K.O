# 智能体系统

智能体系统（界面上叫「猫爪」，NekoClaw）负责让角色在对话之外把事情办成。要不要办，由主对话模型决定，并通过一次工具调用说出来；记账、决定谁来办、执行和汇报，由智能体服务器里的猫爪宿主负责。系统不再在每轮对话结束后自动分析：旧的逐轮分析器和它的几个执行通道已经删除。

下文有两个固定叫法：**委托**（代码名 `commission`）是她交办的一件事；**task agent** 是分多步去办一件委托的执行会话。界面上把 task agent 叫作「使魔」，代码、路由和字段值里一律是 `task_agent`。

## 运行时组件

```text
主服务器                                      智能体服务器 (:48915)
┌───────────────────────────┐                 ┌──────────────────────────────────┐
│ LLMSessionManager         │  HTTP           │ 猫爪宿主 (nekoclaw/host/)        │
│  工具：dispatch_task      │ ──────────────> │  ├─ 任务大脑                     │
│        query_tasks        │ <──── 回执 ──── │  │   台账 · 决策模型             │
│ cross_server.py           │                 │  ├─ task agent 管理              │
│ MainServerAgentBridge     │  ZeroMQ         │  ├─ 能力网关                     │
│ pending_agent_callbacks   │ ── 事后检查 ──> │  └─ 权限                         │
│                           │ <──── 汇报 ──── │ 内嵌插件服务 (:48916)            │
└───────────────────────────┘                 └──────────────────────────────────┘
```

每个智能体进程只有一个宿主。启动时只登记宿主怎么读本进程的开关（`app/agent_server/nekoclaw_mount.py`）；台账文件、agent runtime 和网关监听都等到第一次用到时才创建。

## 两个任务工具

总开关和至少一个能力开关打开时，`main_logic/core/tool_calling.py` 会给主对话模型注册两个内置工具。参数都只有一句自然语言，不带编号；这句话说的是哪一件委托，由宿主判断。工具定义在 `config/prompts/prompts_task_tools.py`。

| 工具 | 参数 | 用途 |
|---|---|---|
| `dispatch_task` | `task` | 派发：交办一件事。补充、改主意、叫停、转达用户对提问的回答也走它 |
| `query_tasks` | `question` | 查询：在办什么、某件委托办得怎样、某件事能不能办。留空就列出在办的事 |

处理函数调用智能体服务器的 `POST /nekoclaw/dispatch` 和 `POST /nekoclaw/query`，整个请求最多等 2.5 秒；连不上智能体服务器、或者请求没被处理就被拒掉（4xx）时，工具结果会写明这件事没有交出去；请求发出去了却没等到回应、或者智能体服务器自己出错（5xx）时，写明不确定有没有交出去（智能体服务器可能照样在办），并让模型稍后用查询确认，不要重新派发。主动搭话的请求不带这两个工具。

## 宿主内部

### 任务大脑

- **台账。** 一个 SQLite 文件 `<数据根>/nekoclaw/ledger.db`，存委托、委托的事件、task agent 干活用的会话、待发汇报（outbox）和任务偏好。委托的状态是 `queued`、`working`、`waiting_user`、`done`、`blocked`、`failed`、`cancelled` 之一，只在一个函数里迁移；`done` 和 `cancelled` 不能再变，所以迟到的结果盖不掉叫停。
- **派发第一轮（等）。** 在本地判断这句话是叫停、回答、补充，还是和在办的事重复；用关键词和 BM25 看有没有候选插件；看 task agent 能不能开。这句话补充的是一件最近一天内 task agent 办完或被叫停的委托时，另立一件新委托，照旧走第二轮选择：选中插件就由插件办，交给 task agent 时才在那件委托的会话里接着办；补充的是一件没办成的委托时，把那件委托接着办下去。回执是「已在做」「没有相关能力」（附原因）「受理」之一。这一轮不调模型，唯一的例外是本地没有候选、task agent 又开不了时跑一次小模型粗筛。超过 1 秒先回「收下了」，结论随后作为一条汇报送达。
- **派发第二轮（后台）。** 决策模型（`nekoclaw/host/decision.py`）用一次模型调用选出插件入口并填好参数。全部插件描述合计超过 3000 token 时先粗筛：关键词命中、BM25 前 10 名、小模型粗筛三者取并集。插件优先：一个入口就能办完的事，直接经插件服务的 `/runs` 协议调用；选不中，或者要分多步，才交给 task agent。模型还可以答插件和 task agent 都办不了、或者这根本不是一件要办的事，这时什么都不启动。答了不存在的插件或入口时不追问，按选不中处理。这一轮推翻了回执时，会立即告诉她。
- **查询。** 任何情况下都不调模型。进展直接读台账；「能不能办」沿用第一轮的本地匹配，不立案。task agent 办的委托，那一行里带上它到现在用了多少 token；没有记到用量的不带（模型的提供方不报用量时就没有）。

### task agent

task agent 在内置 agent runtime（`nekoclaw/runtime/`）的一个会话里干活；agent runtime 跑在子进程里，用到时才拉起。会话是一段留得下来、能接着办的对话，台账里一个会话一行。归到项目的委托在这个项目的那一个会话里办；接着某件旧委托的委托在那件委托的会话里办；其余的委托，以及 task agent 起的每个 task agent，各开一个会话。一个会话一次只办一件委托：前一件办完、没办成、被叫停或卡住之前，后一件停在 `queued`；前一件在等用户回话时，后一件也等着。同时最多 10 个会话在办，其余的委托停在 `queued`。委托开工时打开 runtime 里的会话，结束时关掉；说过的话留在磁盘上，同一个会话的下一件委托从那里接着办。

一件委托是什么（她派发的那句话、用户原话、用户希望这类事怎么办、为它挑出的插件入口、它干活的仓库自带的 agent 文档清单），写在它在会话里开头的那条消息里，不在系统提示里。在一个还什么都没说过的会话里开工的委托，这条消息里另带一段主对话的节选：她和用户在派发之前最近说的几句话的原文，最多 1000 token，标明是背景、不是指令，一句一行（一句话里的换行和连续空白压成一个空格）；除此之外 task agent 拿不到主对话的对话历史。会话第一次打开时用的系统提示和工具定义存在会话目录里（`system.json`），之后每次打开都沿用，所以同一个会话里一件件委托的请求开头是一样的。系统提示里每个会话都不一样的内容（工作目录、回复语言）排在最后。工具相同、宿主给的说明也相同（同一个角色、同一个项目和它的守则）的两个会话，前面的部分是一样的，请求开头相同的部分因此更长；模型服务方读不读缓存，由服务方定。只有对话被压缩成摘要之后才重新拼一份：在那之前，已经没有了的工具被调用时回答「现在用不了」，之后才多出来的自带工具不提供。会话的对话预设按 200,000 token 的上下文窗口管理，到 170,000 开始压缩；这两个数用户都可以按模型另设（内置的免费模型按 128,000：它不拒绝超长的请求，而是悄悄截掉多出的部分）。模型的服务方拒绝了超长的请求以后，这个会话和之后的会话自动按更小的窗口来（它说了窗口就按它说的，没说就按被拒的那次请求的长度），并且提醒用户一次，请用户自己设好这个模型的上下文长度。

task agent 用 agent 模型，还可以再开自己的 task agent。task agent 向用户提问或需要权限批准时，委托进入 `waiting_user`，直到她用 `dispatch_task` 把回答转达过来。

每次模型请求用了多少（请求次数、输入、输出、读缓存、写缓存）记在台账里，会话一份、委托一份；task agent 起的 task agent 用掉的也算进起它的那件委托。一件委托默认最多用 500 万 token（每次请求发出去的和收回来的都算，读缓存的也算）。这个上限每一步看一次：发这一步的模型请求之前，按台账里已经记下的用量看。用到了，内置 runtime 就停在那里（正在跑的工具不会被打断；同一步里的途中压缩和超长后的重试不再另看，所以实际会比上限多用一点），委托进入 `waiting_user`，像要权限一样问用户一次，问话里写明已经用了多少、同意以后再给多少。用户同意就再给 500 万，用完再问；不同意，task agent 被告知在 4 步之内（每步一次模型请求；途中压缩和超长后的重试不另算）把已有的结果交回来、说明还差什么，委托记成卡住了；task agent 报告其实已经办完的，记成办完。dsh 自己发请求，没有这个停下来的位置：用量照记，上限不拦。

会话可以分叉：把一个会话说过的话复制成一个新会话（复制到最后一个完整的位置，工具调用和它的结果成对），新会话沿用原会话的系统提示和工具定义，所以请求开头和原会话逐字相同。被复制的会话可以正在干活，不受打扰。分出来的会话和原会话共用工作目录，所以不给它写文件、跑命令和调用能力的工具，网关也不替它执行调用，只能读和答。正在复制一个会话时，或者它的副本里有委托在办时，这个会话说过的话不会被清理。只有内置 runtime 里的会话能分叉。会话之间互相问一句就是在这样的副本里回答的（见下文）。

宿主还可以替一个闲了很久的项目会话把对话压缩成摘要，让下一件委托少带旧对话。这是宿主自己多发的一次模型请求，默认关着（`TASK_AGENT_IDLE_COMPACT_ENABLED`）；打开以后，NekoClaw 关着、每日额度用完、用户按过「全部停止」（直到这个会话里又有新的事要办）时都不做，正在压缩时来了这个会话的新委托就把压缩打断。新委托接着等 runtime 把宿主开着的这个会话关掉，最多等 30 秒；runtime 一直没说关了的，这件委托以失败结束、写明原因，可以再交一次。拿不到完整的摘要时（请求失败、写到长度上限被截断，或者模型没写摘要而是调了工具），对话原样留着。

### 会话之间的消息和唤醒

task agent 可以找到别的会话、读它留下的东西、给它发消息、问它一句，也可以让宿主过一阵再叫醒自己。这是 runtime 的五个工具，都由宿主执行：`list_sessions` 在会话的名字、项目和最近几件委托的标题里按词找（不调模型），一页 10 行，只在最近用过的 300 个能收消息的会话里找（更早的会话搜不到；已经知道确切名字或完整会话号时，可以直接对它用 `read_session`、`message_session`）；`read_session` 给出一个会话最近几件委托的结果和复盘，或者它的对话记录里哪些位置出现了某些词，或者从某个位置起的一段记录（最多 2,000 token，记录从不整份给；由 dsh 管的会话只有结果和复盘，对话记录读不了）；`message_session` 给另一个会话发一条消息；`schedule_wake` 让自己在至少 10 分钟以后被重新叫起来；`ask_session` 问另一个会话一句，由那个会话的对话分出的一个临时副本来回答。只有在办委托、由内置 runtime 管的会话能被问；副本只能读文件、什么都不改，最多发 8 次模型请求，按提问方起的 task agent 来办：用量算进提问的那件委托，提问的被叫停时它跟着停，答案作为一条消息回到提问方，包装里写明这是模型照那边的对话写的。被问的会话本身不知道。一个会话每小时最多问 6 次，并和发消息一起计数。哪个角色名下的会话都能找到、能读、能发消息，每一行、每条消息都标着这个会话是哪个角色的。指认一个会话用它的名字或会话号；名字正好是另一个会话号的开头、或者两个角色各有一个同名会话时，宿主把这几个会话的完整会话号列出来，要求用完整的那个。task agent 起的 task agent 可以找会话、读会话，但只能给自己这个小队发消息，不能问别的会话，也不能定时。

每一轮都算在一件委托头上。委托自己要的唤醒（它定的时间、它发消息时订的做完通知）叫醒的是这件委托：一轮结束时这样的请求还没到点，这件委托就**歇着**——状态仍是 `working`，台账里记着从什么时候开始歇，runtime 里的会话关掉，位置和会话都让出来，同一个项目后来的委托可以先办。有两种情况不歇，会话不关，位置也不让，同一个项目后来的委托这时仍要等：它起的子使魔还在干（子使魔交回结果会叫起它的下一轮）；会话里还有后台命令在跑、而且它跑完会叫起下一轮（关了会话命令就没了）。这两种情况下到点的请求直接送进这个开着的会话，委托不重新排队。歇着的委托到点以后重新排队，从说过的话接着办。它汇报了办完、卡住或没办成，或者被叫停，没到点的请求随之作废。歇着的委托在宿主重启时不会被记成失败；它等的东西记在台账里，由宿主里第一次干活的调用接着管，不在启动时。发给会话的消息交给这个会话当时在办的那件委托：在跑的，在它下一次请求模型之前送进去；歇着的，叫醒它；在等用户回话的，先留着。没有委托在办时，在这个会话里为这条消息立一件新委托（它接着这个会话上一件委托，照常占位置、扣额度、该问用户时问用户，并向这个会话所属的角色汇报，task agent 没有另外指定时随角色的下一轮带上）。

消息和唤醒请求是台账里的行（`messages`、`wake_requests`），和汇报一样先写后发。消息送达时由宿主当场包一层：写明是哪个会话写的，写明它不是用户的话、不带用户的任何授权，再把正文放在两行边框之间，边框带一串只用这一次的随机字符，正文每行缩进。`read_session` 返回的内容，以及发起方订了做完通知时收到的那句话（`notify_when_done`；12 小时等不到就改成告诉它没等到），都用同一个办法包。别的会话写的话交进一件在办的委托时，用户之前对这件委托「仅本会话允许」过的东西一并作废，之后要用再问：消息不带任何授权，这一条由宿主把关，不只靠模型自觉。单条消息最多 1,500 token；给同一个目标每 60 秒最多发一条；每个会话每小时合计最多发 20 条，不论发给几个目标；一个会话最多有 50 条在排队；被消息叫起来新立的委托还能再用消息叫起一件，那一件就不能再发了。一个会话最多同时定 10 个时间，每天最多自己叫醒自己 300 次。总开关关着、免费额度用完时不叫醒，请求留着。「全部停止」会作废还没送达的消息，歇着的委托和别的委托一起被叫停；各件委托被叫停的这段时间里宿主不交付任何消息，这期间写下的消息在停止结束时一并作废，已经被叫停的委托再写的消息不收。交付时宿主先在台账里记下「已交给哪件委托」，再把话送进去；运行时报告这句话进了对话并且写进了对话记录（dsh 是带着它的那一段办完），才记成「已收下」。别的会话写的话和宿主到点的提醒送进会话时标明「不是用户亲口说的」，在内置 runtime 里不能凭它做只有用户亲口说了才能做的事（比如设目标）。dsh 还不看这个标记：在 dsh 里，只收到这类话的一段仍能设立或修改目标。没送成的、会话没收下就关了的放回去等下一次，赶上「全部停止」的不放回；宿主进程没了的时候还在路上的，下次启动重新交付；「全部停止」作废的在重启以后也不会再交付。宿主关闭时先停掉交付，没交付的留在台账里，下次启动接着办。

别的会话工作目录里的文件、它落盘的工具输出，读的时候不用问用户（设置里禁止读工作目录以外的除外，这时 `read_session` 也不能用）；它的对话记录只能经 `read_session` 读，换个名字的链接指过去也一样，对装着记录的那一层目录做内容搜索也不行（列文件名可以，里面的子目录照常能搜）；别的会话自己的目录不能写，自己的工作目录正好包着它时也不能。

### task agent 空间

task agent 留给以后委托用的东西（界面上叫使魔空间）放在 `<数据根>/nekoclaw/task_agent_space/`（`nekoclaw/host/space.py`）：全是明文，只有宿主写，按用户一份，所有 task agent 共用。里面有用户自己写的守则（`AGENTS.md`）、一行一条的索引（`MEMORY.md`）和一条一个文件的条目（`memory/*.md`）：可复用的经验、对出错之处的反思、东西在哪的参考、项目进度。全局一套，每个项目一套（`projects/<项目>/`）；不属于任何项目的委托归在 `_daily` 下。

- **会话第一次打开时**，守则和两份索引加在它系统提示里宿主给的那一段后面（环境说明和回复语言排在这一段之后），连同各段的标题和截断提示合计不超过 2100 token；再次打开的会话沿用当初那一份，直到对话被压缩成摘要。空间里什么都没有时不加任何东西。条目正文用到再读：task agent 用文件工具读空间里的任何文件都不用问，但不能往里写；写明了空间目录的路径、或要在空间目录里运行的 shell 命令，每次都要问用户，之前对命令给过的「始终允许」「本会话允许」都不算数（设置里禁止命令的仍然禁止）。它想留下的东西经 `note_lesson` 工具提交；用户的纠正与认可不放这里，记成任务偏好。
- **一条经验生不生效**由宿主判断，不问模型。task agent 提交时要说是怎么知道的（亲手核对过、看到过、猜的；必须说，不说的会被挡回去），可以给出能说明它的文件（不是必填）。核对过的直接生效；看到过的要有一个存在于委托的工作目录或它所属项目的工作目录里的文件（这两个目录之外的文件，只有用户把「读工作目录外的文件」设成一律允许时才算）；猜的、还有看到过却没有这样一个文件的，要等第二件委托也提交同一条（一件委托和它派出去的 task agent 合起来只算一件；标题或正文相同就算同一条；比较前会抹平大小写、空白和词两头的标点，词中间的标点保留，所以 `a.b` 和 `a. b` 不算相同；中文、日文这类词之间不空格的文字，句子里的标点也会抹掉，所以「先核对，再提交」和「先核对再提交」算相同），或者等 task agent 核实以后用原标题按「核对过」再提交一次，或者用原文按「看到过」再提交并带上一个存在的文件。还在等的是「待定」条目：和别的条目一样是一个文件，开头写明它还没确认，不进任何索引，task agent 只有搜这个目录时才会碰到。每一层最多 30 条；90 天没人再提交的，整理轮到它时删掉（整理在委托结束以后才做，一次最多看 500 个条目文件；一直没有委托、或条目文件比这多的时候，它会留得更久）；被删掉、被挤掉的以后还能再提交。条目依据的文件确认都不在了就过期（文件留着，索引里那一行拿掉）；当下没法去看的文件（在工作目录外面、而用户已经不再一律允许读那里的，或者所在的盘不应答的）既不算在也不算不在，不会让条目过期；用户在控制台里删掉的条目留一条记录，同样的经验不再收（每一层各记各的，在一个项目里删掉的，别的项目和全局那一层照样能收；直接删文件不留记录；每一层只记最近 1000 条删除；记录写不进去的时候条目照样删，那样同一条以后还能再收）。复盘和归档总结提炼的条目照同样的规则判，只是范围是全局的不管给了什么文件都按猜的算：一个项目里的文件说明不了它对所有项目都成立。这些文件只记成参考，既不让它生效，也不让它过期。复盘只留以后的委托从文件里看不出来、知道了会换个做法的：踩过的坑和绕过去的办法、常规路子不行时走通了的做法、能省时间的做法；文件、仓库自带的文档或历史里看得到的不留，也不复述这件委托做了什么。
- **在仓库里干活时**，每件委托开头的那条消息里另外带一张清单：这个仓库自带的 agent 文档（`AGENTS.md`、`CLAUDE.md`、`.agent/rules/` 等），只有路径和大小。宿主不读这些文件，也不把它们当成指令；task agent 自己读和手头的事有关的，当参考资料。仓库里没有这类文件、或者查找太久没回来（比如目录在不应答的网络盘上）时不带清单，委托照常开工。（dsh 是例外：它自己会把工作目录到仓库根这一路上的 `AGENTS.md`、`CLAUDE.md` 当指令读进去。）
- **委托归到哪个项目**：角色派发的那句话或用户原话里出现了项目的名字，就归到那个项目。这一步不问模型。归到项目的委托在这个项目的会话里办，排在这个项目前面的委托之后。
- **委托收工后**，调一次 summary 模型写复盘（`projects/<项目>/reviews/<委托号>.md`），最多提炼两条条目（被叫停的委托照样写复盘，但不提炼条目），并可以说明这件委托属于哪个项目。它在汇报存好之后在后台跑，每件委托最多一次。工具调用少于三次的委托、直达插件的委托、由别的 task agent 起的 task agent 都不复盘；没办成的委托要保持没办成满一天才复盘，因为它常被接着办。
- **整理**跟在委托收工之后，最多每六小时一次，从不在启动时跑。30 天没有新委托的项目连同一份总结（一次模型调用）搬到 `archive/<年>/<项目>/`，再有委托提到它时取回。会话的对话记录和落盘的工具输出，在这个会话里办过的委托最后一次变动 30 天后删除；其中还有在办、等回话或卡住了的委托时不删。工作目录从不删除。

会话目录（`<数据根>/nekoclaw/task_agents/projects/<项目>/sessions/<会话号>/`；为一件委托新开的会话，会话号就是这件委托的号）故意放在另一棵目录树里：工作目录里有大量链接，更换存储位置时留在原处；使魔空间则跟着用户的其他数据一起搬。

### dsh：可选的 agent runtime

dsh（DeepSeek Harness）是用户可以另外下载的第二个 agent runtime（`nekoclaw/dsh/`），内置的那个始终都在。没装 dsh 的用户什么都不变：它的模块不会被导入，也不起任何进程。

- **用哪个**（`nekoclaw/host/runtimes.py`）。每个会话在第一次有委托开工时定下 runtime，记在台账里，之后不换。新委托在 dsh 上办，条件是 dsh 已安装、用户没有选「只用内置」、委托的模型走 OpenAI 兼容接口；否则在内置 runtime 上办。接着办的委托回到它开工时的 runtime，因为对话记录只有那个 runtime 读得了；task agent 起的 task agent 跟着起它的那个。
- **dsh 用不了时**。dsh 起不来、没有确认权限守卫已加载，或者没给这件委托开成会话，这件委托改由内置 runtime 办，原因记进委托的事件里；之后 5 分钟新委托不再试 dsh。开工在 dsh 上、而 dsh 已被卸载的委托，在内置 runtime 上从头办。dsh 进程中途退出时，在办的委托记为失败，可以接着办。
- **怎么连**（`driver.py`、`acp.py`）。dsh 是一个子进程，经标准输入输出按 ACP（JSON-RPC）通信。一个进程带多个会话，用到时才起，所有会话空闲 5 分钟后退出。驱动把 ACP 的通知翻译成和内置 runtime 一样的事件，所以宿主的其余部分不区分两者。
- **模型请求**（`forward.py`、`endpoint.py`）。dsh 的模型请求发到本机回环地址上的一个转发口，由它换上真正的模型名和 key、补上各厂商需要的参数，再转给用户配置的地址。key 不交给 dsh，每次请求的用量由转发口读出来。转发口端口随机，每个 dsh 进程一个随机令牌，带 `Origin` 头的请求一律拒绝。
- **权限**（`profile.py`）。dsh 自己的沙箱关闭；随配置带上的一个守卫让 dsh 在每次工具调用之前先问，问到的都交给宿主同一段权限代码判断。经能力网关的调用在发出之前判权限、问用户，调用到达网关时不再问。
- **宿主的工具**（`host_tools.py`）。汇报、记经验、网页搜索和抓取、子 task agent 以一个 MCP 服务的形式提供给 dsh，定义和内置 runtime 用的是同一份；dsh 自带的网页搜索和抓取关掉了，所以抓网页和内置 runtime 一样只到公网地址。能力网关按 MCP 直接挂给 dsh。
- **装在哪**（`install.py`）。`<数据根>/nekoclaw/dsh/`：程序、dsh 自己的配置和对话记录都在这里，不随存储位置迁移。下载的版本固定，文件按 sha256 和大小校验。

在 dsh 上有几处和内置 runtime 不同：途中插话要等当前一段结束才送达；回复整条到达，不是逐字；经能力网关的一次调用最长 60 秒；没有「提问并原地等回答」的工具，改用汇报里的等回话；dsh 自己压缩对话、不告诉宿主，所以压缩之后不会重新告诉会话开头说过的那些话，内置工具组也不会重新交一遍。

### 能力网关与权限

除了自带的文件和命令工具，task agent 用到的其它能力都经能力网关（`nekoclaw/host/gateway.py`）取得。网关是回环地址上的一个 MCP 服务，第一个需要它的 task agent 启动时才开始监听，一件委托一个令牌。它提供：

- 对筛选可见的插件入口，每个入口一个工具，和直达调用走同一段 `/runs` 代码；
- `mcp_adapter` 插件里配置的 MCP 服务的工具；
- 键鼠、浏览器两组内置工具，见下一节；只有 task agent 能调用。

task agent 的工具清单里只有网关的两个工具，办哪件委托都一样，当时有没有能调用的东西也都一样：`capability_search` 按用途找能力，`capability_call` 按名字调用。会话存续期间装上的插件、打开的浏览器都经这两个工具使用，会话的工具清单不用变。任务大脑为一件委托挑出的入口（名字和参数）写在这件委托开头的那条消息里。

权限存在 `<数据根>/nekoclaw/permissions.json`，每一类是 `first_ask`（首次询问）、`always_ask`（每次都问）、`allow`（放行）、`deny`（禁止）之一。默认放行插件入口和工作目录内的文件读写；在工作目录外读写文件、跑命令、键鼠、浏览器、每个 MCP 服务默认首次询问。设成 `deny` 的插件或 MCP 服务，直达调用也不会用到。键鼠和浏览器这两类的工具是一次点击、一次按键这样的小步，所以用户只批准「这一次」时，放行到 task agent 这一轮跑完为止。

### 内置工具：键鼠与浏览器

键鼠操控和浏览器操控是猫爪的两组内置工具（`nekoclaw/builtin/`，在智能体进程里）。task agent 在自己的循环里一步一步调用它们，和自带的文件、命令工具并列，每一步都先看到上一步的结果再决定下一步。两组工具都不带自己的循环，调用它们也不会另外请求模型。给模型看的工具定义在 `config/prompts/prompts_nekoclaw_builtin.py`。网关不把它们列进 task agent 的工具清单：每次请求只带每组一行介绍，里面写明这一组的第一步怎么调（打开网页、截一张屏）。第一步经 `capability_call` 调用，照常执行；办成了，回给它的结果前面带着这一组的用法说明和工具定义（每组最多 2000 token）。之后的工具都经 `capability_call` 按名字调用。不从第一步开始的任务，用 `capability_search` 的 `group` 参数单独加载这一组。这一组还没交给它时，第一步以外的调用不会执行，回给它的是这一组的说明和定义。runtime 把对话压缩成摘要以后，之前交过的组在下一次用到其中的工具时重新交一遍。

- **键鼠。** 只有一个工具 `computer`，用 `action` 参数区分动作：`screenshot`、`click`、`move`、`drag`、`scroll`、`type`、`key`、`wait`。它靠截图工作：坐标的横纵两个方向都是 0 到 999 的整数，和屏幕大小无关；每次调用都返回动作之后的一张截图。超出范围的坐标会被拒绝。
- **浏览器。** 15 个 `browser_*` 工具：打开网址、取页面快照、点击、悬停、填输入框、一次填多项、输入文字、按键、截图、列出／切换／新开／关闭标签页、等某段文字出现、处理弹框。页面以文字快照的形式读取，内容是页面的无障碍树，每个元素带一个 uid，操作时用 uid 指明元素。uid 不在最新快照里时拒绝执行。快照最长 3000 token，超出就截断，并写明从哪里接着读。只能打开 `http://` 和 `https://` 地址。

浏览器用的是用户自己装的那个：Chrome、Edge、Brave、Chromium，按这个顺序找；在 Windows 上，系统默认浏览器是其中之一时排在最前。操控走浏览器的调试协议（Chrome DevTools Protocol，一条 WebSocket），不经任何浏览器自动化库。默认给它一份独立的资料目录 `<数据根>/nekoclaw/browser_profile`：在里面登录过的网站会一直保持登录，用户平时的登录状态不在里面。也可以改成直接操控用户正在用的浏览器，这要求 Chrome 144 以上，用户自己在 `chrome://inspect/#remote-debugging` 打开远程调试，每次连接浏览器都会弹窗要用户点允许。选择存在 `<数据根>/nekoclaw/browser.json`；浏览器装在不常见的位置时，在这个文件的 `executable` 里写明路径，或者用环境变量 `NEKO_BROWSER_PATH` 指定。

浏览器工具自己启动的浏览器在任务之间不关：一件任务办完或被叫停，窗口和里面的页面都留着，下一件任务接着用同一个浏览器。应用只在两种时候关它：保存了有变化的浏览器设置，退出应用。叫停全部任务（`end_all`）、关掉浏览器工具的开关或 Agent 总开关，或者 agent 模型连不上、开关被自动关掉时，有窗口的浏览器留着，用户可以接着看里面的内容；开关关着的时候，浏览器工具的调用一律不执行。不开窗口（`headless`）启动的浏览器在这几种时候照旧关掉。应用和留着的浏览器保持连接，所以它照旧碰不到本应用自己的服务端口。直接操控用户正在用的浏览器时，应用任何时候都不关它，只断开连接。

用户自己把这个窗口关掉以后，应用不会自己再打开它。使魔下一次调用浏览器工具时，委托进入「等你回话」（和要权限时一样），问用户要不要重新打开浏览器：本次允许，或者拒绝。浏览器每被关一次就问一次，不看「浏览器」这一类权限的设置，回答没有时限。浏览器自己崩溃和被用户关掉分不开，同样会问。

应用不随包附带浏览器，启动时也不下载浏览器。Playwright 只是测试依赖，`browser-use` 不在依赖里。本机找不到可用的浏览器时，浏览器操控不就绪，原因码是 `AGENT_BROWSER_NOT_FOUND`。

`computer` 和 `browser_take_screenshot` 返回的是图片，所以只提供给模型能看图的 task agent。模型默认按能看图处理；厂商因为请求里带图片而拒绝时，这次请求去掉图片重发一遍，并把这个模型记到 `<数据根>/nekoclaw/model_capabilities.json`。task agent 的上下文里，这些工具的截图合在一起只保留最近 3 张。

桌面只有一个，浏览器也只有一个。一件委托从第一次调用起占用一组工具，直到 task agent 这一轮跑完、委托进入等用户回话，或者委托结束。一件委托和它开的 task agent 共用一次占用。别的委托要用这一组时最多等 120 秒，等不到就被告知是哪件委托占着。

委托开始占用、放手时，智能体进程发出 `builtin_activity` 事件，主服务器把它作为 `agent_builtin_activity` WebSocket 消息转给每个已连接的页面。页面只把它再作为 `neko-agent-builtin-activity` DOM 事件交出去，自己不画任何东西。`GET /api/agent/builtin/activity` 返回当前的占用情况，`POST /api/agent/builtin/stop` 叫停占着的那件委托，见[智能体 REST API](/zh-CN/api/rest/agent)。

## 汇报回流

每条汇报先写进台账的 outbox，再经 ZeroMQ 发给主服务器。发送失败后 1 秒重试，之后每次翻倍，最长 5 分钟；上一个进程没发出去的汇报，在宿主下一次被用到时补发。

| outbox 类型 | 含义 | 发送时的事件 |
|---|---|---|
| `task_result` | 委托怎么结束的 | `task_result` |
| `question` | 委托在等用户回答或批准 | `proactive_message` |
| `correction` | 第二轮或事后检查发现她说的和实际不符 | `proactive_message` |
| `receipt` | 第一轮超过 1 秒后补发的结论 | `proactive_message` |

主服务器把汇报放进对应 `LLMSessionManager` 的队列，按现有的投递方式送达：`proactive` 唤醒她开口，`passive` 在她下一轮带上，`silent` 的结果不向她汇报。文本会话可以立即投递；语音会话可能延迟到注入或热切换边界。她转述汇报的那一轮不会再送去做下面的事后检查。

对话会话每隔几轮就会换一个，自己留不住任务记录。每个新会话都会调用 `GET /nekoclaw/brief`，得知哪些事还在办。委托的每次变化同时作为 `task_update` 事件发出，供[任务 HUD](/architecture/task-hud-system) 显示。

## 事后检查

用户发起的一轮结束、而她这一轮没有调用会动手的工具时（回忆、查知识、`query_tasks` 不算），`main_logic/cross_server.py` 会发出 `turn_check_request`，带上用户这句话和她的回复。`publish_turn_check_reliably()` 短暂等待 `turn_check_ack`，超时重试一次。她自己发起的轮次、智能体回调轮次、只有图片的轮次不发。

宿主先过一道不花钱的门：输入时的意图分数已知且低于 0.2、用户的话里没有命中任何插件关键词、而且每个可被筛选的插件都声明了关键词，这三条同时成立就跳过。过了门的轮次花一次小模型调用，结论四选一。

| 结论 | 处理 |
|---|---|
| 没事，或她有意不办 | 什么都不做 |
| 她说做不到，但本地匹配找得到办法 | 提醒她，由她自己更正 |
| 她答应了，却没派发 | 替她派发，并告诉她 |
| 她说办完了，台账里没有这件委托 | 提醒她，由她自己更正 |

检查本身没有执行权：只有她派发了，或口头答应了，才会立案。

## 传输映射

HTTP 负责控制和查询，监听 `127.0.0.1:48915`；内嵌插件服务监听 `127.0.0.1:48916`。事件走同步 ZeroMQ socket，在后台线程接收，因此也兼容 Windows Proactor 事件循环。

| 默认地址 | 模式 | 方向 | 用途 |
|---|---|---|---|
| `tcp://127.0.0.1:48961` | PUB / SUB | 主 → Agent | 会话和生命周期事件 |
| `tcp://127.0.0.1:48963` | PUSH / PULL | 主 → Agent | 可靠的 `turn_check_request` 队列 |
| `tcp://127.0.0.1:48962` | PUSH / PULL | Agent → 主 | ACK、状态、任务更新和汇报 |

端口可分别通过 `NEKO_ZMQ_SESSION_PUB_PORT`、`NEKO_ZMQ_ANALYZE_PUSH_PORT` 和 `NEKO_ZMQ_AGENT_PUSH_PORT` 覆盖。Agent → 主服务器的事件没有 HTTP 降级路径：汇报留在 outbox 里，直到桥接收下为止；`task_update` 和状态事件只尽力发送。

## 能力状态

权威状态通过主服务器的 `/api/agent/*` 代理暴露。前端通过 `/api/agent/command` 修改状态，通过 `/api/agent/state` 刷新状态，不应把本地复选框当作权威来源。

| 状态 | 含义 |
|---|---|
| `analyzer_enabled` / UI `agent_enabled` | 总开关 |
| `computer_use_enabled` | 给 task agent 用的键鼠工具 |
| `browser_use_enabled` | 给 task agent 用的浏览器工具 |
| `user_plugin_enabled` | 插件入口，直达调用和经网关调用都受它控制 |

Manager 和智能体服务器构造时这些开关均为关闭。首次真实 `greeting_check` 后会恢复持久化的运行时意图，因此“构造时关闭”不表示每次刷新页面都会重置用户选择。键鼠和浏览器还要求 agent 模型的连通性检查通过（`app/agent_server/model_probe.py`）。此外，键鼠要求本机能发出键鼠输入，浏览器要求本机装有可用的浏览器。

## 叫停、上限与重启

- 叫停时先把状态写成 `cancelled`，再取消插件的 Run（调用插件服务的 `POST /runs/{run_id}/cancel`）或关掉 task agent 的会话。`POST /admin/control` 的 `end_all` 和关闭总开关会叫停全部在办的委托。
- 桌面和浏览器同一时间各只归一件委托用（见「内置工具」一节）；同一次占用里的调用一个做完才做下一个。叫停一件委托会取消正在做的调用，并放开它占着的桌面或浏览器；已经发出的点击和跳转撤不回。
- 插件可以返回 `deferred: true`。委托保持 `working`，直到 `/api/agent/tasks/{task_id}/complete` 被调用；一小时没等到就标成 `failed`。
- 宿主重启后，上一个进程留下的 `queued`、`working`、`waiting_user` 委托标成 `failed`，随她的下一轮汇报；deferred 的委托保留到期限为止；歇着的委托原样留着，它等的东西记在台账里。
- 智能体进程给 HUD 用的任务视图会把已结束的任务保留五分钟。
