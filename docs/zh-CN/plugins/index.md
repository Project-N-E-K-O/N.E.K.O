# 插件系统概览

N.E.K.O. 插件系统是一个基于 Python 的插件框架，建立在**进程隔离**和**异步 IPC** 之上。平台只有两种包类型：产品功能使用 **Plugin（插件）**，外部协议桥接使用 **Adapter（适配器）**。原 **Extension（扩展）** 包类型已经移除；`PluginRouter` 仍可在普通 Plugin 内部使用。

## 架构

```
┌────────────────────────────────────────────────────┐
│              Main Process (Host)                   │
│  ┌──────────────────────────────────────────────┐  │
│  │   Plugin Host (core/)                        │  │
│  │   - Plugin lifecycle management              │  │
│  │   - Bus system (memory, events, messages)    │  │
│  │   - ZMQ IPC transport                        │  │
│  └──────────────────────────────────────────────┘  │
│  ┌──────────────────────────────────────────────┐  │
│  │   Plugin Server (server/)                    │  │
│  │   - HTTP API endpoints (FastAPI)             │  │
│  │   - Plugin registry                          │  │
│  │   - Message queue                            │  │
│  └──────────────────────────────────────────────┘  │
└────────────────────┬───────────────────────────────┘
                     │ ZMQ IPC
      ┌──────────────┼──────────────┐
      ▼              ▼              ▼
  Plugin A       Plugin B       Adapter D
  (process)      (process)      (process)
```

## 包类型

| 范式 | 导入来源 | 使用场景 | 运行方式 |
|------|----------|----------|----------|
| **Plugin** | `plugin.sdk.plugin` | 独立功能（搜索、提醒等） | 独立进程 |
| **Adapter** | `plugin.sdk.adapter` | 将外部协议（MCP、NoneBot）桥接到内部插件调用 | 独立进程，带网关管线 |

### 何时使用哪种范式？

- **"我想添加一个新的独立功能"** → 使用 **Plugin**
- **“我想在现有功能周围增加命令”** → 使用普通 **Plugin**；若你维护原宿主且代码很大，可在宿主内使用 `PluginRouter`
- **"我想接受 MCP/NoneBot/外部协议调用并将其路由到插件"** → 使用 **Adapter**

> 从 **Plugin** 开始。迁移原 Extension 时，把 Router 合并进所属 Plugin，或改造成独立 Plugin。

## 开始开发

### 能力告知与启动确认

能力分析完成且未发现敏感能力时，插件可以直接启动，权限页会显示「未发现读取对话、记忆或向本体发送内容的调用」。当插件存在尚未确认的能力时，手动启动（启动按钮、右键菜单、批量启动或权限页启动）会弹出确认对话框，逐项列出待确认的能力；同意后插件才会启动。用户的选择（同意或拒绝）会保存在用户运行数据目录，后续启动、重载和正常升级沿用已有决定。

自动启动、升级重启、切换安装来源重启、卸载回滚重启、热重载和 reload/reloadAll 永远不被确认拦截。唯一的例外是：被用户明确拒绝的插件会被自动启动跳过，直到用户手动启动并同意为止；自动启动开关本身不受影响。

每次打开插件管理页面时，如果存在正在运行且有待确认能力的插件（例如自动启动、绕过确认启动，或升级后出现新能力），页面顶部会显示一条通知，逐行列出插件名称和待确认的能力（曾同意过的插件标记为「升级后新增」），每行提供「同意」和「拒绝」。拒绝会停止该插件并持久化拒绝决定。忽略或关闭通知不做任何处理，下次打开页面会再次出现。

手动启动时如果能力分析尚未完成（排队中、分析中或暂不可用），本次点击会被提示并拦截；30 秒内再次点击同一插件会直接启动且不记录确认。如果在此期间分析完成并发现了待确认能力，则改为弹出确认对话框。分析已完成但失败或仅部分完成且插件未确认时，对话框会显示「分析不完整」警告，同意即可启动。

安装成功后，平台在独立的单工作线程中分析插件自有 Python 源码，识别对话读取、记忆读取和向本体发送内容等 SDK 使用，并在详情页的“权限”标签页展示能力与代码位置。扫描不会导入或执行插件代码。安装和启动无需等待分析完成。已有插件会在服务启动或首次查看权限页时进行后台分析。单个插件重载成功后，如果 Python 源码修订发生变化，会排队重新分析。也可以在权限页手动重新分析。

静态分析展示可能的使用情况，不判断代码分支是否实际执行。通过从插件内部其他模块导入的对象发起调用时，扫描可能漏报。扫描失败不会禁用插件，也不会撤销已保存的决定。确认记录与能力分析报告分别保存；安装替换成功提交后才会通知分析服务，回滚不会发布新版本报告。权限页可以随时「撤回确认」删除已保存的决定，插件会被视为未确认。

先阅读[插件开发入门文档](./plugin-development)，了解插件的目录构成和完整制作流程；然后跟随[快速开始](./quick-start)动手，并在实现功能时查阅[插件能力与 SDK 参考](./sdk-reference)。
