# エージェントシステム

エージェントシステム（画面上の名前は「ネコクロー」、NekoClaw）は、キャラクターが会話の外で用件を片付けるための仕組みです。やるかどうかはメインの対話モデルが決め、ツール呼び出しで伝えます。記録、誰に任せるかの判断、実行、報告は、Agent Server 内の NekoClaw ホストが担当します。ターンが終わるたびに自動で解析する処理はもうありません。以前のターン単位の解析器と、その実行チャネルは削除されました。

以下では二つの用語を使います。**依頼**（コード名 `commission`）はキャラクターが任せた一件の用件、**task agent** は一件の依頼を複数ステップで進める実行セッションです。画面上では task agent を「使い魔」と呼び、コード、ルート、フィールド値では `task_agent` と書きます。

## ランタイム構成

```text
Main Server                                   Agent Server (:48915)
┌───────────────────────────┐                 ┌──────────────────────────────────┐
│ LLMSessionManager         │  HTTP           │ NekoClaw host (nekoclaw/host/)   │
│  tools: dispatch_task     │ ──────────────> │  ├─ task brain                   │
│         query_tasks       │ <── receipt ─── │  │   ledger · decision model     │
│ cross_server.py           │                 │  ├─ task agent manager           │
│ MainServerAgentBridge     │  ZeroMQ         │  ├─ capability gateway           │
│ pending_agent_callbacks   │ ─ turn check ─> │  └─ permissions                  │
│                           │ <── reports ─── │ embedded plugin service (:48916) │
└───────────────────────────┘                 └──────────────────────────────────┘
```

ホストは Agent プロセスごとに一つです。起動時には、プロセスのスイッチの読み方を登録するだけです（`app/agent_server/nekoclaw_mount.py`）。台帳ファイル、agent runtime、ゲートウェイの待ち受けは、最初に必要になった時点で作られます。

## 二つのタスクツール

マスタースイッチと、機能スイッチの少なくとも一つがオンのとき、`main_logic/core/tool_calling.py` がメインの対話モデルに組み込みツールを二つ登録します。どちらも引数は自然文の一文だけで、番号は渡しません。その一文がどの依頼の話かはホストが判断します。定義は `config/prompts/prompts_task_tools.py` にあります。

| ツール | 引数 | 用途 |
|---|---|---|
| `dispatch_task` | `task` | 用件を任せる。追加、変更、中止、質問へのユーザーの回答の伝達にも使う |
| `query_tasks` | `question` | 進行中の用件、ある依頼の進み具合、ある用件ができるかを尋ねる。空なら進行中の用件を一覧する |

ハンドラーは Agent Server の `POST /nekoclaw/dispatch` と `POST /nekoclaw/query` を呼び、リクエスト全体で最大 2.5 秒待ちます。Agent Server に接続できなかったとき、または処理される前に拒否されたとき（4xx）は、ツール結果に「用件は渡せていない」と書かれます。リクエストは送れたが時間内に応答がなかったとき、または Agent Server 自身がエラーを返したとき（5xx）は、「渡せたかどうか分からない」（Agent Server 側では処理が進んでいる可能性があります）と書かれ、もう一度任せるのではなく、少ししてから照会で確かめるよう促します。自発的な話しかけのリクエストには、この二つのツールは付きません。

## ホストの内部

### タスクブレイン（task brain）

- **台帳。** SQLite ファイル `<データルート>/nekoclaw/ledger.db` に、依頼、依頼ごとのイベント、task agent が作業するセッション、送信待ちの報告（outbox）、タスクの好みを保存します。依頼の状態は `queued`、`working`、`waiting_user`、`done`、`blocked`、`failed`、`cancelled` のいずれかで、遷移は一つの関数だけが行います。`done` と `cancelled` は終端なので、遅れて届いた結果が中止を上書きすることはありません。
- **dispatch の第一ラウンド（待つ）。** その一文が中止、回答、追加、進行中の用件の繰り返しのどれかをローカルで判定し、キーワードと BM25 で候補プラグインを探し、task agent を起動できるかを確かめます。その一文が、直近 1 日以内に task agent が完了した依頼、または中止された依頼への追加である場合は、新しい依頼として受け付けます。第二ラウンドはほかの依頼と同じように選び、プラグインが選ばれればプラグインが処理し、task agent に任せるときだけ元の依頼のセッションで続きを行います。失敗した依頼への追加である場合は、その依頼を再開します。レシートは「すでに進行中」「対応できる機能がない」（理由付き）「受理」のいずれかです。モデルは呼びません。例外は、ローカルに候補がなく task agent も起動できない場合の、小型モデルによる粗選別 1 回だけです。1 秒を超えるとレシートは「受け取った」になり、結論は報告として後から届きます。
- **dispatch の第二ラウンド（バックグラウンド）。** 判断モデル（`nekoclaw/host/decision.py`）が、モデル呼び出し 1 回でプラグインエントリを選び、引数を埋めます。全プラグインの説明の合計が 3000 token を超えるときは、先に粗選別を行い、キーワード一致、BM25 上位 10 件、小型モデルの選別結果の和集合に絞ります。プラグインが優先です。エントリ一つで終わる用件は、プラグインサービスの `/runs` プロトコルで直接呼びます。合うエントリがない、または複数ステップが必要な場合に、依頼を task agent へ渡します。モデルは、プラグインでも task agent でもできない、またはそもそも片付ける用件ではない、と答えることもでき、その場合は何も始まりません。存在しないプラグインやエントリを答えたときは聞き直さず、合うエントリがない場合と同じに扱います。このラウンドがレシートを覆したときは、すぐキャラクターに知らせます。
- **query。** モデルは一切呼びません。進み具合は台帳から読み、「できるか」は第一ラウンドのローカル照合を使って答えます。依頼は登録しません。task agent が処理した依頼の行には、これまでに使った token 数も入ります。使用量が記録されていない依頼には入りません（モデルの提供元が使用量を報告しない場合など）。

### task agent

task agent は、組み込みの agent runtime（`nekoclaw/runtime/`）のセッションの中で作業します。agent runtime は必要になったときに起動するサブプロセスで動きます。セッションは、保存されて後から続きを行える一続きの会話で、台帳にはセッションごとに一行あります。プロジェクトに入った依頼は、そのプロジェクトのただ一つのセッションで処理されます。以前の依頼の続きにあたる依頼は、その依頼のセッションで処理されます。それ以外の依頼と、task agent が起動した task agent は、それぞれ自分のセッションを持ちます。一つのセッションが一度に処理する依頼は一件だけです。前の依頼が完了、失敗、中止、または行き詰まりになるまで、次の依頼は `queued` のまま待ちます。前の依頼がユーザーの回答を待っている間も同じです。同時に動くセッションは最大 10 個で、残りの依頼は `queued` のまま待ちます。runtime のセッションは依頼の開始時に開かれ、終了時に閉じられます。やり取りはディスクに残り、同じセッションの次の依頼はそこから続けます。

依頼の内容（任された一文、ユーザーの元の発言、この種の用件についてのユーザーの好み、その依頼のために選ばれたプラグインエントリ、作業するリポジトリが agent 向けに置いているファイルの一覧）は、セッションの中でその依頼を始めるメッセージに書かれます。システムプロンプトには入りません。まだ何も話されていないセッションで始まる依頼には、このメッセージにメインの対話の抜粋も付きます。抜粋では 1 つの発言が 1 行になります（発言の中の改行や連続した空白は 1 つの空白にまとめられます）。依頼の直前にキャラクターとユーザーが交わした発言の原文で、最大 1000 token、指示ではなく背景であることを明記します。それ以外に、task agent がメインの対話の会話履歴を受け取ることはありません。セッションを最初に開いたときのシステムプロンプトとツール定義はセッションディレクトリに保存され（`system.json`）、開くたびにそれを使います。そのため、同じセッションで処理される依頼のリクエストの先頭部分は変わりません。システムプロンプトのうちセッションごとに異なる部分（作業ディレクトリ、返答の言語）は末尾に置かれます。ツールが同じで、ホストからの指示も同じ（同じキャラクター、同じプロジェクトとそのルール）二つのセッションでは、それより前の部分が同じになり、リクエストの先頭で共通する部分が長くなります。その部分をキャッシュから読むかどうかは、モデルの提供元しだいです。組み立て直すのは、会話が要約に圧縮された後だけです。それまでは、なくなったツールは呼び出されると「今は使えない」と答え、後から増えた組み込みツールは提示されません。セッションの会話は、既定では 200,000 token のコンテキストウィンドウに合わせて管理され、170,000 token に達すると要約が始まります。どちらの値もユーザーがモデルごとに設定できます（組み込みの無料モデルは 128,000 です。このモデルは長すぎるリクエストを拒否せず、超えた分を黙って切り捨てるためです）。モデルの提供元が長すぎるリクエストを拒否した場合、そのセッションと以降のセッションは自動的により小さいウィンドウに合わせて管理されます（提供元がウィンドウを示したときはその値、示さなかったときは拒否されたリクエストの長さ）。あわせて、そのモデルのコンテキスト長を自分で設定するよう、ユーザーに一度だけ知らせます。

task agent は agent モデルを使い、自分の task agent をさらに起動することもできます。task agent がユーザーに質問したり権限の承認を求めたりすると、依頼は `waiting_user` になり、キャラクターが `dispatch_task` で回答を伝えるまで待ちます。

モデルへのリクエストごとの使用量（リクエスト数、入力、出力、キャッシュの読み取り、キャッシュへの書き込み）は台帳に記録されます。セッションごとと依頼ごとの両方です。task agent が起動した task agent の使用量は、起動した側の依頼にも加算されます。一件の依頼が使えるのは、既定で 500 万 token までです（各リクエストで送った分と受け取った分の合計で、キャッシュから読んだ分も含みます）。この上限は 1 ステップに 1 回、そのステップのモデルリクエストを送る前に、台帳に記録済みの使用量で確かめます。そこに達していると、組み込みの runtime はその場で止まります（実行中のツールは中断されません。同じステップの中の途中の要約や、長すぎて拒否された後の再試行では確かめ直さないため、上限を少し超えて使うことがあります）。依頼は `waiting_user` になり、権限の確認と同じ形でユーザーに一度尋ねます。質問には、すでに使った量と、許可した場合に追加される量が書かれます。許可されるとさらに 500 万 token が与えられ、使い切るとまた尋ねます。断られると、task agent は 4 ステップ以内で（1 ステップにつきモデルへのリクエストは 1 回。途中の要約や、長すぎて拒否された後の再試行は数えません）手元の結果を引き渡して残りを説明するよう伝えられ、依頼は行き詰まりとして記録されます。task agent が実際には完了していると報告した場合は、完了として記録されます。dsh は自分でリクエストを送るため、このように止まる場所がありません。使用量は記録しますが、上限は適用しません。

セッションは分岐できます。あるセッションのやり取りを新しいセッションにコピーします（やり取りが完結している最後の位置まで。ツール呼び出しとその結果は対になります）。新しいセッションは元のセッションのシステムプロンプトとツール定義を引き継ぐので、リクエストの先頭部分は元のセッションと一字一句同じです。コピーされる側のセッションは作業中でもかまわず、影響を受けません。分岐したセッションは元のセッションと作業ディレクトリを共有するため、ファイルを書き込むツール、コマンドを実行するツール、機能を呼び出すツールは与えられず、ゲートウェイもその呼び出しを実行しません。読むことと答えることだけができます。セッションをコピーしている間や、そのコピーの中で依頼が処理されている間は、元のセッションのやり取りは削除されません。分岐できるのは組み込みの runtime のセッションだけです。セッション同士で一言尋ねるときは、このようなコピーが答えます（後述）。

ホストは、長い間使われていないプロジェクトのセッションの会話を要約に圧縮することもできます。次の依頼が持ち運ぶ古い会話を減らすためです。これはホスト自身が追加で送るモデルリクエストで、既定ではオフです（`TASK_AGENT_IDLE_COMPACT_ENABLED`）。オンにしても、NekoClaw がオフのとき、一日の利用枠を使い切ったとき、ユーザーが「すべて停止」を押した後（そのセッションで新しい用件が始まるまで）には行いません。圧縮の途中でそのセッションに新しい依頼が来た場合は、圧縮を打ち切ります。その依頼は、ホストが開いていたセッションを runtime が閉じるのを最大 30 秒待ちます。runtime が閉じたと知らせてこない場合、依頼はその理由を記して失敗で終わり、もう一度出し直せます。完全な要約が得られなかった場合（リクエストの失敗、長さの上限での打ち切り、モデルが要約を書かずにツールを呼んだ場合）は、会話をそのまま残します。

### セッション間のメッセージと再開

task agent はほかのセッションを探し、そのセッションが残したものを読み、メッセージを送り、一言尋ね、あとで自分を起こすようホストに頼めます。runtime の 5 つのツールがこれを担い、いずれもホストが実行します。`list_sessions` はセッションの名前、プロジェクト、直近の依頼のタイトルを語で探し（モデルは呼びません）、1 ページ 10 行で返します。探す範囲は、メッセージを受け取れるセッションのうち最近使われた 300 件です（それより古いセッションは見つかりません。正確な名前か完全なセッション ID がわかっていれば、`read_session` や `message_session` に直接渡せます）。`read_session` はセッションの直近の依頼の結果とふりかえり、会話記録の中でその語が出てくる位置、またはある位置からの記録の一区切り（最大 2,000 トークン。記録を丸ごと渡すことはありません。dsh が管理するセッションは結果とふりかえりだけで、会話記録は読めません）を返します。`message_session` はほかのセッションにメッセージを送り、`schedule_wake` は 10 分以上あとに自分をもう一度始めるよう頼みます。`ask_session` はほかのセッションに一言尋ね、そのセッションの会話から作った一時的なコピーが答えます。尋ねられるのは、依頼を処理中で組み込みの runtime が管理するセッションだけです。コピーはファイルを読むだけで何も変更せず、モデルへのリクエストは最大 8 回で、尋ねた側が起動した task agent として扱われます。使用量は尋ねた側の依頼に加算され、尋ねた側が止められると一緒に止まり、答えはメッセージとして尋ねた側に戻ります。その際、向こうの会話をもとにモデルが書いたものだと明記されます。尋ねられたセッション自身には伝わりません。1 つのセッションが尋ねられるのは 1 時間に 6 回までで、メッセージと合わせて数えます。どのキャラクターのセッションも探せて、読めて、メッセージを送れます。各行と各メッセージには、そのセッションがどのキャラクターのものかが書かれます。セッションは名前かセッション ID で指定します。名前が別のセッションの ID の先頭と同じ場合や、2 人のキャラクターが同じ名前のセッションを持つ場合は、ホストが該当するセッションの完全な ID を並べ、どれを指すのかを完全な ID で指定するよう求めます。task agent が起動した task agent は、セッションを探して読むことはできますが、メッセージは自分のチームにしか送れず、ほかのセッションに尋ねることも、タイマーを設定することもできません。

どのターンも、ひとつの依頼に属します。依頼が自分で頼んだ再開（自分で決めた時刻、送ったメッセージの完了通知）が起こすのは、その依頼です。そうした要求がまだ残ったままターンが終わると、依頼は**休みます**。状態は `working` のまま、いつから休んでいるかが台帳に記録され、runtime のセッションは閉じられ、枠とセッションを手放すので、同じプロジェクトのあとの依頼が先に進められます。次の 2 つの場合は休まず、セッションは閉じず、枠も手放しません。そのあいだ、同じプロジェクトのあとの依頼は待つことになります。ひとつは、その依頼が起動した task agent がまだ作業中の場合（結果が戻ると次のターンが始まります）。もうひとつは、セッションのバックグラウンドコマンドがまだ動いていて、その終了が次のターンを始める場合です（セッションを閉じるとコマンドも終わるためです）。どちらの場合も、時刻が来た要求は開いたままのそのセッションに渡され、依頼が待ち行列に入り直すことはありません。休んでいる依頼は、時刻が来ると待ち行列に入り直し、それまでの会話の続きから進めます。完了・ブロック・失敗の報告や中止があると、残っていた要求は取り消されます。休んでいる依頼は、ホストが再起動しても失敗にはなりません。待っているものは台帳にあり、ホストで最初に仕事をする呼び出しが引き継ぎます（起動時には何もしません）。セッション宛てのメッセージは、そのセッションがそのとき進めている依頼に渡されます。実行中なら次のモデル要求の前に差し込み、休んでいれば起こし、ユーザーの返事を待っているあいだは渡さずに取っておきます。進行中の依頼がなければ、そのメッセージのための依頼をそのセッションに新しく立てます（セッションの直前の依頼の続きとして扱われ、枠を使い、割り当てを消費し、必要なときはユーザーに確認し、そのセッションのキャラクターに報告します。task agent が指定しないかぎり、報告は彼女の次のターンに添えられます）。

メッセージと再開の要求は台帳の行（`messages`、`wake_requests`）で、報告と同じく先に書いてから渡します。メッセージは、渡すその時点でホストが枠で包みます。どのセッションが書いたか、ユーザーの言葉ではなくユーザーの許可を何も伴わないことを述べ、その回かぎりのランダムな文字列を持つ 2 本の区切り行のあいだに、各行を字下げした本文を置きます。`read_session` が返す内容と、完了通知を頼んだ送り手に届く知らせ（`notify_when_done`。12 時間たっても終わらなければ、その旨が代わりに届きます）も同じ方法で包みます。ほかのセッションが書いた文が進行中の依頼に渡されるとき、ユーザーがその依頼に「このセッションだけ許可」した内容は取り消され、必要になればあらためて確認します。メッセージは何の許可も伴わず、それをモデル任せにはしません。メッセージは 1 件あたり最大 1,500 トークン、同じ相手には 60 秒に 1 件まで、ひとつのセッションが送れるのは相手が何件であっても合計で 1 時間に 20 件まで、ひとつのセッション宛てに待てるのは 50 件までです。メッセージで立てられた依頼は、自分のメッセージでもう 1 件だけ依頼を立てさせることができ、その依頼はだれにも送れません。セッションが同時に設定できるタイマーは 10 件まで、自分で自分を起こせるのは 1 日 300 回までです。NekoClaw がオフのあいだ、または無料枠を使い切っているあいだは何も起こさず、要求は残ります。「すべて停止」は、まだ渡していないメッセージを取り消し、休んでいる依頼もほかの依頼と一緒に止めます。依頼を順に止めているあいだ、ホストは何も渡しません。そのあいだに書かれたメッセージは停止が終わるときに取り消され、すでに止められた依頼が書こうとしたメッセージは受け付けません。渡すとき、ホストはまず「どの依頼に渡したか」を台帳に記録してから、セッションに伝えます。その文がセッションの会話に入り、会話記録にも書き込まれたと runtime が報告した時点で（dsh では、その文を運んだターンが終わった時点で）、「受け取り済み」と記録します。ほかのセッションが書いた文や、時刻が来たことを知らせるホストの文は、「ユーザー自身の言葉ではない」と印を付けてセッションに送ります。組み込みの runtime では、ユーザー自身の言葉がなければできない操作（目標の設定など）の根拠にはなりません。dsh はこの印をまだ見ていないため、dsh ではこうした文だけを受け取ったターンでも目標を設定・変更できます。伝えられなかったもの、セッションが受け取る前に閉じたものは次の機会のために戻しますが、そのあいだに「すべて停止」があった場合は戻しません。ホストのプロセスが終了した時点でまだ途中だったものは、次の起動後にあらためて渡します。「すべて停止」で取り消したものは、再起動後も渡しません。ホストは終了するとき、まず渡す処理を止めます。渡していないものは台帳に残り、次の起動で続きます。

ほかのセッションの作業ディレクトリのファイルと、そのセッションが保存したツール出力は、ユーザーに確認せずに読めます（作業ディレクトリ外の読み取りを設定で禁止している場合を除きます。その場合は `read_session` も使えません）。会話記録は、別名のリンクをたどっても `read_session` 経由でしか読めず、記録が置かれているディレクトリを内容検索することもできません（ファイル名の一覧は取れ、その中のサブディレクトリはこれまでどおり検索できます）。ほかのセッション自身のディレクトリには書き込めません。自分の作業ディレクトリがたまたまそれを含んでいる場合も同じです。

### task agent 空間

task agent が後の依頼のために残すものは `<データルート>/nekoclaw/task_agent_space/`（`nekoclaw/host/space.py`）にあります。すべてプレーンテキストで、書き込むのはホストだけです。ユーザーごとに 1 つで、すべての task agent が共有します。中身は、ユーザーが書くルール（`AGENTS.md`）、1 行 1 項目の索引（`MEMORY.md`）、そして 1 項目 1 ファイルのエントリ（`memory/*.md`）です。エントリには、再利用できる知見、うまくいかなかった点の振り返り、何がどこにあるかの参照、プロジェクトの進捗があります。全体用に 1 組、プロジェクトごとに 1 組（`projects/<プロジェクト>/`）あり、どのプロジェクトにも属さない依頼は `_daily` に入ります。

- **セッションを最初に開いたとき**、ルールと 2 つの索引が、システムプロンプトのうちホストが渡す部分の末尾に追加されます（環境の説明と返答言語はその部分の後に続きます）。各部の見出しと切り詰めの注記を含めて、合計で最大 2100 token です。開き直したセッションは、会話が要約に圧縮されるまで、最初に開いたときの内容をそのまま使います。空間に何もなければ何も追加されません。エントリの本文は必要になったときに読みます。task agent は空間内のファイルをファイルツールで確認なしに読めますが、書き込むことはできません。空間のディレクトリのパスを含む shell コマンドや、空間内で実行しようとするコマンドは、そのたびにユーザーに確認します。コマンドに対して以前に与えた「常に許可」や「このセッションだけ許可」は適用されません（設定でコマンドが禁止されていれば禁止のままです）。残したい内容は `note_lesson` ツールで提出します。ユーザーからの訂正や承認はここには置かず、タスクの好みとして記録します。
- **提出された内容が有効になるかどうか**はホストが判断し、モデルは使いません。task agent は提出するときに、それをどう知ったか（自分で確かめた、見た、推測した）を必ず示し、根拠になるファイルを添えることもできます（ファイルは必須ではありません）。どう知ったかが示されていない提出は受け付けません。自分で確かめたものはすぐ有効になります。見ただけのものは、依頼の作業ディレクトリか、その依頼が属するプロジェクトの作業ディレクトリに実在するファイルが 1 つ必要です（どちらの外にもあるファイルは、ユーザーが作業ディレクトリの外の読み取りを常に許可にしている間だけ根拠として数えます）。推測したもの、および見ただけでそうしたファイルがないものは、別の依頼が同じ内容（依頼と、そこから起動された task agent は合わせて 1 件と数えます。同じ内容とは、タイトルまたは本文が同じもの。比べる前に大文字小文字、空白、語の両端の句読点をならします。語の中にある記号は残すので、`a.b` と `a. b` は別のものです。日本語や中国語のように語の間を空けない文では文の句読点もならすので、「先に確かめ、後で出す」と「先に確かめ後で出す」は同じものです）を提出するか、task agent が自分で確かめたうえで同じタイトルで「確かめた」として提出し直すか、同じ本文を実在するファイルを添えて「見た」として提出し直すまで待ちます。待っているものは「保留」のエントリです。ほかのエントリと同じく 1 つのファイルで、まだ確認されていないことが冒頭に書かれ、どの索引にも入りません。task agent がそれを目にするのは、このディレクトリを検索したときだけです。保留は層ごとに最大 30 件です。90 日間だれも提出し直さなかったものは、空間の整理がそのファイルまで回ってきたときにファイルごと削除されます（整理は依頼が終わった後に行われ、1 回に見るエントリのファイルは最大 500 件です。依頼がない間や、ファイルがそれより多いときは、それより長く残ることがあります）。削除されたものやあふれたものは、後でまた提出できます。エントリの根拠となるファイルがすべてなくなったと確認されると、そのエントリは期限切れになります（ファイルは残り、索引の行だけが外れます）。その時点で確かめられないファイル（作業ディレクトリの外にあり、ユーザーが外の読み取りを常に許可にしていないもの、または応答しないディスク上のもの）は、あるともないとも扱わず、それだけでは期限切れになりません。ユーザーがコンソールから削除したエントリは記録が残り、同じ内容は再び受け付けません（記録は層ごとに別々で、あるプロジェクトで削除した内容でも、別のプロジェクトや全プロジェクト共通の層では受け付けられます。ファイルを直接削除した場合は記録が残りません。記録されるのは層ごとに直近 1000 件の削除までです。記録を書き込めなかったときもエントリは削除され、その場合は同じ内容がまた受け付けられることがあります）。振り返りとアーカイブの要約が残すエントリも同じ規則で判断します。ただし全プロジェクト共通のものは、どのファイルを挙げていても推測したものとして扱います。1 つのプロジェクトのファイルでは、どのプロジェクトにも当てはまることは示せないからです。挙げられたファイルは参考として残すだけで、有効にする根拠にも、期限切れにする根拠にもなりません。振り返りに残すのは、後の依頼がファイルからは分からず、知っていればやり方が変わるものです。つまずいた点とその回避策、定石が通じなかったときに通ったやり方、時間を節約できるやり方などです。ファイル、リポジトリ自身の文書や履歴から分かること、その依頼でしたことの繰り返しは残しません。
- **リポジトリの中で作業するとき**、各依頼を始めるメッセージに、もう 1 つ一覧が付きます。そのリポジトリが agent 向けに置いているファイル（`AGENTS.md`、`CLAUDE.md`、`.agent/rules/` など）のパスとサイズだけです。ホストはこれらのファイルを読まず、指示として取り込むこともありません。task agent が作業に関係するものを参考資料として読みます。リポジトリにそうしたファイルがないとき、または探すのに時間がかかりすぎたとき（応答しない共有フォルダなど）は一覧が付かず、依頼はそのまま始まります。（dsh は例外で、作業ディレクトリからリポジトリのルートまでの `AGENTS.md` と `CLAUDE.md` を自分で指示として読み込みます。）
- **依頼がどのプロジェクトに入るか**：キャラクターが dispatch した一文、またはユーザー自身の言葉にプロジェクト名が含まれていれば、そのプロジェクトに入ります。この判断にモデルは使いません。プロジェクトに入った依頼は、そのプロジェクトのセッションで、先に入った依頼の後に処理されます。
- **依頼の終了後**、summary モデルを 1 回呼び出して振り返り（`projects/<プロジェクト>/reviews/<依頼 ID>.md`）を書き、最大 2 件のエントリを残し（中止された依頼も振り返りますが、エントリは残しません）、その依頼が属するプロジェクトを示すこともあります。報告が保存されたあとにバックグラウンドで実行され、依頼 1 件につき最大 1 回です。ツール呼び出しが 3 回未満の依頼、プラグインを直接呼んだ依頼、他の task agent が起動した task agent は振り返りの対象外です。失敗した依頼は、再開されることが多いため、失敗のまま 1 日経ってから振り返ります。
- **整理**は依頼の終了に続いて行われ、最大でも 6 時間に 1 回で、起動時には実行されません。30 日間依頼のなかったプロジェクトは、要約（モデル呼び出し 1 回）とともに `archive/<年>/<プロジェクト>/` へ移され、依頼で再び名前が出たときに戻されます。セッションの会話記録と保存されたツール出力は、そのセッションで処理された依頼が最後に変化してから 30 日後に削除されます。進行中、回答待ち、または行き詰まりの依頼が残っている間は削除されません。作業ディレクトリは削除されません。

セッションディレクトリ（`<データルート>/nekoclaw/task_agents/projects/<プロジェクト>/sessions/<セッション ID>/`。ある依頼のために新しく作られたセッションの ID は、その依頼の ID と同じです）は、意図的に別のツリーに置かれています。作業ディレクトリにはリンクが多く、保存場所を変更してもそのまま残ります。一方、task agent 空間はユーザーの他のデータと一緒に移動します。

### dsh：オプションの agent runtime

dsh（DeepSeek Harness）は、ユーザーが別途ダウンロードできる 2 つ目の agent runtime です（`nekoclaw/dsh/`）。内蔵の runtime は常にあります。dsh を入れていないユーザーには何の変化もありません。dsh のモジュールは読み込まれず、プロセスも起動しません。

- **どちらを使うか**（`nekoclaw/host/runtimes.py`）。セッションの runtime は、そのセッションで最初に依頼に着手したときに決まり、台帳に記録され、その後は変わりません。新しい依頼は、dsh がインストール済みで、ユーザーが「内蔵のみ」を選んでおらず、依頼のモデルが OpenAI 互換 API で呼び出せる場合に dsh で実行されます。それ以外は内蔵 runtime で実行されます。再開された依頼は着手時の runtime に戻ります。セッションの会話記録を読めるのはその runtime だけだからです。task agent が起動した task agent は、起動元と同じ runtime で動きます。
- **dsh が使えないとき**。dsh が起動しない、権限ガードの読み込みが確認できない、またはその依頼のセッションを開けなかった場合、その依頼は内蔵 runtime で実行され、理由が依頼のイベントに記録されます。その後 5 分間、新しい依頼では dsh を試しません。dsh で着手した依頼は、dsh が削除された後は内蔵 runtime で最初からやり直します。dsh プロセスが途中で終了した場合、実行中の依頼は失敗となり、再開できます。
- **接続方法**（`driver.py`、`acp.py`）。dsh は子プロセスで、標準入出力上の ACP（JSON-RPC）で通信します。1 つのプロセスが複数のセッションを受け持ち、必要になったときに起動し、すべてのセッションが 5 分間アイドルになると終了します。ドライバーは ACP の通知を内蔵 runtime と同じイベントに変換するため、ホストの他の部分は両者を区別しません。
- **モデルリクエスト**（`forward.py`、`endpoint.py`）。dsh のモデルリクエストはループバックアドレス上の転送口に送られ、転送口が実際のモデル名とキーに差し替え、各プロバイダーが必要とするパラメーターを補ってから、ユーザーが設定したアドレスへ転送します。キーは dsh に渡しません。各リクエストの使用量は転送口が読み取ります。転送口はランダムなポートで待ち受け、dsh プロセスごとにランダムなトークンを 1 つ発行し、`Origin` ヘッダー付きのリクエストはすべて拒否します。
- **権限**（`profile.py`）。dsh 自身のサンドボックスは無効にします。設定と一緒に渡すガードが、ツール呼び出しのたびに dsh に確認を取らせ、その確認はすべてホストの同じ権限コードで判断します。能力ゲートウェイ経由の呼び出しは、送信前に権限を判断してユーザーに確認し、呼び出しがゲートウェイに届いたときには再確認しません。
- **ホストのツール**（`host_tools.py`）。報告、経験の記録、ウェブ検索とページ取得、子 task agent は 1 つの MCP サービスとして dsh に提供され、定義は内蔵 runtime と同じものを使います。dsh 自身のウェブ検索とページ取得は無効にしているため、ページ取得は内蔵 runtime と同じく公開アドレスにしか届きません。能力ゲートウェイは MCP で dsh に直接接続します。
- **インストール先**（`install.py`）。`<データルート>/nekoclaw/dsh/` にプログラム、dsh 自身の設定、会話記録を置きます。保存場所の移行では移動しません。ダウンロードするバージョンは固定で、ファイルは sha256 とサイズで検証します。

dsh では内蔵 runtime と異なる点がいくつかあります。途中で追加した指示は現在の作業区切りが終わってから届きます。返信は 1 文字ずつではなくまとめて届きます。能力ゲートウェイ経由の 1 回の呼び出しは最長 60 秒です。「質問してその場で回答を待つ」ツールはなく、代わりに回答待ちの報告を使います。また、dsh は会話の要約を自分で行い、それをホストに知らせません。そのため、要約の後にセッションの最初に伝えた内容を伝え直すことはなく、組み込みツールの組を渡し直すこともありません。

### 能力ゲートウェイと権限

task agent は、自前のファイル・コマンド系ツール以外の機能を、能力ゲートウェイ（`nekoclaw/host/gateway.py`）経由で使います。ゲートウェイはループバックアドレス上の MCP サービスで、最初にそれを必要とする task agent が起動した時点で待ち受けを始め、依頼ごとにトークンを一つ発行します。提供するものは次のとおりです。

- 選択の対象になるプラグインエントリ。エントリごとにツール一つで、直接呼び出しと同じ `/runs` のコードを通ります。
- `mcp_adapter` プラグインで設定した MCP サーバーのツール。
- キーボード・マウス操作とブラウザー操作の二組の組み込みツール。次の節で説明します。呼び出せるのは task agent だけです。

task agent のツール一覧に載るゲートウェイのツールは、どの依頼を処理していても、その時点で呼び出せるものがあってもなくても、次の二つだけです。`capability_search` は用途から機能を探し、`capability_call` は名前を指定して呼び出します。セッションが続いている間にインストールされたプラグインや有効にされたブラウザーも、この二つを通して使うので、セッションのツール一覧は変わりません。タスクブレインがある依頼のために選んだエントリ（名前と引数）は、その依頼を始めるメッセージに書かれます。

権限は `<データルート>/nekoclaw/permissions.json` に保存します。カテゴリごとに `first_ask`（初回に確認）、`always_ask`（毎回確認）、`allow`（許可）、`deny`（禁止）のいずれかです。既定では、プラグインエントリと作業ディレクトリ内のファイル操作は許可、作業ディレクトリ外の読み書き、コマンド実行、キーボード・マウス、ブラウザー、各 MCP サーバーは初回に確認します。`deny` にしたプラグインや MCP サーバーは、直接呼び出しでも使われません。キーボード・マウスとブラウザーのツールは、クリック 1 回、キー入力 1 回といった細かい単位です。そのため、ユーザーが「今回だけ」許可した場合、その許可は task agent の現在の実行が終わるまで続きます。

### 組み込みツール：キーボード・マウスとブラウザー

キーボード・マウス操作とブラウザー操作は、NekoClaw の二組の組み込みツールです（`nekoclaw/builtin/`、Agent プロセス内）。task agent は、自前のファイル・コマンド系ツールと同じように、自分のループの中からこれらを一歩ずつ呼び出し、各ステップの結果を見てから次の一手を決めます。どちらの組も独自のループを持たず、呼び出しのたびに別のモデルを呼ぶこともありません。モデルに見せるツール定義は `config/prompts/prompts_nekoclaw_builtin.py` にあります。ゲートウェイはこれらを task agent のツール一覧には載せません。毎回のリクエストに含まれるのは各組につき一行の紹介だけで、そこにその組の最初の一手（ページを開く、スクリーンショットを撮る）の呼び出し方が書かれています。最初の一手は `capability_call` 経由で呼び出され、そのまま実行されます。成功した場合、返ってくる結果の先頭には、その組の使い方とツール定義（一組あたり最大 2000 token）が付きます。以降のツールはすべて `capability_call` から名前を指定して呼び出します。最初の一手から始まらないタスクでは、`capability_search` に `group` を渡してその組だけを読み込みます。組がまだ渡されていない段階での、最初の一手以外の呼び出しは実行されず、その組の説明と定義が返されます。runtime が会話を要約に圧縮した後は、それ以前に渡された組は、その組のツールが次に呼び出されたときに渡し直されます。

- **キーボード・マウス。** ツールは `computer` の一つだけで、`action` 引数で操作を指定します（`screenshot`、`click`、`move`、`drag`、`scroll`、`type`、`key`、`wait`）。スクリーンショットをもとに動きます。座標は画面サイズに関係なく、縦横とも 0 から 999 の整数です。呼び出すたびに、操作後のスクリーンショットが返ります。範囲外の座標は拒否されます。
- **ブラウザー。** `browser_*` という名前のツールが 15 個あります。URL を開く、スナップショットを取る、クリック、ホバー、入力欄への入力、複数項目の一括入力、文字入力、キー入力、スクリーンショット、ページの一覧・切り替え・新規作成・クローズ、文字列の出現待ち、ダイアログの処理です。ページは、アクセシビリティツリーをテキストにしたスナップショットとして読みます。各要素に uid が付き、操作では uid で要素を指定します。最新のスナップショットにない uid は拒否されます。スナップショットは 3000 token で切り詰められ、続きをどこから読むかが末尾に書かれます。開けるのは `http://` と `https://` のアドレスだけです。

使うのは、ユーザーがインストールしているブラウザーです。Chrome、Edge、Brave、Chromium の順に探し、Windows では、システムの既定ブラウザーがこのいずれかであればそれを優先します。操作はブラウザーのデバッグプロトコル（Chrome DevTools Protocol、WebSocket 接続）で行い、ブラウザー自動化ライブラリは使いません。既定では、専用のプロファイルディレクトリ `<データルート>/nekoclaw/browser_profile` で起動します。そこでログインしたサイトはログインしたままになりますが、ユーザーが普段使っているログイン状態は使えません。代わりに、ユーザーが今使っているブラウザーをそのまま操作する設定にもできます。これには Chrome 144 以降が必要で、ユーザー自身が `chrome://inspect/#remote-debugging` でリモートデバッグをオンにし、接続のたびにブラウザー側で許可します。この選択は `<データルート>/nekoclaw/browser.json` に保存されます。ブラウザーが通常と違う場所にインストールされている場合は、このファイルの `executable` にパスを書くか、環境変数 `NEKO_BROWSER_PATH` で指定します。

ブラウザーツールが起動したブラウザーは、タスクの合間には閉じません。タスクが終わったとき、または中止されたときも、ウィンドウと開いているページはそのまま残り、次のタスクは同じブラウザーを使い続けます。アプリケーションがブラウザーを閉じるのは、内容が変わったブラウザー設定を保存したときと、アプリケーションを終了したときだけです。すべてのタスクを中止したとき（`end_all`）、ブラウザーツールのスイッチや Agent のマスタースイッチをオフにしたとき、agent モデルに接続できずスイッチが自動的にオフになったときは、ウィンドウのあるブラウザーは開いたままにするので、ユーザーは中の内容を引き続き読めます。スイッチがオフの間、ブラウザーツールの呼び出しは一切実行しません。ウィンドウなし（`headless`）で起動したブラウザーは、これらの場合もこれまでどおり閉じます。開いたままにしたブラウザーとの接続は維持するため、そのブラウザーからは引き続き本アプリケーション自身のサービスのポートに届きません。ユーザーが今使っているブラウザーを操作している場合、アプリケーションはそのブラウザーを閉じず、接続を切るだけです。

ユーザーがこのウィンドウを自分で閉じた場合、アプリケーションが勝手に開き直すことはありません。次に task agent がブラウザーツールを呼び出すと、タスクは（権限を求めるときと同じく）ユーザーの返答待ちになり、ブラウザーをもう一度開いてよいかを尋ねます。選択肢は「今回だけ許可」と「拒否」です。ブラウザーが閉じられるたびに尋ね、ブラウザーの権限設定には左右されず、返答に時間制限はありません。ブラウザーが異常終了した場合も、閉じられた場合と区別できないため、同じように尋ねます。

アプリケーションにブラウザーは同梱されず、起動時にダウンロードもしません。Playwright はテスト用の依存関係でしかなく、`browser-use` は依存関係に含まれません。使えるブラウザーが見つからない場合、ブラウザー操作は準備完了にならず、理由コード `AGENT_BROWSER_NOT_FOUND` を返します。

`computer` と `browser_take_screenshot` は画像を返すため、画像を扱えるモデルを使う task agent にだけ提供されます。モデルは、まず画像を扱えるものとみなします。画像が含まれていることを理由にプロバイダーがリクエストを拒否した場合に限り、そのリクエストを画像なしで一度だけ送り直し、そのモデルを `<データルート>/nekoclaw/model_capabilities.json` に記録します。task agent のコンテキストには、これらのツールのスクリーンショットを合わせて直近 3 枚だけが残ります。

デスクトップは一つ、ブラウザーも一つです。依頼は、最初の呼び出しからその組を占有し、task agent の実行が終わる、依頼がユーザーの回答待ちになる、依頼が終わる、のいずれかで手放します。依頼と、その依頼が起動した task agent は、一つの占有を共有します。同じ組を使いたい別の依頼は最大 120 秒待ち、それでも空かなければ、どの依頼が占有しているかを知らされます。

依頼が占有を始めたときと手放したとき、Agent プロセスは `builtin_activity` イベントを送り、Main Server がそれを `agent_builtin_activity` WebSocket メッセージとして、接続中のすべてのページへ転送します。ページはそれを `neko-agent-builtin-activity` DOM イベントとして渡すだけで、自分では何も描画しません。`GET /api/agent/builtin/activity` は現在の占有状況を返し、`POST /api/agent/builtin/stop` は占有している依頼を中止します。詳細は [Agent REST API](/ja/api/rest/agent) を参照してください。

## 会話への報告

報告はすべて、まず台帳の outbox に書き、その後 ZeroMQ で Main Server へ送ります。送信に失敗すると 1 秒後に再試行し、以後は間隔を倍にして最長 5 分まで延ばします。前のプロセスが送れなかった報告は、ホストが次に使われたときに送ります。

| outbox の種類 | 意味 | 送信時のイベント |
|---|---|---|
| `task_result` | 依頼がどう終わったか | `task_result` |
| `question` | 依頼がユーザーの回答または承認を待っている | `proactive_message` |
| `correction` | 第二ラウンドまたはターン後チェックで、キャラクターの発言が事実と合わないと分かった | `proactive_message` |
| `receipt` | 1 秒を超えた第一ラウンドの結論 | `proactive_message` |

Main Server は報告を該当する `LLMSessionManager` のキューに入れ、既存の配信方式で届けます。`proactive` はキャラクターを起こして話させ、`passive` は次のターンに添え、`silent` の結果は報告しません。テキストセッションでは即時に配信でき、音声セッションでは注入またはホットスワップの境界まで遅れる場合があります。キャラクターが報告を伝えるターンは、後述のターン後チェックには送られません。

対話セッションは数ターンごとに入れ替わり、タスクの記録を持ち越せません。新しいセッションは毎回 `GET /nekoclaw/brief` を呼び、まだ進行中の用件を受け取ります。依頼の変化はすべて `task_update` イベントとしても送られ、[Task HUD](/architecture/task-hud-system) に表示されます。

## ターン後チェック

ユーザーが始めたターンが終わり、そのターンでキャラクターが「実際に手を動かす」ツールを呼んでいない場合（記憶の想起、知識の検索、`query_tasks` は数えません）、`main_logic/cross_server.py` がユーザーの発言とキャラクターの返答を載せた `turn_check_request` を送ります。`publish_turn_check_reliably()` は `turn_check_ack` を短時間待ち、タイムアウト時に一度だけ再試行します。キャラクターが自分から始めたターン、エージェントのコールバックのターン、画像だけのターンは送りません。

ホストはまず、費用のかからない関門を通します。入力時の意図スコアが分かっていて 0.2 未満、ユーザーの発言がどのプラグインのキーワードにも一致しない、選択対象のプラグインがすべてキーワードを宣言している、の三つがそろえばスキップします。通過したターンは小型モデルを 1 回呼び、次の四つのいずれかに判定します。

| 判定 | その後 |
|---|---|
| 用件はない、または意図して断った | 何もしない |
| 「できない」と言ったが、ローカル照合では手段が見つかる | キャラクターに知らせ、本人が訂正する |
| 引き受けたのに dispatch していない | 代わりに dispatch し、本人に知らせる |
| 「終わった」と言ったが、台帳にその依頼がない | キャラクターに知らせ、本人が訂正する |

チェック自体に実行の権限はありません。依頼が登録されるのは、キャラクターが dispatch したとき、または口頭で引き受けたときだけです。

## トランスポート

制御と照会は HTTP（`127.0.0.1:48915`）で行い、組み込みのプラグインサービスは `127.0.0.1:48916` で待ち受けます。イベントは同期 ZeroMQ socket とバックグラウンドの受信スレッドで扱うため、Windows Proactor イベントループでも動作します。

| 既定アドレス | パターン | 方向 | 用途 |
|---|---|---|---|
| `tcp://127.0.0.1:48961` | PUB / SUB | Main → Agent | セッション・ライフサイクルイベント |
| `tcp://127.0.0.1:48963` | PUSH / PULL | Main → Agent | 信頼性付き `turn_check_request` キュー |
| `tcp://127.0.0.1:48962` | PUSH / PULL | Agent → Main | ACK、状態、タスク更新、報告 |

各ポートは `NEKO_ZMQ_SESSION_PUB_PORT`、`NEKO_ZMQ_ANALYZE_PUSH_PORT`、`NEKO_ZMQ_AGENT_PUSH_PORT` で上書きできます。Agent → Main のイベントに HTTP フォールバックはありません。報告はブリッジが受け取るまで outbox に残り、`task_update` と状態イベントはベストエフォートです。

## 機能状態

権威ある状態は Main Server の `/api/agent/*` プロキシから取得します。フロントエンドは `/api/agent/command` で変更し、`/api/agent/state` で更新します。ローカルのチェックボックス状態を正として扱ってはいけません。

| 状態 | 意味 |
|---|---|
| `analyzer_enabled` / UI `agent_enabled` | マスタースイッチ |
| `computer_use_enabled` | task agent が使うキーボード・マウスのツール |
| `browser_use_enabled` | task agent が使うブラウザーのツール |
| `user_plugin_enabled` | プラグインエントリ。直接呼び出しとゲートウェイ経由の両方に効く |

Manager と Agent Server は構築時にすべてオフです。ただし最初の実ユーザー `greeting_check` の後に、永続化された runtime intent が復元されるため、ページを更新するたびに設定がリセットされるわけではありません。キーボード・マウスとブラウザーは、さらに agent モデルの接続確認（`app/agent_server/model_probe.py`）が通っている必要があります。加えて、キーボード・マウスはこのマシンで入力を送れること、ブラウザーは使えるブラウザーがインストールされていることが条件です。

## 中止・上限・再起動

- 中止では、先に状態を `cancelled` と書き、その後プラグインの Run を取り消す（プラグインサービスの `POST /runs/{run_id}/cancel`）か、task agent のセッションを閉じます。`POST /admin/control` の `end_all` と、マスタースイッチをオフにする操作は、進行中の依頼をすべて中止します。
- デスクトップとブラウザーは、それぞれ同時に一件の依頼だけが占有します（「組み込みツール」の節を参照）。一つの占有の中では、呼び出しを一つずつ順に実行します。依頼を中止すると、実行中の呼び出しが取り消され、占有していたデスクトップやブラウザーが解放されます。すでに送られたクリックやページ移動は取り消せません。
- プラグインは `deferred: true` を返せます。依頼は `/api/agent/tasks/{task_id}/complete` が呼ばれるまで `working` のままで、1 時間たっても呼ばれなければ `failed` になります。
- 再起動後にホストが起動すると、前のプロセスが `queued`、`working`、`waiting_user` のまま残した依頼は `failed` になり、キャラクターの次のターンで報告されます。deferred の依頼は期限まで残り、休んでいる依頼はそのまま残ります（待っているものは台帳に記録されています）。
- Agent プロセスは、HUD 用のタスク一覧に、終了したタスクを 5 分間残します。
