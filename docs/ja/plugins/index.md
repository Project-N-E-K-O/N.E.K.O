# プラグインシステムの概要

N.E.K.O. のプラグインシステムは、**プロセス隔離**と**非同期 IPC** に基づく Python プラグインフレームワークです。package type は、製品機能向けの **Plugin** と外部プロトコルブリッジ向けの **Adapter** の 2 種類です。旧 **Extension** package type は削除され、`PluginRouter` は通常 Plugin 内部でのみ利用できます。

## アーキテクチャ

```
┌────────────────────────────────────────────────────┐
│              Main Process (Host)                   │
│  ┌──────────────────────────────────────────────┐  │
│  │   Plugin Host (core/)                        │  │
│  │   - プラグインライフサイクル管理              │  │
│  │   - バスシステム（メモリ、イベント、メッセージ）│  │
│  │   - ZMQ IPC トランスポート                   │  │
│  └──────────────────────────────────────────────┘  │
│  ┌──────────────────────────────────────────────┐  │
│  │   Plugin Server (server/)                    │  │
│  │   - HTTP API エンドポイント (FastAPI)         │  │
│  │   - プラグインレジストリ                      │  │
│  │   - メッセージキュー                          │  │
│  └──────────────────────────────────────────────┘  │
└────────────────────┬───────────────────────────────┘
                     │ ZMQ IPC
      ┌──────────────┼──────────────┐
      ▼              ▼              ▼
  Plugin A       Plugin B       Adapter D
  (プロセス)     (プロセス)      (プロセス)
```

## パッケージ種別

| パラダイム | インポート元 | ユースケース | 実行方法 |
|----------|------------|----------|-------------|
| **Plugin** | `plugin.sdk.plugin` | 独立した機能（検索、リマインダーなど） | 別プロセス |
| **Adapter** | `plugin.sdk.adapter` | 外部プロトコル（MCP、NoneBot）を内部プラグイン呼び出しにブリッジ | ゲートウェイパイプライン付き別プロセス |

### どれを使うべきか？

- **「新しいスタンドアロン機能を追加したい」** → **Plugin** を使用
- **「既存機能の周辺にコマンドを追加したい」** → 通常の **Plugin** を使う。host を所有しコードが大きい場合は host 内で `PluginRouter` を使う
- **「MCP/NoneBot/外部プロトコルの呼び出しを受け付けてプラグインにルーティングしたい」** → **Adapter** を使用

> **Plugin** から始めてください。旧 Extension は Router を所有する Plugin に統合するか、独立した Plugin に変換します。

## 開発を始める

### 機能の告知と起動確認

機能解析が完了して機微な機能が見つからなかった場合、プラグインはそのまま起動でき、権限タブには会話や記憶の読み取り、本体へのコンテンツ送信を行う呼び出しが見つからなかった旨が表示されます。未確認の機能がある場合、手動起動（起動ボタン、コンテキストメニュー、一括起動、権限タブ）で確認ダイアログが開き、未確認の機能だけが一覧表示されます。同意して初めて起動します。選択（同意または拒否）はユーザーデータディレクトリに保存され、以後の起動、リロード、通常の更新で再利用されます。

自動起動、更新後の再起動、インストール元切り替えによる再起動、アンインストールのロールバック再起動、ホットリロード、reload/reloadAll は確認にブロックされません。唯一の例外は、ユーザーが明示的に拒否したプラグインで、手動で起動して同意するまで自動起動をスキップされます。自動起動スイッチ自体は変わりません。

プラグインマネージャーを開くたびに、未確認の機能を持つ実行中のプラグイン（自動起動、確認回避で起動、または更新で新機能が増えたプラグインなど）があれば通知が表示されます。各行にはプラグイン名と未確認の機能（以前に同意済みなら「アップグレード後に追加」表示）と「同意」「拒否」ボタンがあります。拒否するとプラグインを停止し、拒否を保存します。通知を無視・閉じても何も決定されず、次回の起動時に再び表示されます。

解析が未完了（キュー中・解析中・利用不可）の間に手動起動をクリックすると、警告が表示されブロックされます。同じプラグインを30秒以内にもう一度クリックすると、決定を記録せずに直接起動します。その間に解析が完了して未確認の機能が見つかった場合は、代わりに確認ダイアログが表示されます。解析が完了したが失敗または部分的で、かつ未確認の場合は「解析未完了」の警告付きでダイアログが表示され、同意すれば起動できます。

インストール成功後、プラットフォームは専用の単一ワーカースレッドでプラグイン自身の Python ソースを解析し、会話の読み取り、記憶の読み取り、コンテンツ送信などの SDK 利用を検出して、権限タブに機能とコード位置を表示します。スキャンはプラグインコードをインポートも実行もしません。インストールと起動は解析の完了を待たずに進みます。既存プラグインは、サーバー起動時または権限タブを初めて開いたときにバックグラウンドで解析されます。個別プラグインのリロードが成功し、Python ソースのリビジョンが変わっていれば、再解析が予約されます。権限タブから手動で再解析することもできます。

静的解析は起こり得る利用を示すもので、コードパスが実際に実行されるかは判断しません。プラグイン内の別モジュールからインポートしたオブジェクト経由の呼び出しは、検出できない場合があります。解析の失敗はプラグインを無効化せず、保存済みの決定も取り消しません。決定と解析レポートは別々に保存され、インストールトランザクションがコミットされた後にのみ解析サービスへ通知されるため、ロールバックが新しいレポートを公開することはありません。権限タブではいつでも「確認を取り消す」で保存済みの決定を削除でき、プラグインは未確認に戻ります。

まず[プラグイン開発入門ガイド](./plugin-development)でディレクトリ構成と制作の流れを確認してください。その後、[クイックスタート](./quick-start)に沿って作成し、実装中は[プラグイン機能と SDK リファレンス](./sdk-reference)を参照します。
