# 护栏测试的十三类失效

护栏测试 = 断言「某个不变量在代码里成立」的测试（源码扫描、AST 守卫、结构断言、容量上界）。下面每一类在出事之前都「绿得很好看」，全部是变异验证或评审才暴露的。写完护栏必须做变异验证（见 `mutation-testing.md`）。

## 1. 清单式漏项

写死文件或路径清单的结构测试，只覆盖「当时想到的那些」，漏掉的往往正是出问题的。

- 目标要**自动发现**（遍历源码树加扫描构造点），不要写清单。
- 确实要按清单查时，守卫先**跨模块把清单数出来**再逐个查。只在一个模块的源码里找字面量，会看不见另一个模块里、换了接收者（`self.x(...)` 对 `obj.x(...)`）的那一处。不在本模块的点，改成断言它们的调用方满足不变量。

## 2. 只测谓词，不测调用点

把共享 helper 测得很细，却没有用例真的走调用方。调用点传错参数时全绿。

- 变异要在**调用点**上打一次，不只打被调函数。如果有 autouse fixture 把那个方法桩掉了，测真实实现之前先解除桩。
- ⚠️ 最隐蔽的形态：测试 helper 自己把逻辑重算了一遍。产品代码里是 `head - base`，测试里也写了一个 `f(head) - f(base)`，把产品那一行改反，一条都不红。自查信号：测试里出现和被测代码同构的表达式（同样的减法、比较、拼接）。修法是加走真实入口的用例（例如走脚本的 `main()`，只把 git 那一层桩掉）。
- ⚠️ 判定「死条目、死代码」之前先做**消费者普查**：搜常量名，列出每一处读它的代码和所属的管线，对每个消费者各跑一遍。只跑一个消费者的测试就删条目，另一条管线的行为可能直接反过来。再补一条同时断言两条管线的用例。
- 端到端的豁免、改写类逻辑，护栏要打在最终输出上。只测一个恒等谓词会放走「豁免声明从未生效」。

## 3. 断言弱于主张

用例名声称 A，断言只验证了比 A 弱的 B。

- 断言「顺序」就比行号；「在某个作用域内」就按函数分组；「只发生一次」就撑开临界区。
- 唯一性用 `count == 1`，不用 `in`。`declaration in rendered` 放过「渲染出两条」。
- 多选项的措辞断言完整短语，或逐个独立断言。
- 结构化文本（`file:line:column`）不要用会跨字段匹配的裸子串：`":3" in stderr` 在行号是 4、列号恰好是 3 时也成立。
- 集合用相等不用包含：`assert obj in terms` 放过多出来的错误项。
- 「密钥没泄漏」在「整段内容都被吞掉」时同样成立。补一条反向断言，证明该保留的还在。
- 否定断言（`== []`）要配一条正向对照：同一夹具下不受干扰地跑一遍，那些钩子确实会触发。
- 写完反向验证：把实现改成「刚好满足断言的最小形态」，测试必须红。

## 4. 切片锚点被新代码改指

靠 `source.split(锚点, 1)[1]`、`find(标记)`、「标记之后的第一个 `catch`」取代码块的静态测试，在源码里新增一处同名锚点后会静默改指，往往仍然绿，或者红在与主张无关的地方。

- 锚点选**唯一且有语义**的（那个分支自己的日志字符串，而不是两处共用的条件表达式）。要「某个 catch」就把绑定名传进去区分。
- 改完源码，回头把引用同一锚点的静态测试重新变异验证一遍。

## 5. 重写测试时旧定义被遮蔽

用追加的方式改写测试，没删原定义。Python 里后定义覆盖先定义，pytest 只收集到新的，不报错不警告，旧断言从此不再执行。「用例数只增不减」不代表旧的还在跑。

追加改写之后查一次重名：

```python
import ast, collections, pathlib
tree = ast.parse(pathlib.Path(f).read_text(encoding="utf-8"))
names = [n.name for n in tree.body if isinstance(n, (ast.FunctionDef, ast.AsyncFunctionDef))]
print([k for k, v in collections.Counter(names).items() if v > 1])
```

## 6. 期望值被实现牵着走

把当时实现返回的值直接钉成期望值。后来实现改对了，这条测试反而挡路。写期望值之前先独立地问「按语义这里该是什么」，和实现不一致时先判断谁错。

## 7. 把「不红」当成证据

两个方向，都错：

- **变异不红 ≠ 删了也对。** 删掉一段后测试全绿，只说明那条路径没被测到。要么补用例证明它该存在，要么构造能区分两种实现的输入证明确实没有行为差异。跑探针时把输出全部看完再动手。
- **全量不红 ≠ 这个改动没有代价。** 评估一个候选修法时，先问「它会改变的那个行为，现在有测试吗」。没有就直接量那个行为本身（和 HEAD 做对照，读文件内容而不是只看文件在不在）。测试不红只能说明没破已有断言。别人（包括子代理）给的结论里带「零代价、无风险」时，关键那一步要自己重做。

## 8. 归一化只做了一半

建表时做了归一化（压掉标点和空格），拿去比对的那一侧用的却是原文切片。没有空格的语言一直是对的；有空格的语言里那条分支从未生效，而所有中文用例都绿。

- 凡是「建表时归一化」的地方，确认比对的另一侧做了同样的归一化。
- 跨书写系统的逻辑，每个机制至少各覆盖一个有空格和一个无空格的语种。

## 9. 发现式护栏扫到 0 个文件

用 `rglob("*.py")` 加跳过目录集合过滤时，如果拿**绝对路径**的各段去匹配，而检出目录本身就位于某个被跳过名字的目录下（例如放在 `.claude/` 下面的 worktree），每个文件都被跳过，扫描量为 0，护栏空转。CI 的检出路径不含这些名字，所以 CI 也绿，两边都没有信号。

- 跳过集合一律匹配 `path.relative_to(仓库根).parts`，绝不匹配绝对路径。
- 给发现式护栏加一条下界自检：`assert len(paths) >= N`，把「扫不到文件」变成会红的用例。

## 10. 用例没走到被测的那条分支

- 夹具让流程在更早的分支就返回了。例如被改的清理点只在「活跃」状态下才到达，而测试用的是不活跃的对象，把修复整个撤掉也照样绿。
- 手搓的夹具走了另一条路由，被断言的钩子在这个夹具下根本不可达。同一个文件里往往已经有正确的夹具，docstring 里写着这个坑。
- 夹具里多调了一步，把状态改成「下游会拒收」，于是被测的那道闸门有没有都一样。
- 桩把被测的开关架空了：整个替换掉某个函数并从桩里抛异常，正在验证的那个参数从未被读到。只桩更下层，让真实函数跑。
- `pytest -k 关键词` 根本没选中新用例，跑出「N passed」。先看通过和失败的总数对不对，或者直接用完整用例名。

做法：断言里每提到一个钩子或分支，就问「它在当前夹具下可达吗」。在断言点之前加一条**前提断言**，钉住「被测闸门的下游此刻确实会放行」。变异通过只证明「至少有一条断言活着」，不证明每条都活着。

## 11. 探针或观测点观测不到要等的状态

- 「轮询直到条件成立」的探针，探测手段和被探测的状态必须互斥。拿一个共享占用去探「是不是还有共享占用」，第一轮就返回真，断言恒真。验证方法：让被等待的一方永不释放，用例必须在**用例体内**红，而不是只在收尾的清账 fixture 里红。
- 观测点要数「入口放进来多少」（数 `put_nowait` 的调用），不是「事后还剩多少」（`queue.qsize()`）。后者分不清「没入队」和「入队后被消费掉」。
- 判据被下游逻辑抹平：断言的字段经过窗口、裁剪、归一化之后，两种实现下读数相同。挑一个能穿过所有下游变换的字段。
- 「登记表的语义对」不等于「窗口关上了」。把锁或登记表的每条语义都测全了，也不说明产品代码里它放对了位置。护栏要打在「不变量对用户意味着什么」上：真的并发跑产品代码，比对消费者看到的内容和校验时批准的内容。

## 12. 比常量证明不了载荷装得下

体积、容量类的上界，护栏最容易写成 `assert A_MAX <= B_MAX`。常量互相自洽，真实载荷仍然超限，因为相邻两跳量的往往不是同一个东西。超限的后果常常是静默的（帧被丢、连接被断，收发两端都不报错）。

容量护栏必须**构造真实的最坏情况载荷，用产品代码那一种序列化打包，再量**。三条自查：

1. 这一跳量的是哪个对象？和上一跳是同一个吗（图片、整条事件、落盘记录）？
2. 用的是同一种序列化吗？相邻两跳的字段集也可能不同，信封本身占字节。
3. 有没有不设上限的字段和设了上限的字段共用同一帧？

链路上每一跳各写一条打包实测的护栏。

## 13. AST 源码守卫的覆盖维度和位置判据

源码守卫有三个互相独立的覆盖维度，漏任何一个都是假绿：

1. **汇聚点类型**：只匹配 `print`，就看不见 `logger.info(...)`（它的 AST 是属性调用）、HTTP 请求体、写文件。
2. **标识名单**：只列源头变量名，不列承载同一内容的中间变量，刚修掉的那处泄漏守卫自己就接不住。
3. **扫描面**：只扫一个模块，而同一条链路的注入点、落盘点分散在别的模块。

收紧一维会撞开另一维（为消除误报把匹配收窄，正好把别的形态漏掉）。守卫自己要有正反两组参数化自测：应抓的形态若干、应放行的形态若干。变异要挑「旧版在两个维度上同时漏掉」的形态。

**执行顺序是位置性质，行为测试抓不到。** 例如某道闸门必须排在所有会落盘的步骤之前；把它挪到后面，闸门自己的行为一点没变，所有放行和拦截的用例照样全绿。这类性质只能按 AST 里的出现顺序钉：

- 比行号必须限定在**同一个外层函数**内，并且**不下降进嵌套函数、lambda 的函数体**。嵌套函数体里那句调用的行号是定义位置，不是调用位置。做法：定位外层函数节点，自己写遍历，遇到 `FunctionDef` / `AsyncFunctionDef` / `Lambda` 不下降，只收直接作用域里的调用。
- 外层函数找不到（被改名）要当场断言失败，否则守卫静默失去目标。
- 位置判据不要一刀切成「X 之前不许有 Y」。按「哪一侧、哪一类」分别算，流程中止记录这类必然排在前面的不算违规。
- 「不许直接出现在 async 函数体里」这类守卫，豁免按**形状**写（例如「在 `except` 处理块内」），不要列名字白名单。

## 同一条护栏可以连着几版都是假绿

每改一版护栏都要单独做变异验证，不要因为「上一版验过」就跳过。出现过连续三版：第一版只断言「下一行开始赋值」，把值换掉照过；第二版按窗口找变量名，而那个名字在紧邻的另一条语句里也出现，断言恒真；第三版把窗口收到赋值语句本身才管用。
