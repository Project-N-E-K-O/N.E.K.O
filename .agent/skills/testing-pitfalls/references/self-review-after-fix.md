# 修完之后、说「修好了」之前的自查

评审里被反复抓到的问题，大多不是逻辑写错，而是下面几种形状。它们的共同点是：改动点自己的测试是绿的。

## 改 A 会让 B 的前提失效

每做一处改动，写下「这次改动让哪些原本成立的判断不再成立」，然后搜出所有依赖那个量、那个前提的地方逐个看。例子：把某个时间戳正确地提前之后，「后一轮的开始时间早于前一轮的结束时间」从异常变成了常态，旁边用这个时间戳判归属的代码当场失效。

最可操作的一条：**改一个分支的控制流，就立刻对齐它的兄弟分支。** 只要在某个分支里加了 `return`、加了会话退休、加了清理、加了失败即拒绝（fail-closed），就当场看同一个函数里的其他分支，逐条问「它们在同样的情形下做了什么，我这条是不是漏了一步」。常见的漏法：

- 加了 fail-closed 的 `return`，没人收拾会话状态，比原来的问题更糟，而且是静默的。
- 加了退休，忘了安排重试。
- 让某个操作「不取消调用者」，解决了「不该被取消」，没解决「该退出」，旧 worker 变成僵尸。

知道判据不等于会在新代码里想起它。写新的有界集合、新的淘汰逻辑、新的时间戳之前，回头过一遍这个领域已经定下的判据（例如「并发下落地顺序不等于发生顺序，抽稀要按发生时间」）。

## 修一个方向的缺陷，造出它的镜像

准备把「实时读某个共享量」改成「钉住某个共享量」（或者反过来）之前，先问**这个量会因为几种原因变化**。只要有两种以上、语义不同，两种写法各有一个对称的漏洞：实时读会让并行的兄弟互相作废，钉死会让后续的顺序批次全被拒。

正解通常是把判断需要的上下文**在同一时刻一起快照到对象上**，比较对象自己采样的那一对值，而不是在读取时机上二选一。测试两个方向各写一条，各自做变异验证（换成另一种写法必须红）。

## 「改动前也是这样」要看整条路径

判断一个问题是不是本次改动引入的，问的不是「这一行以前是不是也这样」，而是**「以前从这里出发，还能走到那个必经的收尾吗」**。新增的 `return`、`continue`、早退点都会改变可达性，而差异里看不出来：同一行代码形状没变，但它后面那条兜底路径被新加的早退截断了。

别人拿对照实验（base 绿、PR 的 head 红）推翻你的静态判断时，先复现再辩。

## 关停用的闭锁，必须在重启入口清掉

给关停路径加「一置就不再变」的状态（`_closed`、`_subscribed` 这类标志或事件）时，同一次改动里要做三件事：

1. 搜这个名字，确认存在一个 `= False` 或 `.clear()`，并且它在**重启入口**上（`start()`、`connect()`）。`start()` 里已经清了别的标志，会让人以为重启处理过了。
2. 查对偶实现（实时和离线两个客户端、宿主和子进程）有没有同名同义的标志，一起改。
3. 守卫要断言**整个「停止再启动」的循环**。只断言「停了之后立刻返回」，漏清和没漏清两种实现都能过。

这类缺陷是静默的：闭锁的语义就是「别做了」，重启后什么都不做看起来完全正常，不抛异常也不红。尽力而为的旁路（抄送、上报）尤其如此。

## 修复和护栏本身可能不生效，或者比原问题更危险

「测试全绿」和「逻辑上说得通」都不算数。出现过的形态：

- **修法比原问题危险。** 清掉了一半状态：界面改指到另一个对象，却还显示旧对象的数据，于是原本无害的操作变成对另一个对象的真实擦除。
- **护栏从不生效。** 加的锁依赖「这期间会有一次同步」这个前提，而实际上没有，锁一次都没起作用，还把原来的小问题扩大了。
- **次数上限被启动时的突发用光。** 重试上限按次数算，启动的一百多毫秒内几次同步就把它烧完了，之后功能永久沉默。这类上限用时间窗口。
- **改判据顺带改了语义。** 把提前返回的条件从一个变量换成另一个，两件本来分开的事被混成一件。
- **刚因为性能改掉的形态，在下一个函数里又写了一遍。** 写任何扫描器、扩展器之前问：输入里有 n 个候选起点时，每个起点会不会各扫一遍尾部？会就是平方复杂度。新代码也要配规模护栏，单测全绿看不出来。

每加一条护栏或修复，除了「撤掉它测试能否变红」，再做两件事：

1. **证明它真的会被执行。** 把它依赖的前提（「这时候会有一次同步」「这个分支可达」）单独验一次，不要从代码结构上推断。
2. **对 HEAD 做行为对照。** 不只看目标场景，跑一条完整的健康路径，逐步比对状态序列和请求序列，差异应该为 0。前端用 jsdom 加载真实模板和真实 JS 来跑。

找人或子代理做对抗式验证时，要求它只报复现出来的问题，并且同时攻击「这一轮新加的代码」，不只验证原来的问题是否修好。
