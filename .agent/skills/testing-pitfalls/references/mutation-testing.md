# 变异验证，以及差分和派生测试的盲区

变异验证 = 把被守护的实现故意改坏，确认对应的用例转红，再还原。它是证明一条护栏有捕捉力的唯一手段。变异本身也会骗人，而且会把改坏的源码留在工作区甚至带进提交，下面的规矩都是踩出来的。

## 一次变异的流程

1. **先提交**。在没提交的文件上做变异，是把变异体带进提交、或者还原时冲掉自己改动的前提。
2. **跑基线**：用和变异时完全相同的命令先跑一遍，必须返回 0。基线里对时序敏感、会偶发失败的用例用 `--deselect` 排掉并写明原因。
3. **应用变异**：锚点断言 `count == 1`；替换后断言「变异后的内容 != 原文」；每条变异打印是否已应用。`str.replace` 在锚点不匹配时静默返回原文，脚本照常跑出「全部通过」。
4. **读一遍变异体**，确认它真的复现了修复前的形态。把「解析挪进锁里」写成 `async with lock: pass` 再照原样解析，锁瞬间就放了，守卫当然还是绿；`A or B` 只改掉 A 半边，闸门照样生效。
5. **跑**：一条变异只对一个用例下结论，用完整用例名（`文件::用例名`），只跑抓它的那一个测试文件。一条变异挂两个目标、「有失败就算转红」，运行时用例的红会盖住旁边那条空转的 AST 护栏。例外是「顺序依赖」这种本身成对的主张，必须带上污染源一起跑。
6. **判定**：看到具体的 `FAILED 文件::目标用例` 才算抓到。
7. **还原并校验**：写回后确认和原文逐字节相同，`git status` 确认没有残留。

一轮加了 N 道护栏就变异 N 次，而且每条证人输入必须只能被它那一道救。同一轮新加的另一道检查常常会替它兜住，撤掉这一道依旧全绿。

每轮只验本轮新改的那几处，不要重跑以前验过的整批。

## 判定时的坑

- ⚠️ **返回码非 0 不等于被抓到。** pytest 返回 4 是参数错（最常见：加了 `-p no:randomly`，和 `pytest.ini` 里的 `--randomly-seed` 冲突），返回 5 是没收集到用例，一条都没跑。带 `-x` 和 xdist 时测试失败的返回码是 2 而不是 1（实测观察）。返回码 4、5，以及输出里没有 `failed` 字样的，都算无效。
- **ERROR 不是 FAILED。** 收集期的导入错误、夹具 setup 的 `PermissionError`（临时目录被别的进程占着）都记成 ERROR。只按 `FAILED` 过滤的脚本会把「根本没跑起来」读成「没红」；只看返回码的脚本会把它读成「抓到了」。两种都要和真正的失败分开报。见到 error 先查是不是还原出了问题、导入挂了。
- **不要加 `-x`。** 用例顺序是打乱的，`-x` 停在随机先跑到的那条失败上，看不出指定的那条有没有被打红。
- **靠超时才「抓到」的变异单独看。** 它说明改坏之后测试是卡死而不是失败。有时这也说明真代码在邻近条件下会卡死（例如循环里 `await` 一个已经结束的 future，不让出事件循环）。让测试明确失败而不是卡死：在测试里给被测调用套 `asyncio.wait_for`，或者用会计数、超了就抛断言的替身。

## 变异不红时，按这个顺序查

1. 变异落地了吗（锚点命中数、是否打印了已应用）。
2. 变异体真的改变行为了吗。
3. 选择器选中目标用例了吗（看通过和失败的总数）。
4. 夹具走到被改的那条分支了吗（加前提断言）。
5. 观测点量的是对的东西吗。
6. 是 node harness 的话，它是不是挂住后以 0 退出了。
7. 以上都排除，才是「测试没覆盖」。这时的正确反应是**补测试**，不是把它记成「预期空隙」，更不是得出「这段代码没用」。

⚠️ 在评审线程里说「我证明不了它可达，所以是死代码」之前，把上面几步走完。出过这样的事：夹具里多调了一步让帧在下一道闸门就被丢，于是公开驳回并回退了一条正确的评审意见。

## 还原的坑

- ⚠️ **不要用 `git checkout -- <文件>` 还原**，除非那个文件没有任何未提交的改动。它回到的是已提交状态，会把还没提交的实现一起冲掉。
- **用字节级备份还原**：`cp "$P" "$P.bak"` 之后 `mv "$P.bak" "$P"`，或 Python 的 `read_bytes()` / `write_bytes()`。
  - 不要 `ORIG=$(cat f)` 再 `printf '%s' "$ORIG" > f`：命令替换会吃掉结尾的全部换行。`.editorconfig` 要求文件以换行结尾，但 CI 不检查这一条，留下的是以后每次改这些文件都多一行噪音。
  - 不要用文本模式读写：Windows 上会改行尾，整个文件变成假差异。读的时候 `newline=""`，按文件实际行尾适配要替换的片段，否则锚点命中数是 0。
- **备份文件名用路径编码**（把 `/` 换成 `_`），不要用 basename。仓库里有同名文件（不同目录下的 `preferences.py`），按 basename 备份会互相覆盖，还原时把一个文件写成另一个，之后所有变异都「红」在导入错误上。
- **还原挂在 `trap` 上**，不要写在命令末尾。中间的 pytest 挂死被超时杀掉时，末尾的还原不会执行：

  ```bash
  cp "$P" "$P.bak"; trap 'mv -f "$P.bak" "$P" 2>/dev/null' EXIT INT TERM
  # 应用变异
  timeout 60 uv run pytest <文件>::<用例>
  ```

- Windows 上写回可能因为文件被别的进程短暂占用而失败。写入和写回都加重试。
- 变异体统一带一个标记（例如注释 `MUTANT`），收尾时在源码和测试目录里搜一遍标记和 `*.bak`。

## ⚠️ 变异在跑的时候不要碰这个工作区

变异脚本的循环是「写变异、跑测试、还原」，工作区在整个过程里反复处于被改坏的中间态。

- 不做任何 git 操作。此时 `git add` + commit 拍到的可能正是某一轮的变异体，而且提交上去的那份内容没有被任何一次测试跑过。
- 不改源码。脚本下一次「还原」会用它之前读到的原文把你的改动整个覆盖，表现为「测试在、实现不在」。
- 不跑别的测试和守卫。那段时间的结果都是在被改坏的树上跑出来的，作废。
- 所以变异脚本要么在前台跑完，要么等它结束再动。脚本被杀掉（工具超时、手动停止）时 `finally` 不会执行，之后第一件事是 `git status` 和 `git diff`，确认只剩预期的改动，并逐个确认本轮的修复行还在。
- 把变异交给另一个有写权限的进程做时，给它单独的检出。

## 变异脚本的实现要点

- 跑测试用 `["uv", "run", "pytest", ...]`。用系统解释器起 pytest 时，导入了产品模块的测试在收集阶段就出错，输出里一条 `FAILED` 都没有。
- 不要 `bash -lc "timeout 90 uv run pytest ..."`：login shell 下找不到 `uv`，返回 127，全部被误判成挂起。直接用 `subprocess.Popen`。
- 每条变异设超时。Windows 上超时后用 `taskkill /F /T /PID` 杀整棵进程树；只杀直接子进程的话，pytest 孙进程成了孤儿，一直握着管道让读取永远不返回，还会锁住 `.venv` 里的可执行文件，之后 `uv run` 报拒绝访问。测试输出写临时文件，不走管道。
- 每条结果打印时立刻刷新输出，中途停掉也能留下已经跑完的结果。
- 启动前检查目标文件没有未提交的改动，有就拒跑；退出前断言文件和 `HEAD` 逐字节相同。
- 变异片段写在脚本文件里，不要经 shell 的 heredoc 或 here-string 传，shell 会改写内容（见 `local-env-pitfalls`）。
- 断言失败要直接可见。不要把输出过滤成只剩 `passed|failed`，那样 Python 的 traceback 被滤掉，只看见绿。

## 差分、语料守卫：跑出 0 不是证据

差分守卫（新旧实现对跑一大批输入，断言「差异 0 条」）的语料如果压根不生成某一族输入，那一族无论代码怎么改都报 0。

- 下「0 违规」的结论之前做一次反向验证：把它声称守护的那个修复撤掉，确认数字真的从 0 变成正数。数字没动就是语料盖不到，先补语料。
- 报数字时连带说明语料覆盖了哪些族（例如有没有「词加句尾标点」「应答词加裸应答」这样的组合）。

## 从常量派生的测试：改常量等于改测试

把测试数据从产品常量派生（`itertools.product(模块.常量A, 模块.常量B)`）能解决「加了新值忘了加测试」，但解决不了「删了值」：从常量里删掉一项，派生出来的组合跟着变少，测试全绿。

三层一起上：派生的组合，加上**常量本身的相等断言**（把闭集钉死），再加几条不依赖常量的行为用例。另外：

- 样本要选能压住那个维度的。太短的样本可能撞上别的下限被丢掉，正则自己改选了别的分支，看不出被测的那一条有没有生效。
