# 本地打包脚本与 Windows 签名

正式版的发布流程见 `docs/deployment/manual-desktop-release.md`。这里补的是本地构建和 CI 之间的关系，以及在 Windows 上出包、签名时踩过的坑。

本地的 Nuitka 打包脚本和签名脚本都不入库（里面有机器路径和签名配置）。下面凡是讲本地脚本的地方，说的是「它应该满足什么」，仓库里没有可以对照的文件。

## 本地脚本和 CI 会各走各的

**现状**：CI 的 `build-desktop.yml` 是入库的、每天在跑的那一份；本地脚本是维护者手工维护的另一份。PR 改了 CI 里的打包步骤，本地脚本不会自动跟上。

**出过的事**：本地脚本曾经落后 CI 将近一个月，后来加的几类模型权重完全没打进正式包。权重不入库，冻结版也没有运行时下载路径，结果是相关功能静默降级，没有任何报错。同一时期还发现本地脚本把开发机上的真实角色配置打进了包，以及前端构建失败只打警告、旧产物照样出货。

**做法**：

- 改 `build-desktop.yml` 里的 Nuitka 参数、资源准备步骤、校验步骤时，在 PR 描述里单列一条「本地打包脚本需要同步」，写清楚加了什么。
- 能进 `scripts/check_nuitka_dist.py` 的 `_REQUIRED_ASSETS` 的校验就放进去，它是本地和 CI 共用的唯一一道闸。只写在 workflow 步骤里的校验，本地跑不到。
- 本地脚本应当和 CI 保持的几件事：用现场生成的中性配置种子，不打包开发机的真实配置；前端构建失败、资源准备脚本失败都要中止；Nuitka 版本和 CI 一致；在 `check_nuitka_dist.py` 之后，照 CI 的 `Verify bundled offline assets` 用 `--asset-dir <dist 里的目录> --offline` 把两个 prepare 脚本对着 dist 再跑一遍。

## 有意保留的差异：向量模型只带 int8

CI 用 `--variant both` 准备向量模型，并在 `Verify bundled offline assets` 里硬性要求 fp32 和 int8 都在。本地出的正式包只带 int8：fp32 权重大约 810MB，压进成品会多出约 370MB，而它只服务于极少数 CPU 上的回退路径。

所以 `check_nuitka_dist.py` 只断言 int8 的那几个文件。**不要把 fp32 加进 `_REQUIRED_ASSETS`**，那会让本地正式包过不了共用的闸。

⚠️ 本地从「两个都带」切到「只带 int8」时，要显式删掉上一轮留下的 fp32 文件。`scripts/prepare_embedding_model.py` 会保留已经存在的文件，而 `--include-data-dir=data/embedding_models` 会把目录里的一切原样带进包。

## 编译后失败，不要从头重编

Nuitka 编译要几个小时。编译成功之后的校验、签名、封包任何一步失败，都不需要重编：

- `check_nuitka_dist.py` 是独立脚本，修好问题后直接对现有 dist 再跑一次即可。前提是 `build/nuitka-plugins` 和 dist 是同一轮产出的，它会对两边做逐文件的摘要比对。
- 如果本地有「从校验闸接着往下跑」的续跑脚本，它和主脚本是两份文件，会各自漂移。改主脚本里任何一条 dist 校验时同步改续跑脚本；续跑脚本报错时，先对比两份脚本的校验段，再去怀疑 dist。
- 例外：改了编进二进制的东西（比如 `APP_VERSION`）必须全量重编，见 `frozen-build-bugs.md`。

不要在别人正在跑构建的时候，对同一个输出目录再起一次构建。实测观察：两个 electron-builder 同时写同一个解包目录，一边报找不到 `app.asar`，另一边报目录非空；清掉解包目录和它的临时目录后单独重跑就好。

## Windows 批处理和 PowerShell 的坑

- **`.bat` 必须是 CRLF。** `.gitattributes` 已经把 `*.bat` / `*.cmd` 定成 CRLF，入库的批处理没问题。坑在新写出来还没经过 Git 的文件：多数工具默认写 LF，LF 行尾的批处理在 UTF-8 代码页（`chcp 65001`）下会按错误的字节偏移切命令，报出和实际内容对不上的 `'xxx' is not recognized`。
- **验行尾按字节数，不要用 Git Bash 的 `grep`。** 实测观察：它会做行尾转换，对纯 LF 的文件也报「每行都以回车结尾」。可靠的办法是用二进制方式读文件，分别数回车换行对和换行符的个数。
- **Windows PowerShell 5.1 的 `Start-Process -PassThru`**：实测观察，不先访问一次返回对象的 `Handle` 属性，进程结束后 `ExitCode` 是空的，冒烟会被误判成失败。CI 用的是 PowerShell 7，没有这个问题；把 CI 里的冒烟步骤抄到本地脚本时要注意。
- **给 PowerShell 5.1 跑的脚本保持纯 ASCII。** 无 BOM 的 UTF-8 脚本里的中文路径会被读成乱码；中文路径改用参数传进去。

## Windows 签名

### CI 里的签名

- 定时构建和 `skip_signing` 为 `true` 的手动构建不签名，发布说明里会标 unsigned。nightly 不是稳定渠道，也不是自动更新渠道。
- macOS 后端的 ad-hoc 重签只是为了让 `.app` 的封印有效，不代表正式签名能过。ad-hoc 签名不带标识符要求，所以「非 ASCII 文件名导致正式签名失败」这类问题在 CI 上永远是绿的，要靠 `scripts/check_no_nonascii_asset_names.py` 这个静态检查来挡。

### 本地签名脚本应当遵守的规则

以下都来自实际出包时的教训：

1. ⚠️ **「签名」和「打时间戳」拆成两次调用。** 签名这一步要用硬件令牌里的私钥，只跑一次，失败就停，绝不自动重试；时间戳这一步不需要私钥，可以重试、可以换时间戳服务器。原因：口令错了还循环重试，会把硬件令牌有限的尝试次数耗尽，令牌被锁死。
2. **每次签名后都检查退出码，再用 `signtool verify /pa` 复验。** 曾经有签名调用后面没有失败检查，签名失败后脚本一路走到「全部完成」，差点发出整包未签名的版本。
3. **`signtool.exe` 通常不在 `PATH` 里。** 它在 Windows SDK 的目录下，只有开发者命令提示符里才能直接调到。脚本要自己去找，不要假定裸命令能用。
4. **electron-builder 的日志不能当证据。** 实测观察：它无条件打印 `signing with signtool.exe`；没有配置签名信息时真正的「跳过签名」提示是调试级别的，默认看不到，构建照样成功。要确认签没签上，只看产物本身的签名状态。
5. **先签，再封包。** 把目录打成单文件或安装包之后再去签里面的可执行文件，封进包里的仍然是没签的那份。带自动更新清单的安装包还多一个问题：清单里的校验值是封包时算的，封完再签会让校验值对不上，自动更新失败。要签就在打包流程内部签（electron-builder 的自定义签名钩子，并打开「签名失败即构建失败」的开关）。
6. **刚跑完冒烟的可执行文件可能被安全软件占用。** 实测观察：这时签名会报文件正被另一个进程使用，几分钟后自己恢复。等一会儿从签名步骤接着跑，不要重编。
7. **换签名证书不只是改签名脚本。** 更新端如果按签名者校验新包，新证书要先进它的信任名单，而且旧证书的条目要保留，因为已经装在用户机器上的旧版本还是旧证书签的。先发了新证书签的包再补名单，存量用户的升级会被拒。这一条涉及主仓库之外的组件，在本仓库里核对不了，换证书前要去对应的仓库确认。

## 正式版发布时主仓库这边的约束

- 发布 GitHub Release 之后，`sync-update-release.yml` 只做一件事：检查附件是否齐全。它要求 Windows x64、macOS x64、macOS arm64、Linux x64、Linux x64 AppImage 五组 Portable 全量包、manifest 和 `.sig`。只发了一部分平台时这个检查会红，这是预期行为。
- 稳定版 tag 必须是 `vMAJOR.MINOR.PATCH`，预发布和草稿不触发检查。
- 发版要同时确认的三样：`config/application.py` 的 `APP_VERSION`、`config/changelog/<版本>.md`（以及各语言子目录下的同名文件）、桌面壳那边的版本号。三者不一致时，要么包名和程序里显示的版本对不上，要么升级用户看到的更新日志是空的。
- 打包目录里的所有东西都会进 Portable 包。封包前看一眼目录根下有没有手工放进去的多余文件。
- 实测观察：安装器解包时受 Windows 路径长度上限约束，包内最长路径加上安装目录前缀不能超过上限。往包里加层级很深或名字很长的文件会吃掉余量；发版前用真实的整包做一次解包验证，不要只信小夹具测试。
