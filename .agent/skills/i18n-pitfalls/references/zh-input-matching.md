# 对用户输入做中文关键词 / 正则匹配

仓库里有几处是不经过模型、直接用词表和正则从用户打的字里识别意图的：

- `config/prompts/prompts_directives.py`：「别再提 X」这类禁止话题的正则（由 `memory/user_directives.py` 的 `record_from_text` 在每条用户消息上同步执行）。
- `config/prompts/prompts_emotion.py`：情绪标签别名、情绪关键词、否定词表（消费方 `main_logic/activity/master_emotion.py`、`main_routers/system_router/emotion.py`）。
- `main_routers/card_assist_router.py`：角色卡助手里「整卡重写还是改单个字段」等判断。
- `config/activity_keywords.py`：窗口标题 / 进程名 / 域名的活动分类词表。

这些地方补繁体、补别的语言、修误报时，下面的判据是反复评审后沉淀下来的。各文件里的注释有更细的逐条理由，改之前先读注释。

## 1. 先定「怎么判该不该修」

每条意见先跑一次**基线差分**：同一句输入，分别用 main 上的实现和当前实现判一次，按（基线结果，当前结果）分类：

| 基线 → 当前 | 处理 |
|---|---|
| 不触发 → 触发，且这个动作用户没有请求 | 必修 |
| 不触发 → 触发，但用户确实请求了这个动作 | 不修（只看数字会误判，要读句子） |
| 触发 → 不触发（少触发） | 一般不修；如果收窄正是这次改动的目的，同族的少触发是设计连带 |
| 两边一样 | 不是这次引入的；可以修，但回复里说清楚不是回归 |

还有一类要单独认出来：**繁体在基线上「侥幸是对的」**（词表里没有那个词，从没进过那条分支），补齐词表之后掉进了简体一直在踩的坑。对繁体用户这是新 bug，要修，并且顺手把简体那侧一起修掉。

修法的约束：优先「往闭集词表里加词」或「给已有判据加左界 / 右界」。**新增一套机制只用于必修类。** 经验是加词条、加边界几乎不出事，每次新增机制都会带进新的缺陷、死代码或空断言。

装基线的办法：`git show origin/main:<路径>` 取出旧文件，用 `importlib` 当成另一个模块加载（有相对 import 的模块，模块名要带包前缀，并在执行前先放进 `sys.modules`）。

## 2. 判据怎么设计

- **先想清楚哪一维是能枚举干净的。** 开集不能用黑名单：前缀、否定符号、装饰符号、大小写写法、设备名、地点名都是开集，每次试图枚举都会漏，最后都得改成白名单或「取补集」。结构往往是闭的：比如「X 里的」里，X 是开集，但方位词是封闭词类，枚举方位词而不是枚举「中的 / 裡的」。
- **换成否定式常常一步到位。** 例子：要判断中文否定词前面是不是「句子开头」，正向枚举「前面可以是什么」补了几轮还有漏网的字符；改成「否定词总是起一个小句，左邻只能是串首、空白、分句标点、开括号」之后一次收住。
- **闭集选对了还要看语法分布。** 同一张限定词表里，全称限定词可以后置浮动，副词和普通名词只能紧贴「的」，一视同仁放进同一个匹配窗口会误判。
- **两个判据缺一不可时不要合并成一个。** 例子：整卡重写的信号是「『的』后面有全量限定词」**加上**「限定词管着的是整卡级的名词」（`_WHOLE_CARD_SCOPE_NOUNS`）。字段名不能拉黑，因为用户可以自建任意字段名。
- **代价不对称，往安全侧收。** 整卡重写宁可触发不足；否定守卫宁可多拦；情绪否定「宁可漏掉一个否定，也不要把肯定读反」；禁止话题多留一个字（话题仍完整）好过吃掉一个字（存进去的是非词）。
- **「在某一点做后视」不等于「把整个短语消费完再判边界」。** 短语可以有任意多节，逐点判断永远漏掉最后一节后面的东西。写成「把可重复的节全部吃完，再看后面是不是结尾或标点」。
- **多字词必须排在它的首字 / 前缀前面。** 正则的多选分支按书写顺序匹配，短的在前会把长的截断。
- **修繁体的洞不能拿简体的既有行为去换。** 每加一个守卫先量基线。守卫的条件要写成「这次新放行的那个前缀真的出现了」，不要写成一条影响所有输入的泛化规则。
- **收紧守卫时给「基线上本来算命令」的用法留出口。** 往出口表里加词只会恢复基线行为，是安全方向；收紧才要慎重。
- **要不要给另一处加同样的守卫，看调用关系，不看形状对称。** 后者只在前者命中之后才被调用的话，不用重复挂。
- **同一件事的两个方面各维护一份表，迟早漂开。** 注释写「必须同源」挡不住，只能提成共用常量。新写词表之前先搜隔壁有没有。
- **上一轮已经定了取哪一半的歧义句，不在同一个 PR 里翻回来。** 纯词汇层面没有结构判据的歧义（「X，Y 别提了」哪半是话题），定了就写测试钉住。
- 注释里的方向性结论可能是标反的。读到「这一侧更安全」之类的话，自己跑一次差分再信。

## 3. 子串匹配的固定毛病

子串匹配的词条会出现在更长的词里，或者跨两个词的接缝。形态很固定：

- 两字的框架词（「就是」「要是」「不管」之类）会出现在无数复合词的接缝上，逐词拉黑追不完。换路：真正的框架词**左邻是闭集**（句首、标点、非汉字、少数代词和助词），统一加一个左界。左邻是开集的就改看右边。
- 单字标记如果是常用词的一部分，删掉它，不要给它加黑名单。
- 有词边界的文字用 `\b`。⚠️ `str.isascii()` 不是「有没有词边界」的判据，带重音的拉丁字母和西里尔字母会被分到错的一边。正确的判据是：汉字、假名、谚文才用子串匹配。
- 一词多义（比如同一个词既表示发怒又表示生机）用「假朋友表」整段剥掉。
- 跨接缝的误命中靠「剥掉左边的词」处理，但剥词自己也会造成反向的碰撞。每加一个剥词都要问：它会不会出现在一个真关键词的前面。
- ⚠️ **补否定词是会自我延续的**：每加一批否定词，就造出一批新的假否定。护栏要写成「自动发现式」：从表里取出全部词条，逐条断言「贴在更长的词后面不命中、独立出现时命中」，不要手写举例。

## 4. 补繁体带来的两片东西

- **日文碰撞。** 很多繁体字和日文汉字同码位。裸的繁体词条会误命中日文句子。
  - 不能一刀切「命中区间里有假名就丢」：被禁的话题经常就是日文名字。要几条同时成立才判成日文：含假名、没有中文的正面证据、话题里含日文助词（闭集）。
  - 「中文正面证据」的字表里不能放中日共用的汉字，否则守卫会被短路。
- **既有的简体误报被原样送给繁体用户。** 补繁体之前先看简体那侧有哪些已知误报，一起处理。
- 语气助词表的判据和使用频率无关：一个字既是语气词又是某个词的末字时，无条件剥掉会造出非词。

## 5. 情绪词表（`config/prompts/prompts_emotion.py`）

- **每张表只喂一条管线。** 标签别名、标签否定前缀 / 否定词 / 程度副词（`EMOTION_LABEL_ALIASES_BY_LANG`、`EMOTION_NEGATION_*_BY_LANG`）只给「解析模型输出的情绪标签」用；情绪关键词和启发式否定（`EMOTION_KEYWORDS_BY_LANG`、`HEURISTIC_NEGATION_*_BY_LANG`）只给「从文本直接猜情绪」的启发式用。改表之前先搜常量名，确认它的消费方。
- **两条管线的否定表要成对收词**，否则同一句话两条管线给出相反的答案。已有覆盖两条管线的断言用例。
- 一个否定词进哪张表，看它否定的范围：整句都算的（不、没、no）进宽回看的表；只否定紧跟的谓语的（并不、无法、难以）进「相邻」的表；作用在开放补语上的（西语 / 葡语 / 英语里相当于「没有……」的介词）**一条都不收**。
- 「替整个标签回答」的否定路径必须有作用域守卫；后置的否定（「X 不起来」）只否定紧挨着的那个词。
- 日语的敬体否定是形态问题，只收一个词尾对不上，要把复合形态整条收进去。每加一条词都用「删掉它，对应用例转红」验证它真的起作用。
- 接口如果允许传置信度，会改变判定门槛。只测严格路径是假保证。

## 6. 繁简折叠（不补繁体词条的那一类）

- `config/activity_keywords.py` 的匹配两侧都先过 `fold_script()` 折叠成简体：建表时折一次，三个分类入口各折一次。**所以不要往表里手写繁体词条**（`tests/unit/test_activity_keywords_script_fold.py` 的 `test_needles_are_stored_folded` 会拦）。
- 为什么折叠而不是补词条：几百条别名逐个手写繁体要永远同步维护；折叠一处覆盖全部表，对以后新增的别名自动生效。方向也有讲究：繁到简几乎是函数，简到繁不是（一个简体字对应多个繁体字），生成繁体变体只能靠猜。
- ⚠️ **折叠表是生成出来的闭集**，只收「简体形已经出现在词表里」的字，这样折叠不会把无关文本拉向某个关键词。代价是：新加的中文别名带进了一个表里没见过的字时，折叠表会**静默过期**，那个字所在的繁体标题继续 0 命中。表旁边有一个字符指纹兜着，测试红了就按提示重跑：

  ```bash
  uv run --with opencc-python-reimplemented python scripts/gen_activity_fold_map.py
  ```

- 记忆召回那边另有一张折叠表（`memory/script_fold.py`），覆盖面和用途不同。两张表有意不合并。

## 7. 正则安全和性能

这些正则跑在用户可控的文本上，有的在每条消息上同步执行。

- ⚠️ **「各分支按首字符互斥」不等于「不会回溯」。** 引号 / 书名号的跨度如果在体内把定界符也一起吃了，连续多对定界符会被指数级地重新分段，一条短输入就能占死一个 worker。做法：跨度体内排除自己那对定界符。**测试要同时断言结构和耗时。**
- 括号体要有长度上界（`prompts_directives.py` 用 `_TERM_MAX_LEN`）；话题单位用原子组；按匹配跨度分桶再过滤，避免平方级扫描。
- ⚠️ 用「非汉字」字符类当收尾判断会把空白放进来，加一个空格就能绕过守卫。空白只能跳过，跳过之后仍然要落到真正的收尾集合里。
- 剥配对括号要在剥语气词之前，判据是「剥完之后前缀是否以收尾括号结束」，不是「是否含任意括号字符」。
- ⚠️ 计时断言测不出「把整段前缀又复制了一遍」这类退化（两个规模一起变慢，比值不变）。这种情况改成替换内部函数、断言实参长度。

## 8. 测试怎么写才不空转

- 举例式的用例多次在全绿的情况下放过真缺陷。护栏用闭集常量拆出来的**笛卡尔积**，加上前提守卫和存活数量的下限；并且**另外钉住简体、繁体、混写三种写法**（否则有人缩表，笛卡尔积跟着缩小，照样全绿）。
- 闭集结构的测试用**相等断言**。「下界加必含项」测不出成对删除一组简繁词条。
- 词表提成模块级常量，测试直接 import。从正则源码里抠表的测试，在正则改结构之后会静默换成另一张表。
- 派生测试有两种空转，都是做了变异验证才发现的：载体句选错了分支（参数列了一堆也到不了目标分支）；参数维度选窄了。
- 反向断言打在守卫本身上，不要打端到端。入口要挑对：宽松兜底的入口永远返回对象，断言它等于没断言。
- 变异脚本先断言「文件确实被改了」，替换打错位置时不会报错。变异杀不掉的代码三种可能：覆盖漏了就补用例；代码已经不可达就删代码；已经是等价变异就删这条变异、改成数据性质的断言。
- 改了共享的中间产物（切分结果、跨度表、归一化后的文本）时，列全下游的消费点逐个验证。
