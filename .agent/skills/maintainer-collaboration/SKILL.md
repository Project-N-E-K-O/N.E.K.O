# 和维护者协作的约定

这些是维护者反复纠正过之后定下来的。目的只有一个：维护者拿到的材料能直接用来做决定，不用打回重问。

## 需要拍板时：六段，缺一不可

凡是要维护者做决定的条目，每条都按下面六段写：

1. **现状**：现在的代码或行为事实上是什么样（读过代码得到的事实，不是猜测），以及这件事是怎么来的。
2. **改动选项**：每个选项具体动哪里、动成什么样。包含「不改」这一项。
3. **回归风险**：每个选项改了之后可能坏掉什么，影响面多大。
4. **成本**：每个选项的工作量和带来的复杂度。
5. **收益**：改了之后实际得到什么。今天收益为零就直说「今天收益为零，是为将来兜底」。
6. **推荐理由**：推荐哪个，为什么。

写法要求：

- **假设读的人不熟悉这块代码**。先说这个东西是干什么的、问题是怎么出现的，用通俗的话把来龙去脉讲完整。函数名、行号放在括号里当注脚，不要堆在正文里。
- 一句话提要（「X 没有校验」）不算交付。长篇的根因分析放在选项前面也不行。
- 每条用固定的小标题。选项多时用表格对比风险、成本、收益。
- 追问、补充选项、细化已经定下的方案时，同样按六段写，不要改用散文补答。
- **拍板前先把那条链路的代码读完**再描述选项。选项描述错了，定下来之后还得再问一次。
- 自己已经定掉、但维护者可能想推翻的事，单列一节「已自行处理、可推翻」，一行一条，不混进拍板项。

## 已经拍板的路径，不再摆「撤回」当选项

维护者选定一条路之后，后续在同一个议题上的修复和调整，都在这条路的语义里做。不要把「撤回这个选择、整体回退」包装成新的取舍再让维护者选一次。

如果确实发现这条路有结构性问题、非退不可，就明说「我要质疑这个选择的前提」，并给出证据。

## 动到模型调用的改动：列消耗对比

设计或评审任何会改变模型调用的改动，先列一张「现在 / 改后 / 变化」的表：

- 按场景分行（比如纯聊天的轮、过了门但没有任务的轮、任务轮）。
- 每行写调用次数、输入和输出 token、首句延迟。
- 有增加的项单独拎出来，按六段格式给维护者拍板。**不许用「别处省了」自己抵掉之后不报**。
- 基线尽量用真实数据（运行数据目录下的 `config/token_usage.json` 按调用类型记了用量）。提示词的固定部分可以静态量。
- 没实测过的延迟要明说是估计，并写清打算在哪一步实测。
- PR 描述里带上这张对比表。

主对话以实时语音为主，每轮多几百 token、首句晚一秒，用户都感觉得到。新增的判断、检查、注入，默认都是成本。

## 哪些自己定，哪些要问

自己定，做完在汇报里写一句：

- 修复做完后的提交、推送、回复评审、是否继续处理下一轮评审。
- 自己这一轮引入、修法明确的回归。当场修掉，汇报写「已修」。
- 影响面为零或极小、自己已有明确建议的取舍。

停下来问：

- 架构或产品取舍：两套设计互斥，或者会推翻别人刚合并且写了测试的行为。
- 会改变既有用户行为的改动。
- 自己拿不准的建议。

PR 相关的细则见 `pr-workflow`。

## 汇报只写核对过的事实

- **不编造工具的执行结果**。没拿到工具真实返回之前，不声称成功，不引用它「返回」的 PR 号、链接、提交号、CI 状态。工具被中断、返回的内容格式异常、本该联网的命令却立刻返回，都当作没有取得可信结果，停下来如实说明。
- 某个通道已经被证明不可靠时，不要再用同一个通道的输出去「核实」。换独立的通道；验证不了就说验证不了。
- 写外部状态（推送、改 PR 描述、发评论）之后回读确认，再汇报。
- 测试失败就带着输出说失败；跳过的步骤说跳过了；没在真实应用里跑过的要写明。
- 引用现成的注释或文档来论证之前，先确认它原本说的是哪个场景。同一句话换一个相邻的场景可能整个不成立。发现自己在用「注释里写了 X」支撑结论，而不是用刚验证过的事实，就该停下来验证。

## 用词

- 用朴素的动词描述工程动作。加几条日志就说「加日志」，不说「加 telemetry」；测一下耗时就说「测耗时」。P50、P95 这类真实的统计术语可以用。
- 对外文案（RFC、issue、README、公告）只陈述事实。出于预防的动机，如实写成条件句（「以后如果……」「与其等问题出现再应对，不如趁早……」），不要包装成正在发生的现实。

## 代码上最常被打回的两件事

仓库的代码风格见 `.agent/rules/neko-guide.md`。实践中最常复发的是：

- **同类支持只加了一处**。给某种输入形态、构造方式、编码路径加支持时，先搜出这项能力的所有入口（同名 helper 的全部调用点、同一个概念的读和写两侧、同一份信息的不同输出通道），一次加全。改完自问：这项能力还有第二个入口吗？
- **改了一处语义，没回头查依赖它的地方**。改完之后搜一遍描述这个语义的注释和依赖这个前提的相邻代码。

## 维护者实测确认过的修复，不要凭推理删行

维护者已经实测确认有效的修复，清理时不要因为「某一次诊断快照里这一行没起作用」就删掉它。窗口可见性、层级、连接、缓存这类状态会随时间和事件变化，单次观测不足以证明某个分支永不触发。拿不准就整段保留，加注释说明每一行为什么需要。

## 派子代理之后

- 改代码的子代理：回来之后看实际的差异，不看它的总结。总结写的是它打算做什么。
- 做调查的子代理：关键结论自己抽检一次证据。
- 让有写权限的子代理做对抗式验证时，给它单独的工作区，或者明确禁止它改磁盘。它在共享工作区里做变异的时候，本地测试结果不可信：出现「整批失败、单独跑全过」，先看有没有别的进程在动同一个工作区。
- 多个子代理的结论要合并时，让每条发现带一个 id，核验方原样回显，按 id 合并。按名字字符串匹配会把已确认的结论当成「没有结论」丢掉。
