# cloud-pr-review 模板

`<...>` 是需要填的占位符。PR 上的内容跟随作者的语言，下面以中文为例。

## §F Attribution footer（每条发到 GitHub 的内容最后都要加）

```

---
_Generated by [Claude Code](https://claude.ai/code)_
```

## §L Ledger 标记（每一轮总结里都要有，放在 footer 前面）

```
<!-- cloud-pr-review v1 round=<k> mode=<full|incremental> reviewed_sha=<40位sha> last_full_sha=<40位sha> incr_since_full=<n> -->
```

- 全量 review：`last_full_sha = reviewed_sha`，`incr_since_full=0`。
- 增量 review：`last_full_sha` 保持上一轮的值，`incr_since_full` 加 1。
- 只要读到 ledger 就能算出"最新代码有没有审过"，不用依赖会话记忆。

## §I 行内 comment（🔴 / ❓，每个问题一个 thread）

```
**🔴 必须修改：<一句话标题>**

**问题**：<哪里错了，为什么错>
**触发场景**：<具体的输入、时序或配置 → 会出现什么错误结果>
**建议**：<最小的改法；能写成 suggestion 块就写>

<可选：```suggestion ... ```>

---
_Generated by [Claude Code](https://claude.ai/code)_
```

PR 改动之前就存在的问题：在 **问题** 前加一行 `**这是已有问题**，不是本 PR 引入的。建议在这个 PR 里顺手修，因为<收益大、成本低的理由>。`

❓ 的写法：标题改成 `❓ 需要说明：<问题>`，正文写"我理解的意图是……，如果是这样，那么……；如果不是，请说明……"。

## §A 第一轮（全量）总结

```
## 自动 Review · 第 1 轮（全量 · <short sha>）

<1–2 句话：PR 做了什么，整体评价>

**需要处理（<n>）**
- 🔴 <标题> — <文件:行>（见行内 comment）
- ❓ <标题> — <文件:行>

<details><summary>🟡 可选建议（不阻塞合并，<m> 条）</summary>

- <文件:行> <一句话>
</details>

<若有：未能放在行内的问题，在这里按 §I 的格式写全>

每次推送后我会自动复审。在 thread 里回复或推送修复即可；如果不同意，请直接说明理由。

<!-- cloud-pr-review v1 round=1 mode=full reviewed_sha=... last_full_sha=... incr_since_full=0 -->

---
_Generated by [Claude Code](https://claude.ai/code)_
```

## §B 后续轮次总结

```
## 自动 Review · 第 <k> 轮（<增量|全量> · <LAST short>..<HEAD short>）

选择<增量|全量>的原因：<一行，对应 §3 决策表里的哪一条>

**上一轮问题的处理情况**
- ✅ <标题> — 已确认修复
- ⏳ <标题> — 尚未处理
- ⚔️ <标题> — 讨论中

**本轮新问题（<n>）**
- 🔴 <标题> — <文件:行>

<n=0 且没有 ⏳/⚔️ 时写这一句：本轮没有发现新问题，此前的阻塞问题都已确认修复。>

<!-- cloud-pr-review v1 round=<k> ... -->

---
_Generated by [Claude Code](https://claude.ai/code)_
```

## Thread 回复

- **§R1 确认已修复**：`已确认修复（<short sha>）：<一句话说明怎么验证的>。` → 然后 resolve
- **§R2 被说服了**：`你说得对：<复述作者的关键理由>。我收回这条意见。` → 然后 resolve
- **§R3 有理有据地反驳（只发一次）**：`我理解你的考虑是<复述>。不过在<具体场景>下，<代码位置>会<错误结果>，<证据：复现步骤、测试或调用链>。如果<某个条件>能保证，可以在<位置>加断言或注释说明，那样我也能接受。`
- **§R4 转交维护者**：`这一点我们双方的理由都已经写在上面了，我先不再展开，交由维护者决定。在那之前，这条不影响其它问题的处理。`（不 resolve）
- **§R5 告知维护者的决定**：`维护者的决定：<采用作者方案 / 按建议修改 / 折中方案：……>。理由：<一句话>。` → 采用作者方案时 resolve

## §C 状态汇报（回复用户"现在怎么样了"）

```
**结论**：<阶段：P1 正在审最新推送 / P2 在等作者处理第 k 轮 / P3 已收敛>，下一步：<作者要做什么 / 需要你做什么 / 什么都不用做>。

| 项 | 状态 |
|---|---|
| 轮次 | 第 <k> 轮（<增量|全量>，审到 <short sha>，<时间>） |
| 最新 head | <short sha>（<已审 / 未审>） |
| CI | <通过 / 失败：哪项，和 PR 有没有关系 / 运行中> |
| 能否合并 | <可以 / 有冲突 / 被阻塞> |
| 问题 | 共 <n> 个：✅ <a> · 🤝 <b> · ⏳ <c> · 🔍 <d> · ⚔️ <e> · 🧑‍⚖️ <f> |

**未解决的问题**（P2 才写）
1. ⏳ <大白话一句话说明问题>（🔴，<文件>）— 作者：<没回应 / 说会改 / ……> — <链接>
...

**需要你拍板的事项**：<P3：按 §D 逐项写；P2：只写"有 <f> 项，等收敛后一起给你"；没有就写"没有">

**建议另开 issue**（有 📋 才写）
1. <建议的 issue 标题> — <为什么值得修、为什么不适合放进这个 PR、大概的改法>。要我开吗？

**其它**：<只给用户看的观察、没把握的问题、作者没采纳的可选建议（一句话）>
```

## §D 决策简报（每个待拍板事项写一份）

```
### 待拍板 <i>：<一句话说清分歧，不用术语>

**背景**
<这块代码是做什么的、用户在哪里会碰到它，1–3 句大白话。必须用到的术语在括号里解释。>

**来龙去脉**
- <时间> reviewer 提出：<观点>（<thread 链接>）
- 作者回应：<观点和理由>
- reviewer 再回应：<观点和证据>
- 作者坚持：<理由>
- 结果：双方都没说服对方，因此交给你决定。

**两个方案对比**

| | 现状（作者的做法） | reviewer 提出的改法 |
|---|---|---|
| 具体做什么 | <...> | <...> |
| 成本 | <改动量、要花多久、牵连哪里> | <...> |
| 风险 | <会出什么事 × 可能性 × 后果> | <...> |
| 收益 | <...> | <...> |
| 理由 | <作者的 justification> | <reviewer 的 justification> |

<如果有折中方案 C，也加一列>

**我的建议**：<选哪个>，把握<高/中/低>。
理由：<2–4 句话>。
可撤回性：<这个决定以后能不能改：以后能低成本补上 / 一旦发布就难改（比如数据格式、对外接口）>。

**请回复**：A 维持现状 / B 按 reviewer 的改 / C <折中方案>
```
