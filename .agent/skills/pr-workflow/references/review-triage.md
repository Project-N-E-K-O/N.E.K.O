# 评审意见怎么判

对象：CodeRabbit、Codex、Greptile、code-quality 这类自动评审，以及人类评审。

## 立场

- 自动评审每次推送都会重新审，而且每轮都能再找出一格新的边界。「还有意见」不等于「还要继续改」。
- 维护者要的是质量，不要过度工程，也不要被机器人牵着无限改。主流程实测稳定，比追平机器人列举的每个理论边界重要。
- 判断完直接回线程，不先请示。只有真正的取舍才端给维护者。
- 评审给的修法多半是读代码推出来的，没跑过运行时。动到点击、动画、窗口生命周期这类已经实测过的链路时，提醒维护者复测。

## 逐条两问

1. **有收益吗**：是真缺陷、一致性问题，还是纯理论边界、几乎不可达。
2. **有回归风险吗**：尤其是碰到层级、全局隐藏这类已经实测过的共享功能，或者跨模块。

- 无风险或低风险、有收益（哪怕小）→ 改。
- 有回归风险 → 不盲改。在线程里写明取舍，批量收进后续 issue。

## 先划边界，再逐条判

一个 PR 会被自动评审反复扫时，开始前先按这个 PR 的目的写下边界。之后每条意见先复现、再归类，明确回「收」或「不收 + 理由」。下面是一份用过的模板，按 PR 的目的改：

收（满足任一）：

- **A 目标缺陷**：PR 要修的那类问题还在。
- **B 自己引入的回归**：对 base 实测，base 正常而 head 不正常。
- **C 破坏性副作用**：写坏用户数据、跨语言污染这类高危后果。
- **D 代码和注释或文档不符**：注释声称的保护实际上是死的。
- **E 同族不一致**：修 A/B/C 时造成同类的两批行为不同。只限本次已修项的同族。

不收（回复里写明理由）：

- **F** base 同样不对（head 和 base 行为一致）。这是既有行为，不是回归。
- **G** 结果只是多带了一点内容，方向在已经选定的安全一侧。
- **H** 修它必须枚举一个开集。
- **I** 退化输入，而且后果只是输出偏长之类。

执行规则：

1. 每条必须先量再表态。不复现就回「不复现」。
2. 一轮意见全落在不收区 → 收工。
3. 不主动外推边界。
4. 边界外的只回复、不改。
5. 能合并了主动告诉维护者。

⚠️ 最容易被自己拉伸的是 E：修 A/B/C 时顺手把 base 既有的同类行为也「一起纠正」。那部分属于 F。

C 和 H 冲突时（修掉一个破坏性副作用的唯一办法是枚举开集），按代价量级判，把取舍写进注释和回复，不要闷头修。

## 三类意见的固定处理

- **PR 把既有行为改坏了**（重构或收口时丢了原来的逻辑：兜底、文案、错误码判据）→ 必修。而且应该主动做一次「main 上的旧实现和新实现逐项对照」，不要等评审一轮轮挤出来。
- **新状态机或两个入口之间的时序竞争** → 继续修，哪怕前置条件要叠加几层、后果不重。不能以「这一类已经连报几轮」为由拒绝。修一处冒一处说明状态机还没收敛，这本身就是该继续修的信号。
- **修了反而更危险的** → 不收，线程里写清理由。

轮数本身不是停的理由。这一条优先于下面的收尾判据。

## 复现属实不等于归因属实

机器人报的现象经常是真的，但它给的根因经常是错的。收到缺陷报告先做最小化对照：把报告认定的成因拿掉，看还复现不复现。仍然复现，说明它诊断错了，照它说的改会修错地方。回线程时把对照实验的输出贴出来。

## 静态分析类门禁被反复挑边界时

守卫脚本、lint 这类东西会被无限外推构造。方针：

1. 优先支持仓库里当前实际存在的写法。
2. 动态的、无法静态证明的构造，明确要求改成规范写法或加 `noqa`，不继续推演。
3. 保留简单的判据，明确接受它的盲点。

把这条方针写进被审对象自己（脚本的 docstring、失败输出），而不是只写在线程回复里。这样以后同类意见有一个可以指过去的依据。给出的 `noqa` 出口必须有测试证明它在那些形态上真的有效。

区分两件事：真实的误报（正常写法被挡住）永远优先修，哪怕那种形态在仓库里一次都没出现。「零出现」只是不值得为它加分析的理由，不是可以放着误报的理由。正确的修法往往是往回删，撤掉那块半吊子分析，而不是再加一层。

## 什么时候收尾

出现下面的信号，把当前这一轮做完，在回复和提交说明里明确写出这是最后一轮、后续发现走独立 issue：

- 同一条判据连续几轮被报严重问题，每次修都在动同一块被多轮加固过的核心逻辑。
- 新报的都是罕见形态，不是真实用户会遇到的。
- 一轮里自己扫出来的回归比评审报的还多。
- 最近几轮里有一半在修自己上一轮的修复。
- 为支持某种写法补进来的分析，对应的写法在仓库里一次都没出现。

节奏上：

- 意见攒成一批再分类处理，不要每来一批就起一整轮。
- 不跑全量测试，只跑相关的测试文件，全量交给 CI。
- 评审正在跑的时候，倾向把确认要做的修复攒在本地一起推，每次推送都会打断正在进行的评审。但这条让位于「修完就推」，除非维护者说先别推。
- PR 合并后不再跟它的评论。

## 已经拍板的取舍被再次提出

维护者定过的取舍，评审会换个说法反复提。先查当时为什么这么定（代码注释、相关 skill 文档、PR 讨论），按同样的理由回复，不重新把「撤回这个选择」摆成选项。

几条已经定下、会被反复提的例子：

- 模型地址必须允许 `http://` 加 key。本地和局域网模型的用户很多，「禁止 http」的安全建议不收。
- 桌面壳仓库是闭源的，许可证不随主仓库同步。「跨仓库许可证不一致」的意见不在范围内。`package-lock.json` 里第三方依赖的 `license` 字段任何情况下都不改。

## 回复怎么写

- 人类评审的实质意见逐条回到原线程。
- 机器人的重复条目、它自己已经标记解决的条目，回一句确认或者不回。不必每条都礼貌回复。
- 驳回要写清理由。需要跟踪的记进 issue，回复里给链接。
- 按线程逐条写针对性的回复。不要写「列出所有未回复线程，循环发同一段话」，查询和发送之间机器人可能新开了无关的线程。
- 回复里引用提交号。代码要先到 PR 的 head 上。
