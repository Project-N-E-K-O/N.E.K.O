# 用 gh 查评论、回复、轮询时踩过的坑

下面每一条都是实际漏过评论或发错回复之后记下来的。

## PR 上的意见分三处，一处都不能少

| 位置 | 接口 | 说明 |
|---|---|---|
| 行内评论（线程） | `repos/{owner}/{repo}/pulls/{n}/comments` | 默认按 id 升序，每页最多 100 条 |
| PR 级评论 | `repos/{owner}/{repo}/issues/{n}/comments` | 整篇的架构评审常常发在这里。查未关线程查不到它 |
| review 正文 | `repos/{owner}/{repo}/pulls/{n}/reviews` | 每条 review 的 `body` |

- ⚠️ CodeRabbit 有几类意见不生成线程，只写在 review 正文里：`Outside diff range comments (N)`、`Nitpick comments (N)`，以及意见多的时候的 `Minor comments: N`（这时它只把 Critical 和 Major 级的发成行内线程，正文开头会有一句说明）。「未关线程为 0」不代表处理完了。说可以合并之前，`gh api --paginate` 拉全部 review，在正文里数这三个标题后面的数字，三个标题下的每一条都逐条对照。这类意见没有线程可回，在 PR 上发一条 PR 级评论，逐条写明处理结论。
- 正文为空的 `COMMENTED` review 不等于「自己回复时带出来的记录」。很多自动评审的 review 本体就是空正文，内容全在行内评论里。看到 review 事件却没有配套的行内评论时，当场查未关线程。
- review 正文里的「可选建议」也不在任何线程里。
- 还在 `PENDING` 状态的 review，通过接口只能看到草稿的一部分。提交之后条数可能变多。
- review 超过 100 条时必须 `--paginate`，否则最新的在第 2 页。

## 查未关线程

必须分页，作者不限：

```bash
timeout 90 gh api graphql --paginate -f query='
query($endCursor: String) {
  repository(owner: "<owner>", name: "<repo>") {
    pullRequest(number: <N>) {
      reviewThreads(first: 100, after: $endCursor) {
        totalCount
        pageInfo { hasNextPage endCursor }
        nodes {
          id isResolved
          first: comments(first: 1) { totalCount nodes { databaseId path body } }
          last: comments(last: 1) { nodes { databaseId author { login } } }
        }
      }
    }
  }
}'
```

- `first` 是线程的根评论（回复、去重都按它的 id），`last` 是线程最后一条评论（判断处理过没有时比的是它）。这个查询只给每个线程的首尾两条。回复之前把线程里的全部评论读一遍（把 `comments(first: 1)` 换成 `comments(first: 100)`，或者在 `pulls/{n}/comments` 里按 `in_reply_to_id` 筛）：评审者连发几条时，中间的只看首尾是看不到的。
- ⚠️ 变量名必须叫 `$endCursor`，`gh` 按这个名字注入游标。写成别的名字会无限重拉第一页、不退出、白烧额度，所以外面套 `timeout`。
- `reviewThreads(last: 100)` 或不分页的 `first: 100`，在线程超过 100 个的 PR 上会静默漏掉一批。
- 顺带看 `totalCount`，和上次比有没有变多。
- **判断「已处理」看线程里有没有你自己发的回复，按你记下的回复 id 认，不看作者，也不能只看条数**。维护者用 PR 所用账号开的线程，作者和你发回复的账号是同一个，按作者筛会把它当成「已回复」。评审者也可能在同一个线程里连发两条，条数到了 2 却没有人回复过。你回复之后线程里又出现别人的新评论，这个线程仍算未处理，回应了才能关：比对的是线程最后一条评论是不是你发的那条回复。
- ⚠️ **批量关闭线程只能按本轮读过并回复过的线程 id 白名单**。「评论条数 ≥ 2」只作为额外的保险写进筛选条件（只有一条评论的线程一定没回复过，绝不批量关），不能反过来当成已处理的证据。按「作者」或「未关闭」筛，会把刚到、还没读的线程一起关掉。

## 自动推送评论的通道会漏

不管用的是哪种自动推送（客户端的自动修复、自己写的轮询脚本），都出现过整批漏推：

- 过滤掉了 PR 所用账号自己发的评论，而维护者的评审正是用这个账号发的。
- 机器人的行内评审没推，只推了它的额度通知。
- PR 级评论不推。

所以：每处理完一轮、推送之前，主动查一次未关线程；每次要说「没有新评论」之前，当场查三处。沉默不是证据，推送通道可能已经无声地停了。

## 回复

- 回到原线程：`POST repos/{owner}/{repo}/pulls/{n}/comments/{comment_id}/replies`。
- 不管回复发到线程里的哪一条，新回复的 `in_reply_to_id` 都是**线程根评论**的 id。带重试的回复要按根 id 去重，按别的 id 查永远对不上，会重复发好几条。同一线程只回一次。
- 用 `--paginate --jq '[...] | length'` 计数时，每页各输出一个数。评论超过 100 条会得到多行，要先加总再比较。
- **正文一律走文件**：先写到文件，再 `-F body=@文件`。
  - `-f` 是纯字符串字段，不解析 `@文件`。用了 `-f body=@路径`，发出去的正文就是字面的那一行路径，而且返回 201、不报错。
  - 内联字符串里的反引号在 bash 里是命令替换，被引用的代码会从正文里消失。
- 发完回读一次正文的前几行。发错了就改原评论，不要再发一条。两类评论的修改地址不同：线程里的行内回复用 `PATCH repos/{owner}/{repo}/pulls/comments/{id}`，PR 级评论用 `PATCH repos/{owner}/{repo}/issues/comments/{id}`。拿行内回复的 id 去调后一个会返回 404。
- 定位要回复的评论，按内容或按 id，并且翻页。不要用「最后几条」定位：行内评论按 id 升序分页，评论一多新的在第 2 页，第 1 页的末尾是旧评论。
- `gh api` 偶尔会 TLS 握手超时，回复和关闭线程都套上几次重试（配合上面的去重）。

## `gh --jq` 的坑

`gh` 内置的是 gojq，和命令行的 jq 不完全一样。Windows 的 Git Bash 里常常没有独立的 `jq`，`gh ... | jq ...` 那一行会直接零输出，所以全程用 `gh ... --jq`。

- `--jq` 只接受一个参数，不支持 `--arg` / `--argjson`。要传值就把值拼进表达式字符串。
- 表达式里不要出现反斜杠。`gsub("\\s+"; " ")`、`test("\\[")` 都会报非法转义。压平空白用 `gsub("[[:space:]]+"; " ")`，字面匹配用 `contains("...")`。
- `gsub` 不支持 `"s"` 标志。
- `--paginate` 会对每一页各跑一遍表达式。`max`、`length`、`sort_by`、`add` 这类聚合都是按页算的。求全局值要先逐条输出，再在管道下游处理。
- `issues/{n}/comments` 不认 `sort` / `direction`，加了会被静默忽略。只有 `pulls/{n}/comments` 和仓库级的评论列表认。
- 多行正文的压平和截断要写在 jq 表达式内部。交给下游按行读，一条多行评论会变成很多条事件。
- 用 Tab 做字段分隔再 `IFS=$'\t' read`，连续的空字段会被折叠，后面的字段错位。空字段用 `-` 占位，分隔符用可见字符，正文放最后一个变量。
- ⚠️ `2>/dev/null || true` 会把语法错误、参数不支持、鉴权失败全变成静默的空输出。错误要落到看得见的地方。

## 自己写轮询脚本时

- `since` 是按 `updated_at` 过滤的：机器人一编辑评论，它就重新冒出来。所以按 id 去重。
- 行内评论的 `created_at` 可能早于它真正可见的时刻（它随 review 一起提交）。`since` 游标没有重叠窗口时，这类评论会被永久跳过。做法：`since` 往回留几分钟重叠，靠 id 去重。
- 接口调用失败的那一轮不要推进游标，也不要记为已见。
- 首次运行前先把已经到达的评论处理完，再把它们记成基线；记基线和处理要用同一次拉取的结果。修脚本、重启脚本和首次启动是同一个风险点。
- 不要按作者过滤掉 PR 所用的账号。要滤掉自己的回复，只能记下自己发出去的评论 id，或者按完整的签名后缀区分。
- 多个通道一起轮询时，一条通道坏了、另一条还活着，从输出上看不出来。启动前做正反两向自检：没有新内容时不输出；把基线人为退后一格，必须能报出已知的那几条。
- 自检要作用在真正被执行的那份脚本上。改了一份、跑的是另一份副本，自检永远通过。
- 每轮对三条通道全量分页，在评论上百条的 PR 上很费额度，多个会话叠加会把同一账号每小时的额度用完。行内和 PR 级评论用带重叠的 `since`，review 只拉最后一页并降低频率，轮询间隔不低于 90 秒。
- Windows 上停掉后台任务不一定会杀掉 bash 脚本，它会变成孤儿继续轮询。脚本里自带截止时间和单实例检查（pid 文件）；重启前按命令行核对旧进程。
- 轮询只推评论和 CI，不推可合并状态。冲突要自己查。

## 写完外部状态要回读

改 PR 描述、issue 正文之后，不能只看命令的退出码：

- 回读正文，确认章节标题都在、长度对得上。
- 改描述时在线上正文的基础上整篇重写，不要对读回来的内容做字符串替换打补丁。
- 中转文件放在当前会话独有的临时目录里，用短名字放在共享的 `/tmp` 下容易和别的会话撞。
