# 活动猜测（activity_guess）的空转开销

## 它是什么

活动追踪器的心跳（`main_logic/activity/tracker.py::_activity_guess_loop`）每隔一小段时间跑一次。心跳里有两类工作：

- **规则类**，不花模型调用：更新状态机、累计休息提醒的计时、把「进入游戏/工作」的情境提示推给前端、驱动话题候选。
- **`activity_guess`**：用情绪档位的小模型把「用户现在在做什么」叙述成一句话和几项分数（`llm_enrichment.py::call_activity_guess`）。它唯一的消费方是主动搭话 Phase 2 的活动状态段。

## ⚠️ 症状：空闲时有规律的模型请求，却没有任何业务日志

`activity_guess` 调用成功时不打日志，只有失败才打（`_report_failure`，按原因节流）。所以日志里只能看到 HTTP 客户端一行行的请求记录，看不到是谁发的。调用类型（`set_call_type`）只进用量统计，不进 HTTP 请求头，从 HTTP 日志反查不到调用者。

看到这种现象，先怀疑 `activity_guess`，再怀疑别的。

## 根因：去重键被「来回切窗口」击穿

最早的门是「活动签名变了就重新叙述，最短间隔一个固定地板」。签名里带具体的应用，用户在两个窗口之间来回切，签名每次都变，于是每过一个地板时间就放行一次，无限持续，叙述的还是那两件事。

## 现在的门：`ActivityGuessGate`

`main_logic/activity/activity_guess_gate.py`，纯决策逻辑，不碰时钟和 I/O，模块开头的说明很完整。要点：

- **签名粗化**成（状态，窗口类别）。同类应用之间切换不算变化。
- **每个签名各自指数退避**：同一个签名、同一段对话下重复叙述，间隔按 `ACTIVITY_GUESS_BACKOFF_MULTIPLIER` 增长，封顶 `ACTIVITY_GUESS_BACKOFF_CAP_SECONDS`。封顶值和「离开」状态的判定时间（`AWAY_IDLE_SECONDS`）对齐。
- **新活动、或对话有了新一轮，立刻重新叙述**，不受退避影响。这个判断排在退避间隔之前，否则退避会拖慢对新活动的反应。
- **全局硬地板** `ACTIVITY_GUESS_BACKOFF_BASE_SECONDS`：放行前要求距离上一次**记入**的调用不小于它。记入的时间是调用开始前取的那个时间戳，不是调用完成的时间；只有调用成功、结果也被采用时才记入（`record_fired`）。模型调用失败、或者调用期间对话有了新一轮导致结果被丢弃，都不记入，所以这两种情况下会按心跳的频率重试。精确语义以 `should_fire` / `record_fired` 和 `tracker.py` 里调用它们的那段为准。
- **叙述按签名缓存**。退避期间消费方读到的是「当前这个活动」的上一次叙述，不是最后一次调用的结果。叙述只描述「在做什么」，活动没变时旧叙述仍然准确，所以封顶可以设得很大。
- 只有调用成功才推进退避和缓存。

改参数时：

- 倍数必须大于 1，构造时会校验并抛错。小于等于 1 等于退化回「每个地板时间烧一次」。
- ⚠️ 倍数在两处用到：算最大连击数、算实际间隔。改实现时两处要用同一个值。

## ⚠️ 封顶是「重述的地板」，不是「停止条件」

只有退避还不够：同一个签名、同一段对话，只要过了封顶时间就会再叙述一次，永远如此。挂一晚上就是每个封顶周期烧一次。

真正让它停下来的是这些提前退出（都在调模型之前）：

| 条件 | 说明 |
|---|---|
| 隐私模式开启 | 这一拍不读窗口和进程，也不调模型；话题候选照常 |
| 状态是 `private` | 前台是敏感应用，不把上下文发给模型 |
| 主动搭话总开关关闭 | 唯一的消费方不存在 |
| 叙述被抑制 | `main_logic/core/notify.py::_should_suppress_activity_narration`：告别后的静默，或者**没有在线的 WebSocket** |
| 状态是 `away` | 没什么可叙述的 |

「没有在线的 WebSocket」这一条是后补的，也是最容易漏的：追踪器的心跳**有意跨会话存活**，会话结束、页面关闭都不会取消它（休息提醒和情境提示这些规则逻辑要继续跑）。原先的抑制只看告别静默，普通断连不触发，于是关掉页面后整夜空烧。`away` 也救不了：它依赖系统空闲信号，拿不到系统信号的环境里永远不会进入 `away`。

抑制只跳过模型调用。规则类的工作、读缓存的 `get_snapshot` 都照常；重连之后缓存还在，按各签名的退避自然恢复。

## 加新的后台模型调用时的检查项

这次踩坑可以推广成三个问题：

1. 它的消费方现在存在吗？没有消费方（断连、功能关闭、静默）时要能停，而不是只降频。
2. 它的去重键会不会被用户的正常操作（切窗口、切标签页）轻易击穿？
3. 它成功时有没有日志？没有的话，至少要让人能从别的地方查到是谁在调。

## 排查时的排除项

- 记忆侧的信号抽取循环也是定时轮询，节奏看起来相似，但它要求「上次检查之后用户发过言」才会跑，一批对话处理完就自己停下，做不出持续的空烧。
- 没有客户端连上过的冷启动空闲期不会有这个调用：心跳是会话建立时才启动的。

## 怎么复现

需要真实会话连上。门什么时候放行，以上面「现在的门」一节和 `activity_guess_gate.py` 的模块说明为准，复现时对着那几条规则构造场景：出现一个还没叙述过的窗口类别、对话有了新一轮、或者模型调用失败，都会再放行；在两个已经叙述过的类别之间来回切换，或者停在一个窗口不动，只会按各自的退避间隔低频重述。要给调用归因，在 `llm_enrichment.py::_invoke_emotion_tier` 这个公共入口临时加一行日志（记得只打标签，不打 prompt 内容）。
