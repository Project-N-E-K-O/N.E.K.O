# 事实：提取、去重、仲裁、纠正、归档

入口代码：`memory/facts.py`（`FactStore`）、`memory/fact_dedup.py`（仲裁队列）、`memory/timeindex.py`（FTS 索引和分词）、`app/memory_server/signal_extraction.py` 和 `post_turn.py`（调度）。链路总览见 `docs/architecture/memory-system.md`。

## 1. 用户参与闸门是设计，不是缺陷

提取链路里有三处「没有用户发言就不做」的闸门：

- `app/memory_server/post_turn.py::_run_post_turn_signals`：`if user_msgs:` 才调 `_signal_check_record_turn` 累加轮数。这个计数是「用户参与了几轮」，不是消息总数。
- `app/memory_server/signal_extraction.py` 的 `_signal_check_one`：窗口里没有用户消息（`if not user_msgs_text:`）就只推进游标、清计数，然后返回。
- `app/memory_server/rows.py::_trim_to_user_msg_bracket`：喂给「看双方发言」那一遍提取的消息，先裁到第一条和最后一条用户消息之间。开头的角色发言是用户没回应过的试探，结尾的是用户没接的独白，都不收。

理由：角色自言自语、用户不搭理，说明用户对这段不感兴趣，不该自动沉淀成事实；只有用户印证过的内容才进记忆。被便宜内容污染记忆的代价，远大于漏掉几条角色自述。

怎么判评审意见：

- 「纯主动搭话 / 只有角色发言的会话走不到提取」「没有用户消息时计数不更新」——这是上面的设计，回复时把这条产品原则讲给对方，不改。
- 确有场景需要在没有用户发言的窗口提取时，另设计触发方式，不要去掉闸门；去掉之前先问维护者。
- 这三处有反向断言守着（`tests/unit/test_ai_aware_stage1_path_b.py` 里带 `Design pin` 的用例），把闸门「修掉」会红。

「看双方发言」那一遍不独立调度，搭在「只看用户发言」那一遍的触发上跑，所以它天然跟着同一个闸门。

## 2. 去重有三层，各管各的

1. **逐字相同**：活跃事实的哈希集合挡掉完全重复。
2. **字面相近（FTS）**：`timeindex.fts_tokens()` 把两侧都切成同一套 token（繁体折成简体、去掉双方称呼、CJK 切 2/3-gram、拉丁转小写），按 `token_overlap`（Dice 系数）打分。这一层**只负责找候选**：重合度 ≥ `FACT_NEAR_DUP_ARBITRATE_OVERLAP`（0.25）的那一对照常写入，再交给仲裁队列。唯一允许当场丢弃新事实的条件是「和命中的那行逐字相同」。
3. **语义相近（向量）**：embedding 后台扫描时把余弦超过 `FACT_DEDUP_COSINE_THRESHOLD` 的同 entity 事实对放进同一个仲裁队列。

仲裁由 `FactDedupResolver.aresolve` 在空闲维护里批量调模型，逐对判 `merge` / `replace` / `keep_both`。

不显然的规则：

- ⚠️ **重合度和语义是反着的。**「养了一只猫」对「养了一只狗」重合 0.87（必须各留一条），「用户是一名程序员」对「用户的职业是程序员」只有 0.29（该合并）。所以任何「把 Dice 或余弦当合并判据」的改动都是错的，0.25 是「值得给模型看」的下限，不是重复线。
- ⚠️ **有损归一不能当等价键。** 每一种都有反例：token 集合丢顺序（「喜欢猫，不喜欢狗」和「喜欢狗，不喜欢猫」集合完全相同）；繁简是多对一（`鍾`、`鐘` 都折成 `钟`）；停用名表同时含双方称呼；标点、大小写、空白都可能带意思（`-10` 和 `10`、`/Foo` 和 `/foo`）。「能不能找到」和「能不能据此丢数据」是两个标准：召回侧可以折，丢弃侧不许折。
- **仲裁队列不依赖向量。** resolver 在 `app/memory_server/runtime.py` 里无条件构造，关掉 embedding 的用户仍有字面相近这一路。新建 `FactStore`（热重载）后要重新 `attach_dedup_resolver`，否则候选被静默丢掉。
- **仲裁按 entity 分桶**，跨 entity 的不比。**已被反思吸收的旧事实不进仲裁**（字面和向量两路都跳过）：把新说法并进去会把它从归档里拉回来，比留着重复更糟。
- 队列文件 `facts_pending_dedup.json` **只存 id**，不存正文：群成员的发言不能在 `facts.json` 之外再有一份明文，而且反规范化的文本会在入队和裁决之间过期。
- **AB-BA 死锁**：入队要拿 resolver 的锁，而 `aresolve` 持着 resolver 的锁去拿事实持久化锁。所以相近配对必须在持久化锁里只收集（`near_dup_pairs_out`），出锁后再投递；投递等锁最多 `FACT_NEAR_DUP_ENQUEUE_TIMEOUT_SECONDS`，超时就丢（尽力而为的旁路）。
- 候选窗口是「先按 BM25 取一窗、再算 Dice」，窗口满了要扩窗重扫，不能因为已经挑到一个候选就停：真正逐字相同的那行可能在窗外。

FTS 索引本身：

- 表是 `facts_fts_v2`，`content` 列存的是 token 串，不是原文。`fact_id` 必须是 `UNINDEXED`，否则 OR 查询里的拉丁 token 会命中每一行的 id 列。
- 回填是否完成看 `facts_fts_meta` 里的标记行，不看「表是不是空的」。
- ⚠️ **会被持久化的分词不许有降级兜底。** `fts_tokens` 在共用分词器 import 失败时直接抛。兜底写出的行正常分词器永远匹配不上，而回填标记还说索引完整。下游函数自己的兜底也要防（`hybrid_recall._tokenize` 内部有一条空白切分兜底，所以 `fts_tokens` 先硬 import 它依赖的模块）。
- 分词抛错的代价是整批事实回滚不写；这是有意的（索引失败必须回滚，否则重试撞去重、报假成功）。
- 去组合符要 NFD → 去 combining → 再 NFC，只到 NFD 会把韩文音节拆成字母。

## 3. 繁简折叠

`memory/script_fold.py` 是一张繁→简单字表，由 `scripts/gen_memory_fold_map.py` 用 OpenCC 在构建时生成，运行时零依赖。召回的 BM25 分词和 FTS 分词共用它，对查询和文档两侧都折。

- 不要把它和 `config/activity_keywords.py` 那张折叠表合并。那张是**闭集**（只收简体形已经出现在别名表里的字，防止把无关窗口标题拽向关键词），这张必须是**开集**（任意用户文字）。合成一张后闭集会让记忆这边静默少折。
- 生成时要把映射压到不动点（OpenCC 有 `薴→苧→苎` 这种链，而 `str.translate` 只走一趟），并且折叠目标要留在 U+4E00–9FFF：`_tokenize` 判 CJK 占比只数这个区，折到扩展区会让整段从「切 n-gram」变成「一个拉丁 token」。
- 只在检索侧折，**写入侧不归一**：事实文本照用户说的语言记。
- 折叠解决不了用词差异（「使用者」和「用户」），那是向量的活。
- `HYBRID_RECALL_BM25_THRESHOLD` 比的是原始 BM25 分，不是 Jaccard，别和重合度的数字混着读。

## 4. 纠正和更新

用户说「其实是珊瑚色」「我现在不喝咖啡了」这类话时：

- 三套提取提示词（`FACT_EXTRACTION_PROMPT`、`FACT_EXTRACTION_BATCH_PROMPT`、`FACT_EXTRACTION_AI_AWARE_PROMPT`，各 8 语）要求把**新状态**提成一条事实，并在事实文本里写明它取代了什么旧说法。假设、第三人的说法、角色的猜测、说的是另一个对象，都不算纠正。
- 旧事实靠第 2 节的配对进仲裁；`FACT_DEDUP_PROMPT` 里有一条：candidate 是较新的记录，文本写明更正 / 取代 / 状态已变、且 existing 正是那个旧说法时选 `replace`。没有这种说明时，肯定 / 否定相反的两条仍按两件事处理（`keep_both`），拿不准也优先 `keep_both`：误合并比冗余更难容忍。

已定的取舍：纠正只靠提示词解决，**不为它加额外的模型核对调用**。评审或贡献者提议加一次核对调用时按此说明。

现状里的缺口（排查「旧说法为什么还在」时先想到）：

- 提取模型没在事实文本里写更正说明时，新旧两条会并存（实测观察，同一模型同一用例里约三分之一的提取没写）。
- 更正说明会稀释字面重合度，新旧两条可能达不到 0.25、配不上对（实测观察：「住在上海」对「搬到杭州了（以前住上海）」只有 0.1 左右）；关掉向量又没有共同词时也配不上。
- 旧事实已被反思吸收后，新说法进不了仲裁，只剩反驳信号那条路。

## 5. 归档、冷存、旧重复

- 已被反思吸收、且创建满 `_ARCHIVE_AGE_DAYS`（7）天的事实，由 `_archive_absorbed` 从 `facts.json` 挪进 `facts_archive.json`。它们仍给召回的 BM25 长尾用，也仍然挡住逐字重复。
- ⚠️ 仲裁队列只认 `facts.json` 里的行。所以**旧的重复事实大多在归档里，平时的去重碰不到**。一次性清理（`memory/legacy_dedup.py`、`app/memory_server/legacy_dedup.py`）不走队列，自己逐对调同一份去重提示词。规则见 `docs/design/long-term-memory-sync-v3.md` 第 8 节。
- 两个文件的提交顺序永远是**先写归档、再写 `facts.json`**。中断时留下两份（靠按 id 去重收敛），反过来就是两边都没有。
- 仲裁输掉的、被撤回的、群组主体按时间归档的事实进冷存（`fact_cold/`），不再被召回、检索、合成读到，见 `storage.md`。
- 活跃区和归档按**主体身份**去重（`_fact_scoped_identity`），不按裸 id：不同主体可能共用同一个事实 id。
- 新提取的事实和退役记录逐对比较有上限，超出的进本机待审队列，规则见同步文档第 9 节。

## 6. 测试这块时

- 改读取路径（比如从 `aload_facts` 换到 `aload_facts_full`）后，所有桩掉旧方法的测试夹具要同步桩新方法，否则会穿透到真实读取，读到开发机上真实的记忆目录。给一个 sidecar 文件做隔离时，读、写、清理三面都要桩，漏一面就会在真实目录里建出空的角色目录。
- 夹具里「忠实复刻」被测分支的桩会让真实分支零覆盖。真实分支要另有直测。
- 索引相关的用例至少留一条走真实 SQLite 的端到端：桩掉索引的用例测不出「写入侧和查询侧对 token 的理解不一致」。写「索引失败就……」的回归用例前先看真实实现会不会抛：`index_fact` 写库那一段自己吞异常，用会抛的假索引测到的是假桩的行为。
- 连续几轮评审都落在同一条补偿链上（「失败了就再补一层」）时，回头撤掉引出这条链的那个决定，别继续叠补偿。
