# 相邻子系统的两道闸：角色释放围栏、工坊内容目录占用

这两块代码不在 `plugin/` 下，但插件会打到它们，改插件框架时也容易顺手碰到。

## 1. 记忆服务的角色释放围栏

改名或删除角色之前，要先让记忆服务放掉这个角色的 SQLite 句柄，否则在 Windows 上文件删不掉、改不了名。代码在 `app/memory_server/runtime.py`（围栏、排空）、`app/memory_server/post_turn.py`（后台任务登记）、`memory/timeindex.py`（引擎释放）。

流程是一条链：给角色加发布保留（hold）→ 新来的写请求返回 409 → 等已经放进来的写请求跑完（排空）→ 取消轮后任务和补跑任务 → 释放引擎。

### 改这段前要知道的规则

**排空的前提是 hold 已经生效。** 没有 hold，新请求不断进来，在途计数不会单调下降，等于永远排不空。只有改名和删除（`main_routers/characters_router/crud.py`）传 `hold_derived_task_admission=True`。云存档下载和工坊取消订阅这两条释放路径**不取 hold**。⚠️ 给它们加排空等于「角色只要还在对话就永远释放不掉」。动之前先确认调用方取不取 hold。

**排空预算必须小于最紧的那个调用方超时。** `_CHARACTER_REQUEST_DRAIN_TIMEOUT_SECONDS` 是 2.0 秒，因为最紧的调用方是工坊取消订阅（`_release_workshop_character_handles` 单次调用 2.5 秒），而它超时之后**照样往下删记忆文件**。预算比它长的话，调用方已经放弃并开始删文件，这边还在排空和释放，正好复现要修的那个句柄问题。有一条跨模块的测试盯着这个大小关系。

**这个预算是整个释放流程共用的截止时间。** 排空、等 settle 锁、等 reload 锁都算在里面（`_acquire_within_deadline`）。锁的等待必须有界，原因是 `/new_dialog` 和后台复盘会拿着同一把按角色的 settle 锁跑完整段提示词组装，而它们故意不在围栏内。无界等待会让这个处理函数在调用方放弃之后还一直跑；所以在期限内拿不到锁，就让这次释放失败。

**后台任务一律不继承准入租约。** 租约的意思是「一个已放行的请求还在跑，释放流程会等它」。`asyncio.create_task` 会复制上下文，脱离请求的后台任务如果带着租约，会活过请求、在引擎释放之后把它重新打开。所以 `_spawn_background_task(coro)` 没有「继承租约」这种参数，别加回来。

**`dispose_engine()` 有两种模式，别混用。** 默认模式用于就地修复，失败也必须清掉簿记，否则一次释放失败就把这个角色永久钉死在同一分支。`retain_on_failure=True` 只给跨代释放用，失败时保留簿记以便重试。释放失败的连接池按**连接串**记，不能事后从数据库路径现推，路径漂移重建后会对不上。

**被围栏时引擎准入抛 `CharacterEngineAdmissionError`，不返回空结果。** 这是有意的：后台循环里有「没查到行就推进游标」的分支，不能把「被围栏」当成「窗口里没数据」。

### 两条结构性守卫

都在 `tests/unit/test_recent_compress_backup.py`。加端点或后台任务时它们会逼你做决定，不要绕过：

- **路由清单**（`test_every_character_scoped_route_is_classified_for_the_fence`）：每个带 `{lanlan_name}` 的路由和方法，要么进围栏，要么写进「故意不进围栏」的清单并注明理由。
- **后台任务清单**（`test_every_memory_server_background_spawn_is_drainable`）：每个 `_spawn_background_task(...)` 要么被 `_track_character_post_turn_task` 包住，要么写进「已被别的登记表覆盖」的清单。

进不进围栏的判据：**写是这个端点的本职，并且调用方扛得住 409**。两条都满足才进。

- `/new_dialog` 不在围栏内，也**不该加**。它的三类调用方（起会话、热切换、主动搭话）都把非 2xx 当成连接错误，会让会话启动硬失败。它顺带的 locale 写入另有可靠的重试。
- 只读端点不进。读路径上顺带刷新冷却这类尽力而为的写，不值得让一次读在发布期间 409。

⚠️ 路由清单这条守卫**看不见角色名在请求体里的端点**。中间件只能从路径里取角色名。请求体寻址的角色写端点要在 handler 里手工调 `_begin_character_request` 登记，以后再加这类端点要自己记得。

### 和插件的关系

- 插件 SDK 的 `get_persona` 打的是围栏内的路由（`GET /internal/memory/{角色}/persona`），角色改名或删除期间会拿到 409。按主体写群组记忆的那组接口（`scoped_facts`、`scoped_history` 等）也在围栏内。插件侧要把 409 当成可重试的失败。
- 给插件开新的、按角色写记忆的宿主接口时，它一定会落到上面两条守卫里，按判据决定进不进围栏。

## 2. 创意工坊内容目录的占用登记

`main_routers/workshop_router/content_gate.py`。按内容目录记「谁在占用」：

- 发布和删目录取**独占**（`claim_content_folder`）。
- 往目录里写单个文件的操作取**共享**（`claim_partial_writer`）。共享之间不互斥，但和独占互斥。
- 抢不到直接抛 `ContentFolderBusy`，路由翻成 409。**从不排队。**

为什么占用要覆盖整个发布过程：Steam 从提交内容到上传结束都在读整个目录，本地写文件和清理目录必须在这整段时间里被挡住，不只是预检读清单的那一小会儿。

两条规则：

**一、占用的获取和释放必须在同一个工作线程单元里，绝不能在事件循环上。** 取消等待的协程杀不掉线程。

- 把占用放在协程的 `finally` 里：客户端一断开，线程还在写盘，目录就被放开了。
- 反过来，在事件循环上获取、只由线程释放：执行器丢掉一个还没开始的任务时，占用永久漏掉，那个目录从此一直 409。

两头都在线程单元里，这两种情况都不会发生。⚠️ 违反这条**没有任何行为测试会变红**，只有 `tests/unit/test_workshop_content_gate.py` 里的 `test_no_claim_is_ever_taken_on_the_event_loop` 这条语法树守卫拦得住。想「顺手把占用提到 handler 里更整洁」的时候记得这里。

**二、不用 `asyncio.Lock`。** 这里没有等待队列要建模；而且 `asyncio.Lock` 只能在事件循环线程上拿，正好被第一条禁掉。

新增往内容目录里写文件的端点时：先把写盘挪进工作线程单元，再在单元里取共享占用；涉及移走或删除整个目录的取独占。
