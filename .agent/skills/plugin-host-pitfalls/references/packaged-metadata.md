# 插件元数据：打包时求值，宿主只读

## 1. 为什么是这个形状

`@plugin_entry` 不声明 `input_schema`，它从 pydantic 模型或函数签名**推导**。这是整套入口元数据里唯一必须执行插件代码才能拿到的东西；其余（id、名字、描述、handler 表）都是字符串字典。宿主重建出来的 handler 本来就只是占位，真正的可调用对象从来不跨进程。

所以现在的做法是：

- **打包时**在作者机器上 import 一次，结果写进包里的 `plugin.meta.json`（`plugin/neko_plugin_cli/core/metadata_probe.py`）。
- **宿主**只读这个文件（`plugin/server/infrastructure/packaged_metadata.py`）。这个模块不 import、不执行、不起子进程跑插件代码。

以前是宿主每次刷新都起子进程把所有插件 import 一遍：插件只要躺在目录里，模块顶层代码就会被执行；启动一个插件会连带 import 其余全部（#3035）。

## 2. 已经否掉的方案

再有人提，直接引用理由：

| 方案 | 为什么不行 |
|---|---|
| 纯静态 AST 扫描入口 | 运行时动态注册入口的插件会得到错的答案 |
| 一个 worker 进程批量扫多个插件 | 互不信任的插件共享进程，A 能改 B 的扫描结果 |
| 打包时 import 失败就让打包失败 | 把一个元数据优化变成了打包闸门。打包机可能缺可选依赖，插件可能是给别的系统写的。现在是警告 + 照常出包，宿主对没有元数据的包有明确行为（回落到清单声明的内容） |
| 给 schema 换号时写内存里的旧版兼容层 | 旧号一律被读取器拒绝，走启动时的回落扫描，然后把文件原地升级。不写内存兼容层 |
| 给未运行插件的入口加「参数结构未知」提示文案 | 全前端只有一处渲染参数表单（`frontend/plugin-manager/src/components/plugin/EntryList.vue` 的执行对话框），而它的按钮在插件没运行时是禁用的。插件一运行就已经 import 过，schema 是真的，这条文案没有地方会显示 |

打包唯一会**硬失败**的情形：源目录里抄进来一份旧的 `plugin.meta.json`，而这次推导失败又删不掉它（比如 Windows 只读属性）。归档器会把旧文件照样打进包，而警告说的是「这次不带元数据」。出不了诚实的包就不出包（`_remove_staged_metadata`）。

## 3. 改这块代码要守的规则

**占位 schema 不能带 `properties` 键。** 没有静态 schema 的入口用 `PLACEHOLDER_INPUT_SCHEMA`（`plugin/core/packaged_metadata.py`）。前端判断「有没有字段」用的是真值判断，空对象也是真，带上 `properties: {}` 会渲染出一个零字段表单，用户没法再填原始 JSON 参数。真正的参数校验在插件进程里按真实模型做，不靠这个占位。

**仍然会 import 插件的只有两处**，都是有意保留的：

- `start_plugin`：包内元数据不可用时回落到隔离扫描（`scan_plugin_metadata_isolated`）。
- 换源校验 `registry_service._validate_plugin_runtime_source_sync`：要先试才知道要不要回滚。

**`start_plugin` 不复用包内 handler 的四种情况**（`lifecycle_service._read_packaged_isolated_metadata`，每条在代码注释里有原因）：

1. 没有可用的元数据。
2. 生效配置改了入口表。打包时只看得到暂存目录里的 `plugin.toml`，看不到用户的运行时配置和 profile。
3. 元数据不是在本机环境（系统 / Python 版本 / 架构）下生成的。插件可能按平台条件注册入口，别的机器上推出来的 handler 表不能当权威。
4. ⚠️ handler 的 key 不属于当前运行 id。key 里内嵌了插件 id（`<插件id>.<入口>`），而插件 id 冲突时会被改名。把旧 id 下铸的 key 交给 `install_isolated_plugin_metadata`，它会全部丢掉，结果是**插件启动成功、报成功、一个入口都没有**。

空的 handler 表是一个答案，不是缺失：只做后台工作的插件就是不注册入口。把空表当成「没有元数据」会让这类插件每次启动被 import 两遍，模块顶层的副作用跟着发生两次。

**环境不一致只拦「启动时复用 handler」，不拦「发现时的预览」。** 两者性质不同：启动时的 handler 要进 `state.event_handlers`，是权威能力集，错了模型会去调一个本机不存在的入口；预览只是展示。如果发现侧也按环境拦，在别的系统上打的包到了用户机器就得全量 import，正是这套设计要去掉的开销。环境不一致时宿主会把本机扫描结果写成本地缓存（`write_local_packaged_metadata`），下次启动走快路径。

**`start_plugin` 里三步的顺序是承重的：读元数据 → 钳启动超时 → 启动 host。**

- 元数据必须在 host 之前。否则回落扫描和插件进程自己的 import 并发，拿文件锁、绑端口、起单例的插件会在第二次 import 上失败，清理逻辑会把健康的 host 杀掉并报启动失败。
- 钳超时必须在元数据之后。读元数据最多会花掉一个扫描超时，在它之前算出来的上限已经过期。

**新鲜度判断是三层快路径加一次内容哈希**（`_validate_packaged_metadata`）：文件清单（确定性的，抓增删）→ 总字节数 → mtime。只有 mtime 说「源码比元数据新」时才算内容哈希。

- 任何一层对不上，这个插件就回落到清单声明的内容，日志里会写原因。改了内置插件的源文件（包括增删文件）而没重新生成 `plugin.meta.json`，就会走到这里，日志提示用 `neko-plugin build` 重新生成。
- 只看 mtime 不行：git 不保留 mtime，新 clone 下来的仓库里源码和生成文件的时间先后是随机的，只看时间戳会让内置插件在每台新机器上集体退化成占位。
- 哈希对上之后要把 `plugin.meta.json` 的 mtime 盖到源码之后（`_stamp_metadata_verified`）。否则解包顺序会让「源码比元数据新」永久成立，每次刷新都在持锁状态下重算整棵树。
- 文件名按 NFC 记录、比对、算摘要，但读文件用文件系统上的原拼写。两个拼写都要留着：拿归一化后的名字去打开文件，在保留原拼写的文件系统上会直接找不到。

**打包时扫哪棵树就指纹哪棵树。** 推导和指纹都在暂存目录上做，不在作者的源目录上做（`write_packaged_metadata` 的说明）。「扫 A、指纹 B」会让包里带着一份由它自己都没装的文件推出来的 handler 表，而宿主的哈希校验照样通过。依赖从暂存树里的 `vendor/` 解析。

**宿主可以重写 `plugin.meta.json`，但只限一种情况**：文件已经存在，只是 schema 版本过期。用的是 `start_plugin` 回落扫描的结果（`refresh_stale_packaged_metadata`）。手工放进去的、开发模式的插件没有这个文件，宿主不凭空造一个。

## 4. `/plugins` 接口里的入口从哪来

`plugin/server/application/plugins/query_service.py`：先用已注册的 handler 建入口表（`_build_entries_from_handlers`），再用预览补上没出现过的（`_append_entries_from_preview`）。

所以同一个插件，**启动前**看到的是包内或扫描出来的预览，**启动后**看到的是 `state.event_handlers` 那份。两份不一致时，用户看到的现象是「入口契约在点启动的前后变了一次」。排查这类反馈先比这两份。

内置插件的 `plugin.toml` 都不声明 `[[entries]]` 表。只影响「配置里声明的入口」的改动，对内置插件是空操作。

## 5. 新装插件的自启动：待批准表

新装的插件即使清单里写了 `auto_start = true`，也要等用户打开它单独的自启动开关才会开机自启。记录用的是「**待批准**名单」而不是「已批准名单」，理由写在 `plugin/server/infrastructure/autostart_approvals.py` 的模块说明里，要点：

- 已批准名单需要一个基线（把存量插件一次性放行的那个时刻）。基线一旦种错（比如种在一个恰好为空的注册表上），用户整套自启动会永久沉默。待批准名单里「没有记录」就等于「不归我管」，这个文件里任何 bug 的后果都是「照老样子自启」。
- 读失败按「没有待批准」处理（放行）；写失败要回滚内存里的改动，并让调用方知道。读侧放行、写侧拒绝，两者不矛盾。
- 读失败留下的空集合只能用来回答「能不能自启」，不能当作写回磁盘的基线，否则会把别的插件的待批准记录一起抹掉。

评审里出现「改成已批准名单更安全」或「读失败应该拦住」时，按上面的理由判。
