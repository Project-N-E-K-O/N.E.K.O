# Live2D 渲染性能：成本结构、Core 层的结论、怎么量

本页的数字都是实测观察，测量环境是单台高端独显桌面机（Chrome、ANGLE D3D11），三个模型 `mao_pro`、`yui-lolita`、`yui-origin`。**核显机器没有实测过**，桌面机的数字不能当核显机的数字引用。

## 钱花在哪

**GPU 侧（结构性的，最大）。** 分发版的 Pet 窗口是一个盖住全部显示器的透明窗口，`#live2d-canvas` 铺满整个窗口。

- `live2d-core.js` 的 `initPIXI` 在桌面上按 `window.screen` 的尺寸建 `PIXI.Application`（手机宽度才按视口），之后 `doResize` 按窗口内尺寸调整。分辨率由画质设置决定（`_getRenderResolutionForQuality`：low 为 0.75 到 1，medium 为设备像素比但不超过 1.5，high 为设备像素比）。
- 所以 WebGL 后备缓冲随「桌面总面积 × 分辨率」线性增长，模型只占其中一小块，其余每帧清空再合成。透明窗口每帧都要走带 alpha 的整窗合成，享受不到不透明窗口的合成优化。
- `#live2d-container` 和 `#live2d-canvas` 各自带 `will-change: transform` 和 `translateZ(0)`，是两层全窗合成层。
- 「把画布裁到模型包围盒」是这一层唯一对症的方向。要做的话有先例可循：Niri 下已经有「虚拟视口 / 物理裁剪」两套坐标的基建（`getLive2DNiriPetVirtualViewportSize`、`getLive2DNiriPetPointerCoordinates`、`window.__nekoNiriPetPhysicalCrop`），复用它，不要另起一套。
- 最便宜的验证办法：在 Pet 窗口 DevTools 里执行 `live2dManager.pixi_app.renderer.resize(800, 1000)`，看任务管理器里 GPU 占用的变化。要在核显机器上看。

**主线程（每帧 1 到 4ms 量级）。** 大致分三块：Core 的 `update`（小模型约 0.3ms，两个 yui 模型约 1ms）；Framework 的动作 / 物理 / 蒙版设置等 JS；绘制发令（每帧几千次 gl 调用，约 1ms）。此外每帧还有锁图标和浮动按钮两个 ticker 回调（各做一次 `model.getBounds()` 加脏检查写样式，只在 Linux X11 下节流到 80ms 一次）。

**已经做掉的。** 空闲降到 30 帧并停掉 rAF（见 `frame-pacing.md`）；Pet 窗口跳过每帧的 profile 保存；动作曲线求值不再整段拷贝（动作文件大的模型上，这一项曾是最大的单项 JS 开销，每帧拷贝数百万个数组元素）。

**结论。** 用户能感知的掉帧由空闲帧率治理和整窗画布这两件事主导。Core 和 SDK 的 JS 侧剩余的优化项，单项多在几十微秒到零点几毫秒，占 60 帧预算的千分之几到百分之几。

## Core 不是瓶颈

评估过「换一个更快的 Core 实现」和「在 Core 这一层降精度」两个方向，都只做了技术测量，没有采用：

- 放回真实流水线（PIXI 加 Framework 加待机循环）之后，Core 这一步再快，整条 `internalModel.update` 每帧也只省零点几毫秒，相当于帧预算的 1% 到 3%。渲染一侧不变。
- ⚠️ Node 里量出来的倍率在浏览器里兑现不了。同一份 wasm 在 Chrome 里比在 Node 里慢得多，两边的数字不能互换。
- ⚠️ **「只重算变了的参数」在真实待机下收益为 0。** 待机时默认循环播放待机动作，内置模型都带物理，每帧被驱动的参数有几十到两百多个，几乎整棵树都是脏的；多出来的簿记还会让它略慢。只有同时停掉待机动作和物理，这个方案才兑现，那等于待机时模型不再自己动，是产品行为的改变，不是优化。
- 时间主要花在逐顶点带分支的变形计算上，编译器自动向量化碰不到。「跳过不可见的网格」这类无损项全部叠起来，每帧也只省不到四分之一毫秒。
- 会改变画面的做法（隔帧更新、顶点减半、变形粗化）要么省得不多，要么肉眼可见。

再有人提「换 Core」或「Core 层降精度提速」，用这一节回答：瓶颈在 GPU 侧的整窗画布，不在 Core。

## 测量方法上的坑

- **高端独显量不出 GPU 侧的差异。** 全窗画布和裁剪画布的微基准在这种机器上每帧都只有百分之几毫秒。
- **`vm.createContext` 沙箱会把 Core 的耗时放大近一个数量级。** 在 Node 的 vm 沙箱里加载 bundle 量绝对耗时是假象；同一套桩换到主上下文就正常了。沙箱里的数字只能看倍率。
- **差分测试要有能变红的负对照。** 「把补丁弄错一位」得到的如果是抛异常中止，而不是结果不相等，就没有证明差分本身有分辨力。负对照要用数值扰动。
- **差分为 0 不等于覆盖到了。** 比如渲染状态缓存的差分，如果夹具里没有强制若干 drawable 走剔面分支，那个分支根本没跑，0 不是证据。仓库里三个内置模型全是双面的，这类分支本地看不出问题，带单面部件的用户模型才会出事。
- **单看主线程时间会漏掉 GPU 进程。** 「去掉某个 gl 调用」这类改动，主线程只省几十微秒，收益在 GPU 进程一侧；判断它值不值要按真实的连续出帧来量，不能只量单帧的同步耗时。
- **按模型分开报。** 很多项的收益随模型规模差一到两个数量级（动作曲线点数、蒙版数量、物理输出数量），只报一个模型会误导。

## 验收怎么做

在目标机器（带核显的 Windows 笔记本）上，用机器上装的 Chrome 打开开发页 `/`，它和分发版走同样的 ANGLE / D3D11，而且 DevTools 齐全。在控制台用 `performance.now()` 包住要量的方法（比如 `model.internalModel.draw`、`model.internalModel.motionManager.update`），补丁开、关两种状态各取 300 帧，比较中位数。加载期的改动用同一台机器、同一个模型冷启动若干次取中位数做相对比较。视觉上至少在 `mao_pro`（蒙版多）上确认裁剪蒙版没有花。

Chrome 开发页量的是补丁在 JS 一侧的耗时。它不是 Pet 窗口：只对 Pet 窗口生效的路径（跳过 profile 保存、帧率总闸）在这里不走，透明整窗的合成成本也量不到。这两类改动要在目标机器的 Pet 窗口里量，同时看 GPU 进程的占用；Chrome 开发页只作补充。
