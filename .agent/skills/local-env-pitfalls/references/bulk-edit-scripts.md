# 用脚本批量改文件

用 Python 脚本按锚点改代码（一次改多个文件、做变异、批量重命名）时反复出过的问题。单处修改优先用编辑工具，它自带唯一性检查。

## 全部锚点命中之后再统一写盘

不要写成「改一个文件、立刻写盘、再改下一个」。中间任何一个锚点断言失败，前面的文件已经落盘、后面的没写，代码停在半截状态。例如「创建处已经造出了对象，但没有任何地方使用或清理它」。这种状态语法检查照样通过，看不出来。

```python
texts = {}                                           # 每个文件只读一次，改动都落在这份缓存上
for tag, path, old, new in plan:
    if path not in texts:
        texts[path] = open(path, encoding="utf-8", newline="").read()
    s = texts[path]
    assert s.count(old) == 1, (tag, s.count(old))   # 带标签，失败时知道是哪一处
    texts[path] = s.replace(old, new)

payloads = [(path, body.encode("utf-8")) for path, body in texts.items()]   # 编码失败时还没碰任何文件
for path, data in payloads:
    open(path, "wb").write(data)
```

同一个文件有多处改动时，都改在同一份缓存上，最后每个文件只写一次。每条改动各读一遍原文件、各写一遍的话，后写的会把先写的盖掉，而且不报错。

## 锚点断言唯一性，不是存在性

- `s.replace(old, new, 1)` 换的是文件里**第一处**匹配，不一定是你正在看的那一处。`assert old in s` 只证明存在，拦不住。出过的事：想改新加的测试，结果改到了同一个文件里更早、结构相同的另一个测试，把它改坏了，而报错信息指向的还是新测试。
- 一律 `assert s.count(old) == 1, s.count(old)`。
- 锚点不唯一时，把上下文加长到唯一（带上函数名那一行，或者带上后面有特征的一行）。字节完全相同的两段代码在同一个文件里出现是常事。
- 锚点会被自己上一轮的改动打破。往某段里插了注释之后，以「原文连续几行」为锚点的字符串就不再匹配。写锚点之前先看一眼当前的真实文本，不要凭记忆。
- 文件的行尾可能是 CRLF 也可能是 LF。读的时候 `newline=""`，多行锚点按文件实际行尾适配，否则命中数是 0。

## 断言失败必须看得见

- 不要把改写脚本塞在一串 `&&` 或 `;` 的中间，也不要把它的输出过滤成只剩几个关键词。断言失败的 traceback 被滤掉之后，后面的测试照常跑、照常绿，而改动根本没应用。
- 做变异时尤其如此：变异没应用成功，那一轮的「测试仍然全绿」是假的。看到「改完仍然全绿」，第一反应是怀疑改动没生效。

## 写盘

- 先 `encode("utf-8")`，成功之后再 `write_bytes`。`write_text` 是先清空文件再编码，内容里有编不了的字符（例如孤立的代理字符）时文件已经空了。
- 用字节模式或 `newline=""` 写，保持原来的行尾。
- 要写进文件的内容里有反斜杠转义序列时，见 `windows-shell-and-bytes.md`。

## 改完回读

- 搜一下新加的标记，看行号是不是落在预期的函数里。
- `git diff --stat` 看改动的文件和行数是不是预期的那些。出现没打算改的文件、或者某个文件有大量删除行，停下来查。
- 改坏了、而文件的其余部分已经提交过：`git checkout HEAD -- <文件>` 取回重做。不要用 `git stash` 回滚（见 `worktree.md`）。文件里有未提交的工作时不能这么做，所以批量改写之前先提交一次。
